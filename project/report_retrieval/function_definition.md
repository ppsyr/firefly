# Report Retrieval：Thread 报告与历史检索

## 总目标

把 thread 中有长期价值的信息保存成**可追溯、可逐层展开、可检索**的报告。普通查询先使用报告摘要；只有摘要不足时，才读取详细知识块和相关的 user/assistant 对话，避免每次把完整历史塞进上下文。

功能明确划分为四个模块：

```text
模块一：报告生成与持久化
  ├─ /report
  ├─ 分层报告（概览、摘要、rag 知识块）
  └─ user/assistant-only 对话副本

模块二：报告索引
  └─ SQLite FTS5

模块三：报告检索
  └─ /search + 当前项目/cwd 范围 + 逐层展开

模块四：Agent 原生检索
  └─ search_reports(query, scope, depth)
```

**模块一先完成**。模块一完成后，报告本身就是完整的持久化产物；模块二到四只消费模块一生成的文件和元数据。

第一版使用 SQLite FTS5，不依赖 Embedding 服务或向量数据库。Embedding、混合检索和普通本地文件知识源放在最后的扩展功能中。

---

## 模块一：报告生成与持久化

模块一包括此前拆开的“报告持久化”和“分层报告/对话副本”。它们属于同一个功能：**生成一份可长期保存、可逐层读取的报告快照**。

### 1. `/report` 用户入口

支持：

```text
/report
/report 自定义报告标题
```

- `/report` 针对当前 thread 生成一份手动报告。
- 不指定标题时使用当前 thread 标题；thread 没有可用标题时使用现有安全的默认标题规则。
- 指定标题只影响本次报告，不重命名 thread，不修改 thread 元数据标题。
- 标题允许中文、空格和普通标点，沿用现有命令解析方式。
- 命令不切换 thread、不创建 thread、不改变 project、`cwd` 或 sandbox。
- 同一个 thread 可以多次执行 `/report`，每次都是独立快照。

报告生成应优先复用现有 reporter、ReportMiddleware 和报告结果。模块一的主要新增工作是把结果规范化并可靠保存，不要为保存报告重写 export 报告流程。

### 2. 用户级存储

默认使用当前用户的 storage root：

```text
~/.poirot/
└── reports/
    └── YYYY/MM/DD/
        ├── report-HH-MM-SS-title.md
        └── report-HH-MM-SS-title.conversation.jsonl
```

- `storage_root` 沿用项目已有配置，测试和部署可以覆盖到临时目录。
- reports 属于用户级存储，不属于项目目录，不随进程 `Path.cwd()` 改变。
- 日期和时间使用报告生成时的本地时间。
- 报告是快照；后续 thread 对话不会修改旧报告，再次 `/report` 才会生成新快照。

### 3. 标题和路径安全

- 标题用于报告展示，也用于文件名；两者可以使用同一个清理后的值。
- 必须处理 `/`、`\\`、`..`、控制字符、换行和超长文本，防止路径穿越和不可读文件名。
- 保留正常中文、英文、数字、空格和常用标点。
- 标题清理后为空时使用稳定的安全后备名或报错。
- 同一秒、同一标题生成多份报告时追加 thread ID、序号或稳定后缀，不能覆盖旧报告。
- 写入采用同目录临时文件、flush/fsync 和原子替换；失败时清理临时文件，不截断已有报告。

### 4. 报告来源元信息

报告开头使用 frontmatter 或项目已有的等价元信息格式，至少保存：

```text
name
description
thread_id
project
cwd
report_created_at
thread_location
conversation_location
schema_version
```

- `thread_location` 指向生成时的原 session 目录。
- `cwd` 使用 thread 元数据中的规范化路径，不能用当前进程的 `Path.cwd()` 代替。
- 旧的无 `cwd` thread 不因生成报告而被隐式绑定目录；按现有兼容规则记录空值或未知状态。
- `conversation_location` 指向本次报告对应的对话副本，而不是共享 checkpoint 或临时文件。
- `schema_version` 为后续报告解析和索引重建预留兼容依据。

### 5. 分层报告内容

报告正文从浅到深组织。生成时可以复用已有报告结果，但最终格式必须能区分这些层级。

#### L0：概览

用于判断报告是否相关，包含：

- 本次 thread 要解决的问题；
- 最终完成的结果和当前状态；
- 主要主题、模块或技术名词；
- 是否存在未完成事项。

L0 要短，不复述完整 prompt，不放大量工具输出。

#### L1：结构化摘要

用于回答大多数历史问题，包含：

- 关键决策和采用原因；
- 交付结果、重要文件和接口；
- 约束、取舍和已知限制；
- 待办和后续建议；
- 每轮的用户目标与 Agent 结果。

逐轮摘要只说明用户让 Agent 做什么、Agent 最终完成什么，不复述详细 prompt、思考过程或每个工具参数。

#### L2：`rag` 知识块

用明确的 `rag` 围栏标记可独立理解、适合长期检索的内容：

````markdown
```rag
可独立检索的事实、设计约定、迁移规则或最终结论。
```
````

适合写入 L2 的内容包括接口约定、配置规则、重要故障结论、稳定的工程决策和可复用操作步骤。普通代码围栏、日志和工具原始输出默认不作为 L2 知识块。

### 6. 对话副本

报告旁保存 `conversation.jsonl`，作为 L3 深度来源：

```json
{"turn": 3, "role": "user", "content": "..."}
{"turn": 3, "role": "assistant", "content": "..."}
```

- 只保存 user 和 assistant 的文本消息，保持原顺序和轮次。
- tool、system、工具参数和工具执行结果不作为对话正文提供给 RAG。
- 工具活动最多写 `[tool]`、`[tool: shell]`、`[tool: file-read]` 等符号。
- 非文本消息跳过或使用明确的类型标记。
- 原有 checkpoint 继续保存完整状态，是 thread 历史的权威来源；对话副本是报告生成时的筛选快照，不替代 checkpoint。
- 后续 thread 对话不会自动追加到旧副本；重新执行 `/report` 生成新副本。

### 7. 模块一的边界

模块一不实现：

- FTS5、`/search` 和 Agent 搜索工具；
- Embedding 和向量数据库；
- 普通本地文件知识源；
- 报告列表、删除、重命名和版本合并；
- 自动 export 报告迁移到 `~/.poirot/reports`。

export 模式仍按现有逻辑生成 `final_report`，并由 artifact store 保存到当前 run 的 `output_dir/final_report.md`。手动 `/report` 和自动 export 报告的触发条件、路径、生命周期保持独立。

## 模块二：SQLite FTS5 报告索引

模块二只消费模块一已经保存的 Markdown 报告，不直接解析完整 checkpoint。索引是派生数据，报告文件才是内容来源。

### 1. 索引内容

第一版索引：

- 报告名称和描述；
- L0 概览；
- L1 结构化摘要、决策、结果和待办；
- L2 `rag` 围栏内容。

L3 对话副本默认不进入首层索引，避免完整历史污染普通查询；需要深度检索时，通过命中的报告和轮次定位后读取。

### 2. 检索块和来源

按章节或可独立理解的段落拆分检索块，每个块保存：

```text
report_id
report_path
thread_id
project
cwd
section
summary_level
turn_start
turn_end
content_hash
created_at
```

来源字段用于项目/cwd 过滤、结果展示、从 L1 找到 L2/L3，以及判断报告是否重复索引。

### 3. 索引生命周期

- 报告保存成功后可以触发索引更新；索引失败不能删除或回滚报告。
- 支持从 reports 目录全量重建。
- 同一报告重复索引应更新原块，不追加重复副本。
- 报告损坏或格式版本未知时跳过并留下诊断信息。
- 索引数据库损坏时保留报告，允许删除并重建索引。
- 中文和中英文混合查询必须通过固定样本实际验证，不默认认为 SQLite tokenizer 已解决中文分词。

第一版不依赖网络、Embedding API 或向量数据库。SQLite 元数据表负责过滤和来源，FTS5 表负责全文匹配，不能把权限过滤信息只编码在正文中。

## 模块三：`/search` 报告检索

### 1. 命令

```text
/search 关键词
/search 一个需要从历史报告回答的问题
/search --all-projects 需要跨项目查找的问题
```

### 2. 默认和扩展范围

- 普通 `/search` 只搜索当前 thread 所属项目且真实 `cwd` 相同的报告。
- 过滤使用规范化后的真实 `cwd` 和报告元数据，不能只比较项目名。
- 同项目名但目录不同的报告不能默认互相命中。
- `--all-projects` 是用户显式授权的范围扩展，搜索全部项目报告，但不改变当前 thread 的文件 sandbox。
- Agent 和普通查询不能根据问题内容自行扩大到 `all-projects`。
- 当前 thread 没有 `cwd` 时，不能悄悄搜索所有报告；应按旧 thread 兼容规则提示或限制范围。

### 3. 渐进式检索

```text
输入 query
  ↓
解析范围和查询文本
  ↓
FTS5 检索 L0/L1
  ↓
摘要足够 ───────────────→ 生成回答
  ↓ 不足
展开相关 L2 rag 知识块
  ↓ 仍不足
读取相关 L3 user/assistant 对话轮次
  ↓
生成带来源的回答
```

支持三种检索深度：

- `summary`：只返回 L0/L1；
- `detail`：返回 L0/L1 并展开相关 L2；
- `conversation`：在 detail 基础上读取相关 L3 轮次。

每层限制报告数量、片段长度和总 token。展开时标注已展开的层级或发生的截断。回答必须引用报告名称、章节、thread ID 或报告路径；没有可靠命中时明确说明未找到，不能用相邻报告补全事实。

明确关键词可以直接查询；自然语言问题可以做轻量查询改写，但不强制每次先调用 LLM。索引缺失、报告损坏、深层读取失败时，保留可用浅层结果并返回诊断信息。

## 模块四：Agent 原生检索

模块四把模块三的能力提供给 Agent，但不让每轮对话无条件触发 RAG。

### 工具接口

建议提供：

```text
search_reports(query, scope="current", depth="summary")
```

- `query`：待查主题或自然语言问题，不能为空；
- `scope`：`current` 或 `all-projects`，默认 `current`；
- `depth`：`summary`、`detail` 或 `conversation`，默认 `summary`；
- 返回带来源的检索片段和是否建议继续展开的状态；
- 不修改当前 thread 的消息、checkpoint 或报告。

### 允许主动调用的情况

Agent 可以在以下情况下调用：

- 用户提到“之前讨论过”“上次方案”或“历史结论”；
- 用户询问当前 thread 之外的项目决策；
- 当前上下文明确缺少已完成工作的背景；
- 用户明确要求查找报告或历史信息。

普通问题不应无条件调用，也不应为了确认“是否有历史”而每轮都查询一次。

### 调用约束

- 默认 scope 是当前项目和真实 cwd。
- 只有用户明确要求跨项目时，Agent 才能使用 `all-projects`。
- 首次调用从 `summary` 开始；摘要不足时才展开 `detail` 或 `conversation`。
- 限制单轮调用次数、结果数量和注入 token，防止搜索循环和上下文膨胀。
- 搜索为空或失败时，Agent 可以基于当前上下文回答，但必须说明没有找到历史依据。
- CLI `/search` 和 Agent 工具共用查询、过滤、逐层展开、来源和预算逻辑。

## 数据关系

```text
thread checkpoint
  └─ 完整历史和运行状态的权威来源

/report
  ├─ report.md
  │    ├─ L0 概览
  │    ├─ L1 结构化摘要
  │    └─ L2 rag 知识块
  └─ conversation.jsonl
       └─ L3 user/assistant 对话副本

report.md
  └─ SQLite FTS5 检索块 + 来源元数据
```

报告保存位置是用户级 `~/.poirot/reports`，检索范围由报告中的 project/cwd 元数据控制。报告索引不能绕过 thread sandbox，也不能把其他项目的文件权限带入当前会话。

## 实施与验收顺序

### P0：模块一，报告生成与持久化

交付 `/report [标题]`、用户级日期目录、来源元信息、L0/L1/L2 分层内容、user/assistant-only 对话副本、原子写入和跨进程读取。验证默认/自定义标题、同名冲突、非法文件名、写入失败、逐层内容和 export 自动报告不回归。

### P1：模块二，SQLite FTS5 索引

交付报告解析、检索块、来源元数据、去重更新和全量重建。验证中文/英文查询、章节定位、索引损坏恢复、报告重复生成和报告不可读时的处理。

### P2：模块三，`/search`

交付默认项目/cwd 范围、显式 `--all-projects`、关键词和问题查询、逐层展开、token 限制及带来源回答。验证无命中、相似报告、跨项目隔离、深层读取失败和非交互终端行为。

### P3：模块四，Agent 原生检索

交付受限的 `search_reports` 工具。验证历史相关问题可以触发，普通问题不会无条件触发，Agent 不自行扩大 scope，调用次数和上下文预算有效。

### 通用测试要求

- 使用临时 `storage_root` 和多个临时项目目录，不读写真实 `~/.poirot`。
- 每阶段先运行新增和受影响测试，再运行全量测试，区分新增失败与已有失败。
- 至少执行一次真实 CLI `/report`、重启后的报告读取和 `/search`；P2 之后再执行跨项目检索。
- 验证同名目录、符号链接、不同 project 名称和不同真实 cwd 不会造成错误匹配。
- 对长报告和长对话验证逐层展开、最大 token、截断标记和来源保留。
- 对索引删除、损坏、报告移动和报告重复生成验证恢复行为。

## 扩展功能（不属于第一版）

### 普通本地文件知识源

以后把本地文件作为另一种知识源，而不是伪装成 thread：

1. 用户显式导入文件或目录；
2. 记录原路径、大小、修改时间和内容 hash；
3. 生成同格式的 L0/L1/L2 分层报告；
4. 在用户级存储中保存原文件快照作为更深层来源；
5. 将报告纳入统一 FTS5/后续向量检索；
6. 需要细节时才读取快照内容。

第一版扩展不做实时监听，文件变化通过显式刷新处理。报告和文件快照记录不同的 `source_type`。函数名、配置键和错误码等精确内容可增加原文 FTS 索引，默认不把整个原文件向量化。

### Embedding 与混合检索

只有当 FTS5 评估显示同义词、自然语言改写和语义问题漏检明显时，再增加 Embedding：

- 优先向量化 L0/L1/L2 报告块，不直接向量化完整 checkpoint；
- 保留 FTS5 处理 thread ID、文件名、函数名和配置键等精确匹配；
- 用 FTS5 和向量分数做混合排序；
- Embedding 服务不可用时回退 FTS5；
- 单独评估命中率、延迟、存储、token 成本、模型升级重建和隐私风险。

Embedding 是检索实现的增强或替换，不改变报告、来源元数据和 L0/L1/L2/L3 渐进式披露协议。
