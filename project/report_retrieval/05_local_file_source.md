# 附加功能 1：普通本地文件知识源

## 本部分实现的功能（一览）

> **本部分 = "把用户显式添加的本地文件整理成可检索报告，并在需要时展开原文件快照"。**

本功能复用已有 Report Retrieval 的报告格式、SQLite FTS5、渐进式披露和来源引用，但本地文件不是 thread，也不伪装成对话。

**前置功能已完成：**

- 模块一已实现 `/report`：thread 报告保存到用户级 `reports/YYYY/MM/DD/`，包含 L0 概览、L1 结构化摘要、L2 `rag` 知识块和 user/assistant-only 的 L3 对话副本。
- 模块二已实现 SQLite FTS5：报告可增量索引、重建，并按来源元信息过滤。
- 模块三已实现 `/search`：支持当前项目/cwd 和显式 `--all-projects`，按摘要、知识块、对话逐层展开。
- 模块四已实现 Agent 原生 `search_reports`：Agent 可以在需要历史背景时受控检索，不会每轮无条件搜索。

**本部分实现：**

1. **显式添加来源**：用户通过命令或已有入口添加单个文件；目录可按明确上限批量导入。
2. **权限校验**：添加和读取都遵守当前 thread 的 sandbox、`cwd` 和已授权追加目录，不因导入功能扩大文件权限。
3. **来源快照**：记录原路径、真实路径、大小、修改时间、内容 hash 和导入时间；保存一份生成时的原文件快照。
4. **文件报告**：为每个来源生成 L0/L1/L2 分层报告，标注 `source_type=local_file`，说明文件用途、结构、关键事实和限制。
5. **统一索引**：把文件报告加入现有 FTS5，支持与 thread 报告共用检索接口和来源过滤。
6. **深层展开**：命中报告但摘要不足时，按需读取对应原文件快照的相关内容，而不是默认把整个文件注入上下文。
7. **显式刷新**：文件变化由用户手动刷新并生成新版本；旧版本可追溯，失败不破坏旧版本。

**本部分不做：**

- 实时文件监听、后台自动刷新或每次搜索自动重新读取磁盘；
- 默认把完整原文件内容加入 FTS5 或 Embedding；
- 直接索引二进制、图片、音视频或多模态内容；
- 让本地文件报告伪装成 thread 报告或进入 thread checkpoint；
- 改变 sandbox、`cwd`、`/add-dir`、项目绑定或文件写入权限；
- Embedding、向量数据库和混合排序；
- 自动导入当前目录下全部文件。

## 用户入口与来源管理

具体命令沿用项目现有命令风格，建议提供：

```text
/source add /path/to/file.md
/source add /path/to/docs
/source list
/source refresh <source_id>
/source remove <source_id>
```

- `add` 只接受用户明确指定的文件或目录，不隐式扫描项目。
- `list` 显示来源 ID、展示名、原路径、当前版本、状态和最近导入时间。
- `refresh` 重新读取原路径；如果原文件已被删除或移动，保留旧版本并报告失败。
- `remove` 删除该来源的索引和来源登记；是否删除历史报告和快照要有明确策略，默认保留历史快照以便报告可追溯，或要求用户显式确认清理。
- 目录添加时逐文件处理，文件数量、递归深度、单文件大小和总大小必须有限制；单个文件失败不应让其他文件的报告全部回滚。
- 来源 ID 是稳定的导入身份，不使用路径作为唯一 ID。路径移动后可以显示为失效来源，不能把新文件静默当作旧来源。

如果项目已有 `/add-dir`，它只提供当前 thread 的引用授权；`/source add` 仍需在该授权范围内读取。来源登记是用户级知识库元数据，不等于给所有 thread 共享文件访问权限。

## 权限和文件读取

- 添加、刷新和深层展开都通过现有 sandbox/file reader；不能直接绕过 guard 使用任意绝对路径。
- 真实路径应在 `thread.cwd` 或会话已授权的追加目录内；拒绝 `../`、相似前缀目录和符号链接逃逸。
- 当前 thread 没有 `cwd` 时，不能把进程当前目录当作来源根；只能按已有兼容策略拒绝或要求显式授权。
- 导入权限和检索范围是两个概念：报告保存于用户级目录，但来源文件只在导入时按 sandbox 读取。
- 保存原文件快照后，后续搜索读取快照，不依赖原路径仍然存在；刷新前不能自动读取已授权范围之外的新路径。
- 读取内容要遵守已有文本大小、编码和二进制限制。大文件应拒绝、分段或只生成受限结构摘要，具体规则必须可配置并测试。

## 存储布局与版本

建议使用用户级存储，并区分 thread 报告和本地文件报告：

```text
~/.poirot/
├── reports/
│   └── sources/YYYY/MM/DD/
│       └── report-HH-MM-SS-source-title.md
├── conversations/
│   └── sources/
│       └── {source_id}/{version}.source-snapshot
└── rag/
    └── index.sqlite
```

实际项目可以选择不同文件名，但必须保持以下关系：

- 报告是可被 FTS5 索引的 Markdown 快照；
- 原文件内容保存在独立的 source snapshot 中，作为最深层来源；
- 报告元信息包含 `source_type=local_file`、`source_id`、原路径、真实路径、hash、版本、快照位置和生成时间；
- source snapshot 不使用 thread 的 `conversation.jsonl` 语义，不写入 user/assistant 消息，也不进入 thread checkpoint。

每次成功刷新生成新版本：

```text
source_id
version
source_path
source_realpath
content_hash
size_bytes
mtime
imported_at
report_path
snapshot_path
status
```

内容 hash 相同可以跳过重复报告生成，但要保留本次检查时间；hash 变化必须生成新报告和新快照。旧版本默认只读保留，检索默认使用最新有效版本，并能按版本追溯来源。

## 文件报告格式

本地文件报告沿用 L0/L1/L2，但内容不是 thread 对话摘要：

- **L0**：文件用途、类型、总体结构、版本状态和适用范围；
- **L1**：关键字段、模块/章节、接口或配置项、约束、依赖和风险；
- **L2 `rag`**：可独立检索的事实、配置含义、API 约定、关键代码行为或操作结论；
- **L3**：原文件快照，按需读取相关片段，保留来源行号或字节范围。

报告必须标明摘要是对哪个 hash/version 的文件生成的。不能在文件变化后继续把旧摘要描述成当前文件状态。

生成摘要可以使用已有 reporter/LLM，但必须把文件正文作为不可信资料输入：文件中的 prompt、命令或“忽略规则”不能覆盖系统规则，也不能授权工具执行操作。无法解析的文件可以生成有限的错误报告，或记录导入失败，但不能编造文件内容。

## FTS5 与渐进式检索

- 文件报告的标题、描述、L0、L1 和 L2 `rag` 块进入现有 FTS5；使用同一索引接口和来源字段。
- 默认搜索范围仍由模块三/四定义。当前项目搜索本地文件时，应只返回当前项目和真实 cwd 下已授权的来源；`--all-projects` 是否包含用户级文件来源必须明确显示 `source_type` 和路径。
- 原文件快照默认不进入向量索引，也不作为首层全文索引。函数名、配置键、错误码等需要精确搜索时，可在同一 SQLite 中增加受控的 source-text FTS 表，作为后续增强，不把全文直接当作语义报告。
- 检索命中 L0/L1 后，摘要不足才展开 L2；仍不足才从匹配的 snapshot 读取有限片段。不能因为命中某个文件就把整个文件加入上下文。
- 返回来源必须包括 source ID、原路径、版本/hash、报告路径和必要的行号/片段范围。

## 更新、失效和删除策略

- 原文件移动、删除或权限变化时，旧报告和快照仍可检索，并标记原路径失效；刷新操作返回明确错误。
- 新文件替代原路径时不能自动覆盖旧 source；必须由用户执行 refresh，并记录 hash 变化。
- 报告生成失败时不写入“成功版本”；若快照已经保存，状态应标记为待报告/待索引，不伪装为可检索完成。
- FTS5 索引失败不删除报告和快照，可重试或使用模块二的全量重建。
- `remove` 的默认行为应清理来源登记和当前版本索引，但保留历史报告/快照，除非用户明确请求永久清理；历史报告的检索可由后续版本策略决定。
- 不因 thread 删除、项目切换或 sandbox 变化自动删除用户级来源；读取时仍执行当前授权和报告来源校验。

## 目标与范围

实现一个 `LocalFileSource`（名称可按项目习惯调整）流程：用户显式添加文件，系统保存源信息和原文件快照，生成同格式的分层报告，将报告加入现有 FTS5，并让 `/search`/`search_reports` 能在来源明确的前提下返回它。

建议提供与现有 CLI 风格一致的来源管理命令，例如：

```text
/source add <path>
/source list
/source refresh <source_id>
/source remove <source_id>
```

如果项目已有更合适的命令命名或管理入口，沿用它，但必须具备添加、查看、刷新和移除的等价能力。目录导入可以支持，但必须逐文件、有数量/深度/大小上限，不能无界扫描。

本功能必须交付：

- 显式文件/目录添加和来源 ID；
- sandbox 范围校验、文本/大小/编码限制；
- 原路径、真实路径、hash、版本和导入状态；
- 原文件快照的可靠写入；
- `source_type=local_file` 的 L0/L1/L2 分层报告；
- 复用现有 FTS5 的索引、重建、搜索和来源展示；
- 显式 refresh 产生新版本、保留旧版本或明确失效状态；
- 删除/失效/索引失败的可诊断处理和测试。

不实现实时监听、后台自动刷新、默认全目录导入、二进制/多模态解析、Embedding、向量数据库、跨项目文件权限、文件写入或 thread checkpoint 修改。

## 开始前源码核查

先简要确认并继续开发：

1. 模块一报告的实际 Markdown/frontmatter 和 P0 生成接口；
2. 模块二 FTS5 的报告来源类型、元数据表、增量/重建接口；
3. 模块三/四如何读取报告、L2、L3，以及如何展示来源；
4. sandbox 的文件读取入口、`thread.cwd`、`/add-dir` 追加目录和真实路径校验；
5. `storage_root`、原子写入、文件锁和现有命令补全/交互机制；
6. 当前文件工具对大小、二进制、编码和符号链接的已有约束。

不要把模块一的 thread `conversation.jsonl` 复用于本地文件，也不要把原路径直接当作永久来源。明确一个文件版本、报告、快照和 FTS 记录之间的一一对应关系。

## 来源添加与权限

- 只接受用户显式的 `/source add` 或等价入口；不扫描当前目录，不因 Agent 查询自动导入文件。
- 使用现有 sandbox/file reader 读取。真实路径必须在当前 thread 的 cwd 或已授权追加目录内；拒绝 `../`、越界绝对路径、相似前缀和符号链接逃逸。
- 添加和 refresh 都重新校验权限；不能因为旧 source 记录曾经允许过，就读取现在已不允许的路径。
- 当前 thread 无 cwd 时不能退回进程 cwd；按现有兼容策略拒绝或要求用户先绑定目录。
- 文件报告保存到用户级 storage root，但这不等于所有 thread 获得源文件访问权限。搜索结果要遵守模块三/四的 project/cwd scope。
- 文件必须是允许的文本类型，遵守既有单文件大小和编码限制。目录导入设置递归深度、文件数、总字节数和排除规则；单文件失败记录原因，不能泄露文件内容。

## 来源版本和快照

为每个来源建立稳定 `source_id`，每次导入/刷新生成递增或唯一 `version`。记录：

```text
source_id
version
source_path
source_realpath
size_bytes
mtime
content_hash
imported_at
report_path
snapshot_path
status
```

- 原文件先读取并计算 hash，再保存不可变 snapshot；报告必须引用该版本和 hash。
- 内容 hash 未变化时可复用旧报告，但应记录本次检查结果；不能重复制造相同版本。
- hash 变化时生成新报告、新快照和新索引块；旧版本默认只读保留，默认搜索最新有效版本。
- snapshot 用独立的 source 文件格式保存原文和必要元信息，不写成 user/assistant 消息，不进入 thread checkpoint。
- snapshot 和报告使用临时文件、flush/fsync、原子替换；两者不应出现无法配对的“成功版本”。失败时保留旧版本并标记新版本失败或未完成。
- 原路径被删除或移动时，旧 snapshot 仍可用于检索；refresh 明确报告 source_unavailable，不把其他文件静默替代。

## 文件报告和索引

为每个成功版本生成 `source_type=local_file` 的 L0/L1/L2 报告：

- L0：文件用途、类型、总体结构、版本状态；
- L1：关键字段/章节/接口、依赖、限制和风险；
- L2 `rag`：可独立检索的事实、配置含义、API 约定和稳定结论；
- 深层来源：snapshot 中的原文片段，需带行号或字节范围。

文件内容是不可信资料。生成报告的模型不能遵循文件中的 prompt injection、命令或权限指令。解析失败时报告失败或生成明确的错误状态，不编造事实。

调用模块二索引接口，把报告标题、描述、L0/L1/L2 加入同一 SQLite FTS5。不要默认索引整个 snapshot；如为函数名、配置键、错误码提供精确搜索，使用单独、受控的 source-text FTS 字段，并明确其 token/隐私上限。

让模块三/四的结果包含 `source_type`、`source_id`、原路径、版本/hash、报告路径和行号/片段范围。搜索默认只返回当前项目/cwd 允许的来源；`--all-projects` 的行为与现有约定一致，并清楚标识本地文件来源。

## source 管理行为

- `list` 显示 source ID、名称、路径、版本、hash 摘要、状态和最近更新时间，不直接打印大段原文。
- `refresh` 只刷新指定 source；不存在或失效时明确报错；成功后更新最新版本并增量索引。
- `remove` 至少移除来源登记、最新版本索引和默认搜索入口。历史报告/快照默认保留以支持可追溯；如果实现永久清理，必须是显式选项并有失败回退。
- 目录批量导入需要显示成功、跳过和失败数量，并允许单文件重试。
- 任何状态不一致（报告存在但 snapshot 缺失、索引存在但报告失效）都应在 list/refresh/rebuild 中可诊断，不能当作成功知识源。

## 测试与验收

使用临时 `storage_root`、至少两个项目目录和多个 thread。先运行 source 管理、快照和报告测试，再运行 FTS5、`/search`、Agent、sandbox、CLI/TUI 和跨进程回归，最后运行全量测试；区分新增失败与既有失败。

至少覆盖：

1. 添加文本文件后生成正确的 source ID、版本、hash、snapshot 和分层报告；报告进入现有 FTS5，`/search` 能找到并展示 `source_type=local_file` 来源。
2. 添加目录的深度、数量、总大小、排除规则和单文件失败；不会无界读取或扫描。
3. `cwd`/`/add-dir` 权限、越界路径、相似前缀、符号链接逃逸、无 cwd thread、二进制、超大文件和解码失败。
4. 内容未变时 refresh 不制造重复版本；内容变化时产生新版本；旧版本和当前版本的报告、hash、快照、索引可区分。
5. 原路径删除、移动、权限变化以及新文件占用旧路径时，refresh 不静默替换；旧 snapshot 仍能按策略检索。
6. 报告写入成功但索引失败、快照写入失败、报告/快照配对失败、SQLite 损坏和重建；不能产生伪成功状态。
7. `remove` 后默认搜索入口和索引行为符合策略；历史保留或永久清理有明确断言。
8. 文件内容中的 prompt injection、命令和“忽略规则”不会改变 Agent 系统规则、工具调用或 sandbox；原文只作为资料。
