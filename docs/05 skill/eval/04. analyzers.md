我按"装配 → 调用 → 内部执行 → 持久化"四条线，把 analyzers 这组组件的工作流程讲清楚。先给一张总览图，再逐个文件拆。

## 1. analyzers 在 eval 中的位置

```
                          ┌─────────────────────────────────────────────┐
                          │            eval/registry.py                 │
                          │   RegistryEvalBridge（L2 唯一可见的 L3 实现） │
                          └───────────────────┬─────────────────────────┘
                                              │ evaluate(ctx)
                                              ▼
                          ┌─────────────────────────────────────────────┐
                          │     response_contract_checker.py            │
                          │      （响应层：candidate 晋升前检查）         │
                          └───────┬──────────────────────────┬──────────┘
                                  │ compile()                │ _run_rule()
                                  ▼                          ▼
                          ┌───────────────┐          ┌───────────────┐
                          │contract_       │          │  checks.py    │
                          │compiler.py     │          │（纯函数检查）  │
                          └───────────────┘          └───────────────┘

          ┌──────────────────────────────────────────────────────────────┐
          │                    两个独立的 LLM 评估器                       │
          ├────────────────────────────┬─────────────────────────────────┤
          │ skill_judgment_analyzer.py │ task_quality_judge.py           │
          │ （执行层，async）            │ （任务层，async）                │
          └──────────────┬─────────────┴──────────────┬──────────────────┘
                         │                            │
                         ▼                            ▼
                  SkillJudgment                TaskQualityScore
                  EvolutionSuggestion
                         │                            │
                         └────────────┬───────────────┘
                                      ▼
                              store（SQLiteSkillStore）
```

**关键点**：analyzers 里有 **3 条独立路径**：

| 路径 | 组件 | 触发时机 | 是否走 registry |
|------|------|---------|:---:|
| 响应层 | `ResponseContractChecker` | candidate 晋升前 | ✅ 走 `RegistryEvalBridge` |
| 执行层 | `SkillJudgmentAnalyzer` | after_agent（异步） | ❌ 独立 |
| 任务层 | `TaskQualityJudge` | 任务结束后（异步） | ❌ 独立 |

`checks.py` 和 `contract_compiler.py` 是**被响应层复用的纯函数/编译层**，不是独立评估器。

## 2. 装配：谁构造谁

### 2.1. 响应层（通过 registry 装配）

```python
# bootstrap 调 build_default_registry()
build_default_registry()
    ├─ ContractCompiler()                       # 无状态，编译规则
    ├─ ResponseContractChecker(compiler)         # 持有 compiler
    └─ EvalRegistry(checker)                     # 注册表
          │
          ▼
    RegistryEvalBridge(registry)                 # 实现 EvalBridge Protocol
          │
          ▼
    注入 L2（ScoreDeltaGate）
```

装配路径：`build_default_registry` → `EvalRegistry` → `RegistryEvalBridge` → 注入 L2。
**L2 只认 `EvalBridge` Protocol，不 import analyzers。**

### 2.2. 执行层 / 任务层（由 bootstrap 直接装配）

```python
# bootstrap 里（示意）
judgment_analyzer = SkillJudgmentAnalyzer(llm=llm, store=store)
task_judge        = TaskQualityJudge(llm=llm, store=store)
runtime_tracker   = RuntimeTracker(...)

EvalLayer(
    bridge=registry_bridge,
    judgment_analyzer=judgment_analyzer,
    task_judge=task_judge,
    runtime_tracker=runtime_tracker,
)
    └─ SkillManager.set_eval_layer(eval_layer)   # 回注
```

**注意区别**：

- 响应层走 **registry/bridge**（L2 通过 Protocol 调用）。
- 执行层 / 任务层直接由 **bootstrap 构造并注入 EvalLayer**，不经过 registry。

### 2.3. 依赖注入的两种方式

| 组件 | 依赖 | 注入方式 |
|------|------|---------|
| `ContractCompiler` | 无 | 直接 `new` |
| `ResponseContractChecker` | `ContractCompiler` | 构造参数（可缺省） |
| `SkillJudgmentAnalyzer` | `llm` / `store` | 构造参数（可 None） |
| `TaskQualityJudge` | `llm` / `store` | 构造参数（可 None） |
| `checks.py` | 无 | 纯函数，直接 import 用 |

**共同点**：`llm` / `store` 都可为 `None`——这是 graceful degradation 的装配前提。

## 3. 调用流程：三条路径分别怎么跑

### 3.1. 响应层（同步，candidate 晋升前）

```
L2 ScoreDeltaGate
    └─ RegistryEvalBridge.evaluate(ctx)
          ├─ registry.get_contract_checker()          ← 取 checker
          ├─ checks.read_content(ctx.candidate)       ← 读 candidate 文件
          ├─ checks.read_content(ctx.baseline)        ← 读 baseline（无则 ""）
          └─ ResponseContractChecker.check(candidate, baseline)
                │
                ├─ 1. rules = compiler.compile(candidate)     ← 编译规则
                │        ├─ 全局硬规则：nonempty / json_parseable
                │        ├─ contract 规则：按 candidate 文本关键词
                │        │     must_cite / lead_with_conclusion / paragraph_limit
                │        └─ soft 规则：no_unfounded_claims / semantic_density
                │
                ├─ 2. for rule in rules:
                │        cand_pass = _run_rule(rule_id, candidate, params)   ← 分发到 checks
                │        base_pass = _run_rule(rule_id, baseline, params)
                │        if rule.hard and not cand_pass:
                │              hard_failures.append(rule_id)
                │        evidence.append(EvalEvidence(...))
                │
                ├─ 3. score = passed / total
                ├─ 4. recommendation = "reject" if hard_failures else "accept"
                └─ 5. return EvalResult(score, metric="hard", hard_failures, ...)
                      │
                      ▼
                回到 L2 → 决定是否晋升
```

**异常路径**：`evaluate` 里任何异常 → `RegistryEvalBridge` fail-closed 返回 reject（不改动 checker 内部）。

### 3.2. 执行层（异步，after_agent）

```
after_agent（调用方负责 asyncio.create_task）
    └─ SkillJudgmentAnalyzer.analyze_execution(
           task_id, journal_events, messages_summary, injected_skills, task_completed)
         │
         ├─ 前置检查：injected_skills 空 或 llm is None → 返 ([], [])
         │
         ├─ try: _llm_analyze(...)
         │       ├─ 构造 prompt（skills 清单 + 摘要 + journal 事件）
         │       ├─ llm.invoke([HumanMessage])
         │       ├─ _extract_json（find { ... rfind }）
         │       ├─ 解析 judgments[] → list[SkillJudgment]
         │       └─ 解析 suggestions[] → list[EvolutionSuggestion]
         │     except → 返 ([], [])
         │
         ├─ _persist(task_id, judgments, task_completed)
         │       └─ for j in judgments:
         │             ├─ store.save_judgment(j)               → skill_eval_judgments 表
         │             └─ store.record_outcome(                → 更新 L1 4 计数器
         │                    j.skill_id, run_id=task_id,
         │                    applied=j.skill_applied,
         │                    task_completed=task_completed,
         │                    note=j.deviation_note)
         │                   （异常 → silent degradation）
         │
         └─ return (judgments, suggestions)
               └─ suggestions 交给 L2 trigger（供进化）
```

**关键设计点**：

- **一次 LLM 调用产两类**（judgment + suggestion），省成本。
- **analyzer 内调 `record_outcome`**（D-L3-3）——这是 eval 层反向更新 L1 计数器的点。
- **异步 fire-and-forget**（D-L3-19）——不阻塞用户，caller 负责 create_task。

### 3.3. 任务层（异步，任务结束后）

```
任务结束后（调用方触发）
    └─ TaskQualityJudge.judge_task(task_id, execution_trace, final_output)
         │
         ├─ 前置检查：llm is None → 返 None
         │
         ├─ try: _llm_judge(...)
         │       ├─ 构造 prompt（trace + output + 4 维说明）
         │       ├─ llm.invoke([HumanMessage])
         │       ├─ _extract_json
         │       ├─ 4 维 clamp 到 [0, 1]
         │       └─ overall = Σ(dim × weight)
         │             权重：0.50 / 0.35 / 0.05 / 0.10
         │     except → 返 None
         │
         ├─ store.save_task_score(score)        → task_quality_scores 表
         │     （异常 → silent degradation）
         │
         └─ return TaskQualityScore
```

**关键设计点**：

- 4 维各自 clamp 到 `[0,1]`，防止 LLM 返回越界值。
- `overall_score = round(Σ(dim × weight), 3)`。
- LLM 失败 → 返 `None`（不抛，不影响主流程）。

## 4. checks.py` 与 `contract_compiler.py` 的关系

这两个是响应层的**支撑模块**，不独立触发：

```
ContractCompiler.compile(skill_content)
    └─ 决定"要跑哪些规则"
          ├─ 全局硬规则：始终有（nonempty / json_parseable）
          ├─ contract 规则：扫 skill 文本关键词决定
          │     _mentions_sources / _mentions_conclusion_first / _paragraph_limit
          └─ soft 规则：始终有（no_unfounded_claims / semantic_density）

ResponseContractChecker._run_rule(rule_id, content, params)
    └─ 把 rule_id 分发到 checks.py 的具体检查函数
          nonempty            → checks.check_nonempty
          json_parseable      → checks.check_json_parseable
          must_cite           → checks.check_must_cite
          lead_with_conclusion→ checks.check_lead_with_conclusion
          paragraph_limit     → checks.check_paragraph_limit
          no_unfounded_claims → checks.check_no_unfounded_claims
          semantic_density    → checks.semantic_density（区间判定）
          未知                → 默认 pass
```

**分工**：

- `checks.py` = **怎么检查**（纯函数，单一真相源）。
- `contract_compiler.py` = **检查哪些**（按 skill 文本编译规则清单）。
- `response_contract_checker.py` = **执行检查 + 汇总打分**。

**关键点**：`checks.py` 被 checker 复用；`contract_compiler` 只产规则，不做检查。

## 5. 完整调用链

```
装配期（bootstrap）
    ├─ build_default_registry()
    │     ├─ ContractCompiler
    │     ├─ ResponseContractChecker
    │     └─ EvalRegistry
    │           └─ RegistryEvalBridge → 注入 L2
    ├─ SkillJudgmentAnalyzer(llm, store)
    ├─ TaskQualityJudge(llm, store)
    └─ EvalLayer(bridge, analyzer, judge, tracker) → set_eval_layer

        ═══════════ 运行期 ═══════════

响应层（同步，candidate 晋升前）
    L2 → RegistryEvalBridge.evaluate(ctx)
            ├─ checks.read_content(candidate/baseline)
            └─ ResponseContractChecker.check(...)
                  ├─ ContractCompiler.compile(candidate) → rules
                  ├─ for rule: _run_rule → checks.check_*(...)
                  └─ EvalResult → L2

执行层（异步，after_agent）
    caller → asyncio.create_task(analyzer.analyze_execution(...))
            ├─ _llm_analyze → SkillJudgment[] + EvolutionSuggestion[]
            ├─ store.save_judgment
            ├─ store.record_outcome（更新 L1 4 计数器）
            └─ suggestions → L2 trigger

任务层（异步，任务结束后）
    caller → asyncio.create_task(judge.judge_task(...))
            ├─ _llm_judge → TaskQualityScore
            └─ store.save_task_score
```

## 6. 总结

| 组件 | 角色 | 触发 | 异常策略 |
|------|------|------|---------|
| `checks.py` | 纯函数检查库（单一真相源） | 被 checker 调 | 读失败返 `""` |
| `contract_compiler.py` | 按 skill 文本编译规则清单 | 被 checker 调 | — |
| `response_contract_checker.py` | 响应层执行 + 打分 | 晋升前（同步） | 走 bridge fail-closed |
| `skill_judgment_analyzer.py` | 执行层 LLM 判断 + 进化建议 | after_agent（异步） | 返空，silent |
| `task_quality_judge.py` | 任务层 LLM 4 维评分 | 任务结束后（异步） | 返 None，silent |

**analyzers 的分工**：`checks` 提供检查能力 → `compiler` 决定检查哪些 → `checker` 执行并打分（响应层）；`analyzer` / `judge` 是两条独立的 LLM 评估线。三条线最终都通过 `store` 落库，供 evolution 消费。
