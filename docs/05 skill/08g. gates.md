
## 1. gates 是什么

gates 是 evolution 闭环的**决策层**——回答"**candidate 能不能晋升**"。它消费 `EvalResult`，产 `GateDecision`（accept / reject / pending_human）。

它由两组东西构成：

| 类别 | 文件 | 状态 | 作用 |
|------|------|:---:|------|
| **决策门** | `score_delta_gate.py` | 2a 实现 | 晋升前判定 accept / reject |
| **监控回滚** | `git_ratchet.py` | 2a 实现 | 上线后退化兜底回滚 |
| **接口预留** | `protocols.py` | 2b/L3 预留 | 5 个未来门的 Protocol |

注意：**`GitRatchet` 不是决策门**——它不在晋升环节，而是"上线后监控"。两者解耦。

## 2. 怎么被调用（谁调它）

### 2.1. `ScoreDeltaGate` —— 被 `EvolutionManager._run_evolution` 调

```
EvolutionManager._run_evolution(ctx)
    ├─ 1. focus
    ├─ 2. mutate
    ├─ 3. eval
    ├─ 4. gate
    │     └─ self._gate.decide(candidate, baseline, eval_result)   ← 调 ScoreDeltaGate
    │           └─ 返回 GateDecision(recommendation, reason, new_version_id)
    ├─ 5. create_version（若 recommendation ∈ {accept, accept_new_best}）
    └─ 6. record
```

**调用点**：闭环第五步（gate 步），在 eval 之后、create_version 之前。

### 2.2. `GitRatchet` —— 被 `EvolutionManager`（或独立调度）周期调

```
EvolutionManager（或独立周期任务）
    └─ git_ratchet.check_and_rollback(store, current)   ← 调 GitRatchet
          └─ 返回回滚到的旧 skill_id 或 None
```

**调用点**：不在 `_run_evolution` 内；是**上线后的独立监控**，按周期触发。

### 2.3. 谁构造它们

bootstrap 装配：

```
ScoreDeltaGate(min_delta=0.0)
GitRatchet(degradation_threshold, min_selections, runtime_tracker)
    ├─ ScoreDeltaGate → EvolutionManager(gate=...)
    └─ GitRatchet     → EvolutionManager（或独立调度）
```

## 3. 怎么触发（判定逻辑）

### 3.1. `ScoreDeltaGate.decide` —— 三条分支

```
输入：candidate, baseline, eval_result

① hard_failures 非空
      → reject（candidate 改坏了）

② baseline is None（CAPTURED 新技能）
      score > 0 → accept（new_version_id=candidate.skill_id）
      score = 0 → reject

③ FIX / DERIVED
      baseline_score = 从 evidence 的 baseline_pass 比例推断
      candidate.score > baseline_score + min_delta → accept
      否则 → reject
```

**设计要点**：

- **零 LLM**：所有决策基于 `EvalResult`（D7：LLM 自评 46.4% 不可靠）。
- **baseline_score 的推断**：不直接存 baseline 分，而是从 `EvalResult.evidence` 里 `baseline_pass` 的通过比例反推；无 evidence 时视为 0。
- **CAPTURED 特例**：无 baseline 可对比，退化为"score > 0 即 accept"。

### 3.2. `GitRatchet.check_and_rollback` —— 退化判定 + 回滚

```
输入：store, current（当前 active skill）

① D-L3-16：runtime_tracker 非 None → degraded_skills()（软信号，异常静默）
② anti-loop：total_selections < min_selections → None（新版本需积累数据）
③ 健康：effective_rate >= threshold → None
④ 退化 → 找回滚目标：
      a. 优先 lineage.parent_skill_ids 里的版本
      b. 无 parent → generation 最低的非当前版
⑤ 未找到 → None
⑥ 找到 → store.rollback(target.skill_id)，返 target.skill_id
```

**设计要点**：

- **anti-loop**：`selections < min` 不评判——避免新版本数据不足时被误回滚。
- **两级兜底**：先找血缘父节点，找不到就退回最早版本。
- **只切指针不删行**：`store.rollback` 只改 `is_active`；旧 node 仍在 DAG（类比 git revert，禁 reset --hard）。
- **软信号**：`runtime_tracker` 只是补充，主判据仍是 `effective_rate`。

## 4. 产出什么

| 门 | 产出 | 被谁消费 |
|----|------|---------|
| `ScoreDeltaGate` | `GateDecision(recommendation, reason, new_version_id)` | `EvolutionManager._run_evolution` 第 5 步 → 决定是否 `create_version` |
| `GitRatchet` | `str \| None`（回滚到的旧 skill_id） | 调用方自行处理（无后续动作） |

`GateDecision` 的 `recommendation` 取值：`accept_new_best` / `accept` / `reject` / `pending_human`。

## 5. 2b / L3 预留的门（`protocols.py`）

| Protocol | 阶段 | 语义 |
|----------|------|------|
| `ChampionGateProtocol` | 2b | score delta + hard_failures 双门（区分关键 vs 非关键） |
| `HITLGateProtocol` | 2b | 人审装饰器，accept 转 pending_human，staging 待 `/skill approve\|reject` |
| `CompositeGateProtocol` | 2b | cascading 链式，早期 reject short-circuit |
| `ValidationGateProtocol` | L3 | held-out 重放 + longitudinal pairs，需 `ValidationGateEvalAdapter` |
| `MultiJudgeGateProtocol` | L3 | 多 LLM judge + majority vote，需 `LLMJudgeEvalAdapter` |

**共同点**：都实现 `PromotionGate Protocol`（`evolution/protocols.py`），签名统一 `decide(candidate, baseline, eval_result) -> GateDecision`，因此 `EvolutionManager` 无需感知具体实现。

## 6. 完整调用链（一张图）

```
bootstrap
    ├─ ScoreDeltaGate(min_delta=0.0)               ← 2a 决策门
    ├─ GitRatchet(degradation_threshold, ...)      ← 2a 回滚监控
    └─ EvolutionManager(..., gate=ScoreDeltaGate)

        ═══════════ 运行期 ═══════════

① 晋升决策（_run_evolution 第五步）
    gate.decide(candidate, baseline, eval_result)
        ├─ hard_failures 非空 → reject
        ├─ baseline None（CAPTURED）→ score>0 ? accept : reject
        └─ FIX/DERIVED → score > baseline_score + min_delta ? accept : reject
    → 若 accept → store.create_version(...)

② 上线后监控（周期）
    git_ratchet.check_and_rollback(store, current)
        ├─ anti-loop：selections < min → None
        ├─ effective_rate >= threshold → None（健康）
        └─ 退化 → store.rollback(target.skill_id)

③ 2b/L3 扩展（预留）
    实现 protocols.py 的 5 个 Protocol → 注册为 gate
```

## 7. 总结

| 问题 | 答案 |
|------|------|
| gates 是什么？ | evolution 的决策层：`ScoreDeltaGate`（晋升决策）+ `GitRatchet`（上线后回滚）。 |
| 谁调用？ | `EvolutionManager._run_evolution` 调 `ScoreDeltaGate.decide`；`GitRatchet` 由 manager 或独立调度周期调。 |
| 怎么触发？ | ScoreDeltaGate：eval 后按分数 + hard_failures 判定。GitRatchet：按周期扫退化。 |
| 产出什么？ | `GateDecision`（决定是否 create_version）/ 回滚的旧 skill_id。 |
| 核心原则？ | 零 LLM（D7）；anti-loop（selections 门槛）；只切指针不删历史。 |
| 2b/L3 预留？ | 5 个 Protocol（ChampionGate / HITLGate / CompositeGate / ValidationGate / MultiJudgeGate），统一 `decide` 签名，零侵入替换。 |

**gates 层的本质**：它是"**晋升把关 + 上线兜底**"——`ScoreDeltaGate` 在闭环第五步决定 candidate 生死；`GitRatchet` 在之后持续监控，必要时回滚。两者一前一后，共同保证"只有更好的版本能留下，退化的版本能退回"。
