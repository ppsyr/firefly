---

name: SkillInjectionMiddleware — before_model 注入 active skills 内容 + selections 打点 + provenance。

description: 
【整体职责】
在每次进入 model 之前，决定本次任务要激活哪些 skill，然后：
1. 把这些 skill 的说明内容作为一条 SystemMessage 注入 messages；
2. 对每个激活的 skill 做「选择打点」（store.record_selection + journal）；
3. 写 provenance 锚点，供下游中间件判断 skill 是否真正被应用。
  
【INVARIANT（必须保持的不变量）】
- 混合注入：激活来源有两路——
· 用户 override（metadata.skill_override，或 /skill 命令经主循环注入的
runtime configurable）；
· agent 自动 select（由 Selector 根据 user_input 选出）。
两路合并后再决定注入内容。
- before_model 负责：注入 SystemMessage + record_selection + journal skill.select。
- provenance 锚点分两处：
· metadata.active_skills ← 本次激活的 skill id 列表；
· metadata.skill_applied ← {id: None}，初始为 None，
由 SkillMetricsMiddleware.awrap_tool_call 在工具真正被调用后标 True。
- 无 active skills 时返回 None（不注入、不打点）。
- 无 store / journal 时静默不报错（INV#13，容忍运行环境缺件）。
- abefore_model 直接委托同步版，保证同步/异步行为一致。  

【ContextVar provenance】
_active_skills_ctx / _applied_ctx 是 request-scoped 的 ContextVar，供 SkillMetricsMiddleware.awrap_tool_call 读取 allowed_tools 并标记 applied。

---

### 0.2. 运行时调用树（按执行阶段分：选择 → 注入 → 打点 → 锚点）

```
LangGraph 进入 before_model 阶段
│
└─ SkillInjectionMiddleware.before_model(state, runtime)
    │
    ├─ 【阶段 1：解析依赖】
    │   ├─ store   = runtime.skill_store or self._store
    │   ├─ journal = runtime.journal（可为 None）
    │   └─ run_id  = runtime.run_id（可为 None）
    │
    ├─ 【阶段 2：解析输入】
    │   ├─ user_input = state["user_input"] or ""
    │   └─ overrides  = runtime.skill_override
    │                   or state.metadata.skill_override
    │                   or []
    │
    ├─ 【阶段 3：选择】
    │   └─ active = selector.select_for_task(user_input, overrides)
    │       └─ if not active: return None        ← 短路：三件事都不做
    │
    ├─ 【阶段 4：打点】
    │   └─ for rec in active:
    │       ├─ store.record_selection(rec.skill_id)          ← try/except
    │       ├─ journal.append("skill.select", {...})          ← if journal + try/except
    │       └─ ids.append(rec.skill_id)
    │
    ├─ 【阶段 5：注入准备】
    │   ├─ injection = build_injection_text(active)
    │   └─ get_stream_writer()({"type": "skill_active", ...}) ← try/except
    │
    ├─ 【阶段 6：写 provenance 锚点】
    │   ├─ _active_skills_ctx.set([(skill_id, allowed_tools), ...])
    │   └─ _applied_ctx.set({sid: None for sid in ids})
    │
    └─ 【阶段 7：返回 state patch】
        └─ {
             "messages": [SystemMessage(injection)],           ← 注入
             "metadata": {
               "active_skills": ids,                            ← 锚点（持久）
               "skill_names": [rec.name, ...],
               "skill_applied": {sid: None for sid in ids},      ← 锚点（待下游标 True）
             },
           }
```

## 1. 把 skill 说明作为一条 SystemMessage 注入 messages

### 怎么做到的

```python
injection = build_injection_text(active)          # records → 一段文本
...
return {"messages": [SystemMessage(content=injection)], ...}  # 追加进 messages
```

三步：
1. `selector.select_for_task` 选出 `active` 列表；
2. `build_injection_text(active)` 把多个 skill 说明拼成**一段**文本；
3. 包成**一条** `SystemMessage`，通过 state patch 追加进 messages。

### 存在的问题

| # | 问题 | 说明 |
|---|---|---|
| 1.1 | **不区分首轮/后续，每轮无条件重选重注入** | 没有 `if first_turn` 判断，同一个 skill 可能被反复注入多次 |
| 1.2 | **不检查已注入内容，可能重复注入** | 不读 state 里已有的 skill SystemMessage，同一 skill 可能每轮都追加一条 |
| 1.3 | **注入位置是末尾，但下游被合并到最前** | `MessageNormalizerMiddleware` 把所有 SystemMessage 合并成 leading，把「追加末尾」的 cache 优势抵消 |
| 1.4 | **KV cache 不友好** | 每轮注入内容随 selector 变化 → 前缀每轮变 → 无法复用 cache |
| 1.5 | **未做分层注入** | 没有「稳定 skill 放最前 system prompt + 增量 skill 放末尾」的分层设计 |
| 1.6 | **覆盖式注入而非增量式** | 每轮都是新的 active 列表，不维护「thread 内已注入 skill 集合」 |

## 2. 对每个激活的 skill 做「选择打点」

### 怎么做到的

```python
for rec in active:
    try:
        store.record_selection(rec.skill_id)          # store 累计
    except Exception:
        pass
    if journal is not None:
        try:
            journal.append("skill.select", {           # journal 事件
                "skill_id": rec.skill_id,
                "name": rec.name,
                "run_id": run_id,
            })
        except Exception:
            pass
    ids.append(rec.skill_id)
```

两路打点：
1. **store**：`record_selection(skill_id)` → 往持久存储给该 skill 的「被选中计数」+1（跨轮累计）。
2. **journal**：`append("skill.select", {...})` → 往当前 run 的事件流追加一条选择事件（带 `run_id`，供 trace 复盘）。

两者都 `try/except: pass`，失败不影响主流程。

### 存在的问题

| #   | 问题                        | 说明                                                               |
| --- | ------------------------- | ---------------------------------------------------------------- |
| 2.1 | **打点语义是「被选中」，不是「被应用」**    | 与 `skill_applied` 是两个概念，容易被误读为应用次数                               |
| 2.2 | **store 打点无去重**           | 同一 skill 同一轮只选一次，但同一 thread 多轮会重复累加；无法区分「同一 run 内重复」还是「跨 run 累加」 |
| 2.3 | **异常被静默吞掉**               | `except Exception: pass` 让打点失败完全不可见，排查困难                         |
| 2.4 | **store 与 journal 可能不一致** | store 写成功、journal 写失败（或反之），两者数据对不上                               |
| 2.5 | **无「未被应用」的显式记录**          | 只记了选择，没记「这个 skill 最终没用上」，需要靠 `skill_applied` 反推                  |
| 2.6 | **打点时机与注入耦合**             | 打点在注入前，若注入环节后续失败，打点已经记了，数据失真                                     |

## 3. 写 provenance 锚点，供下游判断 skill 是否真正被应用

### 怎么做到的

两处写：

**ContextVar（request-scoped，给下游即时读）：**
```python
_active_skills_ctx.set([(rec.skill_id, rec.allowed_tools) for rec in active])
_applied_ctx.set({sid: None for sid in ids})
```

**state.metadata（持久，供 trace/审计）：**
```python
"metadata": {
    "active_skills": ids,
    "skill_names": [rec.name for rec in active],
    "skill_applied": {sid: None for sid in ids},
}
```

- `_active_skills_ctx`：存 `[(skill_id, allowed_tools)]`，下游 `SkillMetricsMiddleware.awrap_tool_call` 读它判断工具调用是否命中 skill。
- `_applied_ctx` / `skill_applied`：初始 `{sid: None}`（未应用），下游命中工具后标 `True`。

## 4. 三件事汇总 + 全局问题

### 4.1. 三件事一览

| 事 | 产出 | 通道 | 谁消费 |
|---|---|---|---|
| ① 注入 | `SystemMessage(injection)` | messages patch | LLM |
| ② 打点 | `store.record_selection` + `journal.append` | store / journal | 统计 / trace |
| ③ 锚点 | `_active_skills_ctx` / `_applied_ctx` / `metadata.skill_applied` | ContextVar + metadata | 下游 `SkillMetricsMiddleware` |

### 4.2. 全局问题（跨三件事）

| # | 问题 | 影响 |
|---|---|---|
| G1 | **KV cache 不友好**：每轮重选重注入 + normalizer 合并到最前 | 前缀每轮变，cache 失效，成本上升 |
| G2 | **无分层注入**：没有「稳定 skill 放最前 + 增量 skill 放末尾」 | cache 与精准度无法兼得 |
| G3 | **无 thread 内 skill 集合维护**：不记「已注入过什么」 | 重复注入、无法做增量 |
| G4 | **打点语义易混淆**：选中 ≠ 应用 | 数据解读容易出错 |
| G5 | **applied 依赖下游且可能不同步** | provenance 可能不完整 |
| G6 | **异常静默吞掉**：打点/流事件/锚点写失败都无感知 | 问题难排查 |
| G7 | **与 `MessageNormalizerMiddleware` 缺乏协调** | 追加末尾的优势被合并抵消 |
| G8 | **无「注入是否值得」的反馈闭环** | 有打点数据，但没有机制用这些数据反哺 selector |

> **skill 的价值在于「按任务动态给对的说明」，但动态注入与 KV cache 天然冲突。**
>
> 项目选了**精度优先**（每轮动态选 + 注入），代价是 cache 不友好；
> 用打点（选中 + 应用）来**观测**这个选择的收益，但：
> - 没有做**分层注入**来缓解 cache；
> - 没有用打点数据**反哺 selector**；
> - `applied` 锚点还依赖下游且可能不同步。
>
> 所以它是「有观测、无优化」的中间形态。

## 5. 如果要改，优先级建议

1. **先修 provenance 同步**（3.1 / 3.2 / G5）：让 `metadata.skill_applied` 与 `_applied_ctx` 最终一致，否则打点数据不可信。
2. **再做分层注入**（1.5 / G2 / G7）：首轮放最前，增量放末尾，并让 normalizer 对 skill 注入豁免合并。
3. **维护 thread 内已注入集合**（1.2 / 1.6 / G3）：避免重复注入。
4. **打点语义显式化**（2.1 / G4）：区分 `select` 与 `apply`，命名上就分开。
5. **异常可观测**（2.3 / 2.6 / G6）：打点失败至少 logger.warning。
6. **闭环反哺 selector**（G8）：用 `select` / `apply` 比率调权。
