### 0.2. 运行时调用树（闭环七步 + 外部入口）

```
① 装配期（bootstrap，一次性）
    ├─ MetricMonitorTrigger(threshold, min_selections, cooldown_turns, llm)
    ├─ CaptureTrigger()
    ├─ IVEFocuser(llm, impl_fail_threshold)
    ├─ LLMMutator(max_changed_lines, max_steps, llm)
    ├─ ProgrammaticEvalBridge()（L3 关闭）或 RegistryEvalBridge(registry)（L3 启用）
    ├─ ScoreDeltaGate(min_delta)
    ├─ GitRatchet(degradation_threshold, min_selections, runtime_tracker)
    └─ EvolutionManager(store, triggers, focuser, mutator,
                        eval_bridge, gate, llm, journal)
          └─ SkillManager.set_evolution_manager(...)

        ═══════════ 运行期 ═══════════

② 自动入口：run_cycle()
    for trigger in triggers:
        contexts = trigger.should_trigger(store)          ← MetricMonitor / Capture
        for ctx in contexts:
            _run_evolution(ctx)                            ← 闭环七步
        trigger.mark_evolved(name, selections)             ← anti-loop 锚点

③ 手动入口：evolve_skill(skill_name)
    store.get_active → EvolutionContext(METRIC, FIX) → _run_evolution

④ 手动入口：capture_skill(pattern, suggested_name)
    CaptureTrigger.manual_capture → EvolutionContext(CAPTURE, CAPTURED)
        → _run_evolution

⑤ 闭环七步：_run_evolution(ctx)
    1. focus    ：focuser.focus(ctx, store)                → 增强 ctx
    2. mutate   ：mutator.mutate(ctx, llm)                 → (candidate, diff)
    3. eval     ：eval_bridge.evaluate(EvalContext)        → EvalResult
    4. gate     ：gate.decide(candidate, baseline, result) → GateDecision
    5. promote  ：accept 时 store.create_version(...)      → created_id
    6. record   ：store.record_evolution(EvolutionRecord)  → skill_evolutions
    7. journal  ：_emit_journal(ctx, decision, rec)        → skill.evolve / captured /
                                                              evolve_rejected

⑥ 上线后监控（独立周期）：GitRatchet.check_and_rollback(store, current)
    ├─ anti-loop：selections < min → None
    ├─ effective_rate >= threshold → None（健康）
    ├─ 找回滚目标：parent_skill_ids 优先，generation 最低兜底
    └─ store.rollback(target.skill_id)                     ← 只切 is_active 指针
```

- **它是编排层，不是决策者**：`EvolutionManager` 只按顺序调 Protocol 实现；accept / reject 由 gate 决定，评估由 eval_bridge 决定。
- **两条落库路径**：`create_version`（accept 时写 version DAG）+ `record_evolution`（无论 accept / reject 都记）。
- **三处 anti-loop**：trigger（min_selections + cooldown）、focuser（impl 累计升级）、ratchet（selections 门槛）。
- **回滚独立于闭环**：`GitRatchet` 不在 `_run_evolution` 内，是上线后的独立监控；只切指针不删行。
- **2a 能力边界**：只支持 FIX + 手动 CAPTURED；DERIVED 和自动 CAPTURED 留 2b；门控的 5 个 Protocol 留 2b/L3。
- **与 eval 的解耦点**：`EvalBridge Protocol`（定义在 evolution，实现在 evolution floor 或 eval L3），数据契约共享（`EvalResult` / `EvalContext` 定义在 `evolution/types.py`）。

## 1. evolution 的组件全景

```
evolution 闭环（L2）
├─ 编排层   EvolutionManager          （run_cycle / evolve_skill / capture_skill）
├─ 触发层   Trigger（Protocol）
│            ├─ MetricMonitorTrigger  （自动 FIX，周期扫 metrics）
│            └─ CaptureTrigger        （2a 仅手动 CAPTURED）
├─ 聚焦层   FailureFocuser（Protocol）
│            └─ IVEFocuser            （IVE 5 问诊断）
├─ 变异层   Mutator（Protocol）
│            └─ LLMMutator            （FIX 编辑 / CAPTURED 生成）
├─ 评估层   EvalBridge（Protocol）
│            ├─ ProgrammaticEvalBridge（L3 关闭时，兼容 facade）
│            └─ RegistryEvalBridge    （L3 启用时）
├─ 门控层   PromotionGate（Protocol）
│            └─ ScoreDeltaGate        （晋升决策，2a）
└─ 回滚层   GitRatchet                （上线后退化兜底）

入口与容器
├─ SkillManager.set_evolution_manager / get_evolution_manager
└─ EvalLayer（L3 侧，回注）
```

**关键**：`EvolutionManager` 是唯一编排者；trigger / focuser / mutator / eval_bridge / gate 都是 Protocol，实现可替换（零侵入）。

## 2. 初始化（装配期，一次性）

### 2.1. 装配调用链

```
bootstrap
    │
    ├─ ① 触发层
    │     MetricMonitorTrigger(threshold, min_selections, cooldown_turns, llm)
    │     CaptureTrigger()
    │
    ├─ ② 聚焦层
    │     IVEFocuser(llm, impl_fail_threshold)
    │
    ├─ ③ 变异层
    │     LLMMutator(max_changed_lines, max_steps, llm)
    │
    ├─ ④ 评估层（二选一）
    │     L3 关闭 → ProgrammaticEvalBridge()
    │     L3 启用 → RegistryEvalBridge(registry)   ← eval 侧装配
    │
    ├─ ⑤ 门控层
    │     ScoreDeltaGate(min_delta)
    │     GitRatchet(degradation_threshold, min_selections, runtime_tracker)
    │
    └─ ⑥ 打包注入
          EvolutionManager(
              store, triggers=[...], focuser, mutator,
              eval_bridge, gate, llm, journal,
          )
              └─ SkillManager.set_evolution_manager(...)   ← 回注，避免循环依赖
```

### 2.2. 装配来源分层

| 组件 | 实现类 | 注入方式 | 依赖 |
|------|--------|---------|------|
| 触发 | `MetricMonitorTrigger` / `CaptureTrigger` | 列表 | store（运行时）/ llm |
| 聚焦 | `IVEFocuser` | 构造参数 | llm |
| 变异 | `LLMMutator` | 构造参数 | llm |
| 评估 | `ProgrammaticEvalBridge` / `RegistryEvalBridge` | 构造参数 | — / registry |
| 门控 | `ScoreDeltaGate` | 构造参数 | min_delta |
| 回滚 | `GitRatchet` | 构造参数（或独立调度） | runtime_tracker（可 None） |
| 编排 | `EvolutionManager` | 构造参数 | 上述全部 + store + journal |

### 2.3. 为什么回注而不是在 `SkillManager.__init__` 里建

- evolution 组件反向依赖 skill 基础层（store）与 eval 类型，直接在建会成环。
- 所以走 `set_evolution_manager` 回注（与 `set_eval_layer` 同理）。

## 3. 在哪里被调用（入口与触发）

### 3.1. 三个对外入口

| 入口 | 调用方 | 触发方式 | 对应类型 |
|------|--------|---------|---------|
| `run_cycle()` | 周期任务 / 手动 | 自动扫 triggers | FIX（2a） |
| `evolve_skill(name)` | `/skill evolve` 命令 | 手动 | FIX |
| `capture_skill(pattern, name)` | `/skill capture` 命令 | 手动 | CAPTURED |

### 3.2. 调用时机

| 阶段 | 谁调 | 说明 |
|------|------|------|
| 周期 | `run_cycle` | 扫所有 trigger，逐个跑闭环 |
| 手动 FIX | `/skill evolve` | 绕过 should_trigger，直接构造上下文 |
| 手动 CAPTURED | `/skill capture` | 走 CaptureTrigger.manual_capture |
| 上线后监控 | `GitRatchet.check_and_rollback` | 独立周期调，不在闭环内 |

## 4. 内部流程（闭环七步）

`EvolutionManager._run_evolution(ctx)` 是核心，按顺序执行：

### 4.1. 第 1 步：focus（聚焦）

```
ctx = focuser.focus(ctx, store)
    ├─ ctx.failure_evidence 空（CAPTURED）→ 原样返回
    ├─ _read_judgment_notes（D-L3-20：读 L3 的 SkillJudgment 历史）
    ├─ llm None → _degrade_focus（全量摘要，默认 IMPLEMENTATION）
    ├─ llm 非 None → _llm_diagnose（IVE 5 问）
    └─ implementation 累计达阈值 → 升级 FUNDAMENTAL
```

产出：增强的 `EvolutionContext`（`failure_class` + `fix_direction`）。

### 4.2. 第 2 步：mutate（变异）

```
candidate, diff = mutator.mutate(ctx, llm)
    ├─ FIX      → _mutate_fix：
    │     ├─ 读原文件 → 切 frontmatter/body
    │     ├─ _llm_edit_body（单维度 + budget 指令）
    │     ├─ _enforce_budget（超 max_changed_lines 截断）
    │     └─ 保留 frontmatter → 写 staging
    └─ CAPTURED → _mutate_capture：
          ├─ _llm_generate_skill（必须有 llm）
          ├─ 校验 name（[a-z0-9-]+）
          └─ 写 staging
```

产出：`candidate`（`is_active=False`）+ `diff`。

### 4.3. 第 3 步：eval（评估）

```
eval_ctx = EvalContext(baseline, candidate, metrics_baseline)
eval_result = eval_bridge.evaluate(eval_ctx)
    ├─ L3 关闭 → ProgrammaticEvalBridge.evaluate
    │     └─ ResponseContractChecker.check → EvalResult
    └─ L3 启用 → RegistryEvalBridge.evaluate
          └─ ResponseContractChecker.check → EvalResult（异常 fail-closed）
```

产出：`EvalResult`（score / hard_failures / evidence / recommendation）。

### 4.4. 第 4 步：gate（门控）

```
decision = gate.decide(candidate, baseline, eval_result)
    └─ ScoreDeltaGate：
          ├─ hard_failures 非空 → reject
          ├─ baseline None（CAPTURED）→ score>0 ? accept : reject
          └─ FIX/DERIVED → score > baseline_score + min_delta ? accept : reject
```

产出：`GateDecision`（recommendation / reason / new_version_id）。

### 4.5. 第 5 步：promote（晋升）

```
if decision.recommendation in ("accept", "accept_new_best"):
    parent_id = baseline.skill_id if baseline else ""
    created_id = store.create_version(parent_id, candidate, candidate.lineage.origin)
```

产出：`created_id`（新版本 skill_id）或 None。

### 4.6. 第 6 步：record（记录）

```
rec = EvolutionRecord(
    evolution_id, skill_name, evolution_type, trigger,
    baseline_id, candidate_id, failure_focus, mutation_diff,
    eval_score, gate_decision, created_version_id, timestamp,
)
store.record_evolution(rec)
```

**注意**：无论 accept / reject 都记录（可审计）。

### 4.7. 第 7 步：journal（事件）

```
_emit_journal(ctx, decision, rec)
    ├─ CAPTURED                → "skill.captured"
    ├─ accept / accept_new_best → "skill.evolve"
    └─ 其他                    → "skill.evolve_rejected"
```

## 5. anti-loop 机制

evolution 有三处 anti-loop，防止无限循环：

### 5.1. Trigger 层（MetricMonitorTrigger）

```
min_selections：total_selections < min → 不触发
cooldown_turns：selections - last_evolve_selections < cooldown → 不触发
mark_evolved(name, selections)：进化完成后更新锚点
```

### 5.2. Focuser 层（IVEFocuser）

```
implementation 累计 >= impl_fail_threshold → 升级 FUNDAMENTAL
FUNDAMENTAL → 重置 implementation 计数
```

### 5.3. 回滚层（GitRatchet）

```
total_selections < min_selections → 不评判（新版本需积累数据）
```

## 6. 回滚机制（GitRatchet）

它不是闭环的一环，而是**上线后独立监控**：

```
check_and_rollback(store, current)
    ├─ D-L3-16：runtime_tracker.degraded_skills()（软信号）
    ├─ anti-loop：selections < min → None
    ├─ effective_rate >= threshold → None（健康）
    ├─ 找回滚目标：
    │     a. 优先 lineage.parent_skill_ids
    │     b. 兜底 generation 最低
    └─ store.rollback(target.skill_id)
```

**只切指针不删行**：旧 node 仍在 version DAG（类比 git revert）。

## 7. 数据回流

| 步骤 | 写入方法 | 目标 |
|------|---------|------|
| promote（accept） | `store.create_version` | 新版本进 version DAG |
| record | `store.record_evolution` | `skill_evolutions` 表 |
| rollback | `store.rollback` | 切 `is_active` 指针 |
| eval（L3） | `store.save_judgment` / `save_task_score` / `save_eval_run` | eval 三表 |
| focus（读） | `store.get_judgments` / `get_metrics` | 读 |
| gate（读） | 从 `EvalResult` | — |

**闭环**：

```
eval 写 judgments → evolution focus 读 judgments
evolution 写 create_version → 新版本 → eval 再评 → 循环
```

## 8. 异常与降级

| 组件 | 触发 | 行为 |
|------|------|------|
| `MetricMonitorTrigger` | LLM 确认异常 | 返 False（保守不触发） |
| `IVEFocuser` | LLM 异常 / JSON 缺失 | 返 `IMPLEMENTATION`（不轻易杀 skill） |
| `LLMMutator` | FIX LLM 失败 | 返原 body（不变异） |
| `LLMMutator` | CAPTURED 无 LLM | `raise ValueError` |
| `ProgrammaticEvalBridge` | 委托 checker | 无特殊降级 |
| `RegistryEvalBridge` | registry 空 / 异常 | **fail-closed** 返 reject |
| `ScoreDeltaGate` | — | 无异常分支（纯计算） |
| `GitRatchet` | runtime_tracker 异常 | silent skip |
| `EvolutionManager` | `get_metrics` / `create_version` / `record_evolution` / journal 异常 | silent pass |
| `EvolutionManager` | 手动入口无记录 | `raise RuntimeError` |

**原则**：

- 自动闭环：所有异常 silent，不阻断。
- 手动入口：无记录时抛错（让用户知道）。
- 门控：fail-closed（宁可错拒）。

        for ctx in contexts:
            _run_evolution(ctx)              ← 闭环七步
        trigger.mark_evolved(name, selections)

② 手动 FIX（evolve_skill）
    store.get_active → EvolutionContext(METRIC, FIX) → _run_evolution

③ 手动 CAPTURED（capture_skill）
    CaptureTrigger.manual_capture → EvolutionContext(CAPTURE, CAPTURED) → _run_evolution

④ 上线后监控（GitRatchet）
    check_and_rollback → store.rollback（退化时）
```


| 层面 | 内容 |
|------|------|
| **初始化** | bootstrap 构造 6 类组件（trigger / focuser / mutator / eval_bridge / gate / ratchet）→ 打包 `EvolutionManager` → `set_evolution_manager` 回注。 |
| **调用点** | 自动 `run_cycle`（周期扫 triggers）；手动 `evolve_skill` / `capture_skill`；上线后 `GitRatchet.check_and_rollback`。 |
| **内部流程** | 闭环七步：focus → mutate → eval → gate → promote → record → journal。 |
| **anti-loop** | 三处：trigger（min_selections + cooldown）、focuser（impl 累计升级）、ratchet（selections 门槛）。 |
| **回滚** | 独立监控，只切指针不删行。 |
| **降级** | 自动 silent；手动抛错；门控 fail-closed。 |

**evolution 的本质**：它是 skill 闭环的发动机——消费 L1 计数器 + L3 评分，诊断失败、变异出新版本、门控把关、晋升写入 version DAG，退化时回滚。它与 eval 一起构成"评估 → 进化 → 新版本 → 再评估"的完整循环。

## 10. 与 eval 之间的联系

### 10.1. 概述

evolution（L2）与 eval（L3）是**上下游 + 双向反哺**的关系：

- **eval → evolution**：eval 产出的评分与建议，是 evolution 决策的输入。
- **evolution → eval**：evolution 产出的新版本，是 eval 下一轮评估的对象。

两者通过 **EvalBridge Protocol** 解耦——evolution 不 import eval 的实现，只认接口。

### 10.2. 三条数据通道（eval → evolution）

```
① EvalResult（响应层 → 门控）
    eval: RegistryEvalBridge.evaluate(ctx) → EvalResult
        ↓
    evolution: ScoreDeltaGate.decide(candidate, baseline, eval_result)
        ↓
    决定 accept / reject

② SkillJudgment（执行层 → 聚焦）
    eval: SkillJudgmentAnalyzer._persist → store.save_judgment
        ↓
    evolution: IVEFocuser._read_judgment_notes → store.get_judgments
        ↓
    作为 failure_evidence 补充，增强 fix_direction

③ EvolutionSuggestion（执行层 → 触发）
    eval: SkillJudgmentAnalyzer._llm_analyze → EvolutionSuggestion
        ↓
    evolution: L2 trigger（补充信号，供 FIX / DERIVED / CAPTURED 判断）
        ↓
    影响下一轮触发
```

**注意**：`EvolutionSuggestion` 是 eval 的副产物——`SkillJudgmentAnalyzer` 一次 LLM 调用同时产 `SkillJudgment` + `EvolutionSuggestion`（D-L3-21）。

### 10.3. 两条数据通道（evolution → eval）

```
① create_version（晋升 → 新评估对象）
    evolution: store.create_version(...) → 新版本进 version DAG
        ↓
    eval: 下一轮 ResponseContractChecker.check(candidate, baseline)
          以新版本为 candidate / baseline
        ↓
    形成"评估 → 进化 → 再评估"闭环

② record_outcome（执行层回流 L1 计数器）
    eval: SkillJudgmentAnalyzer._persist → store.record_outcome
        ↓
    L1: skill_records 的 4 计数器更新
        ↓
    evolution: MetricMonitorTrigger 读这些计数器做诊断
        ↓
    影响下一轮 FIX 触发
```

**注意**：`record_outcome` 严格说是 eval 写 L1、evolution 读 L1——不直接交互，但通过 L1 计数器形成间接反哺。

### 10.4. 关键接口点

| 接口 | 位置 | 方向 | 作用 |
|------|------|------|------|
| `EvalBridge Protocol` | `evolution/protocols.py` | evolution 定义，eval 实现 | 解耦点：evolution 只认接口 |
| `ProgrammaticEvalBridge` | `evolution/eval/programmatic_bridge.py` | L2 自带 | L3 关闭时的 floor |
| `RegistryEvalBridge` | `eval/registry.py` | L3 实现 | L3 启用时替换 |
| `EvalResult` / `EvalContext` | `evolution/types.py` | 共享 | 门控与评估的共同语言 |
| `EvolutionSuggestion` | `eval/types.py` | eval 产 | 喂 L2 trigger |
| `SkillJudgment` | `eval/types.py` | eval 产 | 供 focuser 读 |

**要点**：

- **接口定义在 evolution 侧**（`EvalBridge Protocol`），实现可在 evolution（floor）或 eval（L3）。
- **数据契约共享**：`EvalResult` / `EvalContext` / `EvalEvidence` 定义在 `evolution/types.py`，eval 侧 import 使用——依赖方向是 **eval → evolution/types**，不是反向。

### 10.5. 调用时序（一次完整循环）

```
① after_agent（eval 执行层）
    SkillJudgmentAnalyzer.analyze_execution
        ├─ store.save_judgment         → skill_eval_judgments
        ├─ store.record_outcome        → L1 4 计数器
        └─ EvolutionSuggestion         → L2 trigger（下一轮）

② 周期（evolution 触发层）
    MetricMonitorTrigger.should_trigger
        ├─ 读 L1 计数器（上一步更新过的）
        └─ 产 EvolutionContext（FIX）

③ 进化闭环（evolution）
    _run_evolution(ctx)
        ├─ focus（读 eval 的 SkillJudgment 历史）
        ├─ mutate → candidate
        ├─ eval（EvalBridge.evaluate）→ EvalResult       ← 调 eval
        ├─ gate（ScoreDeltaGate 用 EvalResult 决策）
        ├─ create_version（accept 时）→ 新版本            ← 给 eval 下轮
        └─ record_evolution

④ 下一轮 after_agent（eval 执行层）
    SkillJudgmentAnalyzer 评新版本
        └─ ……回到 ①
```

### 10.6. 层级边界（谁不做什么）

| 层 | 做什么 | 不做什么 |
|----|--------|---------|
| eval（L3） | 评估、评分、产建议 | 不决策晋升、不执行进化 |
| evolution（L2） | 触发、聚焦、变异、门控、晋升、回滚 | 不做评估逻辑、不写 L1 计数器（除 rollback / create_version） |

**边界要点**：

- **eval 不碰 version DAG**：`create_version` 只在 evolution 的 `_run_evolution` 里调。
- **evolution 不碰评估实现**：只通过 `EvalBridge` Protocol 调 `evaluate`。
- **两者共享数据契约**（`EvalResult` / `EvalContext`），但**不共享实现**。

### 10.7. 总结

```
eval ──EvalResult───────────► evolution 门控（accept / reject）
eval ──SkillJudgment────────► evolution 聚焦（failure_evidence）
eval ──EvolutionSuggestion──► evolution 触发（补充信号）

evolution ──create_version──► eval 下一轮评估对象
evolution ──（经 L1 计数器）─► eval 下一轮诊断依据
```

**联系的本质**：eval 是"**评估者**"，evolution 是"**行动者**"。eval 告诉 evolution"这个 skill 表现如何、该修什么"；evolution 据此变异出新版本，再交给 eval 评判。两者通过 `EvalBridge Protocol` 解耦、通过共享数据契约通信、通过 L1 计数器形成间接反哺，共同构成"评估 → 进化 → 再评估"的完整闭环。
