
## 1. triggers 是什么

triggers 是 evolution 闭环的**第一环**——负责回答"**什么时候、对哪个 skill、发起哪类进化**"。它只产 `EvolutionContext`，不负责后续的聚焦 / 变异 / 评估 / 门控。

两个实现：

| 文件 | 类 | 类型 | 触发方式 |
|------|----|------|---------|
| `capture_trigger.py` | `CaptureTrigger` | CAPTURED（新技能沉淀） | 手动 |
| `metric_monitor.py` | `MetricMonitorTrigger` | FIX（修现有技能） | 周期扫描 |

## 2. 怎么被调用（谁调它）

### 2.1. 唯一调用方：`EvolutionManager`

`EvolutionManager` 持有 `triggers: list[Any]`（构造时注入），在两条路径调用它们：

```
① 自动路径：run_cycle()
    for trigger in self._triggers:
        contexts = trigger.should_trigger(self._store)   ← 调 should_trigger
        for ctx in contexts:
            _run_evolution(ctx)
            if hasattr(trigger, "mark_evolved"):
                trigger.mark_evolved(name, selections)   ← 调 mark_evolved

② 手动路径：capture_skill()
    for t in self._triggers:
        if isinstance(t, CaptureTrigger):
            ctx = t.manual_capture(pattern, suggested_name)  ← 调 manual_capture
            break
    if ctx is None:
        ctx = 自造 EvolutionContext(...)                     ← 兜底
    _run_evolution(ctx)
```

### 2.2. 谁构造 trigger

bootstrap 装配：构造 `MetricMonitorTrigger(...)` / `CaptureTrigger()` → 放进 `triggers` 列表 → 传给 `EvolutionManager` → `set_evolution_manager` 回注 SkillManager。

## 3. 怎么触发（内部逻辑）

### 3.1. `MetricMonitorTrigger.should_trigger(store)` —— 自动 FIX

对每个 active skill 依次做 6 步过滤：

```
for rec in store.list_active():

  ① enabled 检查
      not rec.enabled → 跳过

  ② anti-loop：min_selections
      rec.total_selections < min_selections → 跳过
      （新进化 skill selections=0，不会被立刻再触发）

  ③ anti-loop：cooldown
      rec.total_selections - last_evolve_selections[name] < cooldown_turns → 跳过
      （数据驱动：需新增 N 次 selections 才重评，不是时间驱动）

  ④ Phase 1 规则诊断 _diagnose_skill_health(rec)
      fallback_rate > 0.4                        → ("FIX", "常选不用")
      applied_rate > 0.4 且 completion_rate < 0.35 → ("FIX", "用了没完成")
      effective_rate < 0.55 且 applied_rate > 0.25 → ("DERIVED", "中等效果")
      否则                                        → (None, "")
      None → 跳过
      非 "FIX" → 跳过（DERIVED 留 2b）

  ⑤ Phase 2 LLM 确认（llm 非 None 时）
      _llm_confirm_evolution(rec, direction)
      返 False → 跳过
      （llm=None 时此步跳过，退化为纯规则）

  ⑥ 收集
      EvolutionContext(trigger="METRIC", evolution_type="FIX",
                       target_skill=rec, fix_direction=direction)
```

**设计要点**：

- **两阶段筛选**：Phase 1 规则阈值宽松（避免漏报）；Phase 2 LLM 确认（过滤误报）。
- **LLM 失败保守**：`_llm_confirm_evolution` 异常返 False → 不触发（宁可漏，不可误）。
- **只产 FIX**：DERIVED 在 2a 被显式过滤；CAPTURED 不由它产。

### 3.2. `CaptureTrigger.should_trigger(store)` —— 自动 CAPTURED

```
return []   ← 2a 无自动信号
```

2a 的 CAPTURED 完全靠手动。2b 计划补 post-execution 模式识别 + agent 自评。

### 3.3. `CaptureTrigger.manual_capture(pattern, suggested_name)` —— 手动 CAPTURED

```
return EvolutionContext(
    trigger="CAPTURE",
    evolution_type="CAPTURED",
    target_skill=None,          ← 无基线（新技能）
    capture_pattern=pattern,
    suggested_name=suggested_name,
)
```

被 `EvolutionManager.capture_skill` 调用（`/skill capture` 命令触发）。

## 4. 产出什么

两种 trigger 都产 `EvolutionContext`，但字段不同：

| 字段 | FIX（metric_monitor） | CAPTURED（capture_trigger） |
|------|----------------------|----------------------------|
| `trigger` | `"METRIC"` | `"CAPTURE"` |
| `evolution_type` | `"FIX"` | `"CAPTURED"` |
| `target_skill` | 现有 skill（有值） | **None**（新技能） |
| `fix_direction` | Phase 1 诊断文本 | — |
| `capture_pattern` | — | 模式描述 |
| `suggested_name` | — | 建议 name |

**关键区别**：`target_skill` 是否为 None，是 FIX/DERIVED 与 CAPTURED 的分水岭；`_run_evolution` 会据此构造 `EvalContext`（无 baseline 时用 candidate 占位）。

## 5. anti-loop 怎么工作

anti-loop 是 triggers 层的核心保护，**只存在于 `MetricMonitorTrigger`**：

```
状态：self._last_evolve_selections: dict[str, int]
      （skill_name → 上次进化时的 total_selections）

检查（should_trigger 内）：
  ② total_selections < min_selections        → 不触发
  ③ total_selections - last < cooldown_turns → 不触发

更新（manager 调）：
  mark_evolved(name, selections)
      └─ self._last_evolve_selections[name] = selections
```

**为什么是数据驱动而非时间驱动**：

- 用"新增 selections 数"衡量冷却，而不是 wall-clock 时间。
- 意义：没有新数据时，skill 不会被反复触发进化；有新数据积累后才重评。

**为什么需要 anti-loop**：

- 新进化出的 skill 起初 `selections=0`，若不设门槛会立刻被"低有效"再次触发 → 无限循环。
- 进化后 skill 需要重新积累 selections，才能公平评估。

## 6. 完整调用链（一张图）

```
bootstrap
    ├─ MetricMonitorTrigger(threshold, min_selections, cooldown_turns, llm)
    ├─ CaptureTrigger()
    └─ EvolutionManager(store, triggers=[...], focuser, mutator, eval_bridge, gate, llm, journal)
          └─ SkillManager.set_evolution_manager(...)

        ═══════════ 运行期 ═══════════

① 自动（run_cycle）
    for trigger in triggers:
        contexts = trigger.should_trigger(store)
            ├─ MetricMonitorTrigger：扫 active → 6 步过滤 → 产 FIX 上下文
            └─ CaptureTrigger：返空（2a）
        for ctx in contexts:
            _run_evolution(ctx)              ← focus → mutate → eval → gate → record
        trigger.mark_evolved(name, selections)  ← anti-loop 锚点更新

② 手动 FIX（/skill evolve）
    evolve_skill(skill_name)
        └─ 绕过 should_trigger，直接构造 EvolutionContext(METRIC, FIX)

③ 手动 CAPTURED（/skill capture）
    capture_skill(pattern, name)
        └─ 找 CaptureTrigger → manual_capture(...) → EvolutionContext(CAPTURE, CAPTURED)
```

## 7. 总结

| 问题 | 答案 |
|------|------|
| trigger 是什么？ | evolution 闭环的第一环：决定"何时、对谁、发哪类进化"。 |
| 谁调用它？ | `EvolutionManager`：自动路径走 `should_trigger`；手动路径走 `manual_capture` / 直接构造。 |
| 怎么触发？ | MetricMonitor：扫 active → anti-loop 两步 → Phase 1 规则 → Phase 2 LLM 确认 → 产 FIX。Capture：2a 只手动。 |
| 产出什么？ | `EvolutionContext`（FIX 带 target_skill；CAPTURED 的 target_skill=None）。 |
| anti-loop？ | `min_selections` + `cooldown_turns`（数据驱动），由 `mark_evolved` 更新锚点。 |
| 2a 的能力边界？ | MetricMonitor 只产 FIX；Capture 只手动；DERIVED 和自动 CAPTURED 留 2b。 |

**trigger 层的本质**：它是"**信号采集 + 门槛过滤**"层——从 metrics / 手动输入中筛出"值得进化"的信号，产上下文交给 `EvolutionManager`，后续的聚焦/变异/评估/门控都不归它管。
