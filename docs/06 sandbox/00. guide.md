# Sandbox 层学习路线规划


## 阶段零：先明确你要回答的 5 个问题（贯穿全程）

在开始读代码前，先把这 5 个问题写在纸上，每读完一个阶段就尝试回答一次：

1. `bash` 工具调用时，命令到底在哪执行？
2. Agent 视角的虚拟路径（如 `/mnt/poirot/user-data/workspace/a.txt`）映射到宿主机哪里？
3. 危险命令怎么被拦截？规则是什么？
4. 沙箱什么时候启动、什么时候销毁？
5. 多个 Agent 共享同一个沙箱吗？

**这 5 个问题答不上来，就还没真正看懂。**

补充两个"语义级"问题，贯穿阶段一和阶段五：

6. **Guard 拦截时，返回什么？** —— `LocalSecurityGuard` 抛 `SandboxPermissionError`；`DockerPathGuard` 同样抛异常。**不是返回 bool。**
7. **Translator 是可逆的吗？** —— `LocalPathTranslator` 的 `mask_output` 是 `translate_path` 的逆操作（可逆）；`DockerPathTranslator` 正向直传、另提供 `reverse_translate`（不严格对称）。

### 1.1 门面 + 5 个契约

| 顺序 | 文件 | 你要弄明白的事 |
|---|---|---|
| 4 | `sandbox.py` | 门面持有 runtime / translator / guard；**编排顺序** `guard.validate → translator.translate → runtime.execute → translator.mask` |
| 5 | `contracts/sandbox_provider.py` | provider 的 `create / destroy / is_ready / get` 语义 |
| 6 | `contracts/sandbox_backend.py` | backend 的 `execute / read_file / write_file / list_dir` 语义 |
| 7 | `contracts/sandbox_runtime.py` | runtime 的 `start / stop / health` 语义 |
| 8 | `contracts/security_guard.py` | guard 的 `validate_command / validate_path` **抛异常**（不是返回 bool） |
| 9 | `contracts/path_translator.py` | translator 的 `translate_path / translate_command / mask_output` 语义，**是否可逆** |

**阶段产出 B**：画一张契约依赖图。

```
Sandbox (门面，具体类非 ABC)
  ├── holds: SandboxRuntime       ← 裸执行（跑命令 / 读写文件）
  ├── holds: PathTranslator       ← 路径翻译（虚拟 ↔ 真实）+ 输出脱敏
  └── holds: SecurityGuard        ← 安全校验（validate only）

编排顺序：guard.validate → translator.translate → runtime.execute → translator.mask

Provider.create() → (Docker) Backend.create
Runtime 由 Provider 创建时构造，被 Sandbox 持有
```

**阶段产出 C**：一句话写清——**guard 抛异常**；**Local translator 可逆，Docker translator 正向直传 + 反向 `reverse_translate`**。

**关键问题**：
- 为什么 provider 和 backend 要分开？
- 为什么 runtime 不直接由 backend 管？

> 提示：provider 负责"造"，backend 负责"用"，runtime 负责"活着"。三者生命周期不同。

## 阶段二：本地路径先跑通（最容易理解）

**目标**：先看最简单的实现，把整条链路走通。**不要一上来就看 Docker**。

| 顺序 | 文件 | 重点 |
|---|---|---|
| 1 | `local/local_sandbox_provider.py` | 组合 LocalRuntime + LocalPathTranslator + AuditGuard(LocalSecurityGuard)；LRU 缓存 + 确定性 ID |
| 2 | `guards/local_security_guard.py` | 命令黑名单 + 路径白名单 + shlex fail-closed；**唯一防线**所以规则最严 |
| 3 | `guards/permissive_guard.py` | 和 local_security_guard 的区别？全放行；什么时候用（容器已隔离） |
| 4 | `guards/audit_guard.py` | 组合层：三档分级（block/warn/pass）+ 审计；包装底层 guard |
| 5 | `translators/identity_translator.py` | 恒等直传（三个方法都不转换） |
| 6 | `translators/local_path_translator.py` | 双向翻译 + 防穿越 + 缓存；`mask_output` 是逆操作 |
| 7 | `runtimes/local_runtime.py` | `subprocess` 裸执行 + 文件操作；异常统一为 `SandboxError` 子类 |
| 8 | `utils/file_operation_lock.py` | 进程内锁（`WeakValueDictionary`）；**已知限制 S11：不跨进程** |
| 9 | `utils/sandbox_id.py` | sandbox_id 格式校验（8 位小写十六进制，防路径穿越） |

**阶段产出**：口头描述"本地沙箱一次 `bash` 调用的完整链路"，标出每一步经过哪个文件。

**关键问题**：
- 本地沙箱到底"沙箱"在哪？如果只是路径检查 + 命令检查，它算隔离吗？
- `file_operation_lock` 锁的是文件级还是操作级？为什么本地单进程锁在 Docker 场景不够用？

> 提示：本地沙箱本质是"软约束"，不是真隔离。这是理解 Docker 价值的铺垫。

## 阶段三：Docker 路径（真正的隔离）

**目标**：理解容器化的完整生命周期，以及它和本地的差异。

| 顺序 | 文件 | 重点 |
|---|---|---|
| 1 | `docker/docker_sandbox_provider.py` | 三层缓存 + warm_pool + idle_checker；release 移入 warm_pool |
| 2 | `docker/local_container_backend.py` | 容器 CRUD（create/discover/is_alive/destroy/list_running）；**executor 在其之下** |
| 3 | `docker/executor.py` | `DockerExecutor` 抽象；Local / WSL 两实现；`translate_path` 是 daemon 视角翻译 |
| 4 | `docker/readiness.py` | 就绪轮询（sync + async）；60s 超时 |
| 5 | `docker/cross_process_lock.py` | 跨进程文件锁（fcntl / msvcrt）；与阶段二 `file_operation_lock` 对比 |
| 6 | `runtimes/docker_runtime.py` | **经 HTTP 调容器内 AIO 服务**；不在容器里，是"遥控器" |
| 7 | `guards/docker_path_guard.py` | 写入必须落挂载区；读不限制（容器隔离兜底） |
| 8 | `translators/docker_path_translator.py` | 正向直传 + 反向 `reverse_translate` |
| 9 | `docker/remote_container_backend.py` | 和 local 版本差异（K8s 模式，仅 sandbox_url） |

**阶段产出 A**：画出「容器从启动到执行命令到销毁」的时序图。

**阶段产出 B**：填对照表：

| 维度 | local | docker |
|---|---|---|
| Provider 创建什么 | Sandbox 实例（组合三件套） | 容器 + 三层缓存 |
| Backend 类型 | **无** | `LocalContainerBackend` / `RemoteContainerBackend` |
| Backend 下层 | — | `DockerExecutor`（CLI 落点抽象） |
| Runtime | `LocalRuntime`（宿主 subprocess） | `DockerRuntime`（HTTP 调容器） |
| Translator | `LocalPathTranslator`（双向） | `DockerPathTranslator`（正向直传 + 反向映射） |
| Guard | `AuditGuard(LocalSecurityGuard)` | `AuditGuard(DockerPathGuard)` |
| 锁 | `file_operation_lock`（进程内） | `cross_process_lock`（跨进程） |
| 隔离级别 | 软约束 | 硬隔离 |
| 生命周期 | runtime 几乎 no-op | provider 管三层缓存 + warm_pool + idle |

**关键问题**：
- 多个 Agent 共享同一个容器吗？锁的粒度是什么？
- `remote_container_backend` 和 `local_container_backend` 的契约是同一条吗？
- **`DockerExecutor` 和 `DockerRuntime` 是什么关系？**（答案：无直接关系，分属两条独立链路）
- **`DockerRuntime` 在容器里执行吗？**（答案：不在，它是宿主进程里的"遥控器"）

## 阶段四：接入 Agent（真正跑起来）

**目标**：理解 sandbox 怎么和 Agent 的工具体系、中间件、状态流对接。

| 顺序 | 文件 | 重点 |
|---|---|---|
| 1 | `integration/config.py` | 配置结构；哪些字段决定走本地还是 Docker |
| 2 | `integration/context.py` | ContextVar 里存了什么 |
| 3 | `integration/tools.py` | `make_sandbox_tools` 产出 6 个工具（`allow_host_bash=False` 时 5 个）；闭包捕获 provider |
| 4 | `integration/bootstrap_sandbox.py` | `register_sandbox_shutdown` 的 atexit 清理 |
| 5 | `agents/middlewares/sandbox_middleware.py` | `before_agent` 启动沙箱、写 state；`wrap_tool_call` 拦截 |
| 6 | `app/services/stream_service.py` | `state["sandbox"]["sandbox_id"]` → `sandbox_update` 事件 |
| 7 | `multiagent/sandbox_binder.py` | 多 Agent 场景下沙箱绑定/共享 |

**阶段产出**：从 `bootstrap_runtime` 画到 `stream_service` 发 `sandbox_update`，形成完整调用链。

把阶段四拆成三块：

| 子任务 | 职责 | 涉及文件 |
|---|---|---|
| **① 装配** | 选 provider、构造 Sandbox、生成工具、注册清理 | `integration/config.py`、`tools.py`、`bootstrap_sandbox.py` |
| **② 接入** | 工具进 Agent tools 节点、middleware 拦截、state 写出 | `middlewares/sandbox_middleware.py`、`app/services/stream_service.py` |
| **③ 协作** | 多 Agent 场景下沙箱绑定/共享 | `multiagent/sandbox_binder.py` |

**关键问题**：
- 只有配了 provider 才加载 sandbox 工具吗？不配会怎样？
- `SandboxMiddleware` 和 `make_sandbox_tools` 谁先谁后？各自职责？
- 子 Agent 的沙箱是继承 Leader 的还是独立的？

## 阶段五：验证闭环

### 3 个验证实验

| 实验 | 做法 | 验证什么 |
|---|---|---|
| **实验 1：本地路径** | 配本地 provider，跑 `bash "echo hi > /mnt/poirot/user-data/t.txt"`，看文件落在宿主机哪 | 路径映射 + 本地执行 |
| **实验 2：Docker 路径** | 配 Docker provider，跑同样命令，`docker exec` 进容器看文件 | 容器隔离 + 路径映射 |
| **实验 3a：命令拦截** | 跑 `rm -rf /`，看哪个 guard 拦截、抛什么异常 | `validate_command` 语义 + `LocalSecurityGuard` |
| **实验 3b：路径拦截** | 写 `/etc/passwd`，看哪个 guard 拦截、抛什么异常 | `validate_path` 语义 + `DockerPathGuard` |

> 实验 3 拆 a/b：命令检查和路径检查走**不同分支**，报错来源不同。

### 1 个追踪练习

在 `SandboxMiddleware.wrap_tool_call` 和 `runtime.exec_command` 各打一个 log，跑一次 `bash`，看日志顺序是否和时序图一致。**不一致的地方就是你理解错的地方。**

### 2 个语义确认

- Guard 拦截抛 `SandboxPermissionError`（不是返回 bool）——跟日志对照验证。
- Translator 可逆性：`LocalPathTranslator` 的 `translate_path` / `mask_output` 往返转换验证；`DockerPathTranslator` 的 `reverse_translate` 前缀校验验证。

## 三个避坑提醒

1. **别跳过 contracts 直接看 Docker**：五个契约是理解一切的钥匙，Docker 只是其中一种实现。
2. **别把本地沙箱当隔离**：本地只是"软约束"，理解这点才能理解 Docker 存在的意义。
3. **别忘了 `multiagent/sandbox_binder.py`**：这是 sandbox 和多 Agent 的桥，最容易漏，但生产中很关键。
