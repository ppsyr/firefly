## 1. 按契约逐个对应

| 契约                | 实现文件                                                                                                                | 说明                    |
| ----------------- | ------------------------------------------------------------------------------------------------------------------- | --------------------- |
| `SandboxRuntime`  | `runtimes/local_runtime.py`、`runtimes/docker_runtime.py`                                                            | 两个 runtime 适配器        |
| `SecurityGuard`   | `guards/local_security_guard.py`、`guards/docker_path_guard.py`、`guards/audit_guard.py`、`guards/permissive_guard.py` | 四个 guard              |
| `PathTranslator`  | `translators/identity_translator.py`、`translators/local_path_translator.py`、`translators/docker_path_translator.py` | 三个 translator         |
| `SandboxProvider` | `local/local_sandbox_provider.py`、`docker/docker_sandbox_provider.py`                                               | 两个 provider（ABC，显式继承） |
| `SandboxBackend`  | `docker/local_container_backend.py`、`docker/remote_container_backend.py`、`local/` 下对应实现                             | 平台实现（ABC，显式继承）        |

注意：`SandboxProvider` 和 `SandboxBackend` 是 **ABC**（`class XxxProvider(ABC)`），会有显式继承；另外三个是 **Protocol**，不写继承，靠"长得像"满足契约。

### 2.7. 三个关键"持有/调用"关系

1. **`SandboxProvider` 持有 `SandboxBackend`**
   `local/local_sandbox_provider.py` 内部持有 Backend，`acquire` 时调 `backend.create` / `backend.discover`。

2. **`Sandbox` 持有三组件**
   `sandbox/sandbox.py` 的 `__init__` 注入 `Runtime` + `Translator` + `Guard`，编排时按序调用。

3. **工具层通过 Provider 拿 Sandbox，不直接 new**
   `middlewares/sandbox_middleware.py` 调 `provider.get()` 拿到 `Sandbox`，再调它的方法。**两步分离**是关键。


## 3. 为什么 Provider 和 Backend 要分开？

这两个契约看起来都在管沙箱，很容易觉得"合并成一个不就行了"。分开的核心原因是：**它们管的是两个不同生命周期的东西，变化频率和解耦需求完全不同。**

### 3.1 两者管的根本不是同一件事

| | `SandboxProvider` | `SandboxBackend` |
|---|---|---|
| 管的对象 | **进程内对象**（`Sandbox` 实例、缓存、warm_pool） | **基础设施实例**（容器、Pod、进程） |
| 生命周期 | 一次 Agent 会话内 | 跨进程、跨会话、跨重启 |
| 典型操作 | `acquire` / `get` / `release` / `reset` | `create` / `destroy` / `is_alive` / `discover` |
| 关注点 | 复用、缓存、快 | 存在性、健康、可恢复 |
| 状态存在哪 | 内存（dict / pool） | 基础设施（Docker daemon / K8s API） |

一句话：**Provider 管"对象在不在手里"，Backend 管"实例在不在世界上"。**

### 3.2 分开才能各自独立变化

这是最实际的理由。看两种变化：

**变化 A：换基础设施（Docker → K8s）**
- 只需要换 `SandboxBackend` 实现（`LocalContainerBackend` → `RemoteContainerBackend`）
- `SandboxProvider` 完全不用改——它只管"拿/放"，不关心底层是 Docker 还是 K8s

**变化 B：换复用策略（每次新建 → warm_pool 复用）**
- 只需要改 `SandboxProvider`（`release` 从销毁改成移入 warm_pool）
- `SandboxBackend` 完全不用改——它只管"造/杀"，不关心造完怎么复用

如果合并成一个类，**任何一边变化都会牵动另一边**，测试也得一起重写。

### 3.3 分开才能解决"跨进程恢复"

这是分开的硬需求。

`SandboxProvider` 的状态是**进程内内存**——进程一重启，缓存全没了。
但 `SandboxBackend` 的状态在**基础设施上**——容器还在跑，`docker ps` 还能看到。

所以恢复流程是：

```
进程重启 → Provider 缓存为空
    ↓
Provider.acquire(thread_id)
    ↓ 缓存未命中
Backend.discover(sandbox_id)     ← 按确定性 ID 去基础设施找
    ↓ 找到了，且 is_alive=True
复用已有容器，回填 Provider 缓存
```

**如果 Provider 和 Backend 合并，这个"内存丢了但实例还在"的场景就无法表达。**

### 3.4 分开才能支持"一个 Provider 多个 Backend"

`DockerSandboxProvider` 可以同时持有：
- `LocalContainerBackend`（本地 Docker）
- `RemoteContainerBackend`（远程 K8s）

Provider 根据配置/负载决定用哪个 Backend。如果合并，就得写两个 Provider，复用逻辑（缓存、warm_pool）要复制两份。

### 3.5 总结

> **Provider 管"进程内对象生命周期"，Backend 管"基础设施实例生命周期"。**
> 分开是因为：**两者的生命周期、状态存储位置、变化原因都不同**——分开才能各自独立演化，并支撑"进程重启后恢复沙箱"这个硬需求。

## 4. 为什么 Runtime 不直接由 Backend 管？

先看这两者如果合并会怎样：

```
假设：Backend 既管基础设施，又管执行
    class DockerBackend:
        def create(self): ...           # 基础设施
        def exec_command(self): ...     # 执行
        def read_file(self): ...        # 执行
```

看起来也行。但项目里偏偏把它们拆成 `SandboxBackend`（基础设施）和 `SandboxRuntime`（执行）。原因有四层。

### 4.1 粒度不同：Backend 是"实例级"，Runtime 是"操作级"

| | `SandboxBackend` | `SandboxRuntime` |
|---|---|---|
| 调用频率 | 低（会话开始/结束、健康检查） | 高（每次工具调用） |
| 操作粒度 | 实例（create / destroy） | 单次操作（exec / read / write） |
| 是否进 Agent 循环 | 不进 | 每次都进 |

一次 Agent 会话里：
- `Backend.create` 可能只调 **1 次**
- `Runtime.exec_command` 可能调 **几十上百次**

**把高频的执行操作挂到低频的生命周期对象上，职责会糊在一起。**

### 4.2 生命周期不同：Backend 跨会话，Runtime 随 Sandbox

```
Backend 的生命周期：跨进程、跨会话（容器可能活几小时）
Runtime 的生命周期：随 Sandbox 实例（一次会话内）
```

`Sandbox` 注入的是 `Runtime`，不是 `Backend`。因为：

- `Sandbox` 需要的是"执行能力"，不是"造容器能力"
- 造容器是 `Provider` 在 `acquire` 时通过 `Backend` 做的
- 造完之后，`Sandbox` 只需要一个 `Runtime` 来执行

**如果 Runtime 由 Backend 管，那 `Sandbox` 就得持有 `Backend`，等于把"造"和"用"耦合回一起。**

### 4.3 抽象层级不同：Backend 绑基础设施，Runtime 可以中立

看两个契约的"中立性"：

**`SandboxBackend`**：
```python
def create(self, thread_id, sandbox_id, extra_mounts, user_id) -> SandboxInfo
```
参数里有 `extra_mounts`（挂载）、`user_id`（权限）——**这些都是容器/平台特有的概念**。

**`SandboxRuntime`**：
```python
def exec_command(self, command: str) -> str
def read_file(self, path: str) -> str
```
只有"命令"和"路径"——**这是所有执行环境都有的通用概念**。

注释里写得很清楚：

> "不限定容器类型——Docker / K8s / Firecracker microVM / WASM 都是'沙箱运行平台'。"

`SandboxRuntime` 比 `SandboxBackend` **更中立**：
- Backend 至少得是"能跑容器的平台"
- Runtime 可以是"任何能执行命令的东西"，包括 WASM、E2B 这种非容器环境

### 4.4 组合自由：Runtime 可以脱离 Backend 独立换

因为 `SandboxRuntime` 是 Protocol，且和 `SandboxBackend` 无依赖，所以可以：

```
同一个 Docker 容器（Backend 固定）
    ├─ 用 DockerRuntime（docker exec）
    └─ 用 E2BRuntime（通过 E2B SDK 连进去）
```

或者：

```
同一套 Runtime 实现
    ├─ 配 LocalContainerBackend（本地 Docker）
    └─ 配 RemoteContainerBackend（远程 K8s）
```

**如果 Runtime 由 Backend 管，这种"同一实例、不同执行方式"的组合就做不到了。**

### 4.5 和编排层的关系：Runtime 是"三组件之一"，Backend 不是

回顾之前的图：

```
Sandbox 编排：validate → translate → execute → mask
                          ↑
                    Runtime 在这一步

Backend 不在编排链里，只在"拿沙箱"阶段被 Provider 调
```

`SandboxRuntime` 是**编排链的一环**，和 `Guard` / `Translator` 平级。
`SandboxBackend` 是**生命周期链的一环**，和 `Provider` 平级。

**如果 Runtime 由 Backend 管，等于把编排链的一环塞进了生命周期链，两条链就交叉了。**

### 4.6 总结

> **Backend 管"实例怎么造、怎么活、怎么恢复"，Runtime 管"一次操作怎么执行"。**
> 不合并是因为：**调用频率不同（低 vs 高）、生命周期不同（跨会话 vs 随 Sandbox）、抽象层级不同（绑基础设施 vs 中立）、在架构里的位置不同（生命周期链 vs 编排链）。**
