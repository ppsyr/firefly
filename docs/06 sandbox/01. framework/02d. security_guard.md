---

name: SecurityGuard — 安全检查契约（白名单 + 路径穿越拒绝）。

description: 

【整体职责】
定义沙箱操作前的安全校验接口：路径是否在白名单内、命令是否包含越界路径。
方案 C 三组件之一，只做 validate（拦截），不做脱敏（脱敏归 PathTranslator）。

【内容摘要】
- SecurityGuard          : Protocol（runtime_checkable），安全检查契约。
- validate_path          : 验证路径在白名单内 + 拒路径穿越；write=True 检查写权限。
- validate_command       : 验证 bash 命令里的路径在白名单内。

【职责边界】
- 只负责：validate（拦截非法路径 / 命令）。
- 不负责：脱敏（mask_output 归 PathTranslator，Grill #4 决策）、路径转换（Translator）、
  执行（Runtime）、编排（Sandbox）。
- 不持有状态：Protocol 只定义接口；规则由具体 guard 持有。

## 0. 结构树

### 0.1. 静态结构树

```
security_guard.py — SecurityGuard 安全检查契约（白名单 + 路径穿越拒绝）
│
├─ SecurityGuard(Protocol)                    ← 安全检查契约；@runtime_checkable
│   │                                            方案 C 三组件之一：只做 validate，不做 mask
│   │                                            Local 严格 / Docker·E2B 宽松
│   │
│   ├─ validate_path(path, *, write=False)    ← 验证路径在白名单内 + 拒路径穿越
│   │   -> None                                  write=True 检查写权限
│   │   └─ 抛 SandboxPermissionError（路径穿越）
│   │      / SandboxFileError（越界）
│   │
│   └─ validate_command(command) -> None      ← 验证 bash 命令里的路径在白名单内
│       └─ 抛 SandboxPermissionError（命令含越界路径）
│
│   （无 mask_output 方法）                   ← 脱敏归 PathTranslator（Grill #4 决策）
```

### 0.2. 运行时调用树

```
① 装配期（一次性）
bootstrap_sandbox.py
    └─ 选一个 SecurityGuard 实现（LocalSecurityGuard / DockerPathGuard /
          AuditGuard / PermissiveGuard）
          └─ 注入到 Sandbox 构造（Sandbox(runtime, translator, guard)）
    （此时不调任何方法，只是持有 guard）

        ═══════════ 进入 Agent 循环 ═══════════

② 工具调用 —— 经 Sandbox 编排，Guard 是第一步
Sandbox.execute_command(cmd)
    ├─ guard.validate_command(cmd)              ← 本协议方法：拦截危险命令
    │     ├─ 通过 → 继续
    │     └─ 抛 SandboxPermissionError → 中断
    ├─ translator.translate_command(cmd)
    ├─ runtime.exec_command(translated)
    └─ translator.mask_output(output)           ← 脱敏不归 Guard（Grill #4）

Sandbox.read_file(path)
    ├─ guard.validate_path(path, write=False)   ← 本协议方法：只读校验
    │     ├─ 通过 → 继续
    │     └─ 抛 SandboxPermissionError / SandboxFileError → 中断
    ├─ translator.translate_path(path)
    ├─ runtime.read_file(physical)
    └─ translator.mask_output(content)

Sandbox.write_file(path, content, append)
    ├─ guard.validate_path(path, write=True)    ← 本协议方法：写权限校验
    │     ├─ 通过 → 继续
    │     └─ 抛 SandboxPermissionError / SandboxFileError → 中断
    ├─ translator.translate_path(path)
    └─ runtime.write_file(physical, content, append)

Sandbox.list_dir / glob / grep / download_file / update_file
    └─ ... → guard.validate_path(...) 先行   ← 全部走本协议

③ 异常路径 —— 统一异常类型
guard.validate_* 抛 SandboxPermissionError / SandboxFileError
    └─ 工具层 catch SandboxError
          └─ ToolCallMiddleware 统一转 error ToolMessage

（其余 hook 与本模块无关）
```

## 1. 补充

**`SecurityGuard` 是 sandbox 层的"安全校验契约"——它只回答"这个操作允不允许"，不回答"结果怎么脱敏"。这是方案 C 三组件里边界最清晰、也最容易被误解的一个。**

几点补充：

- **"只做 validate，不做 mask"是本协议的核心分界**：注释里两次强调（正文 + INVARIANT）"无 mask_output 方法"。脱敏（宿主路径 → 虚拟路径）归 `PathTranslator`，因为脱敏本质是路径翻译的逆操作，不是安全校验。这是 Grill #4 的明确决策，读代码时别把 mask 往 Guard 里加。

- **Protocol + `@runtime_checkable` 而非 ABC**：和 `SandboxRuntime` 一样用 Protocol。这意味着四个实现（`LocalSecurityGuard` / `DockerPathGuard` / `AuditGuard` / `PermissiveGuard`）不需要显式继承，只要"长得像"就满足契约。

- **两个方法的校验对象不同**：
  - `validate_path` 校验"单个路径"（read_file / write_file / list_dir 等直接传 path）。
  - `validate_command` 校验"命令字符串里的路径"（bash 命令可能内嵌多个路径，需要解析）。
  - 这也是为什么 `execute_command` 走 `validate_command`，而文件操作走 `validate_path`。

- **`write` 是关键字参数而非位置参数**：`validate_path(path, *, write=False)`，强制调用方显式写 `write=True`。这是为了防止"默认只读、误传成写"或反之——写权限是敏感操作，必须显式声明。

- **异常体系是本协议的一部分**：`SandboxPermissionError`（权限/穿越）和 `SandboxFileError`（越界）是硬约定。工具层只需要 `catch SandboxError`，不用关心是哪种 guard 抛的。

- **"严格 vs 宽松"是设计而非妥协**：Local 严格白名单（因为直接跑在宿主机），Docker/E2B 宽松（因为容器内已隔离）。同一个契约，不同实现，严格度不同——这是契约抽象的价值。

- **四个实现的严格度梯度**（对应你之前看的 `guards/` 目录）：
  | 实现 | 严格度 | 场景 |
  |---|---|---|
  | `LocalSecurityGuard` | 严格 | 本机进程，必须拦 |
  | `DockerPathGuard` | 中 | 容器内，限制在 `/workspace` |
  | `AuditGuard` | 只记录 | 观察模式，不拒绝 |
  | `PermissiveGuard` | 宽松 | 全通过，测试用 |
