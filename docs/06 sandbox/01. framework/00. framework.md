# 一次 bash 命令全流程


```
工具层 bash("cat /workspace/a.txt")
    ↓
Middleware: provider.acquire() → 拿 sandbox_id
            provider.get()     → 拿 Sandbox 实例
    ↓
Sandbox.execute_command(cmd)
    ├─ ① guard.validate_command(cmd)       ← 拦截

    └─ ④ translator.mask_output(output)    ← 物理→虚拟（脱敏）
    ↓
返回结果给工具层
```

## 0. 先看全貌：三个阶段

```
┌─────────────────────────────────────────────────────────────┐
│ 阶段一：拿沙箱（不在 Sandbox 编排内）                            │
│   provider.acquire() → sandbox_id                           │
│   provider.get(sandbox_id) → Sandbox 实例                    │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ 阶段二：Sandbox 编排（四步，本文重点）                           │
│   validate → translate → execute → mask                     │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ 阶段三：返回结果                                               │
│   给工具层，异常由 ToolCallMiddleware 统一处理                  │
└─────────────────────────────────────────────────────────────┘
```

**关键认知**：阶段一和阶段二是**分开**的。`Sandbox` 不持有 `Provider`，它只是被 Provider"造出来"后，由工具层拿着用。下面重点讲阶段二。

---

## 1. 阶段一：拿沙箱（为什么先讲这个）

```
Middleware: provider.acquire(thread_id) → sandbox_id
            provider.get(sandbox_id)     → Sandbox 实例
```

**做什么**：
- `acquire`：确保"这个 thread 有一个可用的沙箱"，返回 `sandbox_id`
- `get`：按 `sandbox_id` 从 Provider 的**内存缓存**里取出 `Sandbox` 实例

**为什么分两步**：
- `acquire` 可能阻塞（Docker 要启容器），而且有副作用（创建/复用）
- `get` 是纯内存查找，事件循环安全，高频调用

**没有它会怎样**：工具层每次调用都要自己 `new` 沙箱，无法复用、无法跨进程恢复。

**拿到的 `Sandbox` 长什么样**：

```python
Sandbox(
    id="sb-abc123",
    runtime=LocalRuntime(...),        # 或 DockerRuntime
    translator=LocalPathTranslator(...),
    guard=LocalSecurityGuard(...),
)
```

**注意**：此时 `Sandbox` 已经持有了三个组件，但**还没执行任何操作**。

---

## 2. 阶段二：Sandbox 编排的四步

工具层调用：

```python
sandbox.execute_command("cat /workspace/a.txt")
```

`Sandbox.execute_command` 的内部实现（对应你之前看的 `sandbox.py`）：

```python
def execute_command(self, command: str) -> str:
    self._guard.validate_command(command)              # ① 拦截
    translated = self._translator.translate_command(command)  # ② 翻译
    output = self._runtime.exec_command(translated)    # ③ 执行
    return self._translator.mask_output(output)        # ④ 脱敏
```

**四步是硬约束**，顺序不能变。下面逐步拆。

---

### ① `guard.validate_command(cmd)` —— 拦截

**做什么**：在执行前，检查命令是否安全（是否包含越界路径、危险操作）。

**为什么需要**：
- `bash` 可以 `rm -rf /`、`cat /etc/passwd`、`curl` 外网
- 必须在**执行前**拦截，执行后就晚了

**怎么实现**（以 `LocalSecurityGuard` 为例，伪代码）：

```python
class LocalSecurityGuard:
    ALLOWED_ROOTS = ["/workspace", "/tmp"]
    DENIED_COMMANDS = ["rm -rf /", "mkfs", "dd if=", ":(){:|:&};:"]

    def validate_command(self, command: str) -> None:
        # 1. 命令黑名单检查
        for denied in self.DENIED_COMMANDS:
            if denied in command:
                raise SandboxPermissionError(f"命令被拒绝: {denied}")

        # 2. 提取命令里的路径，检查是否在白名单内
        for path in self._extract_paths(command):
            if not self._is_allowed(path):
                raise SandboxPermissionError(f"路径越界: {path}")

    def _extract_paths(self, command: str) -> list[str]:
        # 用正则/分词从命令里抽出路径
        ...
```

**关键点**：
- **只 validate，不 mask**：Guard 不碰输出（Grill #4 决策）
- **抛异常而非返回布尔**：`SandboxPermissionError` 会被工具层统一 catch
- **检查对象是"命令字符串"**：不是单个路径，需要解析命令

**没有它会怎样**：Agent 一句 `rm -rf /` 就能删掉宿主机。

**四个实现的差异**：

| 实现 | 严格度 | 检查方式 |
|---|---|---|
| `LocalSecurityGuard` | 严格 | 黑名单 + 路径白名单 |
| `DockerPathGuard` | 中 | 路径必须在 `/workspace` 下 |
| `AuditGuard` | 只记录 | 不拒绝，只打日志 |
| `PermissiveGuard` | 宽松 | 全通过 |

---

### ② `translator.translate_command(cmd)` —— 虚拟路径 → 物理路径

**做什么**：把命令字符串里的**虚拟路径**翻译成**物理路径**，让 `runtime` 能在真实文件系统上执行。

**为什么需要**：
- Agent 视角的路径是虚拟的（`/workspace/a.txt`）
- 实际执行时，这个路径在宿主机上可能是 `/home/user/.poirot/sandboxes/sb-abc123/workspace/a.txt`
- 不翻译，`runtime` 就找不到文件

**怎么实现**（以 `LocalPathTranslator` 为例，伪代码）：

```python
class LocalPathTranslator:
    def __init__(self, mappings: list[PathMapping]):
        # mappings 按 container_path 长度降序排（最长前缀优先）
        self._mappings = sorted(mappings, key=lambda m: -len(m.container_path))

    def translate_command(self, command: str) -> str:
        # 把命令里的虚拟路径逐个替换为物理路径
        for mapping in self._mappings:
            command = command.replace(
                mapping.container_path,
                mapping.local_path,
            )
        return command
```

**举例**：

```
虚拟路径映射：
    /workspace  →  /home/user/.poirot/sandboxes/sb-abc123/workspace

输入：  cat /workspace/a.txt
输出：  cat /home/user/.poirot/sandboxes/sb-abc123/workspace/a.txt
```

**关键点**：
- **`translate_path` vs `translate_command`**：
  - `translate_path` 翻译单个路径（`read_file` 用）
  - `translate_command` 翻译命令字符串里的路径（`execute_command` 用）
- **Identity 实现直传**：如果虚拟路径 == 物理路径（比如容器内），直接返回原样
- **幂等**：同一虚拟路径多次翻译结果一致（INVARIANT）

**没有它会怎样**：`cat /workspace/a.txt` 会在宿主机的 `/workspace/a.txt` 找文件——找不到（或找到错误的文件）。

**三个实现的差异**：

| 实现 | 翻译方式 | 场景 |
|---|---|---|
| `IdentityTranslator` | 直传，路径不变 | 容器内路径 == 虚拟路径 |
| `LocalPathTranslator` | 前缀映射 | 本地，虚拟 → 宿主物理 |
| `DockerPathTranslator` | `/workspace` ↔ 宿主目录 | Docker |

---

### ③ `runtime.exec_command(translated)` —— 裸执行

**做什么**：真正执行命令，返回输出。**不关心路径、不关心安全**。

**为什么需要**：
- 这是唯一"真正干活"的一步
- 前面的 validate / translate 都是为它做准备
- 后面的 mask 是它的收尾

**怎么实现**（以 `LocalRuntime` 为例）：

```python
class LocalRuntime:
    def exec_command(self, command: str) -> str:
        try:
            result = subprocess.run(
                command,
                shell=True,
                capture_output=True,
                text=True,
                timeout=30,
            )
            return result.stdout + result.stderr
        except subprocess.CalledProcessError as e:
            raise SandboxCommandError(str(e)) from e
        except subprocess.TimeoutExpired as e:
            raise SandboxRuntimeError("命令超时") from e
```

**Docker 实现**：

```python
class DockerRuntime:
    def exec_command(self, command: str) -> str:
        result = subprocess.run(
            ["docker", "exec", self._container_id, "bash", "-c", command],
            capture_output=True, text=True,
        )
        return result.stdout + result.stderr
```

**关键点**：
- **只管执行，不管路径**：路径已经在上一步翻译好了
- **异常包装**：把 `subprocess.CalledProcessError` 包装成 `SandboxCommandError`
- **路径契约由调用方保证**：注释说"Local 路径已翻译为物理路径；Docker/E2B 直传虚拟路径"
  - 这意味着：**同一个 `exec_command`，在不同 runtime 下收到的 path 语义可能不同**

**没有它会怎样**：命令根本没执行。

---

### ④ `translator.mask_output(output)` —— 物理路径 → 虚拟路径（脱敏）

**做什么**：把执行结果里的**物理路径**翻译回**虚拟路径**，让 Agent 看到的路径是它熟悉的。

**为什么需要**：
- `runtime` 执行后，输出里可能包含物理路径
- 比如 `cat` 报错：`cat: /home/user/.poirot/sandboxes/sb-abc123/workspace/a.txt: No such file`
- 直接给 Agent 看，会：
  - 泄露宿主机内部路径（安全隐患）
  - 让 Agent 困惑（它只认识 `/workspace/a.txt`）

**怎么实现**（`LocalPathTranslator` 的逆操作）：

```python
class LocalPathTranslator:
    def mask_output(self, output: str) -> str:
        # 把物理路径替换回虚拟路径
        for mapping in self._mappings:
            output = output.replace(
                mapping.local_path,
                mapping.container_path,
            )
        return output
```

**举例**：

```
输入：  cat: /home/user/.poirot/sandboxes/sb-abc123/workspace/a.txt: No such file
输出：  cat: /workspace/a.txt: No such file
```

**关键点**：
- **`mask_output` 是 `translate_path` 的逆操作**（INVARIANT）
- **归 Translator，不归 Guard**（Grill #4 决策）：脱敏本质是路径翻译，不是安全校验
- **只有会"回显路径"的方法才 mask**：
  - `execute_command` / `read_file` / `list_dir` / `glob` / `grep` → 需要 mask
  - `write_file` / `update_file` / `download_file` → 不需要（写不回显，字节流无路径）

**没有它会怎样**：Agent 看到宿主机内部路径，可能"学会"用物理路径绕过后续检查。

## 3. 四步的依赖关系图

```
                    ┌─────────────────────────────┐
                    │  sandbox.execute_command()  │
                    └──────────────┬──────────────┘
                                   │
        ┌──────────────────────────┼──────────────────────────┐
        │                          │                          │
        ▼                          ▼                          ▼
   ┌─────────┐              ┌──────────┐              ┌──────────┐
   │ ① Guard │              │ ② Trans  │              │ ③ Runtime│
   │ validate│              │ translate│              │ execute  │
   └────┬────┘              └────┬─────┘              └────┬─────┘
        │                        │                         │
        │ 拦不住就抛异常           │ 改命令里的路径            │ 真正执行
        │                        │                         │
        └────────────────────────┴─────────────────────────┘
                                   │
                                   ▼
                            ┌──────────────┐
                            │ ④ Trans mask │
                            │ 脱敏输出      │
                            └──────┬───────┘
                                   │
                                   ▼
                            返回给工具层
```

**顺序为什么不能变**：

| 如果顺序错了 | 后果 |
|---|---|
| 先 translate 再 validate | Guard 检查的是物理路径，白名单规则失效 |
| 先 execute 再 validate | 已经执行了，拦截没意义 |
| 先 mask 再 execute | 输出还没产生，mask 无从下手 |
| 不 mask 直接返回 | 泄露物理路径 |

## 4. 每一步"没有它会怎样"总表

| 步骤 | 组件 | 没有它的后果 |
|---|---|---|
| ① validate | `SecurityGuard` | `rm -rf /` 直接执行，宿主机被删 |
| ② translate | `PathTranslator` | `cat /workspace/a.txt` 找不到文件 |
| ③ execute | `SandboxRuntime` | 命令根本没执行 |
| ④ mask | `PathTranslator` | 泄露宿主机路径，Agent 困惑 |

## 5. 完整实例：从输入到输出

**输入**：Agent 调 `bash("cat /workspace/a.txt")`

**假设环境**：
- `LocalSecurityGuard`（白名单 `/workspace`）
- `LocalPathTranslator`（`/workspace` → `/home/user/.poirot/sb-abc123/workspace`）
- `LocalRuntime`（subprocess）

**执行过程**：

```
① validate_command("cat /workspace/a.txt")
   ├─ 提取路径：["/workspace/a.txt"]
   ├─ 检查是否在白名单：/workspace ✓
   └─ 通过

② translate_command("cat /workspace/a.txt")
   └─ 替换 /workspace → /home/user/.poirot/sb-abc123/workspace
   └─ 得到 "cat /home/user/.poirot/sb-abc123/workspace/a.txt"

③ exec_command("cat /home/user/.poirot/sb-abc123/workspace/a.txt")
   └─ subprocess.run(...)
   └─ 假设文件不存在，输出：
      "cat: /home/user/.poirot/sb-abc123/workspace/a.txt: No such file"

④ mask_output("cat: /home/user/.poirot/sb-abc123/workspace/a.txt: No such file")
   └─ 替换 /home/user/.poirot/sb-abc123/workspace → /workspace
   └─ 得到 "cat: /workspace/a.txt: No such file"

返回给工具层："cat: /workspace/a.txt: No such file"
```

**Agent 看到的结果**：路径是虚拟的 `/workspace/a.txt`——它熟悉、且不泄露内部结构。

---

## 6. 三个"容易理解错"的点

### 点一：`mask_output` 不是"安全措施"，是"翻译逆操作"

很多人以为 mask 是为了安全。**不完全是。** 它主要是为了让 Agent 看到的路径**一致**——执行前看到 `/workspace/a.txt`，执行后也应该看到 `/workspace/a.txt`。安全是附带效果。

### 点二：`runtime` 收到的路径语义，取决于调用方

`SandboxRuntime` 的注释说：

> "所有方法遵守调用方传入的路径契约（Local 路径已翻译为物理路径；Docker/E2B 直传虚拟路径）"

这意味着：**同一个 `runtime.exec_command`，在 Local 下收到物理路径，在 Docker 下可能收到虚拟路径**。runtime 不负责判断，调用方（`Sandbox` + `Translator`）负责。

### 点三：四步不是"四个独立操作"，是"一条流水线"

`validate → translate → execute → mask` 是一条**有数据依赖的流水线**：

```
cmd → [validate] → cmd → [translate] → translated_cmd
    → [execute] → output → [mask] → masked_output
```

每一步的输入是上一步的输出（或同一个对象的不同形态）。**不是四个平行操作**。

---

## 7. 总结

> `execute_command` 的四步，是 sandbox 层的"最小完整流水线"：
> **① Guard 拦下不该做的 → ② Translator 把路径换成真实可执行的 → ③ Runtime 真正执行 → ④ Translator 把结果换成 Agent 能看懂的。**
> 四步顺序固定，每一步都有明确的"没有它会怎样"，这就是 sandbox 编排的全部精髓。
