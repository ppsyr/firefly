---

name: PathTranslator — 虚拟路径 ↔ 物理路径翻译契约。

description: 

【整体职责】
定义 sandbox 操作中「虚拟路径 ↔ 物理路径」的双向翻译接口，以及输出脱敏。
方案 C 三组件之一：Sandbox 编排时，execute 前调 translate_command，
read/write 前调 translate_path，执行后调 mask_output。

【内容摘要】
- PathTranslator         : Protocol（runtime_checkable），路径翻译契约。
- translate_path         : 虚拟路径 → 物理路径。
- translate_command      : bash 命令里的虚拟路径 → 物理路径。
- mask_output            : 输出里的物理路径 → 虚拟路径（脱敏）。

【职责边界】
- 只负责：路径双向翻译 + 输出脱敏（翻译的逆操作）。
- 不负责：安全校验（Guard）、执行（Runtime）、编排（Sandbox）。
- 不持有状态：Protocol 只定义接口；映射规则由具体实现持有。

## 0. 结构树

### 0.1. 静态结构树

```
path_translator.py — PathTranslator 虚拟路径 ↔ 物理路径翻译契约
│
├─ PathTranslator(Protocol)                   ← 路径翻译契约；@runtime_checkable
│   │                                            方案 C 三组件之一：管翻译 + 脱敏
│   │                                            Local 用 PathMapping；Docker/E2B 用 Identity
│   │
│   ├─ translate_path(virtual_path) -> str    ← 虚拟路径 → 物理路径
│   │   └─ Identity 实现直传
│   │
│   ├─ translate_command(command) -> str      ← bash 命令里的虚拟路径 → 物理路径
│   │   └─ Identity 实现直传
│   │
│   └─ mask_output(output) -> str             ← 输出里的物理路径 → 虚拟路径（脱敏）
│       └─ Identity 实现直传
│
│   （脱敏归本协议，不归 SecurityGuard —— Grill #4 决策）
```

### 0.2. 运行时调用树

```
① 装配期（一次性）
bootstrap_sandbox.py
    └─ 选一个 PathTranslator 实现（IdentityTranslator / LocalPathTranslator /
          DockerPathTranslator）
          └─ 注入到 Sandbox 构造（Sandbox(runtime, translator, guard)）
    （此时不调任何方法，只是持有 translator）

        ═══════════ 进入 Agent 循环 ═══════════

② 工具调用 —— 经 Sandbox 编排，Translator 出现在"执行前"和"执行后"两步
Sandbox.execute_command(cmd)
    ├─ guard.validate_command(cmd)              ← 前置：安全校验
    ├─ translator.translate_command(cmd)        ← 本协议方法：命令内路径改写
    ├─ runtime.exec_command(translated)         ← 裸执行
    └─ translator.mask_output(output)           ← 本协议方法：输出脱敏
                                                   物理路径 → 虚拟路径

Sandbox.read_file(path)
    ├─ guard.validate_path(path, write=False)
    ├─ translator.translate_path(path)          ← 本协议方法：虚拟 → 物理
    ├─ runtime.read_file(physical)
    └─ translator.mask_output(content)          ← 本协议方法：物理 → 虚拟（脱敏）

Sandbox.write_file(path, content, append)
    ├─ guard.validate_path(path, write=True)
    ├─ translator.translate_path(path)          ← 本协议方法：虚拟 → 物理
    └─ runtime.write_file(physical, content, append)   ← 无 mask（写不回显）

Sandbox.list_dir / glob
    ├─ translator.translate_path(path)
    ├─ runtime.list_dir / glob(...)
    └─ 逐项 translator.mask_output(...)         ← 本协议方法

Sandbox.grep
    ├─ translator.translate_path(path)
    ├─ runtime.grep(...)
    └─ 对每个 GrepMatch 用 replace() 逐字段 mask_output(path/line)   ← 本协议方法

Sandbox.download_file / update_file
    ├─ translator.translate_path(path)
    └─ runtime.download_file / update_file(...) ← 无 mask（字节流）

③ 例外路径 —— get_host_path（不经 Guard，只用 Translator）
Sandbox.get_host_path(virtual_path)
    ├─ hasattr(translator, "reverse_translate") ?
    │     ├─ 有 → reverse_translate(virtual_path)     ← DockerPathTranslator 专属
    │     └─ 无 → translate_path(virtual_path)        ← Identity / LocalTranslator
    └─ 返回宿主路径（供外部复制/注册 artifact 用）

（其余 hook 与本模块无关）
```

## 1. 补充

**`PathTranslator` 是 sandbox 层的"路径翻译 + 脱敏契约"——它一头把 Agent 视角的虚拟路径译成物理路径（执行前），另一头把物理路径译回虚拟路径（执行后脱敏）。这是方案 C 三组件里唯一"双向"的组件。**

几点补充：

- **三个方法构成一对"往返"**：
  - `translate_path`（虚拟 → 物理）：执行前用。
  - `translate_command`（命令内路径改写）：执行前用。
  - `mask_output`（物理 → 虚拟）：执行后用，是 `translate_path` 的逆操作。
  - 前两个是"进去"，第三个是"出来"。这构成了路径翻译的闭环。

- **`mask_output` 归本协议是 Grill #4 的关键决策**：注释两次强调"SecurityGuard 不碰输出"。原因是脱敏本质是"路径翻译的逆操作"，和"安全校验"是两件事。把 mask 放这里，Guard 就能保持"只 validate"的纯粹性。

- **`translate_command` 是三个方法里最特殊的**：它不是翻译单个路径，而是翻译"命令字符串里的路径"。因为 `bash "cat /workspace/a.txt"` 里的路径是内嵌在命令里的，需要解析出来逐个翻译。Identity 实现直传，Local/Docker 实现需要做字符串层面的路径替换。

- **"Identity 直传"是理解的钥匙**：`IdentityTranslator` 三个方法都原样返回。这说明在某些沙箱（比如 Docker 内路径 == 虚拟路径）下，翻译是恒等操作。**先看懂 Identity，再看 Local/Docker 的差异**，会容易很多。

- **`translate_path` 幂等是硬约束**：同一虚拟路径多次翻译结果一致。这条 INVARIANT 保证了"翻译可以在任意环节重复调用而不出错"，是编排层能自由插入翻译步骤的前提。

- **`get_host_path` 是协议外的"扩展点"**：`Sandbox.get_host_path` 用 `hasattr(translator, "reverse_translate")` 判断——说明 `reverse_translate` 是 `DockerPathTranslator` 的**可选扩展方法**，不在本协议里。这是协议设计的一个留白：核心三方法必选，反向翻译可选。

- **和三个目录的对应关系**（对应你之前看的 `translators/` 目录）：
  | 实现 | 翻译方式 | 场景 |
  |---|---|---|
  | `IdentityTranslator` | 直传，路径不变 | 本地/容器内路径即虚拟路径 |
  | `LocalPathTranslator` | 前缀映射（PathMapping） | 本地，虚拟路径 ↔ 宿主物理路径 |
  | `DockerPathTranslator` | `/workspace` ↔ 宿主机目录 | Docker，含 `reverse_translate` |

- **和 `types.py` 的耦合点**：本协议本身不 import `types.py`，但 `LocalPathTranslator` 的实现会用到 `PathMapping` 和 `ResolvedPath`。所以 `types.py` 是"实现的依赖"，不是"契约的依赖"。
