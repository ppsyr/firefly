### 0.3. 运行时调用树

```
① 装配期
DockerSandboxProvider(path_mappings, sandbox_config, ...)
    ├─ 构造 LocalContainerBackend（内含 DockerExecutor）
    ├─ _reconcile_orphans()          ← list_running → adopt 进 warm_pool
    ├─ _start_idle_checker()         ← 启守护线程（60s 间隔）
    └─ _register_signal_handlers()   ← SIGTERM / SIGINT / SIGHUP

        ═══════════ 进入 Agent 循环 ═══════════

② 取或建沙箱 —— acquire(thread_id, user_id)
    ├─ per-thread lock
    └─ _acquire_internal（三层缓存）
          │
          ├─ Layer 1: _reuse_in_process
          │     └─ 命中 → is_alive 探活 → 返回 / 不健康 → _drop_unhealthy
          │
          ├─ Layer 1.5: _reclaim_warm
          │     └─ warm_pool 命中 → is_alive 探活 → 转 active
          │
          └─ Layer 2: _discover_or_create
                ├─ validate_sandbox_id
                ├─ cross_process_lock.open_lock_file / lock_file_exclusive
                ├─ _reuse_in_process（锁内复查）
                ├─ backend.discover → 命中 → _register
                └─ backend.create → readiness → _register
                      │
                      ├─ _enforce_replicas → _evict_oldest_warm
                      ├─ _start_container
                      │     └─ executor.run(["docker", "run", ...])
                      └─ wait_for_sandbox_ready(url, timeout=60)
                            └─ 失败 → backend.destroy + raise
                finally: unlock_file / close

③ 一次命令执行
Sandbox.execute_command(cmd)
    ├─ AuditGuard(DockerPathGuard).validate_command / validate_path
    ├─ DockerPathTranslator.translate_command（正向直传）
    ├─ DockerRuntime.exec_command(cmd)
    │     ├─ _lock 串行
    │     ├─ AioSandboxClient.shell.exec_command(...)  ← HTTP
    │     │     └─ 容器内 AIO 服务真正执行
    │     └─ ErrorObservation 签名 → fresh session 重试
    └─ DockerPathTranslator.mask_output（正向直传）

④ 释放 —— release(sandbox_id)
    ├─ 移出 active（_sandboxes / _sandbox_infos / _thread_sandboxes）
    ├─ sandbox.close() → DockerRuntime.close()（属性链挖 httpx.Client.close）
    └─ 转入 _warm_pool

⑤ idle_checker（后台，每 60s）
_idle_checker_loop → _cleanup_idle
    ├─ active 超 idle_timeout → 二次确认 → _destroy_active
    └─ warm 超 idle_timeout → backend.destroy

⑥ 进程退出
shutdown()
    ├─ 停 idle_checker 线程（join 5s）
    ├─ 逐个 _destroy_active
    │     ├─ 清内存状态
    │     ├─ sandbox.close()
    │     └─ backend.destroy(info)
    │           └─ S7 二次 discover 校验 → docker stop（--rm 自动移除）
    └─ 逐个 backend.destroy（warm）
```

### 0.4. 补充

**`docker/` 是 sandbox 层的 Docker 实现目录——它把"容器生命周期管理"和"远程执行"两套机制独立成层，比本地实现多出 provider 编排、backend CRUD、executor 落点抽象、readiness 轮询、cross_process_lock 五层。**

几点补充：

- **两条链路是本目录的核心结构**：
  - **链路 A（容器生命周期）**：`DockerSandboxProvider` → `LocalContainerBackend` → `DockerExecutor` → `docker CLI`。
  - **链路 B（容器使用）**：`Sandbox` → `DockerRuntime` → HTTP → 容器内 AIO 服务。
  - 两者**互不调用**，通过 `SandboxInfo.sandbox_url` 间接握手。

- **`DockerExecutor` 与 `DockerRuntime` 无直接关系**：名字都带 docker，但一个管"docker CLI 在哪跑"（链路 A 底层），一个管"怎么调容器内服务"（链路 B）。这是最容易混的点。

- **`DockerRuntime` 在宿主进程，不在容器里**：它是"遥控器"，发 HTTP 请求；真正执行命令的是容器内 AIO 服务。设计精髓是 `DockerRuntime` 与 `LocalRuntime` 实现同一套契约——换 runtime 就等于换执行环境。

- **三层缓存 + warm_pool 是 provider 的核心**：
  - Layer 1（in-process）—— 最快，命中即返回。
  - Layer 1.5（warm_pool）—— 容器已释放但仍在跑，可快速复活。
  - Layer 2（cross-process lock + discover/create）—— 最慢，跨进程保护。

- **`release` 的 Docker 语义**：移入 warm_pool（**不销毁**），容器继续运行——为下次 `acquire` 快速复用。这和本地 `release` 的 no-op 不同。

- **Docker 特有的三处安全 / 正确性修复**：
  - **S5**：`acquire_async` 用 `acquired` flag 防 cancel 误 release。
  - **S7**：`destroy` 前二次 `discover` 校验，避免误杀别线程新建的同 ID 容器。
  - **#1433**：`DockerRuntime._lock` 串行化，防并发破坏持久 shell session。

- **Docker 比本地简单的地方**：
  - **Guard**：容器隔离兜底，`DockerPathGuard` 只查"写入落挂载区"。
  - **Translator**：bind mount 对齐路径，正向直传，只剩反向 `reverse_translate`。

- **Docker 比本地复杂的地方**：
  - 新增容器生命周期管理（provider + backend + executor + readiness + lock）。
  - 新增远程执行（runtime 经 HTTP 调容器）。
  - 新增跨进程协调（cross_process_lock + 孤儿对账 + 确定性 ID）。

- **`docker/` 与 `runtimes/docker_runtime.py` 的目录差异**：`DockerRuntime` 放在 `runtimes/` 而非 `docker/`——因为它实现的是 `sandbox_runtime` 契约，和 `local_runtime.py` 并列；`docker/` 目录专放 Docker **特有**的基础设施（backend / executor / readiness / lock）。


## 1. Docker 总览

`docker/` 是 sandbox 层的 **Docker 实现目录**——提供容器化沙箱所需的全部组件。它比本地实现多出一整套"容器生命周期管理 + 远程执行"的层次，因为它要回答本地实现不存在的问题：**容器怎么造、在哪造、怎么调、怎么回收。**

核心特征：**复杂度被下沉**——安全隔离下沉到内核（namespace + cgroup），路径对齐下沉到 bind mount，所以 guard / translator 反而比本地简单。

## 3. 各组件定位

### 3.1 DockerSandboxProvider — 生命周期编排

**职责：三层缓存 + warm_pool + idle_checker + 孤儿对账 + 信号清理。**

- **三层缓存**：in-process → warm_pool → cross-process lock + discover/create。
- **release 语义**：移入 warm_pool（容器**保持运行**，不销毁）。
- **idle_checker**：60s 间隔，超 idle_timeout 销毁 active + warm。
- **孤儿对账**：启动时 `list_running` → adopt 进 warm_pool。
- **replicas 软上限**：仅 warm_pool 计入驱逐预算，active 不强制停。
- **S5 修复**：`acquire_async` 用 `acquired` flag 防 cancel 误 release。
- **S7 修复**：destroy 前二次 `discover` 校验，避免误杀别线程新建的同 ID 容器。
- **信号处理**：SIGTERM / SIGINT / SIGHUP → shutdown。

### 3.2 LocalContainerBackend — 容器基础设施 CRUD

**职责：用 docker / Apple Container CLI 管理容器的造 / 找 / 探 / 停。**

- **create 幂等**：已存在则复用；端口重试循环 10 次；名称冲突走 discover。
- **命名确定性**：`{prefix}-{sandbox_id}`——跨进程可发现。
- **bind mount**：`.poirot/sandbox/{sandbox_id}` → `/mnt/poirot/user-data`。
- **is_alive 三态**：True（运行）/ False（不存在）/ None（未知，不误杀）。
- **list_running batch**：2 次 subprocess（`docker ps` + `docker inspect *names`），非 N+1。
- **`--rm`**：容器停止自动移除，`destroy` 只 stop 不 rm，天然幂等。
- **平台分流**：macOS 优先 Apple Container，否则 Docker。
- **mount 格式化**：Docker 用 `--mount type=bind`（避免 Windows 盘符歧义）；Apple 用 `-v`。

### 3.3 DockerRuntime — 调容器内 AIO 服务

**职责：通过 `agent_sandbox` SDK 经 HTTP 调容器内 all-in-one-sandbox 服务。**

- **在宿主进程，不在容器里**——它是"遥控器"，真正执行的是容器内 AIO 服务。
- **`_lock` 串行化**：防并发破坏持久 shell session（#1433）。
- **ErrorObservation 重试**：检测 SDK bug 签名 → fresh session 重试一次（仿 deer-flow）。
- **`close` 属性链挖掘**：SDK 不暴露 close，逐层 getattr 找真实 `httpx.Client.close()`（#2872）。
- **路径不翻译**：容器内 AIO 直接认虚拟路径。

### 3.4 DockerExecutor — CLI 执行落点抽象

**职责：抽象"docker CLI 在哪里执行 + 宿主路径如何翻译成 daemon 视角"。**

- **两个实现**：
  - `LocalDockerExecutor` —— 直接 `subprocess.run`，同 OS。
  - `WslDockerExecutor` —— Windows 项目 + WSL2 daemon；加 `wsl -d <distro> --` 前缀；`D:\foo` → `/mnt/d/foo`。
- **契约**：`run(cmd, **kwargs)` + `translate_path(host_path)`。
- **被谁用**：`LocalContainerBackend`。

### 3.5 readiness — 就绪轮询

**职责：轮询 `{sandbox_url}/v1/sandbox`，200 视为就绪，超时返 False。**

- sync / async 双版本。
- 单次请求 5s；总超时 60s。
- HTTP 异常静默吞掉（未就绪 / 抖动都视为继续等）。
- async 版用 `loop.time()` 算 deadline，sleep 取 `min(poll_interval, remaining)`。

### 3.6 cross_process_lock — 跨进程文件锁

**职责：fcntl（Unix）/ msvcrt（Windows）实现跨进程互斥。**

- 仅 3 函数：`open_lock_file` / `lock_file_exclusive` / `unlock_file`。
- **无 context manager**——sync/async 统一用显式 open/lock/unlock/close。
- 同一文件对象贯穿全流程。
- Windows 需 `seek(0)` 后锁 1 字节（msvcrt 基于字节范围）。

### 3.7 DockerPathTranslator — 路径翻译

**职责：正向直传（容器内路径与虚拟路径对齐）+ 反向映射到 host。**

- **正向三个方法全部直传**：`translate_path` / `translate_command` / `mask_output`。
- **反向 `reverse_translate`**：虚拟 → 宿主机物理路径（artifact 提取用）。
- **前缀校验**：仅接受 `/mnt/poirot/user-data`（精确匹配或带 `/`）。

### 3.8 DockerPathGuard — 路径守卫

**职责：写入必须落挂载区。**

- `validate_path(write=True)`：写入必须落 `/mnt/poirot/user-data/`。
- `validate_command`：bash 重定向目标（绝对路径）必须落同前缀。
- **读不限制**——容器隔离兜底。
- **刻意不覆盖**：`cd` 后相对路径、`tee`、`2>&1`。

## 4. 组件关系图（两条独立链路）

```
DockerSandboxProvider（编排）
    │
    ├── 链路 A：容器生命周期 ──────────────────────────
    │     └─ LocalContainerBackend
    │           ├─ DockerExecutor（本机 / WSL）
    │           │     └─ subprocess.run("docker run/inspect/stop ...")
    │           ├─ readiness.wait_for_sandbox_ready（创建后等就绪）
    │           └─ cross_process_lock（discover/create 临界区保护）
    │
    └── 链路 B：容器使用 ──────────────────────────────
          └─ Sandbox（由 provider._make_sandbox 构造）
                ├─ DockerRuntime ──── HTTP ──► 容器内 AIO 服务
                ├─ DockerPathTranslator
                └─ AuditGuard(DockerPathGuard)

        两条链路通过 SandboxInfo.sandbox_url 间接握手：
        backend 创建容器产出 url，runtime 消费 url 建 HTTP client。
```

**关键区分**：
- `DockerExecutor` 管"**docker 命令在哪跑**"——链路 A 底层。
- `DockerRuntime` 管"**怎么调容器里的服务**"——链路 B 本身。
- **两者互不调用**，只共享"容器"这个目标。

## 5. Docker 沙箱的完整生命周期

```
① 创建阶段
provider._create_sandbox()
    ├─ _enforce_replicas()              ← 副本软上限
    ├─ backend.create(...)              ← LocalContainerBackend
    │     ├─ validate_sandbox_id
    │     ├─ discover（幂等检查）
    │     ├─ 端口 retry loop：
    │     │     └─ executor.run(["docker", "run", ...])
    │     └─ 返回 SandboxInfo(container_id, sandbox_url)
    ├─ readiness.wait_for_sandbox_ready(url, timeout=60)
    │     └─ 失败 → backend.destroy + raise
    └─ _register → _make_sandbox
          └─ DockerRuntime(url) + DockerPathTranslator + AuditGuard(DockerPathGuard)

② 使用阶段（每次工具调用）
Sandbox.execute_command(cmd)
    ├─ guard.validate_command / validate_path
    ├─ translator.translate_command（正向直传）
    ├─ runtime.exec_command(cmd)        ← HTTP 调容器内 AIO
    │     └─ 命令在容器内执行，文件写容器内（bind mount 穿透回宿主）
    └─ translator.mask_output（正向直传）

③ 释放阶段
provider.release(sandbox_id)
    ├─ 移出 active 缓存
    ├─ sandbox.close() → runtime.close()（关 httpx.Client）
    └─ 转入 warm_pool（容器继续运行）

④ 回收阶段（两条路径）
    A. 被复用：_reclaim_warm → 转回 active
    B. 被销毁：
        ├─ idle_checker 超时 → _destroy_active
        └─ shutdown（进程退出）→ _destroy_active

⑤ 销毁阶段
provider._destroy_active(sandbox_id)
    ├─ 清内存状态
    ├─ sandbox.close() → runtime.close()
    └─ backend.destroy(info)            ← docker stop（--rm 自动移除）
          └─ S7 二次 discover 校验，避免误杀新容器
```

## 6. Docker vs Local 的核心差异

| 维度 | Local | Docker |
|---|---|---|
| **隔离级别** | 软约束（靠 guard 拦） | 硬隔离（namespace + cgroup） |
| **安全边界** | Guard（软件层） | 容器（内核层） |
| **Guard 角色** | 唯一防线 → 复杂 | 补漏层 → 简单 |
| **路径翻译** | 双向都复杂（PathMapping） | 正向直传 + 反向一处 |
| **命令执行** | `subprocess.run` 在宿主 | HTTP 调容器内 AIO |
| **基础设施层** | 无 | `LocalContainerBackend` |
| **CLI 执行层** | 无 | `DockerExecutor` |
| **锁** | `file_operation_lock`（进程内） | `cross_process_lock`（跨进程） |
| **生命周期** | runtime 几乎 no-op | provider 管三层缓存 + warm_pool + idle |
| **就绪检查** | 无 | `readiness` 轮询 |
| **信号处理** | 仅 atexit | atexit + SIGTERM/SIGINT/SIGHUP |

**核心规律**：Docker 把"隔离"和"路径对齐"两件事从软件层下沉到内核 / 挂载层，所以 guard / translator 变简单；但同时**新增了"容器生命周期"和"远程执行"两整套机制**，所以 provider / runtime / backend 变复杂。

## 7. Docker 的三层缓存与 warm_pool

```
【三层查找顺序】—— provider._acquire_internal

    Layer 1: in-process 缓存（_sandboxes / _thread_sandboxes）
        ├─ 命中 → 探活 → 返回
        └─ 未命中 → 下一层
              │
              ▼
    Layer 1.5: warm_pool（_warm_pool）
        ├─ 命中 → 探活 → 转入 active
        └─ 未命中 → 下一层
              │
              ▼
    Layer 2: cross-process lock + discover/create
        ├─ validate_sandbox_id
        ├─ cross_process_lock 保护
        ├─ 锁内复查 in-process
        ├─ backend.discover → 命中则 register
        └─ 未命中 → backend.create → readiness → register

【warm_pool 的两个入口】
    ├─ release() —— 主动释放时转入
    └─ _reconcile_orphans() —— 启动时对账遗留容器

【warm_pool 的两个出口】
    ├─ _reclaim_warm() —— 被 acquire 复用
    └─ _evict_oldest_warm() / _cleanup_idle() —— 驱逐 / 超时销毁
```

## 8. 关键辨析（易混点）

### 8.1 runtime 与 backend 的关系

- **不是嵌套**——两者是 `DockerSandboxProvider` 下的两条平行线。
- backend 管容器生命周期（造 / 找 / 探 / 停）。
- runtime 管容器使用（执行 / 读写）。
- 通过 `SandboxInfo.sandbox_url` 间接握手：backend 产出，runtime 消费。

### 8.2 runtime 是否"在容器里执行"

- **`DockerRuntime` 本身不在容器里**——它在宿主进程，发 HTTP 请求。
- **命令在容器里执行**——由容器内 AIO 服务执行。
- `DockerRuntime` 是"遥控器"，容器内 AIO 服务才是"执行者"。
- **设计精髓**：`DockerRuntime` 和 `LocalRuntime` 实现同一套契约，`Sandbox` 门面不用改——换 runtime 就等于换执行环境。

### 8.3 executor 与 runtime 的关系

- **没有直接关系**——名字都带 docker，但分属两层。
- `DockerExecutor` —— 链路 A（backend 层），管 docker CLI 在哪跑。
- `DockerRuntime` —— 链路 B（runtime 层），管怎么调容器内服务。
- 两者互不调用，只共享"容器"这个目标：一个从外面操作壳，一个从里面调服务。

### 8.4 executor.translate_path 与 DockerPathTranslator

- `executor.translate_path` —— 项目视角 → **docker daemon 视角**（WSL 场景：`D:\foo` → `/mnt/d/foo`）。
- `DockerPathTranslator` —— 虚拟路径 ↔ **容器/宿主路径**（沙箱路径映射）。
- 两者用途不同，别混。

---

## 9. 总结

**Docker 实现比本地复杂，因为它要管"容器生命周期"（provider + backend + executor + readiness + cross_process_lock）和"远程执行"（runtime）；但 guard / translator 反而更简单，因为隔离和路径对齐被下沉到内核 / 挂载层。理解 Docker 的关键是分清两条链路——容器生命周期走 backend / executor 调 docker CLI，容器使用走 runtime 调 HTTP，两者互不调用，只通过 `SandboxInfo.sandbox_url` 间接握手。**
