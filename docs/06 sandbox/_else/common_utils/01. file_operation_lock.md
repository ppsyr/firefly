---

name: 文件操作锁 — 进程内 WeakValueDictionary，按 (sandbox_id, virtual_path) 串行化文件操作。

description: 

【整体职责】
为同一沙箱内同一虚拟路径的文件操作提供进程内互斥锁，避免并发"读—改—写"
互相覆盖（如 str_replace 的 read → replace → write）。锁按 (sandbox_id,
virtual_path) 维度隔离：不同沙箱、不同文件互不阻塞。

【内容摘要】
- _LockKey                    : 锁 key 类型别名，形如 (sandbox_id, virtual_path)。
- _FILE_OPERATION_LOCKS       : WeakValueDictionary，key → Lock；锁无引用时自动回收。
- _FILE_OPERATION_LOCKS_GUARD : 保护字典本身的元锁，保证 get-or-create 原子。
- get_file_operation_lock_key : 构造锁 key（用虚拟路径，非物理路径）。
- get_file_operation_lock     : 取锁；不存在则创建。工具层调用入口。

【职责边界】
- 只负责：进程内按 (sandbox_id, virtual_path) 分配互斥锁。
- 不负责：跨进程 / 跨容器的互斥（见【已知限制】）、文件操作的原子性保证
  （本模块只提供锁，不保证调用方正确使用）。

【已知限制（S11 文档声明）】
- 锁仅进程内，不跨进程。Docker 模式下 read_file + write_file 是两次独立 HTTP 调用：
    别进程修改文件 → read 拿旧内容 → write 覆盖别进程的修改 → 静默丢数据（TOCTOU）。
- 当前 Poirot 单进程运行，此限制可接受。
- 多 worker 部署需引入容器内 flock 或 SDK 原子接口。

## 0. 结构树

### 0.1. 静态结构树

```
file_operation_lock.py — 文件操作锁（进程内 WeakValueDictionary，按 (sandbox_id, virtual_path) 串行化）
│
├─ _LockKey: type alias                        ← 锁 key 类型别名
│   └─ tuple[str, str]                           形如 (sandbox_id, virtual_path)
│
├─ _FILE_OPERATION_LOCKS: WeakValueDictionary  ← key → Lock 映射表
│   └─ weakref.WeakValueDictionary[_LockKey, threading.Lock]
│         锁无外部引用时自动 GC，防长跑进程内存泄漏
│
├─ _FILE_OPERATION_LOCKS_GUARD: threading.Lock ← 元锁
│   └─ 保护字典读写，保证 get-or-create 原子；
│      不保护文件操作本身（文件操作用返回的 lock）
│
├─ get_file_operation_lock_key(sandbox_id,    ← 构造锁 key
│                              virtual_path)
│   └─ return (sandbox_id, virtual_path)
│         用虚拟路径（工具层拿到的是虚拟路径，非物理路径）
│
└─ get_file_operation_lock(sandbox_id,         ← 取锁入口；不存在则创建
                            virtual_path)
    ├─ lock_key = get_file_operation_lock_key(...)
    └─ with _FILE_OPERATION_LOCKS_GUARD:
          ├─ lock = _FILE_OPERATION_LOCKS.get(lock_key)
          ├─ lock is None → lock = threading.Lock()
          │                 _FILE_OPERATION_LOCKS[lock_key] = lock
          └─ return lock
```

---

### 0.2. 锁的维度与生命周期

```
【锁的维度】—— (sandbox_id, virtual_path) 二维隔离
    (sandbox_A, /workspace/a.txt)  ← 独立锁
    (sandbox_A, /workspace/b.txt)  ← 独立锁
    (sandbox_B, /workspace/a.txt)  ← 独立锁
    → 不同沙箱、不同文件互不阻塞；同一 (沙箱, 文件) 串行化

【锁的生命周期】
    ┌─ 调用方 get_file_operation_lock(...) 拿到 Lock
    │
    ├─ 调用方 with lock: 执行读—改—写
    │
    └─ 调用方释放引用后 → WeakValueDictionary 自动 GC 回收该 Lock
          → 下次再取同一 key，重新创建
          → 无长期累积，防内存泄漏
```

### 0.3. 运行时调用树

```
① 工具层调用（以 str_replace 为例）
integration/tools.py
    str_replace_tool(path, old_str, new_str, replace_all)
        ├─ sandbox = _ensure_sandbox(provider)
        ├─ lock = get_file_operation_lock(sandbox.id, path)   ← 本模块入口
        └─ with lock:
              ├─ content = sandbox.read_file(path)
              ├─ old_str not in content → raise SandboxRuntimeError
              ├─ new_content = content.replace(...)
              └─ sandbox.write_file(path, new_content)

② get_file_operation_lock 内部
get_file_operation_lock(sandbox_id, virtual_path)
    ├─ lock_key = (sandbox_id, virtual_path)
    └─ with _FILE_OPERATION_LOCKS_GUARD:                     ← 元锁保护字典
          ├─ _FILE_OPERATION_LOCKS.get(lock_key)
          │     ├─ 命中 → return lock
          │     └─ 未命中 → lock = threading.Lock()
          │                 _FILE_OPERATION_LOCKS[lock_key] = lock
          │                 return lock

③ 锁释放与回收
调用方 with lock 结束
    └─ 调用方释放对该 Lock 的引用
          └─ WeakValueDictionary 检测无强引用 → 自动 GC
                └─ 下次取同 key → 重新创建

（本模块不介入文件操作本身，只提供锁）
```

## 1. 补充

**`file_operation_lock.py` 是 sandbox 层的"进程内文件操作互斥"工具——它按 `(sandbox_id, virtual_path)` 分配 `threading.Lock`，让同一沙箱同一文件的"读—改—写"复合操作串行化，避免并发覆盖（如 `str_replace` 的 read → replace → write 丢失更新）。**

几点补充：

- **锁的维度是 `(sandbox_id, virtual_path)` 二维**：不同沙箱、不同文件互不阻塞；只有**同一沙箱的同一文件**才串行化。这是"细粒度锁"——不会因为一个文件忙而阻塞其他文件。

- **key 用虚拟路径，不用物理路径**：工具层拿到的是虚拟路径（Agent 视角），所以锁 key 也用虚拟路径。这是 `Grill #6` 的约定，写进 docstring。

- **WeakValueDictionary 是内存管理的关键**：锁在无人引用时**自动 GC 回收**——否则长跑进程会为每个访问过的文件累积一个永久 Lock，导致内存泄漏。回收后下次取同一 key 会重新创建，**语义仍正确**（无人使用时锁不需要存在）。

- **元锁 `_FILE_OPERATION_LOCKS_GUARD` 是另一层锁**：它**只保护字典读写**（get-or-create 的原子性），**不保护文件操作本身**。这是两个不同的锁：
  - 元锁——保护"锁字典"这个共享数据结构，持有时间极短。
  - 返回的 Lock——保护"文件操作"，由调用方 `with lock:` 持有。

- **已知限制（S11 文档声明）**——这是本模块最重要的约束，原注释完整保留：
  - **锁只进程内，不跨进程**。Docker 模式下 `read_file` + `write_file` 是**两次独立 HTTP 调用**，期间别的进程可能改了文件 → 本进程 read 拿旧内容 → write 覆盖别进程的修改 → **静默丢数据（TOCTOU）**。
  - **当前可接受**：Poirot 单进程运行，无并发写冲突。
  - **多 worker 部署需改**：引入容器内 `flock` 或 SDK 原子接口。
  - **长期方案**：`design_docs/todo_docs/02-sandbox-security-vulnerabilities-fix.md §11 B6`。

- **本模块只提供锁，不保证调用方用对**：调用方必须自己 `with lock:` 包住"读—改—写"复合操作；如果只在写时加锁、读时不加，仍会 TOCTOU。这是职责边界，写进注释。

- **使用场景**：目前唯一已知调用方是 `integration/tools.py` 的 `str_replace_tool`（读—改—写复合操作）。其他工具是单次原子操作，不需要锁。
