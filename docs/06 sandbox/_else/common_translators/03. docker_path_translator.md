---

name: DockerPathTranslator — Docker 路径翻译器（容器内直传 + 反向映射到 host）。

description: 

【整体职责】
实现 path_translator 契约的"Docker 版本"：正向翻译（translate_path /
translate_command / mask_output）全部直传——容器内 /mnt/poirot/user-data
就是 bind mount 的物理路径，虚拟路径与容器路径本就一致，无需翻译。
额外提供反向映射 reverse_translate，把容器内虚拟路径还原为宿主机物理路径，
供 artifact 提取（如 Sandbox.get_host_path）使用。

【内容摘要】
- _VIRTUAL_PREFIX  : 唯一可反向映射的虚拟路径前缀（/mnt/poirot/user-data）。
- DockerPathTranslator : Docker 路径翻译器类。
    ├─ __init__            : 由 sandbox_root + sandbox_id 推出 host 根路径。
    ├─ translate_path      : 虚拟 → 容器路径，直传（原样返回）。
    ├─ translate_command   : 命令翻译，直传（原样返回）。
    ├─ mask_output         : 输出脱敏，直传（原样返回）。
    └─ reverse_translate   : 虚拟 → host 物理路径（供 artifact 提取）。

【职责边界】
- 只负责：正向直传（容器内路径本就对齐）、反向映射（虚拟 → host 物理路径）。
- 不负责：安全校验（guard）、命令执行（backend）、容器内路径的校验规则
  （由 DockerPathGuard 负责）。
- 持有 host_root：由构造参数 sandbox_root + sandbox_id 拼出，构造后不可变。

## 0. 结构树

### 0.1. 静态结构树

```
docker_path_translator.py — DockerPathTranslator（容器内直传 + 反向映射到 host）
│
├─ _VIRTUAL_PREFIX: str                        ← 唯一可反向映射的虚拟路径前缀
│   └─ "/mnt/poirot/user-data"                   注意：不带尾斜杠（支持精确匹配）
│
└─ DockerPathTranslator
    ├─ _host_root: str                        ← host 物理根路径（构造时确定，不可变）
    │   └─ str(Path(sandbox_root) / sandbox_id).replace("\\", "/")
    │
    ├─ __init__(sandbox_root, sandbox_id)     ← 由 root + id 拼出 host_root
    │
    ├─ translate_path(virtual_path) -> str     ← 正向：虚拟 → 容器路径，直传
    │   └─ return virtual_path
    │
    ├─ translate_command(command) -> str       ← 正向：命令翻译，直传
    │   └─ return command
    │
    ├─ mask_output(output) -> str              ← 正向：输出脱敏，直传
    │   └─ return output
    │
    └─ reverse_translate(virtual_path) -> str  ← 反向：虚拟 → host 物理路径
        ├─ 前缀校验：
        │     virtual_path == _VIRTUAL_PREFIX（精确匹配）
        │     或 startswith(_VIRTUAL_PREFIX + "/")
        │     └─ 不满足 → raise ValueError
        ├─ relative = virtual_path[len(_VIRTUAL_PREFIX):].lstrip("/")
        └─ return f"{_host_root}/{relative}"（relative 为空则返回 _host_root）
```

### 0.2. 正向 / 反向对照（本文件的关键不对称）

```
【正向：全部直传】——translate_path / translate_command / mask_output
    virtual_path / command / output
        ↓ 不做任何转换
    原样返回
    原因：容器内 /mnt/poirot/user-data = bind mount 物理路径
          虚拟路径与容器路径本就一致，无需翻译

【反向：唯一做映射】——reverse_translate
    /mnt/poirot/user-data/foo
        ↓ 前缀校验（必须落 _VIRTUAL_PREFIX）
        ↓ 剥离前缀，取 relative
    foo
        ↓ _host_root + relative
    <sandbox_root>/<sandbox_id>/foo（host 物理路径）
    用途：artifact 提取（Sandbox.get_host_path）
```

## 1. 补充

**`docker_path_translator.py` 是 Docker 场景的路径翻译器——它的"正向"（虚拟 → 容器路径）三个方法全部直传，因为容器内 `/mnt/poirot/user-data` 就是 bind mount 物理路径；只有"反向" `reverse_translate` 才做真实映射，把虚拟路径还原成宿主机物理路径，服务于 artifact 提取。**

几点补充：

- **正向 / 反向不对称是本文件最大特征**：
  - **正向三个方法**（`translate_path` / `translate_command` / `mask_output`）**全部直传**——和 `IdentityTranslator` 行为一致。因为容器内路径本就对齐，不需要翻译。
  - **反向 `reverse_translate`** 才做真实映射——把容器内 `/mnt/poirot/user-data/foo` 还原成 `<sandbox_root>/<sandbox_id>/foo`。
  - 看代码时**别以为"正向直传"就等于"什么都不做"**——它的价值在反向。

- **`reverse_translate` 是 Docker 特有的扩展方法**：它**不在 `path_translator` 契约里**（`IdentityTranslator` / `LocalPathTranslator` 都没有）。它是 Docker 场景下为了 artifact 提取（`Sandbox.get_host_path`）而额外加的能力。

- **`_VIRTUAL_PREFIX` 不带尾斜杠**（`/mnt/poirot/user-data`）——和 `DockerPathGuard` 里**带尾斜杠**的（`/mnt/poirot/user-data/`）不同。原因是本文件要支持"精确匹配"（`virtual_path == _VIRTUAL_PREFIX`），所以前缀不能带尾斜杠，否则 `startswith` 判断会受影响。两个文件里名字相同、值不同，容易看漏。

- **前缀校验的边界**：精确匹配 `/mnt/poirot/user-data` **或** 以 `/mnt/poirot/user-data/` 开头——两条都接受，但 `/mnt/poirot/user-data-extra` **不接受**（因为它既不是精确匹配，也不以 `+ "/"` 开头）。这是防前缀误匹配的关键。

- **输出统一正斜杠**：`__init__` 里 `.replace("\\", "/")` 把 Windows 反斜杠统一成 `/`，保证跨平台一致（`shutil.copy2` 在 Windows 上兼容两种分隔符）。

- **`_host_root` 构造后不可变**：`sandbox_root + sandbox_id` 在 `__init__` 时拼好，之后只读——这是 `INVARIANT` 里明确说的。

- **三个 translator 的对照**：

| 维度 | IdentityTranslator | LocalPathTranslator | DockerPathTranslator |
|---|---|---|---|
| 适用场景 | Docker（对齐）/ E2B | 本地（虚拟 ≠ 物理） | Docker（需 artifact 提取） |
| translate_path | 直传 | 虚拟 → 物理 | 直传 |
| translate_command | 直传 | 命令中路径替换 | 直传 |
| mask_output | 直传 | 物理 → 虚拟（脱敏） | 直传 |
| reverse_translate | 无 | 无 | **有**（虚拟 → host） |
| 状态 | 无 | PathMapping + 缓存 | host_root |
| 核心复杂度 | 零 | 双向匹配 + 防穿越 | 反向映射 + 前缀校验 |

- **与 `DockerPathGuard` 的分工**：`DockerPathGuard` 管"**允不允许**写"（安全），`DockerPathTranslator` 管"**路径怎么对应**"（映射）。两者都用 `/mnt/poirot/user-data` 这个前缀，但一个做校验、一个做翻译，**互不替代**。

## 2. docker 的 translator 逻辑更简单

## 2.1. 核心原因：Docker 把「路径对齐」这件事做在了挂载层

**本地**：虚拟路径和宿主机真实路径**本来就不一样**，必须靠 translator 翻译。

```
虚拟路径（Agent 视角）       宿主机真实路径
/mnt/poirot/user-data/  ←→  /home/xxx/.poirot/sandbox/abc123/user-data/
      ↑                                    ↑
   写死的虚拟前缀                    实际存储位置，因机器/用户而异
```

这两个路径**没有任何天然关系**，只能靠 `PathMapping` 显式绑定，translator 负责双向转换。

**Docker**：用 **bind mount 把虚拟路径挂到容器内同一个路径**，让两边**物理对齐**。

```
宿主机                          容器内
<host_root>/abc123/user-data/  ←→  /mnt/poirot/user-data/
                  ↑                        ↑
        （bind mount 挂载）        容器内就是虚拟路径
```

**关键**：容器内 `/mnt/poirot/user-data` 本身就是挂载点——**它既是"虚拟路径"也是"物理路径"**。Agent 写 `/mnt/poirot/user-data/foo`，落到容器内就是 `/mnt/poirot/user-data/foo`，不需要任何翻译。

**路径对齐了，正向翻译自然就不需要了。**

## 2.2. 那为什么还需要 `reverse_translate`？

因为**宿主机那一侧**仍然需要一个真实路径来拿产物。

```
Agent（容器内）视角              宿主机视角
/mnt/poirot/user-data/report.pptx
        ↓ 怎么从宿主机拿到这个文件？
<host_root>/abc123/user-data/report.pptx
```

- **容器内**：路径就是虚拟路径，正向不用翻。
- **宿主机**：要提取 artifact 时，得知道这个文件**实际落在宿主机哪**——所以需要 `reverse_translate` 做一次反向映射。

**所以 Docker translator 不是"更简单"，而是"只在一个方向复杂"**：
- 正向：直传（因为挂载对齐了）。
- 反向：仍然要映射（因为宿主机路径和虚拟路径不同）。

## 2.3. 和本地 translator 的对比

| | 本地 | Docker |
|---|---|---|
| 虚拟路径 vs 物理路径 | **天然不同** | **挂载对齐**（正向相同） |
| 正向 translate_path | 必须翻译（PathMapping） | 直传 |
| 正向 translate_command | 必须替换命令中路径 | 直传 |
| 反向 mask_output | 必须脱敏（防泄漏宿主路径） | 直传（容器路径不构成泄漏） |
| 反向 reverse_translate | 无（mask_output 已是逆操作） | **有**（artifact 提取用） |
| 复杂度分布 | **双向都复杂** | **正向零、反向一个方法** |

**本地是"双向都要翻"，Docker 是"正向不用翻、反向只翻一次"。**

## 2.4. 为什么 Docker 能做到"正向直传"

三个前提，缺一不可：

1. **bind mount 对齐路径**：挂载时故意让容器内路径 == 虚拟路径。
2. **容器内路径不构成泄漏**：`/mnt/poirot/user-data` 是**约定路径**，不是宿主真实路径，输出里出现它不泄漏任何信息——所以 `mask_output` 不需要脱敏。
3. **正向执行不需要知道宿主路径**：命令在容器内跑，容器只认容器内路径。

而本地**三个前提都不成立**：
- 虚拟路径 ≠ 宿主路径（无挂载对齐）。
- 宿主路径出现在输出里会泄漏真实目录结构（需要 mask）。
- 命令在宿主跑，必须先把虚拟路径换成宿主真实路径。

## 2.5. 总结

**本地 translator 复杂，是因为"虚拟路径"和"宿主真实路径"天然不一致，双向都要靠 `PathMapping` 翻译；Docker translator 简单，是因为 bind mount 让容器内路径与虚拟路径物理对齐，正向变成直传，只剩反向 `reverse_translate` 一处需要映射。**

**根本机制**：Docker 把"路径转换"这件事**从软件层（translator）下沉到了挂载层（bind mount）**——挂载时就把路径对好了，运行时自然不用再翻。
