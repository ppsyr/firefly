---

name: DockerPathGuard — Docker 路径白名单守卫（写入必须落挂载区）。

description: 

【整体职责】
实现 security_guard 契约的"Docker 路径"版本：约束**写入**操作只能落在挂载区
（/mnt/poirot/user-data/），包括两条路径——
① validate_path(write=True)：直接写入的路径；
② validate_command：bash 重定向目标（> / >>）的绝对路径。
读操作不限制——容器边界本身已提供隔离，读越界危害有限。

【内容摘要】
- _VIRTUAL_PREFIX   : 唯一允许写入的虚拟路径前缀（/mnt/poirot/user-data/）。
- _REDIRECT_PATTERN : 捕获 bash 重定向目标绝对路径的正则（> 或 >>）。
- DockerPathGuard   : Docker 路径守卫类。
    ├─ validate_path    : 写入路径校验（write=True 时才查前缀）。
    └─ validate_command : 命令中重定向目标校验。

【职责边界】
- 只负责：写入路径的前缀白名单校验（直接路径 + 重定向目标）。
- 不负责：读路径校验（读不限制）、路径转换（translator）、
  相对路径解析 / cd 后路径解析（容器隔离兜底）。
- 无状态：不持有任何字段，规则全在模块级常量里。

## 0. 结构树

### 0.1. 静态结构树

```
docker_path_guard.py — DockerPathGuard（Docker 路径白名单守卫：写入必须落挂载区）
│
├─ _VIRTUAL_PREFIX: str                        ← 唯一允许写入的虚拟路径前缀
│   └─ "/mnt/poirot/user-data/"
│
├─ _REDIRECT_PATTERN: Pattern                  ← 捕获 bash 重定向目标（绝对路径）的正则
│   └─ r'>{1,2}\s*(/[^\s;|&]*)'
│         ├─ > 或 >>（重定向符）
│         ├─ \s*（可含空白）
│         └─ (/[^\s;|&]*)（以 / 开头，遇空白/; | & 停 → 仅绝对路径）
│
└─ DockerPathGuard                             ← Docker 路径守卫类（无状态）
    │
    ├─ validate_path(path, *, write=False)     ← 写入路径校验
    │   ├─ not write → return（读不限制，直接放行）
    │   └─ not path.startswith(_VIRTUAL_PREFIX)
    │         → raise SandboxPermissionError
    │           (operation="validate")
    │
    └─ validate_command(command)               ← 命令校验：扫重定向目标
        └─ _REDIRECT_PATTERN.finditer(command)
              └─ 每个 target：
                    ├─ startswith(_VIRTUAL_PREFIX) → 放行
                    └─ 否则 → raise SandboxPermissionError
                              (operation="validate_command")
```

```
① 装配期
DockerPathGuard()
    └─ 无参构造，无状态；规则全部来自模块级常量
    → 产出 guard 实例（Docker 场景下按需叠加）

        ═══════════ 进入命令执行 ═══════════

② 路径校验 —— validate_path(path, write)
sandbox.execute_command(cmd) 内部对涉及的写入路径
    └─ guard.validate_path(path, write=...)
          ├─ write=False → return（读不限制）
          └─ write=True
                ├─ path.startswith("/mnt/poirot/user-data/") → 放行
                └─ 否则 → raise SandboxPermissionError
                          （write path must be under ...）

③ 命令校验 —— validate_command(command)
sandbox.execute_command(cmd) 前
    └─ guard.validate_command(command)
          └─ _REDIRECT_PATTERN.finditer(command)
                ├─ 匹配 "> /abs/path" 或 ">> /abs/path"
                │     ├─ target.startswith("/mnt/poirot/user-data/") → 放行
                │     └─ 否则 → raise SandboxPermissionError
                │               （redirect target must be under ...）
                └─ 不匹配（相对路径、2>&1、tee 等）→ 跳过（容器隔离兜底）

（本模块不介入路径转换、命令执行、读路径校验、cd 解析）
```

## 1. 补充

**`docker_path_guard.py` 是 Docker 场景的"窄规则"守卫——它只补一条约束："写入必须落挂载区"。读、相对路径、`cd` 后的路径、`tee` 全部交给容器隔离兜底。这与 `LocalSecurityGuard`（本地无兜底，规则宽）形成鲜明对照。**

几点补充：

- **只约束写入，不约束读取**：`validate_path` 在 `write=False` 时**直接 return**。因为 Docker 下读越界危害有限——容器边界已经隔离，读了也出不去。这是本 guard 和 `LocalSecurityGuard` 最大的差异。

- **两条路径、同一个前缀**：
  - `validate_path(write=True)` — 管"**直接调用**写路径"（如 `write_file` 工具）；
  - `validate_command` — 管"**bash 重定向**写路径"（如 `echo x > /etc/passwd`）。
  两者都以 `_VIRTUAL_PREFIX` 为唯一白名单，规则统一。

- **`_REDIRECT_PATTERN` 的边界是刻意的**：
  - `>{1,2}` — 只匹配 `>` 和 `>>`（覆盖重定向与追加重定向）。
  - `(/[^\s;|&]*)` — **只捕获绝对路径**，遇空白 / `;` / `|` / `&` 停。
  - 结果：**跳过**相对路径重定向、文件描述符重定向（`2>&1`）、`tee` 等。

- **为何故意不覆盖这些情况**（原 INVARIANT 直接列了三条）：
  - **不解析 `cd` 后相对路径** — 实现复杂、需模拟 shell 状态，收益低；容器隔离已兜底。
  - **不检查 `tee`** — 罕见，LLM 通常用 `>` 重定向。
  - **跳过 `2>&1`** — 这是文件描述符重定向，不是文件路径，误拦会阻断正常命令。

- **"误拒优于放过"的取向**：命中违规直接抛 `SandboxPermissionError`，LLM 可据错误信息重试改路径。宁可拒绝合法路径，也不放过越界写入。

- **无状态**：不持有字段，所有规则是模块级常量（`_VIRTUAL_PREFIX` / `_REDIRECT_PATTERN`）——构造无需参数，可安全共享。

- **与 AuditGuard 的关系**：Docker 模式下通常是 `AuditGuard(PermissiveGuard)`——`PermissiveGuard` 全放行、`AuditGuard` 做三档分级。`DockerPathGuard` 是**另一条独立的路径守卫**，在需要"写入落挂载区"约束时按需叠加，**不一定被 AuditGuard 包装**。这一点和 `LocalSecurityGuard` 被 `AuditGuard` 包装的模式不同。

- **和 `LocalSecurityGuard` 的对照表**：

| 维度              | LocalSecurityGuard      | DockerPathGuard |
| --------------- | ----------------------- | --------------- |
| 适用场景            | 本地（无容器隔离）               | Docker（有容器隔离）   |
| 读路径             | 校验（白名单）                 | 不限制             |
| 写路径             | 校验（白名单 + 只读标记）          | 校验（唯一前缀）        |
| 命令校验            | 危险黑名单 + shlex + 绝对路径白名单 | 只查重定向目标         |
| 路径穿越            | 拒绝 `..`                 | 不查（容器隔离兜底）      |
| 误拒取向            | fail-closed             | 误拒优于放过          |
| 被 AuditGuard 包装 | 是（本地模式）                 | 按需叠加，通常不包装      |

## 2. docker 的 guard 逻辑更简单

### 2.1. 根本原因：安全边界转移了

```
本地模式：安全边界 = Guard（软件层）
    ┌─────────────────────────┐
    │  Agent                  │
    │    ↓                    │
    │  Guard  ← 唯一防线       │  本地没有硬件/内核隔离
    │    ↓                    │  只能靠软件规则拦住
    │  宿主机（无隔离）        │
    └─────────────────────────┘

Docker 模式：安全边界 = 容器（内核层）
    ┌─────────────────────────┐
    │  Agent                  │
    │    ↓                    │
    │  Guard  ← 补漏，不是主防线│  容器边界已经兜底
    │    ↓                    │  Guard 只补"容器挡不住的"
    │  ┌───────────────┐      │
    │  │ 容器（硬隔离） │      │  namespace + cgroup
    │  │  ↓            │      │  越界也出不去
    │  │ 容器内文件系统 │      │
    │  └───────────────┘      │
    └─────────────────────────┘
```

**本地**：Guard 是**唯一防线**——因为本地进程和宿主机之间**没有隔离**，`rm -rf /` 真的会删宿主机根目录。所以 Guard 必须**什么都查**：路径穿越、危险命令、白名单、只读、畸形引号……

**Docker**：Guard 是**补漏层**——容器已经用 namespace（文件系统、进程、网络隔离）+ cgroup（资源限制）把 Agent 关住了。Agent 在容器里 `rm -rf /` 删的是**容器内的 `/`**，不是宿主机的。**边界挡住了绝大部分攻击，Guard 只需补容器挡不住的那部分**。

### 2.2. 容器挡住了什么

| 攻击 | 本地（Guard 必须查） | Docker（容器挡住） |
|---|---|---|
| `rm -rf /` | 会删宿主机根 | 删的是容器内 `/`，宿主机没事 |
| 路径穿越 `../..` | 能逃出白名单目录到宿主机 | 逃不出容器文件系统 |
| 访问 `/etc/passwd` | 读到宿主机敏感文件 | 读到的是容器内的 `/etc/passwd` |
| 越权写系统目录 | 真的写到宿主机 | 写到容器内，宿主机不受影响 |
| 读任意路径 | 能读宿主机任意文件 | 只能读容器内文件 |
| 危险命令（`mkfs` 等） | 会破坏宿主机 | 破坏的是容器，重建即可 |

**容器边界一挡，Guard 的"路径穿越拒绝""危险命令黑名单""读白名单"全都变得不必要了**——因为它们要防的是"逃出隔离区"，而容器本身就是隔离区。

### 2.3. 那 DockerPathGuard 为什么还要存在？

因为**容器不是万能的**，有一件事容器挡不住：**写入落到挂载区之外**。

Docker 容器通常用 **bind mount** 把宿主机的某目录挂进容器（比如 `/mnt/poirot/user-data/` ↔ 宿主机某目录）。这个挂载点是**双向穿透的**：

```
容器内 /mnt/poirot/user-data/  ←→  宿主机某真实目录
        （读写都会穿透到宿主机）
```

**如果 Agent 往 `/mnt/poirot/user-data/` 里写东西，会真的落到宿主机上**——这是挂载的设计目的（让产物能被宿主机访问），但也是**唯一的"容器挡不住"的通道**。

所以 `DockerPathGuard` 只查一件事：**写入必须落在这个挂载区**。
- 写到挂载区 → 穿透到宿主机，但这是**受控的**（宿主机只暴露这一块）。
- 写到挂载区外（如 `/etc/passwd`）→ 只写在容器内，**宿主机的 `/etc/passwd` 不受影响**。

等等——那写到容器内 `/etc/passwd` 也不危险，为什么还要拦？

因为**容器的可写层也可能是挂载的，或者容器重启后容器内文件会丢**。更重要的是：**规则要统一**——如果允许写容器内任意路径，LLM 可能写出"在容器里生成产物但宿主机取不到"的文件，导致交付失败。约束写入落挂载区，**既保证安全，又保证产物可交付**。

### 2.4. 总结

**本地 Guard 复杂，是因为它必须独自承担全部安全责任（本地无隔离）；Docker Guard 简单，是因为大部分安全责任已由容器内核承担，它只需补容器挡不住的那条缝——写入穿透到宿主机的挂载区。**

这是**"纵深防御（defense-in-depth）"**的典型体现：不是每层都做全套，而是**外层（容器）做粗粒度隔离，内层（Guard）做细粒度补漏**。
