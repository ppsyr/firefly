```
【内容摘要】
- AuditGuard         : 审计守卫——命令三档分级（block / warn / pass）+ 审计日志，
                       组合模式，包装一个底层 guard。
- LocalSecurityGuard : 本地安全守卫——本地场景的命令 / 路径校验规则实现。
- PermissiveGuard    : 宽松守卫——全放行（no-op），用于容器已提供硬隔离的场景。
- DockerPathGuard    : Docker 路径守卫——Docker 场景的路径越界校验实现，
                       约束访问不越出挂载目录。
```

Docker：

        → AuditGuard(PermissiveGuard, journal)
Docker 写约束（按需）：
    DockerPathGuard()

    └─ guard.validate_command(cmd)              ← 通常 guard = AuditGuard

          └─ warn / pass → inner.validate_command(cmd)
                │
                ├─ inner = LocalSecurityGuard：
                │     ├─ 扫 _DANGEROUS_PATTERNS → 命中拦
                │     ├─ shlex.split → ValueError 则 fail-closed 拦
                │     └─ 遍历 tokens，绝对路径白名单：
                │           _SYSTEM_PATH_PREFIXES 放行

                │     └─ no-op（直接放行）
                │

                      └─ 扫 _REDIRECT_PATTERN，重定向目标必须落

③ 路径校验 —— validate_path(path, write)
sandbox.execute_command(cmd) 内部 / 上游透传
    └─ guard.validate_path(path, write=...)
          │
          ├─ [AuditGuard 层] 直接透传底层（本层不做分级）
          │
          ├─ inner = LocalSecurityGuard：
          │     ├─ _reject_path_traversal → 含 ".." 拦
          │     ├─ _find_mapping → 未命中拦
          │     └─ write=True 且 read_only → 拦
          │
          ├─ inner = PermissiveGuard：
          │     └─ no-op（直接放行）
          │
          └─ [若叠加 DockerPathGuard]：
                ├─ write=False → 直接放行
                └─ write=True  → path 必须落 _VIRTUAL_PREFIX，否则拦

### 0.4. 补充

**`guards/` 是 sandbox 层的安全校验实现层——它按两条正交轴组织：一条是"隔离类型"（本地严 / Docker 窄 / Permissive 放行），一条是"职责类型"（AuditGuard 作为组合层叠加分级与审计）。所有实现满足同一契约，校验失败统一抛 `SandboxPermissionError`。**

几点补充：

- **两条轴不是并列，是正交**：
  - **轴一（隔离类型）**：`LocalSecurityGuard` / `DockerPathGuard` / `PermissiveGuard` —— 回答"这个隔离实现下，什么该拦？"
  - **轴二（职责类型）**：`AuditGuard` —— 回答"要不要在外层叠加分级和审计？"
  - 两者组合出实际使用的 guard：`AuditGuard(LocalSecurityGuard)` 或 `AuditGuard(PermissiveGuard)`。

- **规则简繁的根源是"安全边界在哪"**：
  - 本地无隔离 → Guard 是**唯一防线** → 规则严（白名单 + 黑名单 + fail-closed）。
  - Docker 有内核隔离 → Guard 是**补漏层** → 规则窄（只查写入穿透）。
  - 这不是"偷懒"，是 defense-in-depth：外层粗隔离，内层细补漏。

- **`AuditGuard` 是组合层，不是底层实现**：它持有 `_inner`，把底层规则交给 inner；自己只做"三档分级 + 审计 + 按档决定拦还是透传"。这解释了为什么 guard 目录里既有"被包装的"（Local / Permissive），又有"包装者"（Audit）。

- **`DockerPathGuard` 是独立的补漏守卫**：它和 `LocalSecurityGuard` 不互斥——本地模式用 Local，Docker 模式用 Permissive + AuditGuard 做分级，需要"写挂载区"约束时再叠加 DockerPathGuard。它**通常不被 AuditGuard 包装**，与 Local 模式的组合方式不同。

- **三档分级是 `AuditGuard` 的核心契约**：
  - `block` — 破坏性命令，**无论 Local/Docker 都拦**（本地/容器都危险）。
  - `warn` — 危险但非破坏，**记日志放行**（靠容器隔离兜底）。
  - `pass` — 其余，**透传底层 guard**。
  - **block 优先于 warn**：`_classify` 先扫 block，命中即返回，顺序不能反。

- **`LocalSecurityGuard` 的 fail-closed 是安全底线**：`shlex` 解析失败（畸形引号）时选择**拒绝**而非放行——因为畸形引号本身就是绕过尝试的信号。

- **`DockerPathGuard` 的"窄"是刻意的**：
  - 只约束**写入**，不约束读取（容器隔离下读越界危害有限）。
  - 只捕获**绝对路径**重定向，跳过 `2>&1`（文件描述符）、相对路径、`tee`、`cd` 后路径（容器隔离兜底）。
  - 误拒优于放过。

- **`PermissiveGuard` 的存在理由**：容器边界（namespace + cgroup）本身就是安全边界，路径白名单由容器负责，Guard 层不再重复校验。它是"零拦截"的极端实现，通常配合 `AuditGuard` 使用。

- **统一契约**：所有 guard 都满足 `contracts/security_guard.py` 的 `validate_command / validate_path`，工具层只需 `catch SandboxPermissionError` 即可统一处理。


## 1. Guard 总览

Guard 是 sandbox 层的**安全校验抽象**——在命令/路径真正执行前，判断"允不允许"。它满足 `contracts/security_guard.py` 契约，核心两个方法：

- `validate_command(command)` — 命令级校验
- `validate_path(path, *, write=False)` — 路径级校验

校验失败统一抛 `SandboxPermissionError`。

---

## 2. Guard 的两条分类轴

Guard 目录里有四个实现，但它们**不在同一分类维度**：

### 2.1 轴一：按「隔离类型」分（谁做底层校验）

| Guard | 适用场景 | 底层逻辑 |
|---|---|---|
| `LocalSecurityGuard` | 本地（无容器隔离） | 严格：白名单 + 黑名单 + 路径穿越拒绝 + shlex fail-closed |
| `DockerPathGuard` | Docker（有容器隔离） | 窄：只查"写入必须落挂载区" |
| `PermissiveGuard` | Docker / E2B（容器已硬隔离） | 全放行（no-op） |

### 2.2 轴二：按「职责类型」分（是否叠加）

| Guard | 角色 | 是否拦截 |
|---|---|---|
| `AuditGuard` | **组合层**——包装一个底层 guard，叠加三档分级 + 审计 | 部分（block 档拦） |

**关键**：`AuditGuard` 不和上面三个并列，它是**包装者**，被包装的是 `LocalSecurityGuard` 或 `PermissiveGuard`。

---

## 3. 四个 Guard 的定位

### 3.1 LocalSecurityGuard — 本地严格防线

**本地无隔离，它是唯一防线，所以规则最严：**

- `validate_path`：拒绝 `..` 穿越 → 查白名单前缀（`/mnt/poirot/user-data` 读写、`/mnt/skills` 只读）→ 只读映射禁止写。
- `validate_command`：危险模式黑名单 → `shlex` 解析（失败 **fail-closed**）→ 绝对路径白名单（系统路径放行 `/bin/` `/usr/` `/lib/`，不放行 `/tmp/`）。

**白名单匹配规则**：最长前缀优先（`_find_mapping` 按 `container_path` 长度降序）。

### 3.2 DockerPathGuard — Docker 窄规则补漏

**容器挡住绝大部分攻击，它只补容器挡不住的一条缝：写入穿透。**

- `validate_path(write=True)`：写入必须落 `/mnt/poirot/user-data/`。
- `validate_command`：bash 重定向目标（绝对路径）必须落同一前缀。
- **读不限制**——容器隔离兜底。

**刻意不覆盖**：`cd` 后相对路径、`tee`、`2>&1`（文件描述符重定向）。

### 3.3 PermissiveGuard — 全放行

**容器边界即安全边界，Guard 层不再重复校验：**

- 两个方法都是 no-op。
- 通常作为 `AuditGuard` 的 inner 使用：`AuditGuard(PermissiveGuard)`。

### 3.4 AuditGuard — 组合层（分级 + 审计）

**不自己定义底层规则，包一个 inner guard，在外层叠加：**

- **三档分级**：
  - `block` — 破坏性命令（`rm -rf /`、`mkfs`、fork bomb 等），**无论 Local/Docker 都拦**。
  - `warn` — 危险但非破坏（`sudo`、`chmod 777`、`eval` 等），**记日志放行**，靠容器隔离兜底。
  - `pass` — 其余，透传底层 guard。
- **审计日志**：每次都写 `sandbox.command` 事件（`journal` 失败静默吞掉）。
- `validate_path` **不做分级**，直接透传底层。

## 4. 组合关系（谁包装谁）

```
本地模式：
    AuditGuard( LocalSecurityGuard )
        └─ 外层分级 + 审计；block 直接拦；warn/pass 透传严格本地规则

Docker 模式：
    AuditGuard( PermissiveGuard )
        └─ 外层分级 + 审计；block 直接拦；warn/pass 直接放行（容器兜底）

Docker 写入约束（按需叠加）：
    DockerPathGuard
        └─ 独立路径守卫，不一定被 AuditGuard 包装
```

## 5. 为什么 Docker 的 Guard 更简单

**根本原因：安全边界转移了。**

| | 本地 | Docker |
|---|---|---|
| 安全边界 | Guard（软件层） | 容器（内核层：namespace + cgroup） |
| Guard 角色 | **唯一防线** | **补漏层** |
| 必须查 | 路径穿越、危险命令、白名单、只读、畸形引号…… | 只查"写入穿透到挂载区" |
| 规则复杂度 | 高 | 低 |

- **本地**：进程和宿主机之间无隔离，`rm -rf /` 真的会删宿主机根——Guard 必须独自承担全部安全责任。
- **Docker**：容器已把 Agent 关住，容器内 `rm -rf /` 删的是容器内的 `/`，宿主机没事——容器边界挡住了绝大部分攻击。
- **唯一挡不住的**：bind mount 的挂载区是双向穿透的。Agent 往 `/mnt/poirot/user-data/` 写会真落到宿主机——所以 `DockerPathGuard` 只补这一条缝。

这是 **defense-in-depth（纵深防御）** 的典型：外层（容器）做粗粒度隔离，内层（Guard）做细粒度补漏。

---


## 6. 总结

**Guard 是 sandbox 的安全校验抽象；本地模式下它是唯一防线（规则严），Docker 模式下它退居补漏层（规则窄）；AuditGuard 是叠加在底层 guard 之上的分级 + 审计组合层。规则简繁的差异，本质是"安全边界放在软件层还是内核层"。**
