### 0.3. 运行时调用树（一次 bash 调用）

```
① 工具层 integration/tools.py
bash_tool(command)
    └─ _ensure_sandbox(provider)
          ├─ get_sandbox_id()          ← ContextVar
          └─ provider.get(sandbox_id)  ← 按 id 查 Sandbox

② Sandbox 门面 sandbox.py
sandbox.execute_command(cmd)
    ├─ ① guard.validate_command(cmd)
    ├─ ② guard.validate_path(path)
    ├─ ③ translator.translate_command(cmd)
    ├─ ④ runtime.exec_command(cmd)
    │     │
    │     ├─ [本地] LocalRuntime：subprocess.run
    │     │
    │     └─ [Docker] DockerRuntime：HTTP 调容器内 AIO
    │           （在 backend.execute 之下有 Docker 专属分层：
    │             cross_process_lock → readiness → executor.exec）
    │
    └─ ⑤ translator.mask_output(output)

③ 返回结果给工具层 → LLM

【装配期 —— 发生在 bash 调用之前】
provider.acquire(thread_id, user_id)
    ├─ [本地] 组合 LocalRuntime + LocalPathTranslator
    │         + AuditGuard(LocalSecurityGuard)
    └─ [Docker] 三层缓存 / warm_pool / discover+create
              → _make_sandbox 组合 DockerRuntime
                + DockerPathTranslator + AuditGuard(DockerPathGuard)

【收尾期 —— 进程退出】
bootstrap_sandbox._shutdown_all_providers()（atexit）
    └─ provider.shutdown()
          └─ [Docker] 逐个 _destroy_active → backend.destroy
```

### 0.4. 补充

**`sandbox/` 是 Agent 代码/文件操作的执行边界——以 `Sandbox` 门面为核心，组合 Runtime（裸执行）+ Translator（路径翻译 + 脱敏）+ Guard（安全校验）三可替换组件，编排 `validate → translate → execute → mask` 四步；本地 / Docker 各有实现，通过同一套契约解耦。**

几点补充：

- **目录按"公共 / 实现 / 配套"三层组织**：
  - **公共**：`types.py` / `exceptions.py` / `contracts/` / `utils/` / `integration/`。
  - **实现**：`local/` / `docker/` / `runtimes/` / `translators/` / `guards/`。
  - **注意 `runtimes/` 不在 `local/` 或 `docker/` 下**——它平级放两个 runtime（`local_runtime` / `docker_runtime`），因为都实现 `sandbox_runtime` 契约。

- **契约层是理解一切的钥匙**：五个契约（provider / backend / runtime / guard / translator）定义了稳定抽象；本地 / Docker 都只是它们的实现。

- **两条正交分类轴贯穿 guard 和 translator**：
  - **轴一（隔离类型）**：local / docker / permissive / identity —— 回答"这个隔离实现下怎么做"。
  - **轴二（职责类型）**：`AuditGuard` 是组合层 —— 回答"要不要叠加分级 / 审计"。
  - 这解释了为什么 `guards/` 有四个实现、`translators/` 有三个实现——**它们不在同一维度**。

- **Docker 目录里有两条独立链路**：
  - **链路 A（容器生命周期）**：provider → backend → executor → docker CLI。
  - **链路 B（容器使用）**：Sandbox → runtime → HTTP → 容器内 AIO。
  - 两者通过 `SandboxInfo.sandbox_url` 间接握手。

- **`utils/` 是跨实现的公共工具箱**：`file_operation_lock`（进程内锁）/ `sandbox_id`（格式校验）/ `search`（忽略判定 + 行截断）。

- **`integration/` 是装配与接入层**：`config`（配置）/ `context`（ContextVar）/ `tools`（工具工厂）/ `bootstrap_sandbox`（收尾）。

- **三处"安全 / 正确性加固"编号**（读代码时会看到）：
  - **S2**：`allow_host_bash=False` 禁用 bash 工具。
  - **S5**：`acquire_async` 防 cancel 误 release。
  - **S7**：`destroy` 前二次 discover 校验。
  - **S9**：`list_dir` BFS 剪枝。
  - **S10**：`grep` ReDoS 防护。
  - **S11**：`file_operation_lock` 的进程内限制声明。
  - **#1433**：`DockerRuntime._lock` 串行化。
  - **#2872**：`DockerRuntime.close` 属性链挖掘。

- **本地 vs Docker 的复杂度反直觉**：
  - **本地**：无隔离 → Guard 复杂；路径不对齐 → Translator 复杂；runtime 直接在宿主执行。
  - **Docker**：容器隔离 → Guard 简单；bind mount 对齐 → Translator 正向直传；但新增容器生命周期（provider + backend + executor + readiness + lock）和远程执行（HTTP runtime）。

- **公共组件优先理解**：读代码时先看 `types.py` / `exceptions.py` / `contracts/`，再看 `local/`（最简单），最后看 `docker/`（最复杂）——这是理解整个 sandbox 的推荐顺序。


## 1. Sandbox 系统总览

Sandbox 是 Agent 代码/文件操作的**执行边界**——把 Agent 对文件系统、命令的访问约束在受控范围内。

采用**方案 C 组合模式**：`Sandbox` 具体类组合三个可替换组件，编排 `validate → translate → execute → mask` 四步流程。

```
Sandbox（门面 / 编排者）
    ├── SandboxRuntime      ← 裸执行（跑命令 / 读写文件）
    ├── PathTranslator      ← 路径翻译（虚拟 ↔ 真实）+ 输出脱敏
    └── SecurityGuard       ← 安全校验（validate only）
```

三组件各有独立契约（`contracts/`），本地 / Docker 各有实现，运行时可替换。

## 3. 三组件的职责边界

### 3.1 SandboxRuntime — 裸执行

- **只做**：真正跑命令、读写文件。
- **不做**：路径翻译、安全检查——这两件事交给 translator / guard。
- **异常统一**：全抛 `SandboxError` 子类，runtime 实现负责包装内置异常（`FileNotFoundError` → `SandboxFileNotFoundError` 等）。
- **两个实现**：
  - `LocalRuntime` —— `subprocess.run` 直接在宿主执行。
  - `DockerRuntime` —— 经 HTTP 调容器内 AIO 服务。

### 3.2 PathTranslator — 路径翻译 + 输出脱敏

- **正向**：`translate_path` / `translate_command` —— 虚拟路径 → 真实路径。
- **反向**：`mask_output` —— 真实路径 → 虚拟路径（脱敏，防泄漏宿主目录）。
- **额外**：`DockerPathTranslator.reverse_translate` —— 虚拟 → 宿主机物理路径（artifact 提取）。
- **三个实现**：
  - `IdentityTranslator` —— 恒等直传。
  - `LocalPathTranslator` —— `PathMapping` 双向翻译 + 防穿越 + 缓存。
  - `DockerPathTranslator` —— 正向直传 + 反向映射。

### 3.3 SecurityGuard — 安全校验

- **只做**：`validate_path` / `validate_command`——判断"允不允许"。
- **不做**：脱敏（归 translator）。
- **四个实现**：
  - `LocalSecurityGuard` —— 本地严格（白名单 + 黑名单 + fail-closed）。
  - `DockerPathGuard` —— Docker 窄规则（写入必须落挂载区）。
  - `PermissiveGuard` —— 全放行（容器已硬隔离）。
  - `AuditGuard` —— **组合层**：三档分级 + 审计，包装底层 guard。

## 4. 本地 vs Docker：复杂度下沉

**核心规律**：Docker 把「隔离」和「路径对齐」两件事从软件层下沉到内核 / 挂载层，所以 guard / translator 反而更简单；但新增了「容器生命周期」和「远程执行」两整套机制。

| 维度 | Local | Docker |
|---|---|---|
| 隔离级别 | 软约束（靠 guard 拦） | 硬隔离（namespace + cgroup） |
| 安全边界 | Guard（软件层） | 容器（内核层） |
| Guard 角色 | 唯一防线 → 复杂 | 补漏层 → 简单 |
| 路径翻译 | 双向都复杂 | 正向直传 + 反向一处 |
| 命令执行 | `subprocess.run` 在宿主 | HTTP 调容器内 AIO |
| 基础设施层 | 无 | `LocalContainerBackend` |
| CLI 执行层 | 无 | `DockerExecutor` |
| 锁 | `file_operation_lock`（进程内） | `cross_process_lock`（跨进程） |
| 生命周期 | runtime 几乎 no-op | provider 管三层缓存 + warm_pool + idle |
| 信号处理 | 仅 atexit | atexit + SIGTERM/SIGINT/SIGHUP |

## 5. 本地实现（local/）

```
local/
└── local_sandbox_provider.py — LocalSandboxProvider（LRU 缓存 + 确定性 ID）
```

**本地沙箱 = LocalRuntime + LocalPathTranslator + AuditGuard(LocalSecurityGuard)**

- **确定性 ID**：`sha256(user:thread)[:8]`——跨进程可推导。
- **LRU 缓存**：默认 256 条，命中 `move_to_end` 刷新，超容量驱逐最旧。
- **`release` 是 no-op**：保留缓存供复用。
- **`_lock` 是 `threading.Lock`**：多线程共享。

**本地三件套都比 Docker 复杂**：
- `LocalRuntime` —— 直接在宿主执行，必须靠 guard 拦危险命令。
- `LocalPathTranslator` —— 虚拟路径 ≠ 宿主路径，必须双向翻译。
- `LocalSecurityGuard` —— 本地无隔离，是唯一防线，规则最严。

## 6. Docker 实现（docker/ + runtimes/docker_runtime.py）

```
docker/
├── docker_sandbox_provider.py   ← 生命周期编排
├── local_container_backend.py   ← 容器基础设施 CRUD
├── remote_container_backend.py  ← 远程 / K8s 容器
├── executor.py                  ← docker CLI 执行落点抽象
├── readiness.py                 ← 就绪轮询
└── cross_process_lock.py        ← 跨进程锁

runtimes/docker_runtime.py       ← 调容器内 AIO 服务
translators/docker_path_translator.py
guards/docker_path_guard.py
```

### 6.1 两条独立链路

```
DockerSandboxProvider
    │
    ├── 链路 A：容器生命周期
    │     └─ LocalContainerBackend
    │           ├─ DockerExecutor → subprocess.run("docker run/inspect/stop")
    │           ├─ readiness（等就绪）
    │           └─ cross_process_lock（临界区保护）
    │
    └── 链路 B：容器使用
          └─ Sandbox
                ├─ DockerRuntime → HTTP → 容器内 AIO
                ├─ DockerPathTranslator
                └─ AuditGuard(DockerPathGuard)

两条链路通过 SandboxInfo.sandbox_url 间接握手
```

### 6.2 关键辨析

- **`DockerExecutor` 与 `DockerRuntime` 无直接关系**——分属两条链路：一个管"docker CLI 在哪跑"，一个管"怎么调容器内服务"。
- **`DockerRuntime` 在宿主进程，不在容器里**——它是"遥控器"，发 HTTP 请求；真正执行的是容器内 AIO 服务。
- **`executor.translate_path` 与 `DockerPathTranslator` 是两回事**——前者是"项目视角 → daemon 视角"（WSL 场景），后者是"虚拟路径 ↔ 容器/宿主路径"。
- **`LocalContainerBackend` 与 `DockerRuntime` 不是嵌套**——是 provider 下的两条平行线，通过 `SandboxInfo.sandbox_url` 握手。

### 6.3 三层缓存 + warm_pool

```
Layer 1: in-process 缓存
    └─ 命中 → 探活 → 返回

Layer 1.5: warm_pool
    └─ 命中 → 探活 → 转 active

Layer 2: cross-process lock + discover/create
    └─ 锁内复查 → discover → create
```

- **`release` 语义**：移入 warm_pool（**容器保持运行**，不销毁）。
- **warm_pool 两个入口**：`release` + `_reconcile_orphans`（启动对账）。
- **warm_pool 两个出口**：`_reclaim_warm`（复用）+ `_evict_oldest_warm` / `_cleanup_idle`（销毁）。

### 6.4 Docker 特有的正确性修复

- **S5**：`acquire_async` 用 `acquired` flag 防 cancel 误 release。
- **S7**：`destroy` 前二次 `discover` 校验，避免误杀别线程新建的同 ID 容器。
- **#1433**：`DockerRuntime._lock` 串行化，防并发破坏持久 shell session。

## 7. 一次 bash 调用的完整链路

```
① 工具层 integration/tools.py
bash_tool(command)
    └─ _ensure_sandbox(provider)
          ├─ get_sandbox_id()          ← ContextVar
          └─ provider.get(sandbox_id)

② Sandbox 门面 sandbox.py
sandbox.execute_command(cmd)
    ├─ ① guard.validate_command(cmd)        ← 命令级拦截
    ├─ ② guard.validate_path(path)          ← 路径级拦截
    ├─ ③ translator.translate_command(cmd)  ← 虚拟 → 真实路径
    ├─ ④ runtime.exec_command(cmd)          ← 裸执行
    └─ ⑤ translator.mask_output(output)     ← 真实 → 虚拟（脱敏）

③ Docker 特有分层（仅在 backend.execute 之下）
    ├─ cross_process_lock.acquire()
    ├─ readiness.wait_until_ready()
    ├─ executor.exec(container_id, cmd)     ← docker exec
    └─ cross_process_lock.release()
```

**关键**：公共流程到 `runtime` / `backend` 层分叉；本地直接 `subprocess`，Docker 多出「锁 + executor + 就绪 + 容器生命周期」四件事。

## 8. 工具层与生命周期

### 8.1 工具工厂（integration/tools.py）

- 产出 6 个工具：`bash` / `read_file` / `write_file` / `list_dir` / `str_replace` / `present_files`。
- `allow_host_bash=False` 时**不注册 `bash`** → 5 个工具（S2 安全加固）。
- 闭包捕获 `provider`，工具运行时通过 `_ensure_sandbox` 取当前沙箱。

### 8.2 生命周期

```
创建 → provider.create()
    ├─ 本地：组合 LocalRuntime + LocalPathTranslator + AuditGuard(LocalSecurityGuard)
    └─ Docker：三层缓存 → backend.create → readiness → _make_sandbox

使用 → sandbox.execute_command(cmd)
    └─ 四步编排（validate → translate → execute → mask）

释放 → provider.release()
    ├─ 本地：no-op（保留缓存）
    └─ Docker：移入 warm_pool（容器继续运行）

销毁 → provider.shutdown() / _destroy_active()
    └─ 清状态 + close + destroy
```

## 9. 总结

**Sandbox 是 Agent 文件/命令操作的执行边界——`Sandbox` 门面组合 `Runtime`（裸执行）+ `Translator`（路径翻译 + 脱敏）+ `Guard`（安全校验）三可替换组件，编排 `validate → translate → execute → mask` 四步。本地实现三件套都复杂（无隔离，Guard 是唯一防线）；Docker 实现把隔离和路径对齐下沉到内核/挂载层，guard / translator 变简单，但新增了容器生命周期和远程执行两整套机制。理解 Docker 的关键是分清两条链路——容器生命周期走 backend/executor 调 docker CLI，容器使用走 runtime 调 HTTP，两者互不调用，只通过 `SandboxInfo.sandbox_url` 间接握手。**
