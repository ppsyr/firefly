---

name: SituationReport — 求助时的结构化态势分析。

description: 

【整体职责】
在需要求助（help request）时，生成一份结构化态势报告：程序化部分从 StallTracker
的失败记录中提取尝试、环境与阻塞点；LLM 部分额外调用一次 LLM 综合出 2-4 个可选方案
与推荐项。

【内容摘要】
- SituationReport              : 态势报告数据结构（原因、尝试、环境、阻塞、方案、推荐）。
- SituationReport.to_text      : 渲染为 Markdown 文本。
- build_programmatic_report    : 从 StallTracker 失败记录构建报告的程序化部分。
- _OPTIONS_PROMPT              : 生成方案的 LLM 提示词模板。
- synthesize_options_with_llm  : 调用 LLM 综合方案与推荐（原地修改并返回报告）。

【职责边界】
- 只负责：组织态势报告的数据结构、程序化提取、渲染文本、调用 LLM 补充方案。
- 不负责：失败信号的采集（StallTracker）、停滞判定（StallTracker）、求助的触发与
  处置（stall_detection_middleware / HITL）、LLM 的构造与路由（config / model_router）。

## 0. 结构树

### 0.1. 静态结构树

```
situation_report.py — SituationReport（求助时的结构化态势分析）
│
├─ SituationReport(dataclass)                 ← 态势报告数据结构
│   ├─ reason: str                             ← 求助原因
│   ├─ attempts: list[dict] = []               ← 尝试记录（command / error / capability）
│   ├─ environment: dict = {}                  ← 环境信息
│   ├─ blocker: str = ""                       ← 阻塞点描述
│   ├─ options: list[str] = []                 ← 可选方案（LLM 补充）
│   ├─ recommendation: str = ""                ← 推荐方案（来自被标记项）
│   └─ to_text() -> str                        ← 渲染为 Markdown
│       ├─ ## Help Request · {reason}
│       ├─ ### Attempts    ← 逐条 "command → error"
│       ├─ ### Environment ← 逐项 "- k: v"
│       ├─ ### Blocker     ← blocker 文本
│       └─ ### Options     ← 逐条方案，第 1 项若有推荐则附 "(recommended)"
│
├─ build_programmatic_report(failures, reason, environment) -> SituationReport
│   ├─ attempts ← failures 映射为 {command, error, capability}
│   ├─ caps ← 按 capability 归组 errors
│   ├─ blocker ← "{cap}: {n} failure(s)" 拼接；无则回退 reason
│   └─ return SituationReport(reason, attempts, environment, blocker)
│
├─ _OPTIONS_PROMPT: str                        ← LLM 生成方案的提示词模板
│   └─ 占位符：{reason} / {blocker} / {attempts}
│
└─ synthesize_options_with_llm(report, llm) -> SituationReport
    ├─ attempts_text ← report.attempts 渲染为 "- cmd → err"
    ├─ prompt ← _OPTIONS_PROMPT.format(...)
    ├─ try:
    │   ├─ llm.invoke(prompt) → response
    │   ├─ text ← response.content | str(response)
    │   └─ 逐行解析：
    │       ├─ "[RECOMMENDED]" 开头 → 去标记写入 options + 设 recommendation
    │       └─ 其他 → 写入 options
    ├─ except Exception → options = []          ← 容错，不抛
    └─ return report（原地修改）
```

### 0.2. 运行时调用树（求助时的两段式构建）

```
① 触发求助（stall_detection_middleware / HITL）
middleware
    ├─ 从 StallTracker 取失败记录与停滞原因
    │     └─ tracker.get_failures() / tracker.get_stuck_reason()
    │
    ├─ 【程序化段】build_programmatic_report(failures, reason, environment)
    │     ├─ 提取 attempts（command / error / capability）
    │     ├─ 按 capability 归组 → 生成 blocker
    │     └─ return SituationReport（options 仍为空）
    │
    ├─ 【LLM 段】synthesize_options_with_llm(report, llm)
    │     ├─ 组装 _OPTIONS_PROMPT
    │     ├─ llm.invoke(prompt)
    │     ├─ 解析行 → options / recommendation
    │     └─ 异常 → options = []（报告仍可用）
    │
    └─ 【渲染】report.to_text()
          └─ Help Request · reason + Attempts / Environment / Blocker / Options

② 消费
    ├─ 展示给用户（CLI / TUI）
    └─ 或写入 events / journal
```

### 0.3. 补充

**`situation_report.py` 是求助场景的态势组织器——把 StallTracker 的失败记录转成结构化报告（程序化段），再用一次 LLM 调用补上可选方案与推荐（LLM 段），最终渲染成可供人阅读的 Markdown。**

几条主线：

- **两段式构建**：`build_programmatic_report`（确定性、必成）负责提取事实；`synthesize_options_with_llm`（非确定性、容错）负责生成建议。两段解耦，LLM 失败不影响报告主体。
- **数据来自 StallTracker**：`attempts` 直接映射 `ToolFailure`（`command` / `error` / `capability`），`blocker` 按 capability 归组计数生成——与 `stall_tracker` 的 `get_failures()` / `get_stuck_reason()` 对接。
- **LLM 容错是硬约束**：`try/except` 包住整个 LLM 调用与解析，异常时仅清空 `options`，报告仍可渲染——保证求助流程不因 LLM 故障而中断。
- **推荐标记约定**：LLM 以 `[RECOMMENDED]` 前缀标记推荐项，解析时去标记、写入 `options` 并设为 `recommendation`；`to_text` 据此在第 1 项附 `(recommended)`。
- **渲染顺序固定**：Attempts → Environment → Blocker → Options，且每段均为可选（无内容则不渲染），适应不同信息完整度。
- **原地修改**：`synthesize_options_with_llm` 修改并返回同一 `report` 对象（非 frozen），便于链式补充。
- **消费方是中间件**：与 `stall_detection_middleware` / HITL 链路对接，是"检测到停滞 → 生成求助报告 → 交给用户"的中间一环。
