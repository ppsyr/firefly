---

name: StallTracker — 检测 agent 是否陷入死胡同。

description: 

【整体职责】
通过四类信号判断 agent 是否停滞（stuck）：
1. 能力耗尽：同一 capability 经 5 次不同命令尝试仍失败。
2. 错误模式重复：同一错误类别反复出现 5 次。
3. 待办停滞：同一 todo 连续 15 轮 LLM 仍处 in_progress。
4. 长操作无进展：工具运行 180s 无新输出（依赖 RunActivityTracker 心跳，Phase 3 接入）。

三个主动信号在最近 120 秒内有过成功工具调用时被抑制（_success_decay_window），
避免长时间编码任务中"瞬时错误与真实进展并存"导致误报。

tracker 跨 run 无状态；help 请求解决后 reset() 清空所有信号，让 agent 重新开始。

【内容摘要】
- ToolFailure            : 单次工具失败记录。
- _CAPABILITY_PATTERNS   : 能力分类正则表。
- _ERROR_CLASS_PATTERNS  : 错误类别正则表。
- classify_capability    : 按 tool/input/error 文本归类 capability。
- classify_error_class   : 按 error 文本归类错误类别。
- StallTracker           : 停滞追踪器，记录失败/成功/待办/进展并判定 stuck。
- StallTracker.stuck / get_stuck_reason / reset 等。

【职责边界】
- 只负责：记录信号、判定停滞、给出停滞原因、重置。
- 不负责：活动生命周期追踪（RunActivityTracker）、停滞的处置与介入（interrupt_protection /
  HITL 中间件）、信号的采集来源（工具调用方 / todo 中间件）。
  第 4 类信号（no-progress）所需心跳来自 RunActivityTracker，本模块仅预留阈值。

## 0. 结构树

### 0.1. 静态结构树

```
stall_tracker.py — StallTracker（检测 agent 是否陷入死胡同）
│
├─ ToolFailure(dataclass)                    ← 单次工具失败记录
│   ├─ capability: str                        ← 能力分类（sandbox/postgres/root/docker/network/unknown）
│   ├─ error_class: str                       ← 错误类别（permission/sandbox/network/not_found/unknown）
│   ├─ command: str                           ← 命令或输入摘要（截断 200）
│   ├─ error: str                             ← 错误信息（截断 500）
│   └─ timestamp: float                       ← 发生时间戳
│
├─ _CAPABILITY_PATTERNS: list[tuple]          ← 能力分类正则表
│   ├─ sandbox   ← winerror|sandbox|exec failed|...
│   ├─ postgres  ← postgres|psql|pg_isready|pgvector
│   ├─ root      ← apt-get|apt |dpkg|sudo|/var/lib/apt
│   ├─ docker    ← docker|docker-compose|containerd
│   └─ network   ← curl|wget|http(s)://|504|gateway timeout
│
├─ _ERROR_CLASS_PATTERNS: list[tuple]         ← 错误类别正则表
│   ├─ permission ← permission denied|eacces|403|forbidden
│   ├─ sandbox    ← winerror|sandbox fail/error/refus|exec/write/read failed
│   ├─ network    ← timeout|504|connection refused|unreachable
│   └─ not_found  ← not found|no such file|404|not installed|absent
│
├─ classify_capability(tool_name, tool_input, error) -> str ← 归类 capability
│   └─ 拼接文本 → 逐 pattern 匹配 → 命中返回 / 否则 "unknown"
│
├─ classify_error_class(error) -> str          ← 归类错误类别
│   └─ 逐 pattern 匹配 → 命中返回 / 否则 "unknown"
│
└─ StallTracker(dataclass)                     ← 停滞追踪器
    ├─ 阈值配置
    │   ├─ capability_failure_threshold = 5    ← 能力耗尽阈值（不同命令数）
    │   ├─ error_pattern_threshold = 5         ← 错误模式重复阈值
    │   ├─ todo_stagnation_rounds = 15         ← 待办停滞轮数阈值
    │   └─ no_progress_timeout = 180.0         ← 无进展超时（第 4 类信号预留）
    │
    ├─ 内部状态
    │   ├─ _failures: list[ToolFailure]        ← 失败记录
    │   ├─ _error_counts: dict[cls, int]       ← 各错误类别计数
    │   ├─ _todo_in_progress_hash: str | None  ← 当前 in_progress 待办哈希
    │   ├─ _todo_stagnation_count: int         ← 待办停滞累计轮数
    │   ├─ _last_progress_ts: float            ← 最近进展时间戳
    │   ├─ _last_success_ts: float = 0.0       ← 最近成功时间戳（0=从未成功）
    │   └─ _success_decay_window: float = 120.0 ← 成功衰减窗口
    │
    ├─ stuck (property) -> bool                ← 三类信号任一成立
    │   └─ _capability_stuck() or _error_pattern_stuck() or _todo_stuck()
    │
    ├─ 判定辅助（均受 _recent_success() 抑制）
    │   ├─ _recent_success() -> bool           ← 窗口内是否成功过
    │   ├─ _capability_stuck() -> bool         ← 不同命令数 >= 阈值（unknown 不计）
    │   ├─ _error_pattern_stuck() -> bool      ← 任一错误类别计数 >= 阈值
    │   └─ _todo_stuck() -> bool               ← 停滞轮数 >= 阈值
    │
    ├─ 记录入口
    │   ├─ record_tool_failure(...)            ← 记录失败 + 累加错误类别
    │   ├─ record_tool_success()               ← 刷新成功/进展时间戳（触发衰减）
    │   ├─ record_todo_state(todos)            ← 更新待办停滞计数
    │   └─ record_progress()                   ← 刷新进展/成功时间戳
    │
    ├─ 查询 / 重置
    │   ├─ get_failures() -> list[ToolFailure] ← 失败记录副本
    │   ├─ get_stuck_reason() -> str | None    ← 停滞原因描述
    │   └─ reset() -> None                      ← 清空信号，成功时间戳归 0
    │
    └─ 【第 4 类信号未接入】
        └─ no_progress_timeout 已定义，心跳来自 RunActivityTracker（Phase 3 接入）
```

### 0.2. 四类信号与抑制机制

```
┌─────────────────────────────────────────────────────────────────────────┐
│ 四类信号（design_docs/45 §3.3）                                          │
├─────────────────────────────────────────────────────────────────────────┤
│ ① 能力耗尽        _capability_stuck()      同一 capability 的不同命令数 ≥ 5 │
│ ② 错误模式重复    _error_pattern_stuck()   同一错误类别计数 ≥ 5             │
│ ③ 待办停滞        _todo_stuck()            同一 in_progress 待办轮数 ≥ 15   │
│ ④ 长操作无进展    （未接入）                工具 180s 无输出（需心跳，Phase 3）│
└─────────────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ 抑制机制：_recent_success()                                              │
│   最近 _success_decay_window（120s）内有成功 → ①②③ 均被抑制             │
│   目的：长时间编码任务中"瞬时错误与真实进展并存"时避免误报                  │
│   初始 _last_success_ts = 0（epoch）→ 从未成功过 = 不抑制                 │
└─────────────────────────────────────────────────────────────────────────┘
                              │
                              ▼
                    stuck = ① or ② or ③
                              │
                              ▼
                  get_stuck_reason() → 原因描述
                              │
                              ▼
                  消费方（stall_detection_middleware）
```

### 0.3. 运行时调用树

```
① 记录信号（由工具调用方 / todo 中间件喂数据）
    ├─ record_tool_failure(tool_name, tool_input, error)
    │     ├─ classify_capability(...) → capability
    │     ├─ classify_error_class(error) → cls
    │     ├─ _failures.append(ToolFailure(...))
    │     └─ _error_counts[cls] += 1
    │
    ├─ record_tool_success()
    │     └─ _last_success_ts = _last_progress_ts = now
    │
    ├─ record_todo_state(todos)
    │     ├─ 提取 in_progress 内容 → sorted → hash
    │     ├─ 同 hash → _todo_stagnation_count += 1
    │     └─ 变化 → 重置（空则归 0）
    │
    └─ record_progress()
          └─ _last_progress_ts = _last_success_ts = now

② 判定停滞（由 stall_detection_middleware 调用）
middleware
    └─ tracker.stuck
          ├─ _capability_stuck()   ← _recent_success() 抑制？
          ├─ _error_pattern_stuck() ← _recent_success() 抑制？
          └─ _todo_stuck()          ← _recent_success() 抑制？
    └─ tracker.get_stuck_reason() → 原因（capability exhausted / error pattern repeated / todo stagnated）

③ 处置后重置
    └─ tracker.reset()   ← help 请求解决后，清空信号让 agent 重新开始

④ 第 4 类信号（未接入）
RunActivityTracker.heartbeat / get_stale_activities
    └─ （Phase 3 将心跳接入 StallTracker，用 no_progress_timeout 判定）
```

### 0.4. 补充

**`stall_tracker.py` 是停滞检测器——记录失败/成功/待办/进展四类信号，据此判定 agent 是否陷入死胡同，并用"成功衰减窗口"抑制误报。**

几条主线：

- **三类主动信号 + 一类预留**：能力耗尽（不同命令数 ≥ 5）、错误模式重复（同类别 ≥ 5）、待办停滞（同 in_progress 连续 ≥ 15）已实现；长操作无进展（180s）仅预留阈值，待 Phase 3 接入 `RunActivityTracker` 心跳。
- **成功衰减是防误报核心**：`_recent_success()` 在 120s 窗口内有过成功则抑制全部三类信号——因为长时间编码任务中"瞬时错误与真实进展"常并存。
- **初始不抑制**：`_last_success_ts` 初始为 0（epoch），"从未成功过"时 `_recent_success()` 为 False，保证新会话不会被误抑制。
- **能力信号按"不同命令"计**：同一 capability 下 command 去重后 ≥ 5 才算耗尽，避免同一命令重复失败被误判为"尝试了多种方式"。
- **unknown 排除**：capability / error_class 为 "unknown" 的失败不参与对应判定，避免噪声。
- **reset 语义一致**：清空全部信号并把 `_last_success_ts` 归 0，与构造时行为一致。
- **与 RunActivityTracker 的关系**：本模块第 4 类信号依赖后者的心跳，但两者职责不同——前者"判定停滞并给原因"，后者"记录活动并播报"，通过心跳数据衔接（Phase 3）。
- **消费方是中间件**：`stall_detection_middleware` 调用 `stuck` / `get_stuck_reason()`，并在处置后 `reset()`——这与 `RunActivityTracker`（由 TUI/CLI 轮询、执行侧推送）形成两条不同的链路。
