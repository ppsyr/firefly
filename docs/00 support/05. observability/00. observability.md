---

name: Observability layer — runtime activity tracking, stall detection, situation reports.

description: 

【整体职责】
监控运行健康度：追踪运行期活动（是否在活动）、检测停滞（是否卡住）、保护原子任务
（卡住时能否暂停）、组织求助态势（如何向用户求助）。构成一条"活动 → 停滞 → 保护 →
求助"的因果链，为 HITL 与界面展示提供信号。

【内容摘要】
- activity_tracker     : 活动追踪器（RunActivityTracker），记录模型/工具/沙箱/specialist
                         调用的生命周期与心跳，供 TUI/CLI 轮询与事件播报。
- stall_tracker        : 停滞追踪器（StallTracker），四类信号判定 stuck 并给出原因，
                         含成功衰减窗口防误报。
- interrupt_protection : 中断保护，线程局部标志，供 middleware 暂停前检查，保护原子任务。
- situation_report     : 态势报告（SituationReport），两段式构建（程序化提取 + LLM 补方案），
                         渲染为求助报告。

【职责边界】
- 只负责：活动记录、停滞判定、中断保护标志、求助态势组织。
- 不负责：停滞的处置决策（stall_detection_middleware / HITL）、受保护任务本身的执行
  （上下文压缩 / 证据持久化 / 报告生成）、界面展示（TUI / CLI）。

【四层因果链】
- activity_tracker   ：还活着吗（记录活动 + 心跳）。
- stall_tracker      ：卡住了吗（四类信号判定停滞）。
- interrupt_protection：卡住后怎么办（暂停前检查保护）。
- situation_report   ：对外怎么呈现（求助报告）。

## 0. 结构树

### 0.1. 静态结构树

```
observability/ — 可观测性模块（运行健康度监控）
│
├─ __init__.py                              ← 可观测性包初始化（对外导出面）
│
├─ activity_tracker.py                      ← 【第一层】活动追踪：还活着吗
│   ├─ Activity(dataclass)                   ← 单条活动记录
│   │   ├─ activity_id / kind / summary      ← 标识 / 类型 / 摘要
│   │   ├─ started_at / last_progress_at     ← 开始 / 心跳
│   │   ├─ status / output_size              ← 状态 / 输出量
│   │   ├─ finished_at / error               ← 结束 / 错误
│   │   ├─ elapsed (property)                ← 已耗时
│   │   └─ no_progress_duration (property)   ← 无进展时长
│   └─ RunActivityTracker                    ← 活动追踪器
│       ├─ __init__(heartbeat_interval, no_progress_threshold, on_event)
│       ├─ start / finish / heartbeat        ← 生命周期入口
│       ├─ get_active / get_recent_completed / get_stale_activities
│       ├─ total_elapsed / reset
│       └─ _emit                             ← 向回调发事件
│
├─ stall_tracker.py                         ← 【第二层】停滞检测：卡住了吗
│   ├─ ToolFailure(dataclass)                ← 单次工具失败记录
│   ├─ _CAPABILITY_PATTERNS                  ← 能力分类正则表
│   ├─ _ERROR_CLASS_PATTERNS                 ← 错误类别正则表
│   ├─ classify_capability / classify_error_class
│   └─ StallTracker(dataclass)               ← 停滞追踪器
│       ├─ 阈值：capability_failure_threshold / error_pattern_threshold /
│       │        todo_stagnation_rounds / no_progress_timeout
│       ├─ 内部状态：_failures / _error_counts / _todo_* / _last_* / _success_decay_window
│       ├─ stuck (property)                  ← 三类信号任一成立
│       ├─ _recent_success / _capability_stuck / _error_pattern_stuck / _todo_stuck
│       ├─ record_tool_failure / record_tool_success / record_todo_state / record_progress
│       ├─ get_failures / get_stuck_reason
│       └─ reset
│
├─ interrupt_protection.py                  ← 【第三层】中断保护：卡住后怎么办
│   ├─ _protection_state: threading.local()  ← 线程局部保护标志
│   ├─ is_interrupt_protected() -> bool      ← 查询是否受保护
│   └─ interrupt_protection(active=True)     ← 上下文管理器（支持嵌套）
│
└─ situation_report.py                      ← 【第四层】态势汇总：对外怎么呈现
    ├─ SituationReport(dataclass)            ← 态势报告
    │   ├─ reason / attempts / environment / blocker / options / recommendation
    │   └─ to_text() -> str                  ← 渲染为 Markdown
    ├─ build_programmatic_report(...)        ← 从 StallTracker 失败记录构建程序化部分
    ├─ _OPTIONS_PROMPT: str                  ← LLM 生成方案提示词
    └─ synthesize_options_with_llm(...)      ← LLM 补充方案与推荐
```

### 0.3. 运行时调用树

```
① 执行侧喂数据（模型/工具/沙箱/specialist 调用）
调用方（middleware / runtime）
    └─ RunActivityTracker.start(activity_id, kind, summary)
    └─ RunActivityTracker.heartbeat(activity_id, output_size)
    └─ RunActivityTracker.finish(activity_id, status, error, output_size)
          └─ _emit → on_event 回调（journal / TUI）
          ═══════════ 心跳数据 ═══════════
                └─ （Phase 3）接入 StallTracker 的第 4 类信号

② 检测侧判定停滞（每轮中间件）
stall_detection_middleware
    ├─ StallTracker.record_tool_failure / record_tool_success
    ├─ StallTracker.record_todo_state / record_progress
    ├─ StallTracker.stuck          ← 三类信号任一成立（受 _recent_success 抑制）
    └─ StallTracker.get_stuck_reason()

③ 暂停前检查保护
stall_detection_middleware（暂停前）
    └─ is_interrupt_protected()
          ├─ True  → 延迟暂停，等 interrupt_protection 上下文退出
          └─ False → 允许暂停

④ 触发求助 + 生成报告
stall_detection_middleware（需求助）
    ├─ build_programmatic_report(tracker.get_failures(), reason, environment)
    ├─ synthesize_options_with_llm(report, llm)
    └─ report.to_text() → 展示给用户（CLI / TUI）

⑤ 处置后重置
    ├─ StallTracker.reset()            ← help 解决后清空信号
    └─ RunActivityTracker.reset()      ← 新 run 时清空活动

═══════════ 消费方 ═══════════
├─ stall_detection_middleware  ← 停滞检测 + 求助触发（主消费方）
├─ TUI / CLI                   ← 轮询 get_active / get_recent_completed 展示
└─ journal / events            ← on_event 回调写入事件流
```

### 0.4. 补充

**`observability/` 是运行健康度监控层——四份文件构成一条因果链：`activity_tracker` 记录"是否在活动"，`stall_tracker` 判定"是否停滞"，`interrupt_protection` 决定"停滞时能否暂停"，`situation_report` 组织"如何向用户求助"。**

按四层展开：

- **第一层 · 活动追踪（`activity_tracker.py`）**：把每次模型/工具/沙箱/specialist 调用登记为带生命周期与心跳的 `Activity`，提供 `get_active` / `get_stale_activities` / `total_elapsed`，经 `on_event` 播报 `activity.started/finished/heartbeat`。消费者是 TUI/CLI（轮询）与 journal（回调）。
- **第二层 · 停滞检测（`stall_tracker.py`）**：记录失败/成功/待办/进展四类信号，判定 `stuck` 并给出 `get_stuck_reason`。核心是"成功衰减窗口"（120s 内有过成功则抑制三类信号）防误报；第 4 类信号（无进展）待接入 `activity_tracker` 心跳。
- **第三层 · 中断保护（`interrupt_protection.py`）**：线程局部标志，供 `stall_detection_middleware` 在暂停前检查；受保护（上下文压缩/证据持久化/报告生成）时延迟暂停。
- **第四层 · 态势汇总（`situation_report.py`）**：两段式构建——程序化提取（`build_programmatic_report`）+ LLM 补方案（`synthesize_options_with_llm`），渲染为 Help Request 报告，供用户查看。

几条主线：

- **两条链路并行**：`activity_tracker`（记录 + 播报，供界面与 journal）与 `stall_tracker`（判定 + 触发，供中间件决策）——你之前观察到的"中间件只调 StallTracker 不调 RunActivityTracker"正是这个分工的体现。
- **数据流方向**：执行侧 → `activity_tracker`（活动）→ 心跳 → `stall_tracker`（停滞）→ `situation_report`（求助）→ 用户；`interrupt_protection` 是决策侧的旁路开关。
- **防误报贯穿**：`stall_tracker` 的成功衰减窗口、`activity_tracker` 的心跳节流、`situation_report` 的 LLM 容错，都是为"不误报、不中断"服务。
- **两个 tracker 定位不同**：`RunActivityTracker` 是"记录器/播报器"（被动、推送），`StallTracker` 是"检测器/决策源"（主动、被中间件拉取）。
- **Phase 3 衔接点**：`stall_tracker` 的第 4 类信号（`no_progress_timeout`）已定义阈值，等待接入 `activity_tracker` 的心跳数据。
- **与 HITL 配置对应**：`HitlConfig` 里的 `activity_heartbeat_interval` / `no_progress_timeout` / `cancel_grace_period` 分别对应 `activity_tracker` / `stall_tracker` / `interrupt_protection` 的配置值（具体接入点待确认）。
