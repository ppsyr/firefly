---

name: 运行管理器 — 运行（run）的创建、状态推进与持久化。

description: 

【整体职责】
管理单次运行的生命周期：创建 run（生成 RunContext + RunRecord + RunJournal）、
推进状态（running / success / failed）、更新并持久化 RunRecord 到磁盘。
内存中维护 run_id → RunRecord / RunContext 的映射。

【内容摘要】
- _CST            : 东八区时区常量，用于生成 run_id 时间戳。
- _make_run_id    : 生成 run_id（run-{时间戳}-{4位随机后缀}）。
- RunManager      : 运行管理器，含 create_run / mark_running / mark_success /
                    mark_failed / get_run 及内部持久化辅助。
- _store_record   : 更新内存记录并写盘。
- _write_record   : 把 RunRecord 序列化写入 record_path。
- _require_record : 取记录，缺失抛 KeyError。
- _require_context: 取上下文，缺失抛 KeyError。

【职责边界】
- 只负责：run 的创建、状态推进、记录持久化、内存映射维护。
- 不负责：RunRecord / RunContext 的结构定义（run_record / run_context）、
  事件日志实现（RunJournal）、配置结构（AppConfig）、实际执行业务逻辑（graph / agent）。

## 0. 结构树

### 0.1. 静态结构树

```
run_manager.py — 运行管理器（创建 / 状态推进 / 持久化）
│
├─ _CST: timezone(+8h)                          ← 东八区时区常量，用于生成 run_id 时间戳
│
├─ _make_run_id() -> str                        ← 生成 run_id
│   └─ f"run-{东八区时间戳}-{4位随机后缀}"       ← 例：run-20240101T120000-ab3d
│
└─ RunManager                                   ← 运行管理器
    ├─ __init__(config)                          ← 初始化
    │   ├─ config: AppConfig
    │   ├─ _records: dict[run_id, RunRecord]     ← 内存记录映射
    │   └─ _contexts: dict[run_id, RunContext]   ← 内存上下文映射
    │
    ├─ create_run(thread_id, user_id, run_id, session_id, trace_id,
    │             model_name, thread_dir) -> RunContext
    │   ├─ created_run_id ← run_id | _make_run_id()
    │   ├─ output_dir ← {thread_dir}/runs/{run_id} | {logs_root}/{run_id}
    │   ├─ journal = RunJournal(run_id, events_path=output_dir/events.jsonl)
    │   ├─ context = RunContext(run_id, thread_id, ..., budget={},
    │   │                       output_dir, enabled_middlewares, journal)
    │   ├─ record = RunRecord(status=PENDING, created_at=updated_at=now,
    │   │                      model_name ← 参数 | config.models.researcher_model,
    │   │                      metadata={"expert_mode": ...})
    │   ├─ _contexts[run_id] = context
    │   ├─ _records[run_id] = record
    │   ├─ _write_record(record)                 ← 首次写盘
    │   └─ return context
    │
    ├─ mark_running(run_id) -> RunRecord         ← PENDING → RUNNING
    │   ├─ replace(record, status=RUNNING,
    │   │         started_at=record.started_at or now, updated_at=now)
    │   ├─ _store_record(updated)                ← 内存 + 写盘
    │   └─ journal.append("run.started", {expert_mode})
    │
    ├─ mark_success(run_id, usage_summary) -> RunRecord ← RUNNING → SUCCESS
    │   ├─ replace(record, status=SUCCESS, updated_at=now, finished_at=now,
    │   │         total_tokens ← usage.get("total_tokens", record.total_tokens))
    │   ├─ _store_record(updated)
    │   └─ journal.append("run.finished", usage)
    │
    ├─ mark_failed(run_id, error) -> RunRecord   ← RUNNING → ERROR
    │   ├─ replace(record, status=ERROR, updated_at=now, finished_at=now, error=error)
    │   ├─ _store_record(updated)
    │   └─ journal.append("run.failed", {"error": error})
    │
    ├─ get_run(run_id) -> RunRecord | None       ← 按 id 取记录，不存在返回 None
    │
    ├─ _store_record(record)                     ← 更新内存 + 写盘
    │   ├─ _records[run_id] = record
    │   └─ _write_record(record)
    │
    ├─ _write_record(record)                     ← 序列化写入 context.record_path
    │   ├─ context = _require_context(run_id)
    │   ├─ context.output_dir.mkdir(parents=True, exist_ok=True)
    │   └─ record_path.write_text(json.dumps(record.to_dict(), ...))
    │
    ├─ _require_record(run_id) -> RunRecord      ← 取记录；缺失抛 KeyError
    │
    └─ _require_context(run_id) -> RunContext    ← 取上下文；缺失抛 KeyError
```

### 0.2. 运行时调用树（一次 run 的生命周期）

```
① 创建运行
调用方（CLI / bootstrap / app 层）
    └─ RunManager.create_run(thread_id, ..., thread_dir)
          ├─ _make_run_id()                    ← 缺省生成 run_id
          ├─ 计算 output_dir                    ← thread_dir/runs/{id} 或 logs_root/{id}
          ├─ RunJournal(run_id, events_path)   ← journal 模块
          ├─ RunContext(...)                   ← run_context 模块
          ├─ RunRecord(status=PENDING)         ← run_record 模块
          ├─ _contexts / _records 写入内存
          ├─ _write_record(record)
          │     ├─ _require_context(run_id)
          │     ├─ mkdir(output_dir)
          │     └─ record_path.write_text(json) ← 落盘 record.json
          └─ return RunContext

② 标记运行中
    └─ RunManager.mark_running(run_id)
          ├─ _require_record(run_id)
          ├─ replace(record, status=RUNNING, started_at, updated_at)
          ├─ _store_record(updated) → _write_record
          └─ journal.append("run.started", {expert_mode})

③ 成功 / 失败终结
    ├─ RunManager.mark_success(run_id, usage_summary)
    │     ├─ replace(..., status=SUCCESS, finished_at, total_tokens)
    │     ├─ _store_record(updated) → _write_record
    │     └─ journal.append("run.finished", usage)
    │
    └─ RunManager.mark_failed(run_id, error)
          ├─ replace(..., status=ERROR, finished_at, error)
          ├─ _store_record(updated) → _write_record
          └─ journal.append("run.failed", {"error": error})

④ 查询
    └─ RunManager.get_run(run_id) → RunRecord | None

═══════════ 状态机 ═══════════
PENDING ──mark_running──▶ RUNNING ──mark_success──▶ SUCCESS
                                     └─mark_failed──▶ ERROR
```

### 0.3. 补充

**`run_manager.py` 是运行生命周期的调度中心——创建 run 时同时装配 RunContext / RunRecord / RunJournal 并落盘，之后通过 mark_* 推进状态，每次变更都写盘并记事件。**

几点补充：

- **三件套同时装配**：`create_run` 一次性组装 `RunContext`（上下文）、`RunRecord`（记录）、`RunJournal`（事件日志），三者以 `run_id` 关联。
- **状态单向推进**：`PENDING → RUNNING → SUCCESS / ERROR`，用 `dataclasses.replace` 生成新 `RunRecord`（frozen），不改原实例。
- **每次变更都持久化**：`_store_record` 同时更新内存与写盘，保证内存与磁盘一致；`record.json` 落在 `context.record_path`。
- **双映射严格校验**：`_require_record` / `_require_context` 缺失即抛 `KeyError`，避免静默错误。
- **输出目录两种规则**：有 `thread_dir` 时按线程组织（`runs/{run_id}`），否则回退到 `logs_root/{run_id}`。
- **时间戳职责分离**：`created_at` / `updated_at` 等用 `utc_now_iso()`（UTC），而 `run_id` 内嵌的是东八区时间戳（`_CST`），两者用途不同。
- **journal 与 record 分工**：`record.json` 存状态快照，`events.jsonl` 存事件流，互为补充。

## 1. `create_run`

```
    def create_run(
        self,
        thread_id: str,
        user_id: str | None = None,
        run_id: str | None = None,
        session_id: str | None = None,
        trace_id: str | None = None,
        model_name: str | None = None,
        thread_dir: Path | None = None,
    ) -> RunContext:
```

### 1.1. `create_run` 的参数是"运行元信息"，不是"执行依赖"

`RunManager` 的职责是**管理 run 的生命周期与记录**，不是**执行 run**。所以它需要的只是：

- **标识类**：`thread_id` / `user_id` / `run_id` / `session_id` / `trace_id`
- **记录类**：`model_name`（写进 `RunRecord.model_name`，用于记录"这次用了哪个模型"）
- **落盘位置**：`thread_dir`（决定输出目录）

它**不需要** Lead Agent、graph、capability_registry 这些"执行依赖"，因为 `RunManager` 从不调用它们——它只创建上下文、推状态、写盘。

### 1.2. 那 Lead Agent 在哪？——通过 `RunContext` 挂载

注意 `create_run` 返回的是 **`RunContext`**，而不是 `RunRecord`。`RunContext` 才是运行期各组件共享的上下文容器。从 `create_run` 的构造看，它已经装了：

```python
context = RunContext(
    run_id=..., thread_id=..., user_id=..., session_id=..., trace_id=...,
    config=self.config,              # ← AppConfig（含全部配置）
    budget={},
    output_dir=output_dir,
    enabled_middlewares=self.config.middleware.enabled,
    journal=journal,
)
```

这里已经有 `config`（整个 `AppConfig`）。**Lead Agent 之类的对象很可能是在 `RunContext` 里以字段形式挂载，或者在 `create_run` 之外、由 bootstrap/app 层装配后注入 `RunContext`。** 你之前看的 `_ReportRuntime` Protocol 就是线索：

```python
class _ReportRuntime(Protocol):
    leader_agent: Any
    thread_id: str
    capability_registry: Any
    thread_dir: Path
    config: Any
```

这说明**运行期确实有一个对象同时持有 `leader_agent` / `capability_registry` / `thread_dir` / `config` / `thread_id`**——它的形状和 `RunContext` + `RunManager` 的组合高度吻合（`thread_dir` 对应 `output_dir`，`thread_id`/`config` 已在 `RunContext` 里，`leader_agent`/`capability_registry` 则可能挂在 `RunContext` 上或由更高层的 AppRuntime 持有）。

### 1.3. 谁负责把 Lead Agent 接进来？

**装配发生在更上层**：

- `poirot/backend/app/bootstrap.py` — 应用启动时构造
- 某个 **AppRuntime** — 持有 `leader_agent`、`capability_registry`，并**拥有** `RunManager` / `RunContext`

也就是说：

```
AppRuntime（app 层）
├─ leader_agent            ← Lead Agent
├─ capability_registry     ← 能力注册表
├─ config: AppConfig
└─ RunManager              ← 运行管理
      └─ create_run() → RunContext   ← 只装配"运行元信息 + config + journal"
```

**Lead Agent 不经过 `create_run` 传参，而是在 AppRuntime 层与 RunManager/RunContext 并存或注入。**

### 1.4. 那 `model_name` 为什么只传名字？

因为 `RunManager` 只需要"记录这次运行用了哪个模型名"用于展示/统计，**不需要模型实例**（模型实例由 `ModelRouter` 构造、由 Lead Agent 使用）。这是"记录层"与"执行层"的解耦。

### 1.5. 需要确认的一点

上面关于"Lead Agent 挂在 RunContext 还是 AppRuntime"是**基于间接线索的推断**，不是从 `run_context.py` 直接看到的结论。要确认，需要看：

- **`run_context.py`** — 看 `RunContext` 字段里是否含 `leader_agent` / `capability_registry`
- **`app/bootstrap.py`** 或某个 AppRuntime — 看它在哪构造 Lead Agent、如何与 RunManager 关联

### 1.6. 小结

| 问题 | 回答 |
|---|---|
| `create_run` 只需要 `model_name` 够吗？ | 对 `RunManager` 的职责（记录+生命周期）而言**够**；执行依赖不归它管 |
| Lead Agent 这些配置不需要吗？ | **需要，但不从这里传**。它们由上层（AppRuntime/bootstrap）装配，通过 `RunContext` 或 AppRuntime 挂载 |
| 为什么 `model_name` 是名字不是实例？ | 记录层只需名字；实例由 `ModelRouter` 构造、Lead Agent 使用 |
| 怎么确认 Lead Agent 挂在哪？ | 看 `run_context.py` 与 app 层的 bootstrap/AppRuntime |

`create_run` 造的是"运行的壳"（元信息 + config + journal + 输出目录），Lead Agent 等"执行内脏"由上层装配后挂到 `RunContext` 或 AppRuntime 上——两者职责分离，不是遗漏。
