---

name: 模型提供者配置 — 从 ProviderProfile 解析 ProviderConfig，并构造 ChatModel。

description: 

【【整体职责】
负责 provider 维度的配置解析与模型构造：读取环境变量把 ProviderProfile 解析为
ProviderConfig（含 key / base_url / model / 优先级 / 窗口），提供按 provider 或按角色
（researcher / reporter / reflection）的选择与路由，并最终按 provider kind 分发构造
BaseChatModel。

【内容摘要】
- ProviderConfigError       : provider 配置缺失或非法时抛出。
- ProviderConfig            : 单个 provider 的解析后配置（frozen）。
- _resolve_profile          : 从 ProviderProfile 读 env，解析为 ProviderConfig。
- _all_configs              : 解析全部 profile 为 ProviderConfig（含 disabled）。
- select_provider_config    : 按 provider 或默认优先级选择配置（可覆盖 model）。
- get_provider_config       : 按 provider 名取配置。
- _find_provider            : 在候选中按名查找，找不到则抛错。
- MODEL_ROUTES              : 角色 → provider 偏好链（链尾恒含 deepseek 兜底）。
- discover_available_providers : 返回 enabled 且 key 非空（或免 key）的 provider，按 priority 升序。
- _is_no_key                : provider 是否免 API key（fake / ollama）。
- route_chain_for           : 按角色路由链筛 provider，保证 deepseek 兜底。
- build_chat_model          : * 按 provider kind 构造 BaseChatModel。

【职责边界】
- 只负责：provider 配置解析、选择、路由，以及 ChatModel 的构造。
- 不负责：ProviderProfile 的定义（provider_profile）、环境变量名声明（profile）、
  模型路由的上层决策（model_router）、配置 Schema（schema）。

## 0. 结构树

### 0.1. 静态结构树

```
provider_config.py — 模型提供者配置（解析 + 选择 + 路由 + 构造）
│
├─ ProviderConfigError(ValueError)              ← provider 配置缺失或非法时抛出
│
├─ ProviderConfig(frozen)                       ← 单个 provider 的解析后配置
│   ├─ provider: str                            ← provider 名称
│   ├─ model: str                               ← 模型名
│   ├─ api_key: str                             ← API key（免 key provider 可为空）
│   ├─ base_url: str | None                     ← 自定义 base URL；无则 None
│   ├─ priority: int                            ← 优先级，数值越小越优先
│   ├─ default: bool                            ← 是否为默认 provider
│   ├─ enabled: bool                            ← 是否启用
│   ├─ window: int = 0                          ← 上下文窗口（token），0=未知
│   └─ require_api_key() -> str                 ← 校验并返回 api_key；为空抛错
│
├─ _resolve_profile(profile) -> ProviderConfig  ← 从 ProviderProfile 读 env 解析
│   │                                              每个 provider 支持 {NAME}_ENABLED=false
│   ├─ api_key    ← os.environ[profile.env_key]
│   ├─ base_url   ← env_base_url | profile.default_base_url
│   ├─ model      ← env_model | profile.default_model
│   └─ enabled    ← {NAME}_ENABLED != "false"
│
├─ _all_configs() -> list[ProviderConfig]       ← 解析全部 profile（含 disabled）
│
├─ select_provider_config(provider, model)      ← 选择配置（可覆盖 model）
│   ├─ 过滤 enabled                              ← candidates
│   ├─ provider 指定 → _find_provider
│   ├─ 未指定 → default / priority 排序取首
│   └─ model 非空 → 复制并覆盖 model
│
├─ get_provider_config(provider) -> ProviderConfig ← 按 provider 名取配置
│
├─ _find_provider(candidates, provider)         ← 按名查找；找不到抛 ProviderConfigError
│
├─ MODEL_ROUTES: dict[str, list[str]]           ← 角色 → provider 偏好链（链尾含 deepseek）
│   ├─ "researcher" → [openai, qwen, anthropic, gemini, deepseek]
│   ├─ "reporter"   → [qwen, deepseek]
│   └─ "reflection" → [deepseek]
│
├─ discover_available_providers() -> list       ← enabled 且 key 非空（或免 key），按 priority 升序
│
├─ _is_no_key(provider) -> bool                 ← provider 是否免 API key（fake / ollama）
│
├─ route_chain_for(role, providers) -> list     ← 按角色路由链筛 provider，保证 deepseek 兜底
│   ├─ role 未配置 → ["deepseek"]                ← 默认链
│   ├─ 链空或尾非 deepseek 且可用 → 追加 deepseek ← 兜底
│   └─ 链空 → 抛 ProviderConfigError
│
└─ build_chat_model(config) -> BaseChatModel    ← 按 provider kind 分发构造 ChatModel
    ├─ kind == "deepseek"       → ChatDeepSeek
    ├─ kind == "openai_compat"  → ChatOpenAI
    ├─ kind == "anthropic"      → ChatAnthropic（包缺失抛错提示安装）
    ├─ kind == "gemini"         → ChatGoogleGenerativeAI（同上）
    ├─ kind == "ollama"         → ChatOllama（同上）
    ├─ kind == "fake"           → FakeListChatModel
    └─ unknown kind             → 抛 ProviderConfigError
```

### 0.2. 运行时调用树

```
① 配置选择（按 provider 或按默认）
调用方（model_router / loader）
    └─ select_provider_config(provider, model)
          ├─ _all_configs()
          │     └─ _resolve_profile(profile) × N   ← 逐个读 env 解析
          ├─ provider 指定 → _find_provider(candidates, provider)
          └─ model 覆盖 → 复制 ProviderConfig

② 智能路由（按角色选链）
调用方（model_router）
    ├─ discover_available_providers()
    │     ├─ _all_configs()
    │     └─ _is_no_key(provider) → get_provider_profile
    └─ route_chain_for(role, providers)
          ├─ 按 MODEL_ROUTES[role] 筛 by_name
          └─ 保证 deepseek 在链尾（若可用）

③ 构造 ChatModel
调用方（model_router / fallback_model）
    └─ build_chat_model(config)
          ├─ get_provider_profile(config.provider) → profile.kind
          ├─ profile.no_key_required 为假 → config.require_api_key()
          └─ 按 kind 分发 import 并实例化
                └─ optional provider 包缺失 → 抛 ProviderConfigError（提示安装）

④ 免 key 判定
_is_no_key(provider)
    └─ get_provider_profile(provider).no_key_required
```

### 0.3. 补充

**`provider_config.py` 是 provider 维度的"解析 + 选择 + 路由 + 构造"中枢——把 profile 声明翻译为可用配置，按角色选出 provider 链，并最终实例化 LangChain ChatModel。**

几点补充：

- **延迟读 env 是测试友好设计**：环境变量在 `_resolve_profile` 内读取，而非模块加载时，便于 `monkeypatch` 覆盖。
- **三类选择入口**：`select_provider_config`（按名/默认）、`route_chain_for`（按角色）、`discover_available_providers`（列可用），覆盖不同上层需求。
- **deepseek 是硬兜底**：`MODEL_ROUTES` 链尾恒含 deepseek，`route_chain_for` 再显式保证其位于链尾，形成路由安全网。
- **kind 分发是构造核心**：`build_chat_model` 按 `profile.kind` 分发到不同 LangChain 实现，optional 依赖缺失时给出明确的安装提示。
- **免 key 白名单**：fake / ollama 经 `no_key_required` 跳过 key 校验，用于本地与测试场景。
- **frozen 保证可共享**：`ProviderConfig` 不可变，`model` 覆盖通过构造新实例实现，不修改原对象。


## 1. LangChain 在模型调用中做了什么、没做什么

**问题**：从模型厂商的 LLM 接收信息到拿到包装好的对象，信息处理是否都已由 LangChain 完成，只需拿对象即可？

**结论**：基本成立，但需精确区分"协议封装"与"业务处理"两个层次。

### 1.1. LangChain 做了的（协议层与抽象层统一）

`build_chat_model` 返回的对象（`ChatDeepSeek` / `ChatOpenAI` / `ChatAnthropic` ...）均继承自 `BaseChatModel`，替你统一了：

- **请求构造与鉴权**：组装 `api_key` / `base_url` / `model`，处理鉴权头、重试、超时。
- **厂商协议差异**：抹平各家请求/响应字段差异（如 OpenAI 与 Anthropic 的 `messages` 结构差异）。
- **返回值统一抽象**：无论哪家，返回统一为 **`AIMessage`**（`BaseMessage` 子类），`.content`、`.tool_calls`、`.usage_metadata` 等字段标准化。
- **流式输出**：`.stream()` / `.astream()` 把各家 SSE 差异统一为逐 chunk 的 `AIMessageChunk`。
- **工具调用**：把各家 function calling 格式归一为 `tool_calls`。

即：**你只负责构造对象 + 发消息，厂商交互细节被 LangChain 封装。**

### 1.2. LangChain 没做的（业务层与治理层）

1. **不做业务级信息处理**：不解析领域语义、不摘要、不抽证据、不判断成功与否——这些是 Poirot 中间件 / summarizer 的职责。
2. **不保证高级能力完全对齐**：prompt caching、reasoning content、多模态等各家支持度不同，LangChain 只做尽力归一；`usage_metadata` 各家填写不完整（对应 Poirot 中 `TokenUsage` 可选、None 表示未上报）。
3. **不做准确的 token 计数与窗口管理**：窗口大小、token 估算仍需项目自维护（对应 `default_window` / `resolve_window_size` / `_MODEL_WINDOW_MAP`）。
4. **不管理上下文**：裁剪、摘要、外置化由 `context_engineering` 层负责；超窗由厂商报错，LangChain 不管。
5. **不做重试之外的容错策略**：降级到 fallback model、切换 provider 链由 `model_router` / `fallback_model` 实现。

### 1.3. 一句话总结

> **"从厂商 LLM 接收信息到拿到 LangChain 包装对象"这一段，LangChain 确实替你做完了——只需拿对象、调 invoke/stream、拿回统一的 `AIMessage`。但"信息处理"（业务语义、上下文治理、token 预算、容错降级、结果校验）仍是项目自己的活，LangChain 只保证协议层与消息抽象层的统一。**

### 1.4. 对本项目的实际含义

Poirot 在 `build_chat_model` 之上叠加了 `model_router`、`fallback_model`、`resolve_window_size`，处理的正是 **LangChain 封装层之下的"策略与治理"问题**。若 LangChain 连这些也包了，这几个模块便无存在意义。因此：

- **封装层（LangChain）**：协议统一、消息抽象、厂商调用。
- **治理层（Poirot）**：路由、降级、窗口预算、上下文管理、业务语义处理。
