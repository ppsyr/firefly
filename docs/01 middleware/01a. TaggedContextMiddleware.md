作用：
把送往 LLM 的上下文渲染成「扁平 XML 标签序列 + `<turn>` 时序分组」。
渲染是 request-scoped 的：只在本次模型调用内生效，不落盘、不持久化。
state 中始终保存原始 message content 与 additional_kwargs 标记，
渲染只是「读取并改写」，不回写原始数据。

1. 上下文分层与筛选
   头部块（goal/plan/reflection/summary）和对话历史是分开渲染的。压缩、裁剪时可以按标签粒度操作——比如丢掉旧 turn、只保留 summary，而不是去解析嵌套结构。这是为「压缩筛选」铺路的。
2. 幂等 + trace 审计
   `additional_kwargs` 里的 `poirot.*` 标记，让同一份渲染结果可复现、可审计（`after_model` 会把渲染快照写进 `state.tagged_context`）。这不是格式问题，是可观测性问题。
3. 给 LLM 一个稳定的语义结构
   `<thinking>` / `<answer>` / `<toolcall>` / `<toolresult>` 这些标签，是在**引导模型按固定角色理解历史**——哪段是它的推理、哪段是最终答复、哪段是工具输出。这会影响模型行为，不只是「换个皮」。
4. 角色保留 vs 压平的取舍（方案 H）
   代码里特意区分了两条渲染路径：`render_messages`（纯字符串，给 trace）和 `render_messages_for_llm`（保留 message 角色，只改 AI content）。这个取舍是有意为之的工程决策，涉及多轮工具调用场景下模型能不能正确对齐 tool_call / tool_result。

> 它的表层是「格式转换」，实质是「**上下文组织策略**」——决定 LLM 看到什么、以什么结构看到、哪些被丢弃、哪些被标记。格式只是这个策略的呈现方式。

**state（LangGraph 的状态）**
- 是持久的、跨轮次保留的。
- 里面存的是**原始 message 对象**：`HumanMessage` / `AIMessage` / `ToolMessage`，各自带着原始 `content` 和 `additional_kwargs`（比如 `poirot.thinking`、`poirot.externalized` 这些标记）。
- 这是「源头数据」。

**渲染结果（组装出来的 XML 文本 / 改写后的 messages）**
- 是**临时算出来的**，为了这一次调用 LLM 而生成。
- 生成完就用来发请求，**不写回 state**。
- 这是「派生视图」。

│   ├─ POIROT_SUMMARY               ← HumanMessage 是摘要消息

│   ├─ POIROT_EXTERNALIZED_PATH     ← 外置结果存储路径

│   │
│   ├─ 【头部上下文块】────────────────────────────

│   │   ├─ _render_reflection(state)             ← 最近 N 条 reflection_items

│   │   └─ _current_date()                       ← 东八区日期

│   ├─ render_messages(messages)                 ← <turn id=N> 时序分组

│   │   ├─ AIMessage                → <thinking> / <toolcall> / <answer>
│   │   └─ ToolMessage              → <toolresult>（externalized 带 path/tokens）
│   │
│   ├─ 【消息渲染 — 真正送 LLM，方案 H】────────────
│   ├─ render_messages_for_llm(messages)         ← 保留角色，只改写 AIMessage
│   │   ├─ SystemMessage            → 跳过（提取进 <system>）
│   │   ├─ HumanMessage summary     → 跳过

### 0.2. 运行时调用树（真正跑一次模型调用）

```
LLM 调用触发
│
├─ TaggedContextMiddleware.wrap_model_call(request, handler)      ← 同步路径
│   │   （或 awrap_model_call → await handler）
│   │
│   └─ _assemble(request)
│       ├─ state           = request.runtime.state
│       ├─ messages        = request.messages
│       ├─ system_text     = _extract_system(messages)
│       │
│       ├─ context_block   = assembler.render_context_block(state, governance)
│       │   ├─ _render_plan(todos)
│       │   ├─ _render_reflection(state)
│       │   ├─ _render_summary(governance)
│       │   └─ _current_date()
│       │
│       ├─ if system_text:
│       │     context_block = "<system>…</system>\n\n" + context_block
│       │
│       ├─ rewritten = assembler.render_messages_for_llm(messages)
│       │   └─ (逐条) AIMessage → _rewrite_ai_message(msg)
│       │         ├─ additional_kwargs[poirot.thinking] → reasoning_content → <thinking>
│       │         ├─ _extract_text(msg)                → <answer>
│       │         └─ model_copy(update={"content": ...})
│       │
│       ├─ new_messages = [SystemMessage(context_block)] + rewritten
│       └─ return request.override(messages=new_messages)
│
├─ handler(assembled)                                             ← 真正发 LLM
│
└─（LLM 返回后）
    TaggedContextMiddleware.after_model(state, runtime)
    ├─ messages       = state.messages
    ├─ system_text    = _extract_system(messages)
    ├─ context_block  = render_context_block(...) + <system>
    ├─ messages_trace = render_messages(messages)                 ← 纯字符串 <turn> 分组
    │   └─ (逐条) HumanMessage / AIMessage / ToolMessage → 对应标签
    └─ return {"tagged_context": {rendered, created_at}}
```

## 1. 「扁平 XML 标签序列」

传统做法里，对话上下文可能是嵌套的 JSON 结构，比如：

```json
{
  "context": {
    "goal": "...",
    "plan": { "todos": [...] }
  },
  "messages": [
    { "role": "user", "content": "..." },
    { "role": "assistant", "content": "...", "tool_calls": [...] }
  ]
}
```

而这里的做法是**不嵌套**，把所有信息拍平成一层层并列的 XML 标签，直接顺序排列：

```xml
<goal>研究 XXX 问题</goal>
<plan>
[>] 收集资料
[x] 初步分析
</plan>
<reflection>
- [open] scope/kind: 某疑问
</reflection>
<summary>
之前对话的摘要...
</summary>
<date>2026-09-17, Thursday</date>

<turn id="1">
<message role="user">帮我查一下...</message>
</turn>

<turn id="2">
<thinking>我需要先调用搜索工具</thinking>
<toolcall name="search" args="{'query': '...'}"/>
<answer>根据搜索结果...</answer>
<toolresult name="search">返回的内容...</toolresult>
</turn>
```

所谓「扁平」，就是**没有深层嵌套结构**，LLM 看到的就是一串平铺的标签，从上到下读。这么做的好处：
- LLM 对 XML 标签边界识别比 JSON 更稳（尤其长上下文里不容易漏括号）。
- 每个标签语义自解释，方便模型定位「哪段是目标、哪段是计划、哪段是历史」。
- 压缩/筛选时按标签粒度裁剪即可，不用解析嵌套树。

## 2. 「`<turn>` 时序分组」

上面的标签序列里，**普通对话消息**不是散着放的，而是按「轮次」用 `<turn id="N">...</turn>` 包起来：

- 一条普通 `HumanMessage`（用户发话）= 开启一个新 turn。
- 紧随其后的 AI 回复、思维链、工具调用、工具结果，都归到这个 turn 里面。
- 下一条用户消息来了，就关掉上一个 `</turn>`，开新 turn。

对应到代码里的逻辑：

```python
if isinstance(msg, HumanMessage):
    if turn_open:
        lines.append("</turn>")   # 关上一个 turn
    turn_id += 1
    lines.append(f'<turn id="{turn_id}">')  # 开新 turn
    turn_open = True
```

末尾还会补一个 `</turn>` 收尾。这样做的意义：

- **给对话历史一个明确的时间线结构**：LLM 能清楚看到「第 1 轮用户问了什么、AI 做了什么、工具返回了什么；第 2 轮又问了什么」。
- **工具调用/思维链不会和用户消息混淆**：它们都被圈在同一个 turn 内，而不是和用户消息平级乱放。
- **便于按轮裁剪**：压缩历史时可以整轮丢弃或整轮保留，边界清晰。

> 送给 LLM 的不是原始 message 对象数组，而是**一个用 XML 标签平铺写成的文本块**：头部是 goal/plan/reflection/summary/date 这类全局上下文，后面是按「用户每发一次话」切分出的一个个 `<turn>` 分组，组内依次是用户消息、思维链、工具调用、回答、工具结果。

这就是「扁平 XML 标签序列 + `<turn>` 时序分组」的意思。


这句话在讲一个很关键的**数据边界**问题：**渲染出来的东西是「临时视图」，state 里的原始数据才是「唯一真相」**。逐句拆。



## 3. 「渲染只在本次模型调用内生效」

`request-scoped` = 作用域限定在「一次模型调用请求」内。
每次 `wrap_model_call` 被触发（即每次要调 LLM），middleware 才**现场**从 state 读数据、渲染一份上下文。这次调用结束，这份渲染结果就丢了。下一次调用会**重新渲染一遍**。它不是常驻的、不是缓存的。

> **不落盘、不持久化**

渲染结果不会写进数据库、不会存进 state、不会作为快照长期保留（`after_model` 里写 `state.tagged_context` 是**另一条** trace 路径，属于审计用途，跟送 LLM 的那份不是同一个东西）。
所以你在持久层里**找不到**那串 XML 标签，它只存在于「从组装到发请求」这段短暂的内存生命周期里。

> **state 中始终保存原始 message content 与 additional_kwargs 标记**

state 里从头到尾存的都是**原始数据**，没有被渲染「污染」：
- message 的 `content` 还是原始文本（不是包了 `<answer>` 的版本）；
- `additional_kwargs` 里的 `poirot.*` 标记原样保留。

**关键点**：`_rewrite_ai_message` 里用了 `msg.model_copy(update={"content": new_content})`——是**复制一份再改**，没有原地修改原对象。所以原始 AIMessage 在 state 里毫发无损。

> **渲染只是「读取并改写」，不回写原始数据**

- **读取**：从 state 的 messages 和字段里读。
- **改写**：生成一份**新的** messages 列表 / 新的 XML 字符串（`request.override(messages=new_messages)` 也是产出一个新 request，不动原 request）。
- **不回写**：这些新东西不会替换 state 里的原始数据。

### 为什么要这么设计

一句话：**原始数据是真相，渲染是按需生成的投影。**

好处有三：

1. **可重放 / 可复现**
   原始数据不变，任何时候重新渲染都能得到一致的上下文（幂等）。如果渲染结果回写了 state，改一次就污染一次，越滚越乱。

2. **多消费者共享同一份真相**
   state 里的原始 message 不只给这个 middleware 用：ReflectionMiddleware 要看反思项、压缩逻辑要筛消息、trace 要审计。如果渲染把原数据改写了，其他消费者就拿不到干净数据了。

3. **渲染策略可随时改**
   因为原始数据没被动过，你明天想换一套标签格式、换一种渲染顺序，只要改渲染函数即可，历史数据不用迁移。

### 一个类比

把 state 想成**原始录音文件**，渲染结果想成**每次播放时实时生成的带字幕画面**：
- 录音文件一直躺在硬盘上，不动。
- 每次播放（每次调 LLM）现场生成字幕叠上去（渲染）。
- 关掉播放器，字幕就没了（不持久化）。
- 你改字幕样式（改渲染逻辑），录音文件不用重录（原始数据不变）。

### 一个容易混淆的点

代码里 `after_model` 会写 `state.tagged_context`，看起来像「渲染结果落盘了」。但要注意：

- `wrap_model_call` / `_assemble` 生成的那份（真正送 LLM 的），**不落盘**。
- `after_model` 是**另起炉灶**，从 `state.messages` **重新渲染一遍**，写进 `tagged_context` 做审计。

两者内容可能相似，但**用途不同、生成时机不同**：一个用于发请求，一个用于留痕。所以「不落盘」说的是前者，别跟后者混为一谈。


## 4. KV Cache

### 设计不会破坏 KV Cache

KV Cache（以及服务端的上下文缓存）命中要求输入前缀**从第 0 个 token 开始完全相同**。渲染逻辑保证了这一点：

1. **`<system>` 块稳定**：从 `request.messages` 提取的 SystemMessage 文本，只要系统提示词不变，渲染出的 `<system>` 内容就不变。
2. **头部上下文块稳定**：`<goal>`、`<plan>`、`<reflection>`、`<summary>` 这些字段在两次请求之间通常不会突变。即使有更新（比如 todo 状态变化），变化的也是尾部，前缀依然可命中。
3. **`<date>` 是唯一潜在“污染源”**：它输出的是东八区日期（精确到天）。同一天内的多次请求，`<date>` 不变，前缀稳定。跨天时会有一次缓存未命中，但只影响当次请求。

这正好符合 KV Cache 的命中规则：前缀一致即命中，后续新增的 `<turn>` 内容走增量计算。

### 需要担心的是

渲染方式会让**每一轮对话都在尾部追加新的 `<turn>`**。这意味着：

- **多轮对话场景**：第 N 轮请求的前缀 = 第 N-1 轮请求的前缀 + 上一轮的完整内容。前缀是**递增**的，因此每一轮都能命中上一轮缓存的部分。
- **风险点**：如果某轮渲染时，历史消息的**任何位置**发生了变化（比如 `_render_reflection` 的 `max_reflections` 截断导致早期 reflection 被丢弃），那么被丢弃位置之后的前缀全部失效。

 `render_messages` 和 `render_messages_for_llm` 都是**从同一条消息列表顺序渲染**的，只要 `state.messages` 的增量追加模式不变（只追加新消息，不修改旧消息），前缀就是稳定的。


`render_context_block` 每次都在**头部**插入 `<goal>`、`<plan>` 等标签。如果这些字段的内容发生变化（比如 plan 的某条 todo 状态从 `in_progress` 变成 `completed`），那么 `<plan>` 标签内的文本就变了，**从变化点开始的前缀全部失效**。

这不是 bug，而是 KV Cache 的固有约束：**任何前缀内的修改都会导致缓存失效**。设计在“状态不频繁变化”的场景下缓存友好，在“每轮都更新 plan”的场景下会持续 miss。

### 实操建议

如果想最大化缓存命中率：

1. **把稳定内容前置**：你的 `<system>` 已经在最前，这是对的。
2. **考虑把 `<date>` 移到末尾或去掉**：它每天变化一次，是唯一“非状态驱动”的前缀扰动源。如果不需要日期信息，去掉后跨天也不会失效。
3. **plan/reflection 的更新频率**：如果这些字段每轮都变，缓存命中率会受影响。但这是业务逻辑问题，不是渲染格式的问题。

渲染格式**本身不破坏 KV Cache**。真正决定命中率的是：渲染输出的前缀在两次请求之间是否保持一致。
