---

name: MemoryConsolidationMiddleware — aafter_model 每 N 轮非阻塞触发记忆沉淀（L5）。

description:

【整体职责】
在每次模型调用结束后（after_model），按「用户轮次」计数；每到 N 的倍数
就构造一个沉淀任务（MemoryTask）丢给后台 worker 异步处理，本中间件立即
返回、不阻塞主流程。

【挂载位置】
MemoryMiddleware 之后（召回在前，沉淀在后）。

【设计要点】
- 不阻塞：worker.submit(task) 后立即 return None，真正处理由 worker 异步完成。
- 不抽取全量历史：只取最近 N*2 条 messages（N 轮 ≈ 2N 条 message），
  避免 token 爆炸。
- 轮次计数只算 HumanMessage（用户轮次），tool / AI / memory_recall 等
  不计入。

【INVARIANT（必须保持的不变量）】
- 仅 aafter_model 触发（abefore_model 为 no-op）。
- turn_count % N == 0 才触发（非 N 的倍数不 submit）。
- submit 后立即 return None（worker 异步处理）。
- messages 截断到最近 N*2 条（避免 token 爆炸）。

## 1. 记忆沉淀每一步具体怎么实现

这里说的「沉淀」指**本中间件负责的那一段**：判定时机 → 截取数据 → 打包成任务 → 交给 worker。真正的 LLM 抽取 / 写库在 worker 侧，本文件看不到，下面会标注边界。

### 步骤 1：取 messages

```python
messages = state.get("messages", []) or []
```

- 从当前 state 里取对话消息列表。
- `or []` 兜住 None，保证后面 `sum(...)` 与切片不会炸。

### 步骤 2：统计用户轮次（只数 HumanMessage）

```python
user_turn_count = sum(1 for m in messages if isinstance(m, HumanMessage))
```

- 轮次口径是「用户说了几轮」，所以只数 `HumanMessage`。
- `ToolMessage`、`AIMessage`、以及 `MemoryMiddleware` 注入的
  `HumanMessage(name="memory_recall")` 都会计入 HumanMessage 吗？
  —— 会，因为它们的类型也是 HumanMessage。也就是说 recall 注入消息
  **会被算进轮次**。这是代码现状，注释里写的「不算 memory_recall」
  与实现有出入，这里只描述实现。
- 用 `sum(1 for ...)` 而不是 `len([...])`，省一次中间列表分配。

### 步骤 3：触发判定（每 N 轮一次）

```python
if user_turn_count == 0 or user_turn_count % self._n != 0:
    return None
```

- `self._n` 在 `__init__` 里已做 `max(1, trigger_every_n_turns)`，避免 0 导致除零。
- 两个短路条件：
  - `== 0`：一轮都没有，不必触发；
  - `% N != 0`：不是 N 的整数倍，不触发。
- 也就是**只在第 N、2N、3N… 轮**触发一次，天然节流。
- 返回 `None` 表示本 hook 不写 state，框架继续走下一步。

### 步骤 4：截断最近窗口（防 token 爆炸）

```python
recent = messages[-(self._n * 2):]
```

- 只取**最近 N*2 条** message。
- 取 N*2 的理由：一轮对话大约对应 2 条 message（一问一答），
  N 轮 ≈ 2N 条。这样既覆盖最近 N 轮，又不把全量历史丢给 worker。
- 切片用负数下标，messages 不足 N*2 条时自然取全部，不报错。

### 步骤 5：解析 thread_id（多级回退）

```python
thread_id = "unknown"
try:
    config = getattr(runtime, "config", None) or {}
    configurable = config.get("configurable", {}) if isinstance(config, dict) else {}
    thread_id = configurable.get("thread_id") or state.get("thread_id") or "unknown"
except Exception:
    thread_id = state.get("thread_id", "unknown")
```

- 优先级：
  1. `runtime.config["configurable"]["thread_id"]`（标准来源）；
  2. `state["thread_id"]`（回退）；
  3. 字面量 `"unknown"`（兜底）。
- 用 `getattr(..., None) or {}` + `isinstance(..., dict)` 两层保护，
  防止 runtime 形态不一致（测试 SimpleNamespace、LangGraph runtime）导致崩。
- 外层 `try/except` 再兜一层：即便取 runtime 抛异常，也能退回 state。
- thread_id 用于把沉淀结果挂到正确的会话线程上（worker 侧按它归档）。

### 步骤 6：构造任务并提交（非阻塞关键点）

```python
task = MemoryTask(
    thread_id=thread_id, messages=recent, turn_count=user_turn_count,
)
self._worker.submit(task)
```

- 把「哪条线程 + 最近哪些消息 + 当前第几轮」打包成 `MemoryTask`。
- `worker.submit(task)` 是**投递**语义，不是**执行**语义：
  任务进队列/线程池，worker 异步处理，本方法不等结果。
- 这就是「不阻塞」的实现方式：submit 后立刻往下走。

### 步骤 7：记 debug 日志并返回

```python
logger.debug(
    f"MemoryConsolidationMiddleware submitted task: "
    f"thread={thread_id} turn={user_turn_count}"
)
return None
```

- 只记 debug 级别，避免正常运行时刷日志。
- 返回 `None`：本 hook 不修改 state，沉淀产物由 worker 后续自行落库。

## 2. 边界说明：本文件到哪为止

| 环节 | 归属 | 本文件是否可见 |
|---|---|---|
| 何时触发（每 N 轮） | 本中间件 | 可见 |
| 截取哪些消息（最近 N*2） | 本中间件 | 可见 |
| 打包成 MemoryTask | 本中间件 | 可见 |
| 投递到 worker | 本中间件（submit） | 可见 |
| 实际 LLM 抽取记忆 | `MemoryWorker` | 不可见 |
| 写库 / 去重 / 合并 | `MemoryWorker` | 不可见 |
| 失败重试 / 幂等 | `MemoryWorker` | 不可见 |

所以「记忆沉淀的每一步」在本文件里是**前四步**；后三步在 `poirot.backend.agents.memory.worker` 里，需要看那个文件才能继续往下讲。需要的话我可以接着梳理 `MemoryWorker` 的结构树与 submit 之后的处理链。
