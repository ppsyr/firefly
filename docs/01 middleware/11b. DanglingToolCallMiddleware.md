---

name: DanglingToolCallMiddleware — 在 resume 时修补悬空的工具调用。

description:

【背景问题】
当 graph 因为 help request 或用户中断（interrupt）而恢复（resume）时，
历史里最后一条 AIMessage 可能带有一批 tool_calls，但并没有对应的
ToolMessage。这些「有 call 没有 result」的调用就是 dangling calls。
消息历史不完整会让严格后端直接返回 LLM 400 错误。

【整体职责】
在每次进入 model 之前（before_model）扫描消息历史，
为每个 dangling 的 tool_call 补一条「占位用的错误 ToolMessage」，
让 tool pairing 重新变得完整。

【模式来源】
借鉴 deer-flow DanglingToolCallMiddleware 模式。


---


## 0. 结构树

### 0.1. 静态结构树（模块 → 类 → 方法）

```
DanglingToolCallMiddleware — patch interrupted tool calls on resume
│
├─ 模块级常量
│   ├─ _MAX_RECOVERY_DETAIL_LEN = 500     ← 预留（本文件未使用）
│   └─ json / AIMessage / ToolMessage / Runtime / ThreadState 导入
│
└─ class DanglingToolCallMiddleware(AgentMiddleware)
    ├─ state_schema = ThreadState
    │
    ├─ _extract_tool_calls(msg) [static]   ← 从 AIMessage 提取 tool_calls（双形态兼容）
    │   ├─ 优先：msg.tool_calls（LangChain 规范位置）
    │   └─ 回退：additional_kwargs["tool_calls"]（OpenAI 原始形态）
    │       ├─ name = rtc.name or rtc.function.name or "unknown"
    │       └─ args = rtc.args or json.loads(rtc.function.arguments)
    │                  （解析失败 → {}）
    │

    │   └─ return {"messages": patch} | None
    │
    └─ abefore_model(state, runtime)       ← 异步：直接转调同步版
```

## 1. 修补悬空工具调用每一步具体怎么实现

### 步骤 1：取消息历史

```python
messages = state.get("messages") or []
if not messages:
    return None
```

- 从 state 拿消息列表；空则直接退出（没什么可补）。

### 步骤 2：收集「已应答」的 tool_call_id

```python
answered_ids: set[str] = set()
for msg in messages:
    if isinstance(msg, ToolMessage):
        answered_ids.add(msg.tool_call_id)
```

- 遍历所有 ToolMessage，把它们的 `tool_call_id` 收进集合。
- 这些 id 代表**已经有结果的工具调用**，一会儿要拿它判断谁悬空。
- 用 `set` 而不是 `list`：判定「是否已应答」是 O(1)。

### 步骤 3：扫描 AIMessage，找出 dangling call

```python
for msg in messages:
    if not isinstance(msg, AIMessage):
        continue
    calls = self._extract_tool_calls(msg)
    for tc in calls:
        tc_id = tc.get("id", "")
        if tc_id and tc_id not in answered_ids:
            patch.append(ToolMessage(...))
            answered_ids.add(tc_id)
```

- 只处理 AIMessage，其他类型跳过。
- `_extract_tool_calls` 把「工具调用声明」归一化取出，兼容两种存储位置：
  - LangChain 规范字段 `msg.tool_calls`；
  - OpenAI 原始形态 `msg.additional_kwargs["tool_calls"]`（回退）。
- 对每个 tool_call：
  - 只要 `id` 非空且不在 `answered_ids` 里，就判为 dangling。
  - `id` 为空时**跳过**（不能凭空造 id，否则配对更乱）。
- 每补一条就把 id 加进 `answered_ids`，避免同一 id 被多次补。

### 步骤 4：dangling call 的兼容解析

`_extract_tool_calls` 里对原始形态的解析：

```python
fn = rtc.get("function", {})
name = rtc.get("name") or fn.get("name", "unknown")
args = rtc.get("args", {})
if not args and isinstance(fn, dict):
    raw_args = fn.get("arguments", "{}")
    try:
        args = json.loads(raw_args) if isinstance(raw_args, str) else raw_args
    except (json.JSONDecodeError, TypeError):
        args = {}
calls.append({"id": rtc.get("id", ""), "name": name, "args": args})
```

- name 三级回退：`rtc.name` → `rtc.function.name` → `"unknown"`。
- args：优先 `rtc.args`；若为空则尝试把 `function.arguments`（字符串）`json.loads`。
  解析失败（非法 JSON / 类型不对）→ 落回 `{}`，绝不抛。
- 也就是说：**修补只需要 id + name**，args 只是顺带带上，补的 ToolMessage 里也不用。

### 步骤 5：构造占位 ToolMessage

```python
patch.append(ToolMessage(
    content="[Tool call was interrupted and did not return a result.]",
    tool_call_id=tc_id,
    name=tc.get("name", "unknown"),
))
```

- `content` 是固定文案，明确告诉 LLM「这次调用没结果」。
- `tool_call_id` 用 dangling call 的 id —— 这是配对的关键，
  只有 id 对上，消息历史才合法。
- `name` 用 tool_call 的 name（兜底 `"unknown"`），便于展示/审计。

### 步骤 6：返回补丁

```python
if not patch:
    return None
return {"messages": patch}
```

- 什么都没补 → 返回 None，不写 state，零副作用。
- 有补 → 返回 `{"messages": patch}`，框架把这几条 ToolMessage
  按顺序并入 `state.messages`。位置在末尾，紧跟在原悬空 AIMessage 之后，
  配对关系正确。

## 2. 修补后，这些工具调用会重新执行吗？

**不会。**

关键在于：本中间件补的是一条 `ToolMessage`，它代表的是**「这次工具调用的结果」**。
在 LangGraph / LangChain 的消息协议里：

- AIMessage 里声明 `tool_calls`
- 紧随其后必须有对应的 ToolMessage（同 `tool_call_id`）

一旦这条 ToolMessage 存在，**这次 tool_call 就被视为「已完成」**，
模型看到的是一个「调用过、有结果（结果是错误说明）」的历史，而不是
「待执行的调用」。所以：

| 层面 | 行为 |
|---|---|
| 消息协议 | 该 tool_call 已有对应 ToolMessage，配对完整 |
| 模型决策 | LLM 看到 tool 结果是「被中断，无结果」，据此决定下一步 |
| 工具执行 | **不会再触发该工具**；工具执行由「新的 tool_call」触发，不是由补的 ToolMessage 触发 |
| 后续选择 | 模型可以：重新发一次同名 tool_call（新 id）、换工具、或直接回答用户 |

换句话说：

- **补 ToolMessage ≠ 重放工具**。
- 它只是把「历史欠账」补上，让历史合法、让 LLM 不被 400 卡住。
- 真正的「要不要再调一次」由**模型的下一步输出**决定；
  如果它认为还需要这个工具，会**新发一个带新 id 的 tool_call**，
  那条才会真正执行。

这也正是文案写成「was interrupted and did not return a result」的原因：
给模型一个明确信号——上次没结果，你可以重试或换路。
