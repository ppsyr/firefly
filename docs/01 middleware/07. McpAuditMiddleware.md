---

name: MCP per-tool-call 审计中间件 — 熔断器 + 审计 + 外化联动标记。

description:

【整体职责】
在每次工具调用前后做三件事：
1. 熔断器检查：若该工具的 breaker 处于 open 状态，则不调用工具，
   直接返回一条 error ToolMessage，并记 circuit_open 事件。
2. 审计打点：把这次工具调用的关键信息（工具名、来源、参数摘要、状态、
   耗时、错误、是否外化）写入 journal（thread-events.jsonl）。
3. 成功/失败联动熔断器：成功 record_success，失败 record_failure，
   并在失败时对错误信息做凭证脱敏后再回 LLM。

【INVARIANT（必须保持的不变量）】
- awrap_tool_call 拦截所有工具调用（MCP / builtin / sandbox 统一走这里）。
- 熔断器检查：open 时不调用工具，记 circuit_open 事件。
- 成功：record_success + 记 ok 事件。
- 失败：record_failure + sanitize_error + 记 error 事件。
- 外化联动：result 含 POIROT_EXTERNALIZED 标记时，事件里加
  externalized=true + externalized_path。
- 凭证脱敏：error_text 经 CredentialSanitizer 清洗后才回 LLM / 写日志。

│   └─ logger

│   ├─ json.dumps 成功 → _truncate(s, 200)

### 0.2. 运行时调用树（awrap_tool_call 主流程）

```
工具调用进入 awrap_tool_call
│
├─ tool_call = request.tool_call
├─ tool_name = tool_call["name"]
├─ runtime   = request.runtime
├─ entry     = registry.get(tool_name)
├─ source    = entry.source or "unknown"
├─ start     = time.time()
│
├─ 【熔断器检查】
│   └─ if entry and not entry.breaker.allow_call():
│       ├─ _audit(status="circuit_open")
│       └─ return ToolMessage(status="error", content="circuit open...")
│
├─ 【调用工具】
│   ├─ try:
│   │   ├─ result = await handler(request)
│   │   ├─ if entry: entry.breaker.record_success()
│   │   ├─ _audit(status="ok", result=result)
│   │   │   └─ 若 result 带 POIROT_EXTERNALIZED → externalized + path
│   │   └─ return result
│   │
│   └─ except Exception as exc:
│       ├─ if entry: entry.breaker.record_failure()
│       ├─ sanitized = sanitizer.sanitize_error(str(exc))
│       ├─ _audit(status="error", error=sanitized)
│       └─ raise
│
└─ _emit(runtime, "tool.call", event)
    └─ journal.append("tool.call", event)（异常吞掉）
```

## 1. 熔断器检查

### 为什么要做

MCP 工具（尤其外部服务）可能连续失败：网络挂了、凭证过期、对端限流、服务宕机。如果每次调用都硬打过去，会有三个后果：

- **浪费时间和 token**：每次都要等超时、走完整条 LLM → tool → LLM 链路。
- **放大故障**：对端已经挂了，还持续打请求，等于雪上加霜。
- **污染上下文**：一串相同的失败结果会塞满 messages，挤占有效上下文。

熔断器（circuit breaker）就是「连续失败到阈值后，短时间内直接拒绝调用」的开关。`breaker` 处于 **open** 状态时，本中间件不再调工具，直接返回一条 error ToolMessage，让 LLM 知道「这工具暂时不可用，换条路」。

### 怎么实现的

```python
entry = self._registry.get(tool_name)          # 从注册表拿工具条目
source = entry.source if entry else "unknown"

# 熔断器检查
if entry and not entry.breaker.allow_call():   # ← 关键判断
    self._audit(runtime, tool_name, source, tool_call, None, "circuit_open", start)
    return ToolMessage(
        content=f"tool {tool_name} unavailable (circuit open), try alternative",
        tool_call_id=tool_call.get("id", ""),
        status="error",
    )
```

拆开看：

- **谁持有 breaker**：每个工具条目 `entry` 自带一个 `breaker`（来自 ToolRegistry）。所以熔断是 **per-tool** 的，A 工具挂了不影响 B 工具。
- **判断入口**：`entry.breaker.allow_call()` —— 返回 False 表示当前处于 open，不允许调用。
- **短路行为**：
  - **不调 handler**（根本不发工具请求）；
  - **记 circuit_open 事件**（审计留痕，说明这次不是真调用，是被熔断拦下）；
  - **返回 error ToolMessage**：`status="error"`，内容提示「unavailable, try alternative」，让 LLM 自己决定换工具或换策略。
- **没 entry 的情况**：`entry` 为 None（工具不在注册表）时**不做熔断检查**，直接往下走 —— 熔断只对注册过的工具有意义。

## 2. 审计打点

### 为什么要做

工具调用是 agent 里**副作用最大、最需要留痕**的动作：它可能读文件、发请求、改数据。出问题时需要能回答：

- 这次 run 到底调了哪些工具？
- 每个工具传了什么参数（摘要）？
- 成功还是失败？耗时多久？
- 失败原因是什么（且不能泄露凭证）？
- 结果有没有被外置（externalized）到文件？

这些信息写进 journal（`thread-events.jsonl`），供审计、回放、UI 活动展示、故障排查使用。

### 怎么实现的

审计统一走一个内部方法 `_audit`，由 `_emit` 落到 journal：

```python
def _emit(self, runtime, event_type, payload):
    journal = self._journal(runtime)              # runtime → journal
    if journal is not None:
        try:
            journal.append(event_type, payload)   # 追加到 thread-events.jsonl
        except Exception as exc:
            logger.debug("journal append failed: %s", exc)   # 静默不报错
```

事件体在 `_audit` 里组装：

```python
event = {
    "tool_name":     tool_name,
    "source":        source,                      # mcp / builtin / sandbox / unknown
    "args_summary":  _summarize_args(tool_call.get("args")),   # 截断到 200
    "status":        status,                      # ok / error / circuit_open
    "duration_ms":   int((time.time() - start) * 1000),
}
if error:
    event["error"] = error                        # 已脱敏
if status == "ok" and isinstance(result, ToolMessage):
    ak = getattr(result, "additional_kwargs", {}) or {}
    if ak.get(POIROT_EXTERNALIZED):               # 外化联动标记
        event["externalized"] = True
        event["externalized_path"] = ak.get(POIROT_EXTERNALIZED_PATH, "")
self._emit(runtime, "tool.call", event)
```

要点：

- **三个调用点都走 `_audit`**：熔断（circuit_open）、成功（ok）、失败（error）各一次，保证「每次工具调用都有且只有一条 tool.call 事件」。
- **参数摘要 `_summarize_args`**：`json.dumps(..., ensure_ascii=False, default=str)` 后截断到 200 字符，防止大参数炸日志；序列化失败退回 `str(args)` 再截断。
- **耗时 `duration_ms`**：从 `start = time.time()` 到写事件时的差值。
- **外化联动**：仅当 `status == "ok"` 且 result 是 ToolMessage 且带 `POIROT_EXTERNALIZED` 标记时，才补 `externalized` / `externalized_path` —— 用来告诉审计「这次结果被外置到文件了」，和 `TaggedContextMiddleware` 的外化标记对齐。
- **降级**：`journal` 为 None 时 `_emit` 直接跳过，不报错（INVARIANT：无 journal 静默不记）。

## 3. 成功/失败联动熔断器 + 凭证脱敏

### 为什么要做

第 1 步的熔断器需要**有信号驱动状态迁移**：失败累积到阈值就 open，成功则清零。所以每次调用结束必须回报结果给 breaker。同时，失败信息要回给 LLM，但**不能把凭证/密钥原样吐出去**，必须脱敏。

### 怎么实现的

```python
try:
    result = await handler(request)
    if entry:
        entry.breaker.record_success()            # ← 成功：清失败计数
    self._audit(runtime, tool_name, source, tool_call, result, "ok", start)
    return result

except Exception as exc:
    if entry:
        entry.breaker.record_failure()            # ← 失败：累加失败计数（到阈值→open）
    sanitized = self._sanitizer.sanitize_error(str(exc))   # ← 凭证脱敏
    self._audit(runtime, tool_name, source, tool_call, None, "error", start, error=sanitized)
    raise                                         # ← 重新抛出，交给上层 middleware
```

拆开看：

- **成功路径**：
  - `entry.breaker.record_success()` —— 告诉 breaker「这次成功」，通常会把连续失败计数清零，避免偶发失败累积成 open。
  - 写 `ok` 审计事件。
  - 原样返回 result（本中间件不改成功结果）。

- **失败路径**：
  - `entry.breaker.record_failure()` —— 累加失败计数；到阈值后 breaker 转 open，下次调用就会被第 1 步拦下。
  - `sanitized = self._sanitizer.sanitize_error(str(exc))` —— 用 CredentialSanitizer 把错误信息里的凭证/密钥洗掉。
  - 写 `error` 审计事件，`error` 字段用**脱敏后**的文本。
  - `raise` —— **重新抛出**，不在这里吞异常。原因：让上层 `ToolCallMiddleware` 把异常转成 ToolMessage 回给 LLM，错误处理职责分层，本中间件只管「熔断 + 审计 + 脱敏」。

- **entry 缺失时**：`entry` 为 None（工具不在注册表）时，`record_success` / `record_failure` 都跳过 —— 没有 breaker 可联动，其余逻辑照常。

- **为什么脱敏要在回 LLM 之前**：错误信息最终会进 messages 被 LLM 看到、也可能被写进日志/审计。如果里面带了 API key、token、密码，等于泄露。所以先用 `sanitize_error` 洗一遍，再写审计、再抛出。

## 4. 三者串起来看

```
awrap_tool_call
│
├─【1 熔断】entry.breaker.allow_call() == False?
│     ├─ 是 → 记 circuit_open + 返回 error ToolMessage（不调工具）
│     └─ 否 ↓
│
├─ try: await handler(request)
│     │
│     ├─ 成功 →【3 联动】breaker.record_success()
│     │         └─【2 审计】_audit(status="ok")（含外化联动）
│     │         └─ return result
│     │
│     └─ 失败 →【3 联动】breaker.record_failure()
│               └─【3 脱敏】sanitize_error(str(exc))
│               └─【2 审计】_audit(status="error", error=脱敏后)
│               └─ raise（交给上层转 ToolMessage）
```

一**1 是入口闸门，2 是全程留痕，3 是结果回灌 + 安全出口**。三者都围绕同一个 breaker 与同一个 journal，保证「每次工具调用都有决策、有记录、有反馈」。
