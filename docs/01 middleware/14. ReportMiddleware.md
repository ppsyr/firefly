---

name: ReportMiddleware — ReAct 循环结束后独立合成 final_report。

description:

【整体职责】
在 after_agent 阶段（ReAct 循环结束之后），如果 state 里已有 observations，
就单独调一次 LLM，基于 observations + sources + errors 合成一份结构化
Markdown 报告，写回 state["final_report"]。

【为什么不复用最后一条 AIMessage】
不再赌「最后一条 AIMessage 就是最终答案」（deer-flow 模式），
而是独立发起一次报告合成调用，由专门的 reporter prompt 生成报告。

【启用范围】
仅 general / expert 模式启用。default 模式不自动合成，报告靠 /report 命令触发。

【MVP 说明】
MVP 阶段复用 researcher 模型来当 reporter（D5）。

└─ class ReportMiddleware(AgentMiddleware)

## 1. ReAct 循环结束后独立合成 final_report 是怎么实现的

### 1.1. 触发时机：`after_agent`

```python
@override
def after_agent(self, state, runtime):
    if not self._auto_synthesize:
        return None
    observations = state.get("observations") or []
    if not observations:
        return None
    report = self._synthesize(state)
    return {"final_report": report}
```

`after_agent` 是 LangGraph 在 ReAct 循环**完全结束之后**触发的 hook。此时 agent 已经不再调用工具，正在准备收尾。ReportMiddleware 在这里做两件事：

1. **条件检查**：`auto_synthesize=False`（default 模式）或没有 observations → 不合成，直接退出；
2. **独立合成**：有 observations 就调 LLM 生成报告。

### 1.2. 构造 reporter 消息：`_build_reporter_messages`

```python
def _build_reporter_messages(state):
    question = state.get("research_question") or state.get("user_input") or "Research report"
    observations = state.get("observations") or []
    sources = state.get("sources") or []
    errors = state.get("errors") or []

    user_content = (
        f"# 研究问题\n{question}\n\n"
        f"# 已收集的观察（observations）\n{_format_observations(observations)}\n\n"
        f"# 来源（sources）\n{_format_sources(sources)}\n"
    )
    err_block = _format_errors(errors)
    if err_block:
        user_content += f"\n# 工具失败（errors）\n{err_block}\n"
    user_content += "\n\n请基于以上证据撰写完整研究报告。"

    return [SystemMessage(content=get_reporter_system()), HumanMessage(content=user_content)]
```

把 state 里的三类证据（observations / sources / errors）和原始问题拼成一份人类可读的 prompt，交给 reporter 模型。

### 1.3. 独立调用 LLM：`_synthesize`

```python
def _synthesize(self, state):
    messages = _build_reporter_messages(state)
    with interrupt_protection():
        response = self._model.invoke(messages, config={"tags": ["internal_llm"]})
    return getattr(response, "content", str(response))
```

关键点：**这是一次独立的 LLM 调用**，不依赖 ReAct 循环里最后一条 AIMessage。模块 docstring 明确写了「不再赌最后一条 AIMessage（deer-flow 模式）」——意思是以前可能直接拿循环结束时的 AI 输出当报告，现在改为单独发起一次 reporter 调用。

### 1.4. 写回 state

```python
return {"final_report": report}
```

报告内容写进 `state["final_report"]`，供下游（UI、文件导出、后续中间件）读取。

## 2. 这个 report 步骤会本地化存储吗？

**ReportMiddleware 本身不写文件。**

它只把报告字符串写回 `state["final_report"]`，这是内存中的图状态。是否落盘取决于：

| 层面 | 行为 |
|---|---|
| **ReportMiddleware** | 只写 `state["final_report"]`，不碰文件系统 |
| **LangGraph Checkpointer** | 如果 graph 配置了持久化 checkpointer（SqliteSaver / PostgresSaver），state 会被 checkpoint 持久化，间接落盘 |
| **CLI / 应用层** | 如果 CLI 在 run 结束后读取 `final_report` 并写文件（比如导出 `.md`），那才是真正的文件落盘 |

你的 Poirot CLI 可能有一个独立的「导出报告」步骤（比如 `/report` 命令或 run 结束后的后处理），但**这部分不在 ReportMiddleware 的代码里**。

## 3. 在其他 agent（比如 Claude Code）中存在吗？

**存在，但形态不同。**

在 **Claude Code** 的上下文中，「report」相关能力以**自定义 slash command** 的形式存在。有一个社区工具包 `claude-code-toolbox` 提供了 `/report` 命令，用于「从多个项目的 git 提交记录生成统一日报/周报」。但它：

- 不是 agent 内置的「循环结束后自动合成研究报告」；
- 是用户主动触发的、面向 git 提交记录的命令；
- 与 ReportMiddleware 的「基于 observations/sources 合成研究报告」语义不同。

在**其他 deep research agent 框架**中，「独立 report 合成」是常见模式：

- **NVIDIA AIQ deep-researcher** 有专门的 **writer** 角色，负责读取持久化的 artifacts 和 sources，执行最终合成，写入 `/shared/output.md`；
- **gpt-researcher** 有 **PublisherAgent**，把研究结果合成为 Markdown/PDF/DOCX 并写入 `output_dir`；
- 这些框架的共同点：**报告合成是独立阶段，由专门的角色/agent 完成**，而不是直接拿 ReAct 循环的最后输出。

所以 ReportMiddleware 的设计（独立 reporter 调用 + observations/sources 作为输入）与业界 deep research agent 的主流做法一致。

## 4. 和命令行的 `/report [topic]` 命令之间有什么联系？

**两者在语义上相关，但实现路径不同。**

你的 CLI 里 `/report [topic]` 的用途是「从当前 thread 生成报告」。它和 ReportMiddleware 的关系取决于你的实现：

**情况 A：`/report` 命令直接调用了 ReportMiddleware 的逻辑**
- 命令触发 → 构造一个包含当前 state 的调用 → 调 `_synthesize` 或类似的 reporter LLM → 拿到报告 → 输出或写文件。
- 这种情况下，`/report` 是 ReportMiddleware 的**手动触发入口**，而 `after_agent` 的自动合成是**自动触发入口**。两者共享同一套 prompt 和合成逻辑。

**情况 B：`/report` 命令有独立实现**
- 命令自己构造 prompt、调 LLM、拿结果，不经过 ReportMiddleware。
- 这种情况下，两者是**两套独立的报告生成路径**，可能共享 prompt 模板，也可能不共享。

从你提供的 ReportMiddleware 代码看，`auto_synthesize` 参数就是为「手动触发」预留的开关：

```python
if not self._auto_synthesize:
    return None
```

`auto_synthesize=False` 时（default 模式），ReportMiddleware **不自动合成**。这暗示：default 模式下报告靠**外部触发**（很可能就是 `/report` 命令）来生成。

所以最可能的联系是：

```
/report [topic] 命令（手动触发）
        │
        ▼
   构造 state / 调用 reporter LLM
        │
        ▼
   拿到报告 → 输出到 CLI / 写文件

ReportMiddleware.after_agent（自动触发，仅 general/expert）
        │
        ▼
   同样调 reporter LLM → 写 state["final_report"]
```

**两者共享的核心是「reporter prompt + 证据格式」**，但触发时机和输出目标不同：命令是用户主动、输出给用户；中间件是流程自动、写回 state。

## 5. 总结

| 问题                | 答案                                                                                                       |
| ----------------- | -------------------------------------------------------------------------------------------------------- |
| 怎么合成              | `after_agent` 检查条件 → `_build_reporter_messages` 构造 prompt → 独立调 reporter LLM → 写 `state["final_report"]` |
| 会本地化存储吗           | 中间件本身不落盘，只写 state；落盘取决于 checkpointer 或 CLI 后处理                                                           |
| Claude Code 有吗    | 有类似能力，但以 slash command（如 `/report` 生成 git 日报）形式存在，语义不同                                                   |
