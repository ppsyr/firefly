---

name: HelpRequestMiddleware — 拦截 ask_help 工具调用并暂停 graph。

description:

【整体职责】
当 LLM 调用 ask_help 工具时，本中间件在工具真正执行前拦截它：
1. 拦截这次调用，不让它走到实际工具；
2. 把参数格式化成一条对用户友好的求助消息；
3. 返回 Command(goto=END) 暂停 graph，把控制权交回用户；
4. 向 journal 写一条 help.requested 事件。

【模式来源】
借鉴 deer-flow ClarificationMiddleware 的「拦截工具调用 → 暂停 graph」
模式。

【触发条件】
只看 tool_call["name"] == "ask_help"；其他工具一律透传给下游 handler。


---

## 0. 结构树

### 0.1. 静态结构树（模块 → 函数/类 → 方法）

```
HelpRequestMiddleware — 拦截 ask_help 工具调用并暂停 graph
│
├─ 模块级常量
│   └─ _HELP_TYPE_ICONS: {help_type: 图标}
│       （missing_info ❓ / approach_choice 🔀 /
│         risk_confirmation ⚠️ / stuck_report 🚧）
│
├─ _format_help_message(args)                ← ask_help 参数 → 用户可读文本
│   ├─ 取 question / help_type / context / options
│   ├─ 按 help_type 取图标（默认 ❓）
│   ├─ 首部：有 context → "{icon} {context}\n{question}"
│   │        无 context → "{icon} {question}"
│   └─ options 非空 → 空行 + "  {i}. {opt}"
│
└─ class HelpRequestMiddleware(AgentMiddleware)
    ├─ wrap_tool_call(request, handler)      ← 同步：识别 ask_help，其余透传
    │   └─ _handle_help(request, tool_call)
    │
    ├─ awrap_tool_call(request, handler)     ← 异步：同上，透传改 await
    │   └─ _handle_help(request, tool_call)
    │
    └─ _handle_help(request, tool_call)      ← 核心：格式化 + 写 journal + 返回 Command
        ├─ args / tool_call_id
        ├─ message = _format_help_message(args)
        ├─ journal.append("help.requested", {run_id, help_type, question})
        └─ return Command(update={messages: [ToolMessage]}, goto=END)
```

---

### 0.2. 运行时调用树（wrap_tool_call / awrap_tool_call 主流程）

```
工具调用进入 wrap_tool_call / awrap_tool_call
│
├─ tool_call = request.tool_call
├─ if tool_call["name"] != "ask_help":
│     return handler(request)          ← 同步
│     return await handler(request)    ← 异步
│
└─ _handle_help(request, tool_call)
    ├─ args         = tool_call["args"]
    ├─ tool_call_id = tool_call["id"]
    ├─ message      = _format_help_message(args)
    │   ├─ icon      = _HELP_TYPE_ICONS.get(help_type, "❓")
    │   ├─ 首部      = "{icon} {context}\n{question}" 或 "{icon} {question}"
    │   └─ options   = "  1. ..." / "  2. ..."（若有）
    │
    ├─ journal = runtime.journal（可 None）
    ├─ run_id  = runtime.run_id（可 None）
    ├─ if journal: journal.append("help.requested", {...})
    │
    └─ return Command(
         update={"messages": [ToolMessage(content=message,
                                          tool_call_id=tool_call_id,
                                          name="ask_help")]},
         goto=END,
       )
```

## 1. 拦截的每一步具体怎么实现

### 步骤 1：拿到这次工具调用的结构

```python
tool_call = getattr(request, "tool_call", None) or {}
```

- `request` 是 `ToolCallRequest`，`tool_call` 是本次调用的描述（含 `name` / `args` / `id`）。
- `getattr(..., None) or {}` 兜住缺失，后面 `.get(...)` 不会炸。

### 步骤 2：判断是不是 ask_help

```python
if tool_call.get("name") != "ask_help":
    return handler(request)      # 同步
    return await handler(request)  # 异步
```

- 只有 `name == "ask_help"` 才进入拦截分支。
- 其他工具（web_search、bash、present_files…）一律原样透传给下游 handler，
  本中间件对它们完全无感。
- 同步 / 异步两条路径的判断完全一致，区别只在透传时是否 `await`。

### 步骤 3：进入 `_handle_help`（真正拦截）

```python
def _handle_help(self, request, tool_call):
    args = tool_call.get("args", {})
    tool_call_id = tool_call.get("id", "")
    message = _format_help_message(args)
```

- 关键点：这里**根本不调用 `handler(request)`**。
  也就是说 ask_help 的实际工具实现永远不会被执行，调用被彻底截断。
- `args` 里通常含 `question` / `help_type` / `context` / `options`。
- `tool_call_id` 用于给回填的 ToolMessage 挂上正确的调用 id，
  保证消息配对关系不破。

### 步骤 4：格式化求助文本

```python
def _format_help_message(args):
    question    = args.get("question", "")
    help_type   = args.get("help_type", "missing_info")
    context     = args.get("context")
    options     = args.get("options") or []
    icon        = _HELP_TYPE_ICONS.get(help_type, "❓")
    parts = [f"{icon} {context}\n{question}"] if context else [f"{icon} {question}"]
    if options:
        parts.append("")
        for i, opt in enumerate(options, 1):
            parts.append(f"  {i}. {opt}")
    return "\n".join(parts)
```

- 按 `help_type` 选图标，未知类型用默认 `❓`。
- 有 `context` 就放在 question 前面（给用户更多背景），没有就只显示 question。
- 有 `options` 就编号列出，方便用户直接回「1 / 2 / 3」。
- 这是纯字符串处理，无副作用、无 IO。

### 步骤 5：写 journal（可选审计）

```python
runtime = getattr(request, "runtime", None)
journal = _get_runtime_value(runtime, "journal", None) if runtime else None
run_id  = _get_runtime_value(runtime, "run_id", None)  if runtime else None
if journal is not None:
    journal.append("help.requested", {
        "run_id": run_id,
        "help_type": args.get("help_type", "missing_info"),
        "question": args.get("question", ""),
    })
```

- 从 runtime 取 journal / run_id（走 `_get_runtime_value`，兼容多种 runtime 形态）。
- journal 为 None 时静默跳过（容忍缺件）。
- 记录 `help.requested` 事件，便于审计 / 回放 / UI 展示「本 run 曾向用户求助」。

### 步骤 6：构造 Command 暂停 graph

```python
return Command(
    update={"messages": [ToolMessage(
        content=message, tool_call_id=tool_call_id, name="ask_help",
    )]},
    goto=END,
)
```

- 两件事同时做：
  1. `update.messages`：把格式化好的求助文本作为一条 **ToolMessage** 写回 state。
     用 ToolMessage 而不是 HumanMessage，是为了满足「每个 tool_call 必须有
     对应 tool 结果」的配对约束——否则消息历史会不合法。
  2. `goto=END`：直接把图跳到 END 节点，即**暂停本次运行**。
- 返回值是 Command，不是普通 result，LangGraph 会按 `goto` 改变控制流。

## 2. 拦截流程是什么？拦截后是否退出 graph 等用户指令？

### 2.1. 流程一图

```
LLM 输出 tool_call: ask_help
        │
        ▼
ToolNode / 工具执行入口
        │
        ▼
HelpRequestMiddleware.wrap_tool_call / awrap_tool_call
        │
        ├─ name != "ask_help" → handler(request) 正常执行
        │
        └─ name == "ask_help"
              │
              ├─ 不调 handler                ← 拦截点
              ├─ 格式化求助文本
              ├─ journal.append("help.requested")
              └─ return Command(
                    update={messages: [ToolMessage(...)]},
                    goto=END,
                 )
        │
        ▼
LangGraph 按 goto=END 跳转
        │
        ▼
本次 graph 运行结束（暂停），控制权交回调用方（CLI / 上层）
        │
        ▼
用户看到求助文本，输入下一步指令
        │
        ▼
调用方再次以「用户输入」为起点启动 graph（新一轮 run）
```

### 2.2. 是否退出 graph？

**是。** 具体说是：

- `goto=END` 让 LangGraph 把本次运行推进到终止节点，**本次 run 到此结束**。
- 不是「挂起等用户输入再 resume 同一个 run」，而是**结束本次 run**；
  用户的下一步指令会作为**新一轮 run** 的输入重新进入 graph。
- 之所以要用 `update.messages` 补一条 ToolMessage，是因为 LLM 已经发出了
  `ask_help` 这个 tool_call，消息历史里必须有一条对应的 tool 结果，
  否则下次构建上下文时 tool pairing 不完整（严格后端会拒绝）。

### 2.3 和「人类在环中断（interrupt）」的区别

- 本中间件用的是 **「结束 run」**，不是 LangGraph 的 `interrupt()` /
  checkpointer 的「挂起后 resume」。
- 好处：实现简单、不依赖 checkpointer 的 resume 语义；
  用户输入天然作为新 run 的起点。
- 代价：本次 run 的「未完成状态」不保留为可 resume 的中断点，
  而是靠 messages 里那条 ToolMessage + journal 事件做衔接。

一句话总结：
**拦截 = 不执行 ask_help 工具，改写成一条 ToolMessage 写回历史，
并用 `goto=END` 结束本次 run；用户下一步输入开启新一轮 run。**
