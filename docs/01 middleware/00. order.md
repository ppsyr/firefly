
# 1. 组间顺序


**为什么是 `context → skill → state → tool → memory → tool → workflow`**

实际装配序列画出来：

```
01a 01b 01c 02   ← context & state（前段）
03 04 05          ← skill
06a 06b           ← context & state（后段，Title/RunJournal）
07 08             ← tool（第一半：McpAudit/Sandbox）
09 10             ← memory
11a 11b 11c 12    ← tool（第二半：HelpRequest/Dangling/ToolCall/Orchestration）
13a 13b 13c 13d 14 ← workflow
```

---

## 1. 为什么 `context & state` 的两段分别在头和中间？

`context & state` 组有 6 个：`TaggedContext` / `MessageNormalizer` / `Strategy` / `SystemContext` / `Title` / `RunJournal`。

### 前段（01a / 01b / 01c / 02）：治理层必须在最前

```
01a TaggedContext      改"送 LLM 的 messages"
01b MessageNormalizer  合并 SystemMessage
01c Strategy           治理策略（最外层决策）
02  SystemContext      写 system_context 元数据
```

**为什么必须在最前**：

- 它们改的是"送 LLM 的 request"——必须在**所有注入完成之后、模型调用之前**执行；
- `StrategyMiddleware` 要在 `wrap_model_call` **最外层**（注册最早 = 最外）；
- `MessageNormalizer` 要合并"所有注入产生的 SystemMessage"——注册早，但在洋葱里它包住所有注入（**注册顺序≠执行顺序**，这是洋葱的妙处）。

### 后段（06a / 06b）：Title / RunJournal 卡在 skill 和 tool 之间

```
06a Title        after_agent 写 metadata.title
06b RunJournal   全钩子写 journal
```

**为什么它们不在最前，而在 05 和 07 之间**：

- **`RunJournal` 的 `wrap_tool_call` 必须在 tool 组外层**——它要记录所有工具调用的完整生命周期；
- 它注册在 `07 McpAudit` **之前** → 在洋葱里它就包住 `McpAudit` → ✅ 满足"记录在外层"；
- 但它不需要比 `skill` 更早（skill 的 `before_model` 注入先发生，`RunJournal.before_model` 记录 llm.request 时正好能反映"注入了什么"）；
- **所以它的最优位置是"skill 之后、tool 之前"**——这就是 06 的位置。

**`Title` 为什么跟 `RunJournal` 挤在一起**：它只有一个 `after_agent` 钩子（写 metadata.title），位置相对自由；跟着 `RunJournal` 走，是最简单的处理。

**这一段揭示了第一个组间原则**：

> **一个中间件的"注册位置"由它的"最敏感钩子"决定**——`RunJournal` 最敏感的是 `wrap_tool_call`（要在 tool 外层），所以它必须卡在 tool 组之前。

---

## 2. 为什么 `skill` 在 `tool` 之前？

```
03 SkillInjection  → 写 _active_skills_ctx（provenance 写入者）
04 SkillMetrics    → 读 _active_skills_ctx（provenance 读取者）
05 SkillActivation → 写 skill_suggestion
```

**为什么 `skill` 必须在 `tool` 之前**：

- `SkillInjection` 在 `before_model` 写 `_active_skills_ctx`；
- `SkillMetrics` 在 `awrap_tool_call` 读它；
- **写入者必须在读取者之前注册**——虽然它们都属 skill 组，但 `SkillMetrics` 的钩子在**工具调用阶段**；
- 若 `skill` 组注册在 `tool` 组之后，`SkillMetrics` 就会在 `ToolCall` 内层（洋葱），打点时机错乱。

**更重要的**：`SkillInjection.before_model` 必须在**所有注入之前**（它决定"本轮激活哪些 skill"），而 `RunJournal.before_model`（记录 llm.request）要在它**之后**——所以 `skill` 组卡在 `context & state` 后段之前。

**这一段揭示第二个组间原则**：

> **跨组传递靠 ContextVar 时，写入组必须早于读取组注册**——即使读取者本身在别组的钩子里。

---

## 3. 为什么 `tool` 组被 `memory` 劈成两半？

**这是你观察到的核心现象**。看真实装配序列：

```
07 McpAudit         ← tool 第一半
08 Sandbox          ← tool 第一半
09 Memory           ← memory
10 MemoryConsolidation ← memory
11a HelpRequest     ← tool 第二半
11b DanglingToolCall ← tool 第二半
11c ToolCall        ← tool 第二半
12 Orchestration    ← tool 第二半
```

**为什么 `memory` 插在 `Sandbox`（08）和 `HelpRequest`（11a）之间**：

### 理由一：`Memory` 必须在 `Sandbox` 之后（数据依赖）

- `Memory` 召回的内容可能引用 sandbox 结果（"上次在沙箱里做了什么"）；
- 所以 `Sandbox`（08）先注册、`Memory`（09）后注册——**这是数据依赖约束**。

### 理由二：`Memory` 必须在 `HelpRequest` / `ToolCall` 之前（注入不进 pairing）

- `Memory` 注入的是 `HumanMessage(name="memory_recall", hide_from_ui=True)`；
- 它**不能进 tool pairing**（不是工具调用的一部分）；
- `HelpRequest` / `ToolCall` 都在工具阶段——`Memory` 必须在它们**之前**注入完；
- **这是"注入内容不该被工具治理误伤"的约束**。

### 理由三：`MemoryConsolidation` 与 `Memory` 成对

- `MemoryConsolidation`（10）是 `Memory`（09）的写路径——两者职责对偶，**必须相邻**；
- 它只能在 `after_model` 提交沉淀——位置只要在"工具阶段之前"即可。

**所以 `memory` 组**恰好卡在 `Sandbox`（08）和 `HelpRequest`（11a）之间**——这是约束的必然**，不是人为设计。

**这一段揭示第三个组间原则**：

> **数据依赖（谁读谁写的 state/ContextVar）会跨越"职责分组"强制插入——`memory` 就是被 `Sandbox → Memory → HelpRequest` 这条数据链"钉"在 tool 组中间的。**

---

## 4. 为什么 `tool` 第二半是 `HelpRequest → Dangling → ToolCall → Orchestration`？

```
11a HelpRequest    → 拦截 ask_help（wrap_tool_call）
11b DanglingToolCall → 修补悬空 tool_call（before_model）
11c ToolCall       → 工具账本+预算（wrap_tool_call，最内层）
12 Orchestration   → 派活拦截（wrap_tool_call）
```

**为什么这个顺序**：

- `HelpRequest` 要在 `ToolCall` **外层**——拦截 `ask_help` 要在"工具治理"之前；
- `DanglingToolCall` 是 `before_model` 钩子，插在 `HelpRequest` 和 `ToolCall` 之间——**它不占 wrap 位置，只占 before_model 位置**；
- `ToolCall` 要**贴近 handler**（最内层）——判成败、记 AgentError；
- `Orchestration` 要在 `ToolCall` **外层**——派活归集产物，再让 `ToolCall` 记失败/预算。

**洋葱结构（外→内）**：

```
RunJournal（06b）→ McpAudit（07）→ Sandbox（08）
    → HelpRequest（11a）→ Orchestration（12）→ ToolCall（11c）→ handler
```

**注意**：`Orchestration`（12）注册在 `ToolCall`（11c）**之后**，但在洋葱里它在 `ToolCall` **外层**——**这是因为注册顺序决定外层/内层**：

- 注册**更早**的 = 更**外**层；
- `Orchestration` 注册在 `ToolCall` 之后 → 它是**更内层**？

**等一下，需要重新核对**：LangGraph 的 `wrap_tool_call` 洋葱，注册顺序是**由外到内**（先注册的在外层）——所以：

```
注册顺序：      洋葱嵌套（外→内）：
06b RunJournal  RunJournal
07 McpAudit       → McpAudit
08 Sandbox          → Sandbox
11a HelpRequest       → HelpRequest
11c ToolCall            → ToolCall
12 Orchestration          → Orchestration
                        → handler
```

**但这样一来 `Orchestration`（12）注册在 `ToolCall`（11c）之后 → 它在更内层**——而我们要它"拦截 delegate_to_*"，它必须在 `ToolCall` 之前执行（才能先派活、再让 `ToolCall` 记）？

**关键修正**：`Orchestration` 拦截的是 `delegate_to_*`，而 `ToolCall` 治理的是**所有工具**——**两者不是"先派活再治理"，而是"派活工具被 Orchestration 特殊处理，其他工具走 ToolCall"**。它们**不冲突**，顺序不影响功能：

- 若 `Orchestration` 在外：先拦 `delegate_to_*`，其他工具透传给 `ToolCall`；
- 若 `Orchestration` 在内：`ToolCall` 先看所有工具，`delegate_to_*` 透传给 `Orchestration`。

**实际选择"Orchestration 在内层"**的原因：`ToolCall` 要**统一治理所有工具**（包括 `delegate_to_*` 的预算/重试），所以 `ToolCall` 在外层更合理——**`Orchestration` 在 `ToolCall` 内层，只处理"派活特有的打点/归集"**。

**这一段揭示第四个组间原则**：

> **洋葱的"外/内"由注册顺序决定；"谁在外"取决于"谁要统一处理、谁只处理子集"——统一处理的在外，子集处理的在内。**

---

## 5. 为什么 `workflow` 在最后？

```
13a Evidence         → 证据抽取（wrap_tool_call）
13b StallDetection   → 停滞检测（wrap + after_model）
13c Todo             → 任务管理（多钩子）
13d Reflection       → 反思（after_model）
14  Report           → 报告合成（after_agent）
```

**为什么 `workflow` 必须在最后**：

- `Evidence` 要在 `Orchestration` **之后**（派活归集 → 证据抽取）；
- `StallDetection` 要在 `Evidence` **之后**（检测整个工具链健康度）；
- `Todo` / `Reflection` 在 `after_model` **尾部**——它们是"退出闸门"，要在**所有其他 after_model 中间件之后**判断"是否跳回 model"；
- `Report` 在 `after_agent`——**整个 run 的收口**。

**为什么 `Evidence` 移到了 `workflow`**（你上一版从 tool 移过来的）：

- 它钩子在 `wrap_tool_call`（工具侧），但职责是"证据沉淀"（流程侧）；
- 它注册在 `Orchestration`（12）**之后**——恰好符合约束；
- **所以归 `workflow` 不破坏顺序**——这是"分类与顺序恰好重合"的好例子。

**这一段揭示第五个组间原则**：

> **"退出闸门"类中间件（Todo / Reflection / StallDetection）必须排在 `after_model` 的尾部——它们决定"要不要跳回 model"，是循环的最后一道关口。**

---

## 6. 组间顺序的"真正的决定因素"

把上面五段串起来，**组间顺序不是按"分组"排的，而是按这五个约束排的**：

```
约束一：治理层（改 request 的）必须最前
        → context & state 前段（01a-02）

约束二：写入者必须在读取者之前
        → skill（03-05）必须在 tool（07-）之前
        → Sandbox（08）必须在 Memory（09）之前
        → Orchestration（12）必须在 Evidence（13a）之前

约束三：注入内容不进 tool pairing
        → Memory（09-10）必须在 HelpRequest（11a）/ ToolCall（11c）之前

约束四：记录者必须在被记录者之外层
        → RunJournal（06b）必须在 tool 组之前
        → ToolCall（11c）必须贴近 handler

约束五：退出闸门必须在 after_model 尾部
        → Todo（13c）/ Reflection（13d）在 after_model 最后
        → Report（14）在 after_agent
```

**所以真实装配顺序**：

```
01a 01b 01c 02  ← 约束一（治理层最前）
03 04 05        ← 约束二（skill 写入者）
06a 06b         ← 约束四（RunJournal 要在 tool 外）
07 08           ← 约束二（Sandbox 在 Memory 前）
09 10           ← 约束二 + 三（Memory 在 Sandbox 后、在 tool 前）
11a 11b 11c 12  ← 约束四 + 二（HelpRequest 在 ToolCall 外；Orchestration 在 Evidence 前）
13a 13b 13c 13d 14 ← 约束二 + 五（Evidence 在 Orchestration 后；退出闸门在尾部）
```

**分组视图是事后归类的**——把 07/08 和 11a-12 归为 `tool`，它们中间的 09/10 归 `memory`——**分组视图看起来"tool 被劈开"，但装配顺序本身是连续的、由约束决定的。**

---

## 7. 总结

> **组间顺序不是按"分组"排的，而是按五个约束排的**：
> 1. **治理层最前**（改 request 的）→ context & state 前段在最前；
> 2. **写入者在读取者前**（跨组传 ContextVar / state）→ skill 在 tool 前、Sandbox 在 Memory 前、Orchestration 在 Evidence 前；
> 3. **注入不进 tool pairing** → Memory 必须在 HelpRequest / ToolCall 前；
> 4. **记录者在外层** → RunJournal 在 tool 组前、ToolCall 贴近 handler；
> 5. **退出闸门在 after_model 尾部** → Todo / Reflection / Report 在最后。
>
> **你观察到的"两个 tool 夹一个 memory"不是人为设计**——是 `Sandbox → Memory → HelpRequest` 这条数据链（约束二 + 三）**恰好把 tool 组劈开**。**分组视图看起来是 5 组，真实装配顺序是约束驱动的连续序列**——`context & state` 和 `tool` 各被劈开，是约束的必然结果，不是设计缺陷。



# 2. 组内顺序

## 1. `context & state`（01a / 01b / 01c / 02 / 06a / 06b）

**这一组的职责**：**处理"送 LLM 的 messages 内容 + 运行期元数据/日志"**。

### 为什么 `TaggedContext` / `MessageNormalizer` / `Strategy` 在最前？

它们是**治理层**，职责是"决定送 LLM 的 messages 长什么样、占多少预算"：

```
01a TaggedContext      → 渲染 XML 标签序列（<goal><plan><thinking><answer>...）
01b MessageNormalizer  → 合并 SystemMessage 为单条 leading
01c Strategy           → 治理策略编排（预算/压缩/jump）
```

**必须在最前，三个理由**：

1. **必须在模型调用前完成**——它们改的是"送 LLM 的 request"，晚了模型就看不到；
2. **必须在所有注入之后**——`MessageNormalizer` 要合并"所有注入产生的 SystemMessage"，所以它要在 `SkillInjection` / `SystemContext` 之前**注册**（但钩子在 `wrap_model_call` 层面，所以实际执行时它排在注入之后——这是洋葱的妙处）；
3. **治理是最外层的决策点**——`StrategyMiddleware` 在 `wrap_model_call` 最外层，能决定"要不要跳回 model / 换 model / 改 request"。

### 为什么 `SystemContext` 排第 2？

```
02 SystemContext → 写 metadata.system_context（agent 身份 + 时区）
```

**位置讲究**：它写的是**旁路元数据**，谁读它由下游 prompt 拼装决定。放在第 2 位（`Strategy` 之后、`SkillInjection` 之前），是因为：

- 它在 `SkillInjection` 前——`SkillInjection` 可能读 `system_context` 做决策；
- 它在 `TaggedContext` 后注册——但 `TaggedContext` 的钩子在 `wrap_model_call`（更外），执行时反而在它之后——**这就是为什么"注册顺序"和"执行顺序"要分开看**。

### 为什么 `Title` / `RunJournal` 被归到这一组？

这是**这一版最关键的修正**（上一版把它们归 `context_engineering`）：

```
06a Title      → after_agent 写 metadata.title（展示用）
06b RunJournal → 全钩子写 journal 事件（日志用）
```

它们**不属于"上下文治理"**（不改 messages），但**属于"context & state"这个更大的范畴**——因为它们**读写的是 state 的旁路字段 / 事件流**：

- `Title` 写 `metadata.title`（state 的 metadata）；
- `RunJournal` 写 `events.jsonl`（state 外的运行事件）。

**归到 "context & state" 是对的**——比上一版"硬塞进 context_engineering"准确。

**为什么 `RunJournal` 必须在早期注册？**

```
RunJournal 的钩子：before_agent / after_agent / before_model / after_model / wrap_tool_call
```

- `before_agent` 要早——标记 run 开始；
- `wrap_tool_call` 要在**外层**——记录工具完整生命周期；
- **早期注册 = wrap 外层** ✅，这是它必须在最前几组的根本原因。

---

## 2. `memory`（09 / 10）

**这一组的职责**：**长期记忆的读（召回）+ 写（沉淀）**。

### 为什么 `MemoryMiddleware` 在 `MemoryConsolidation` 前？

```
09 Memory              → abefore_model（召回+注入）+ aafter_model（清 turn_id）
10 MemoryConsolidation → abefore_model（no-op）+ aafter_model（submit 沉淀）
```

**写在前、读在后**的对称关系：

- `Memory` 是**读路径**（召回）——想早（模型调用前注入）；
- `MemoryConsolidation` 是**写路径**（沉淀）——想晚（每 N 轮异步提交）；
- 两者**职责矛盾**，所以**拆成两个中间件**——这正是上一轮我们讨论的"前后矛盾就拆开"。

### 为什么 `memory` 组在 `skill` 组之前装配？

看你的编号：`memory`（09/10）装配在 `skill`（03/04/05）之前？

**不是**——按编号，装配顺序是 `01a→01b→01c→02→03→04→05→06a→06b→07→08→09→10→11a→...`。

**所以 `memory`（09/10）实际装配在 `skill`（03-05）和 `tool`（07/08）之后**——这是**按约束定的**：

```
Sandbox（08）→ Memory（09）→ MemoryConsolidation（10）→ HelpRequest（11a）
```

**为什么 `Memory` 必须在 `Sandbox` 之后**：

- `Memory` 召回的内容**可能引用 sandbox 结果**（"上次在沙箱里做了什么"）；
- 所以 `Memory` 要在 `Sandbox` 之后——**这是数据依赖约束**。

**为什么 `Memory` 在 `HelpRequest` / `ToolCall` 之前**：

- 记忆注入是 `before_model` 阶段的事；
- 而 `HelpRequest` / `ToolCall` 的 wrap_tool_call 在工具阶段；
- 记忆注入的内容**不进 tool pairing**（`hide_from_ui=True`）；
- 所以它要在 tool 相关中间件之前——**这是"注入内容不该被 tool 治理误伤"的约束**。

---

## 3. `skill`（03 / 04 / 05）

**这一组的职责**：**技能的选择、注入、打点、建议**。

### 为什么顺序是 `SkillInjection → SkillMetrics → SkillActivation`？

```
03 SkillInjection  → 写 _active_skills_ctx（provenance 写入者）
04 SkillMetrics    → 读 _active_skills_ctx（provenance 读取者）
05 SkillActivation → 写 skill_suggestion（建议旁路）
```

**写在前、读在后**：

- `SkillInjection` 写 `_active_skills_ctx`（本轮激活哪些 skill）；
- `SkillMetrics` 读它（判断"工具是否被 skill 允许"→ 打点 applied）；
- **写入者必须在前**——否则 `SkillMetrics` 读到空。

**为什么 `SkillActivation` 在最后**：

- 它只写旁路字段 `skill_suggestion`（不改 system prompt，保护 caching）；
- 位置相对自由——放最后是因为它不影响主流程。

### 为什么 `skill` 组在 `context & state` 之后、`tool` 之前？

```
context & state（01a-06b）
    → skill（03-05）  ← 注意：编号 03-05 排在 06 前，但装配顺序其实是 03-05 在 06 前
        → tool（07-12）
```

**等一下，编号有蹊跷**——`03/04/05` 排在 `06a/06b` **之前**，所以**实际装配顺序是**：

```
01a 01b 01c 02 03 04 05 06a 06b 07 08 09 10 11a 11b 11c 12 13a ...
```

**所以 `skill`（03-05）确实装配在 `Title` / `RunJournal`（06a/06b）之前**——**这是设计**：

- `SkillInjection` 要在 `RunJournal.before_model`（写 llm.request）**之前**——因为 skill 注入是"准备 request"的一部分，应该先注入再记录 request；
- 其实更准确：`SkillInjection.before_model` 要**最先**（它写 `_active_skills_ctx`），`RunJournal.before_model` 记录时已经能反映"要注入什么"。

### 为什么 `skill` 在 `tool` 之前？

```
skill（03-05）→ tool（07-12）
```

- `SkillInjection` 写 `_active_skills_ctx`（provenance）；
- `SkillMetrics.awrap_tool_call` 读它——但 `SkillMetrics` 本身在 `skill` 组（04）；
- **看似不需要 `skill` 组在 `tool` 组前**——因为 `_active_skills_ctx` 是 ContextVar，跨组传递没问题；
- 真正的原因是**洋葱嵌套**：`SkillMetrics.wrap_tool_call` 要在 `ToolCall.wrap_tool_call` **外层**（先打点，再治理）——注册早 = 外层。

## 4. `tool`（07 / 08 / 11a / 11b / 11c / 12）

**这一组的职责**：**四类工具（MCP / sandbox / builtin / multiagent）的治理与调用链**。

### 为什么顺序是这个？

```
07 McpAudit         → MCP 工具熔断+审计（wrap_tool_call）
08 Sandbox          → sandbox 工具 acquire+release（wrap_tool_call）
11a HelpRequest     → 拦截 ask_help（wrap_tool_call）
11b DanglingToolCall → 修补悬空 tool_call（before_model）
11c ToolCall        → 工具账本+预算（wrap_tool_call，最内层）
12 Orchestration    → 派活拦截（wrap_tool_call）
```

**这个顺序由"洋葱嵌套 + 钩子约束"共同决定**：

**wrap_tool_call 洋葱（外→内）**：

```
RunJournal（06b，更外）
    → McpAudit（07）
        → Sandbox（08）
            → HelpRequest（11a）
                → Orchestration（12）
                    → Evidence（13a，workflow 组）
                        → ToolCall（11c，最内层，贴近 handler）
                            → handler（工具执行）
```

**注意**：`DanglingToolCall`（11b）是 `before_model` 钩子，不是 wrap_tool_call——它在洋葱里"不占位"。

**每个位置的讲究**：

| 中间件 | 为什么在这个位置 |
|---|---|
| `McpAudit` | 在外层——熔断器要先于一切判断"要不要执行" |
| `Sandbox` | 在 McpAudit 内——sandbox 工具要先 acquire 才能执行 |
| `HelpRequest` | 在 ToolCall 外层——拦截 `ask_help` 要在"工具治理"之前 |
| `Orchestration` | 在 ToolCall 外层——派活要先归集产物，再让 ToolCall 记失败/预算 |
| `ToolCall` | **最内层**——贴近 handler，才能准确判成败、记 AgentError |
| `DanglingToolCall` | `before_model` 钩子——必须在模型读历史前修补 |

### 为什么 `HelpRequest` 留在了 `tool` 而不是 `workflow`？

这是**你这一版的聪明之处**：

- 上一版讨论时，我曾建议 `HelpRequest` 归 `workflow`（职责是 HITL）；
- 但**你把它留在 `tool`**——理由是**"钩子位置"优先**；
- **实际这是对的**——因为 `HelpRequest` 必须**在 `ToolCall` 之前**（拦截要在治理前），按分组装配会破坏这个约束；
- **所以"留在 tool"反而是对约束的尊重**——这一版比"纯按职责域分"更成熟。

**这说明你的分类维度是"职责域为主 + 钩子位置修正"**——当两者冲突时，**用钩子位置保住约束**。这是成熟的做法。

### 为什么 `Evidence` 移到了 `workflow`？

```
13a Evidence  → 证据抽取（wrap_tool_call）
```

**它在 `workflow` 组，但装配在 `Orchestration`（12）之后**——这符合约束（派活归集 → 证据抽取）。

**为什么能移到 workflow 而不破坏顺序**：

- `Evidence` 在洋葱里**位于 Orchestration 内层**——注册顺序上它在 `Orchestration` **之后**；
- 而 `workflow` 组的装配位置**恰好在 `tool` 组之后**；
- 所以"移到 workflow"和"保持在 tool 之后"**两个诉求恰好一致**——这是**分类与顺序的巧妙重合**。

**这就是为什么这一版成熟**——`Evidence` 归 workflow 既符合职责（证据沉淀），又符合顺序（在 Orchestration 之后）。

## 5. `workflow`（13a / 13b / 13c / 13d / 14）

**这一组的职责**：**研究流程的收口、反思、任务管理、停滞检测、报告合成**。

### 为什么顺序是这个？

```
13a Evidence          → 证据抽取（wrap_tool_call，靠前）
13b StallDetection    → 停滞检测（wrap_tool_call + after_model）
13c Todo              → 任务管理（多钩子）
13d Reflection        → 反思（after_model）
14  Report            → 报告合成（after_agent）
```

**这个顺序是"从工具侧 → 模型侧 → 收口侧"的自然推进**：

- `Evidence` 在工具阶段（wrap_tool_call）；
- `StallDetection` 工具阶段 + 模型阶段；
- `Todo` / `Reflection` 在模型阶段（after_model）；
- `Report` 在收口阶段（after_agent）。

### 几个关键位置

| 中间件 | 位置讲究 |
|---|---|
| `Evidence` | 在 `Orchestration` 之后（派活归集 → 证据抽取） |
| `StallDetection` | 在 `Evidence` 之后——检测的是"整个工具链的健康度" |
| `Todo` | 在 `StallDetection` 之后——任务管理是更高层 |
| `Reflection` | 在 `Todo` 之后——反思是最后的退出闸门 |
| `Report` | 最后——整个 run 的收口 |

**`StallDetection` 为什么不在 `tool` 组？**

- 它的 `wrap_tool_call` 钩子确实属工具侧；
- 但它的 `after_model` 钩子属流程侧（暂停 + 求助）；
- **核心职责是"流程控制"**——所以归 `workflow` 是对的。

**`Reflection` 与 `Todo` 的共享 jump 预算**：

- 两者都在 `after_model` 阶段"拦截最终答案 + jump_to=model"；
- **共享 jump 预算（合计 ≤3）**——所以它们要**相邻**，且都在 `after_model` 的**尾部**（先 Todo 再 Reflection，或反之，视设计）。

## 6. 为什么这版"成熟"——三个判断标准

你这版分类成熟，是因为它同时满足：

### 标准一：**职责域一致**

- 每组内部职责一致（`context & state` 管 messages+元数据；`memory` 管记忆；`skill` 管技能；`tool` 管工具；`workflow` 管流程）；
- 组间边界清晰，无"钩子位置"与"职责域"混用。

### 标准二：**装配顺序保持**

- 编号仍是装配顺序（01a→14）；
- 分组是**视图**，不是"装配依据"——顺序仍由约束决定。

### 标准三：**冲突处做了正确取舍**

- `HelpRequest` 留 `tool`（按钩子位置）——尊重"必须在 ToolCall 前"；
- `Evidence` 移 `workflow`（按职责域）——恰好与"在 Orchestration 后"一致；
- `Title` / `RunJournal` 移出 `context_engineering`——按职责归 `context & state`。

**这三条同时满足，就是成熟分类**——因为它在**职责域**和**装配顺序**两个维度上都站得住。

## 7. 一句话总结

> **这版成熟，因为它同时满足三个标准**：
> 1. **职责域一致**——每组内部职责统一，组间边界清晰；
> 2. **装配顺序保持**——编号仍是装配顺序，分组只是视图；
> 3. **冲突处正确取舍**——`HelpRequest` 留 `tool`（钩子位置优先）、`Evidence` 移 `workflow`（恰好一致）、`Title`/`RunJournal` 移出 `context_engineering`（职责归位）。
>
> **几个关键位置的理由**：
> - `TaggedContext` / `MessageNormalizer` / `Strategy` 在最前——治理层必须最先介入；
> - `SkillInjection` 在 `SkillMetrics` 前——provenance 写入者在读取者前；
> - `Sandbox` 在 `Memory` 前——记忆引用 sandbox 结果；
> - `Memory` 在 `HelpRequest` / `ToolCall` 前——注入内容不进 tool pairing；
> - `McpAudit` / `Sandbox` / `HelpRequest` / `Orchestration` 在 `ToolCall` 外层——先熔断/acquire/拦截/派活，再治理；
> - `ToolCall` 最内层——贴近 handler 判成败；
> - `Evidence` 在 `Orchestration` 后——派活归集 → 证据抽取；
> - `Reflection` / `Todo` 在 `after_model` 尾部——共享 jump 预算的退出闸门；
> - `Report` 最后——收口。
>
> **核心洞察**：**分类是"职责域"维度，装配是"顺序"维度，两者正交。成熟的做法是——顺序按约束定，分组只作视图；冲突时用钩子位置保住约束（如 HelpRequest）。**
