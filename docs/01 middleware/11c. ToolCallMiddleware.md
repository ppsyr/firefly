---

name: ToolCallMiddleware — 工具调用账本 + 失败分类 + 重试预算 + 超限禁工具 + 硬预算。

description:

【整体职责】
作为最外层的 wrap_tool_call，能同时看到「工具最终结果」和「内层抛出的异常」，
因此在这里统一做四件事：
1. 账本：无论成功还是失败，都往 state.errors 里追加一条 AgentError
   （kind=success / failure），作为后续判定的数据来源。
2. 失败分类：把异常 / 业务失败归到 network / rate_limit / blocked / empty /
   server_error / client_error / unknown 等类型，并给出中文原因。
3. 重试预算：per-tool 连续失败达到 retry_budget 时，短路禁用该工具。
4. 硬预算：per-run 工具调用总数达到 hard_budget 时，短路禁用所有工具，
   强制模型基于现有证据收尾。

【数据来源】
per-tool 连续失败次数、全局调用数，都从 state.errors 派生（不另存计数器）。
per-run 计数用 before_agent 记录的 baseline 做切片，避免跨 run 累积。

【启用范围】
仅 general / expert 模式启用。

【配对完整性】
异常或 handler 返回 None 时，会合成一条 ToolMessage 补上 tool_call_id，
保证 AIMessage(tool_calls) 后紧跟 ToolMessage，否则下一轮 model 调用会 400。

【延迟注入】
failure_summary / budget_exhausted 提示不在 wrap_tool_call 里直接注入
HumanMessage（那会插在并行 tool_calls 的多条 ToolMessage 之间，破坏配对），
而是先入队，等 before_model（此时 ToolMessage 已全部就位）再 drain 注入。

### 0.2. 运行时调用树（wrap_tool_call 主流程）

```
工具调用进入 wrap_tool_call / awrap_tool_call
│
├─ tool_name / state.errors / run_count / run_errors
│
├─ 【短路 1：per-tool retry budget】
│   └─ if _latest_attempt(run_errors, tool_name) >= retry_budget:
│       ├─ _emit("tool.blocked")
│       └─ return Command(update={messages: [error ToolMessage]})
│
├─ 【短路 2：per-run hard budget】
│   └─ if run_count >= hard_budget:
│       ├─ _emit("tool.budget_exhausted")
│       └─ return Command(update={messages: [error ToolMessage]})
│
├─ 【正常路径】
│   ├─ try:
│   │   └─ result = handler(request)
│   │       └─ _process_result(request, result, runtime, exc=None)
│   └─ except Exception as exc:
│       └─ _process_result(request, None, runtime, exc=exc)
│
└─ _process_result 内部
    ├─ 判定成败：
    │   ├─ exc 非空 → _classify_exception → failure AgentError + 合成 error ToolMessage
    │   ├─ _is_failure(result) 命中 → failure AgentError
    │   └─ 否则 → success AgentError
    ├─ run_count = per-run 计数 + 1
    ├─ result is None → 补空 ToolMessage（保配对）
    ├─ failure 且 attempt ∈ (3,6,9) → _queue_summary(失败摘要)
    ├─ run_count >= hard_budget → _queue_summary + _emit("tool.budget_exhausted")
    └─ 返回 Command：
        ├─ result 是 Command → 合并 errors 进 result.update
        └─ 否则 → update={errors, messages:[result]}
```

## 1. 工具调用治理

这个中间件的核心是**工具调用治理**，一共四件事：

| 职责       | 具体做什么                                                                                       | 对应代码                                                               |
| -------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| **账本**   | 每次工具调用（成功/失败）都往 `state.errors` 追加一条 `AgentError`                                            | `_process_result` 里的 `AgentError(...)`                             |
| **失败分类** | 把异常 / 业务失败归到 network / rate_limit / blocked / empty / server_error / client_error / unknown | `_classify_exception`、`_classify_business_failure`、`_is_failure`   |
| **预算控制** | per-tool 连续失败达上限 → 禁该工具；per-run 调用总数达上限 → 禁所有工具                                             | `wrap_tool_call` 里两个短路分支                                           |
| **失败摘要** | 连续失败到 3/6/9 次时，生成结构化摘要，延迟注入给模型                                                              | `_build_failure_summary` + `_queue_summary` + `before_model` drain |

也就是说，它站在**最外层 wrap_tool_call**，同时能看到「工具最终结果」和「内层抛出的异常」，所以被用来做**统一治理点**。

## 2. 这些功能是怎么实现的

### 2.1. 账本：成败都记 `state.errors`

核心在 `_process_result`，分三条路径：

**路径 A：handler 抛异常**

```python
if exc is not None:
    error_type = _classify_exception(exc)          # 分类
    attempt = _latest_attempt(run_errors, tool_name) + 1   # 连续失败 +1
    err = AgentError(
        error_id=_make_id("err"), stage="tool",
        message=f"{tool_name}: {exc}", tool_name=tool_name,
        kind="failure", attempt=attempt,
        error_type=error_type, reason=_reason_for(error_type),
        related_refs=(call_id,), created_at=_now_iso(),
    )
    self._emit(runtime, "tool.failure_streak", {...})
    result = ToolMessage(                          # 合成 error ToolMessage
        content=f"⚠️ 工具 {tool_name} 执行异常（{error_type}）：{exc}",
        tool_call_id=call_id, status="error",
    )
```

关键点：**异常不能直接往上抛**，否则 AIMessage 的 tool_calls 没有对应 ToolMessage，下一轮 model 调用会 400。所以这里合成一条 `status="error"` 的 ToolMessage 补上 `tool_call_id`。

**路径 B：handler 正常返回，但结果被判为失败**

```python
fail = _is_failure(result)          # 业务失败 / status=error / error JSON
if fail:
    error_type, reason = fail
    attempt = _latest_attempt(run_errors, tool_name) + 1
    err = AgentError(..., kind="failure", ...)
    self._emit(runtime, "tool.failure_streak", {...})
```

**路径 C：成功**

```python
else:
    kind = "success"
    attempt = 0
    err = AgentError(..., kind="success", attempt=0, error_type="", reason="")
```

**三条路径都写一条 AgentError 进 `update["errors"]`**，成功也记——这是「账本」的含义，不是只记失败。

### 2.2. 失败分类：三级判定

**第一级：异常分类 `_classify_exception`**

```python
TimeoutError / ConnectionError              → "network"
openai.RateLimitError                       → "rate_limit"
openai.APIStatusError + status_code 5xx     → "server_error"
openai.APIStatusError + status_code 4xx     → "client_error"
文本含 timeout / timed out / connection     → "network"
文本同时含 rate 与 limit                    → "rate_limit"
其余                                        → "unknown"
```

**第二级：结果状态判定 `_is_failure`**

```python
1. ToolMessage.status == "error"：
   从 content 里找 "network"/"rate_limit"/"blocked"/"empty"/
   "server_error"/"client_error" 关键词 → 对应类型；否则 unknown
2. HTTP 200 但内容命中正则：
   _BLOCKED_RE（blocked/forbidden/captcha/403） → "blocked"
   _EMPTY_RE  （no results/empty result/0 results） → "empty"
3. 工具返回的 error JSON（含 '"error"' 且文本含 search failed /
   not installed / failed） → "unknown" + "工具返回错误"
4. 否则 None（成功）
```

**第三级：类型 → 中文原因 `_reason_for`**

```python
_REASON_MAP = {
    "network":      "网络问题（超时/连接失败）",
    "rate_limit":   "API 限流",
    "blocked":      "内容被封锁/拒绝访问",
    "empty":        "无搜索结果",
    "server_error": "服务端错误（5xx）",
    "client_error": "客户端错误（4xx，换 provider 也会失败）",
    "unknown":      "未知错误",
}
```

分类结果写进 `AgentError.error_type` 和 `AgentError.reason`，供后续预算判定、摘要、审计使用。

### 2.3. 预算控制：两个短路分支

**短路 1：per-tool 连续失败 → 禁该工具**

```python
if _latest_attempt(run_errors, tool_name) >= self._retry_budget:
    self._emit(runtime, "tool.blocked",
               {"tool": tool_name, "reason": "retry_budget_exhausted"})
    return Command(update={"messages": [ToolMessage(
        content=f"⚠️ 工具 {tool_name} 已达重试上限（{retry_budget}），已被禁用，请换方法或收尾。",
        tool_call_id=..., status="error",
    )]})
```

- `_latest_attempt` 从 errors 末尾往前找该 tool 最新一条，取其 `attempt`。
- 达到 `retry_budget` 就**不调 handler**，直接返回一条 error ToolMessage。
- 用 `run_errors`（当前 run 切片）判定，避免跨 run 累积把工具永久禁掉。

**短路 2：per-run 调用总数 → 禁所有工具**

```python
if run_count >= self._hard_budget:
    self._emit(runtime, "tool.budget_exhausted",
               {"count": run_count, "max": self._hard_budget})
    return Command(update={"messages": [ToolMessage(
        content=f"⚠️ 本轮工具调用已达预算上限（{hard_budget}），所有工具已禁用，请立即基于现有证据输出最终报告。",
        tool_call_id=..., status="error",
    )]})
```

- `run_count = len(errors) - baseline`，baseline 在 `before_agent` 记录。
- 达到 `hard_budget` 后，**所有**后续工具调用都被拒绝，逼模型收尾。

注意：当前 `_RETRY_BUDGET = _HARD_BUDGET = 999`，注释里写明「用户要求取消限制」，所以实际运行时这两个短路几乎不会触发——但机制仍在。

### 2.4. 失败摘要：延迟注入

**为什么延迟？**
并行 tool_calls 时，若在 `wrap_tool_call` 里直接插 HumanMessage，会插在多条 ToolMessage 之间，破坏 `AIMessage(tool_calls) → ToolMessage` 的配对。所以先入队，等 `before_model`（ToolMessage 已全部就位）再注入。

**入队（`_process_result` 里）**

```python
if kind == "failure" and attempt in _SUMMARY_THRESHOLDS:   # 3/6/9
    summary = self._build_failure_summary(errors + [err], tool_name)
    self._queue_summary(request.runtime, summary)
```

**摘要内容（`_build_failure_summary`）**

```
工具 {tool_name} 已连续失败 {N} 次：
- {error_type}: {reason}
- {error_type}: {reason}
- {error_type}: {reason}
请分析失败模式，考虑换搜索词/换工具/换方法；若判断不可恢复，基于现有证据收尾报告。
```

**注入（`before_model`）**

```python
summaries = self._drain_summaries(runtime)
if not summaries:
    return None
combined = "\n\n".join(dict.fromkeys(summaries))       # 去重
return {"messages": [HumanMessage(
    name="tool_failure_summary",
    additional_kwargs={"hide_from_ui": True},
    content=f"<system_reminder>\n{combined}\n</system_reminder>",
)]}
```

- `dict.fromkeys` 去重，避免同一摘要重复注入。
- `hide_from_ui=True`：UI 不展示这条内部提示。

### 2.5. 队列 / 基线的隔离机制

**队列按 `(thread_id, run_id)` 分组**（`_queue_key`），避免不同线程 / run 的摘要串台。

**baseline 在 `before_agent` 记录**：

```python
errors = state.get("errors") if isinstance(state, dict) else None
self._set_baseline(runtime, len(errors or []))
```

之后 `run_count = len(errors) - baseline`、`run_errors = errors[baseline:]`，实现「只看当前 run」的语义。

**`before_agent` 还清理同 thread 下其他 run 的残留**：

```python
stale = [k for k in list(self._pending_summaries)
         if k[0] == tid and k[1] != rid]
for k in stale:
    self._pending_summaries.pop(k, None)
    self._run_baselines.pop(k, None)
```

防止上个 run 未 drain 的摘要污染新 run。

### 2.6. 返回值合并：兼容内层 Command

```python
if isinstance(result, Command):
    merged = dict(result.update)
    merged.setdefault("errors", []).extend(update["errors"])
    return Command(update=merged)
update["messages"] = [result] if result is not None else []
return Command(update=update)
```

- 若内层（如 Evidence）返回 `Command`，把 errors 合并进它的 update，保留它原有的控制流。
- 否则包一个 `Command(update={errors, messages})` 返回。

## 3. 总结

**工具调用的统一治理点**：

- **记**：成败都入账（`state.errors`）
- **判**：异常 / 业务失败分类
- **管**：per-tool 重试预算 + per-run 硬预算，超限短路禁工具
- **劝**：连续失败到 3/6/9 次时，延迟注入结构化摘要，引导模型换路或收尾

所有判定都从 `state.errors` 派生，不另存计数器；per-run 语义靠 `before_agent` 记录的 baseline 切片实现；摘要延迟到 `before_model` 注入，是为了不破坏 tool_call / tool_response 的消息配对。
