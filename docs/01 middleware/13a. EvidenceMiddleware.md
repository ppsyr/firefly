---

name: EvidenceMiddleware — 拦截证据类工具调用，沉淀 Source / Observation / AgentError 进 ThreadState。

description:

【整体职责】
只在 wrap_tool_call 层拦截一批「证据类工具」的调用，把工具返回的结果
结构化成两类旁路存档：
- Observation：结果的裁剪正文（约 800 字），并关联本次抽取到的 Source；
- Source：从文本里启发式抽取出的 URL。
同时把工具原始结果继续作为 ToolMessage 写回 messages（模型可见），
实现「双写」：messages 给模型看，observations / sources 给旁路存档用。

【设计要点】
- 激活 observations / sources / errors 这几个原本闲置的 state 字段。
- 只挂 wrap_tool_call hook，不改 ReAct 内核（不替模型做决策）。
- 仅处理白名单内的证据类工具；其余工具直接 passthrough。
- 本中间件只负责「成功时抽取证据」；失败分类 / 账本归 ToolCallMiddleware
  （它在外层捕获异常）。

【为什么只在这里做抽取】
证据抽取依赖工具结果文本，属横切逻辑；把它放在中间件里做，
业务工具实现本身不需要感知 observation / source 结构。

## 0. 结构树

### 0.1. 静态结构树（模块 → 函数/类 → 方法）

```
EvidenceMiddleware — 拦截证据类工具调用，沉淀 Source/Observation 进 ThreadState
│
├─ 模块级常量
│   ├─ _EVIDENCE_TOOLS: frozenset            ← 证据类工具白名单
│   │   （web_search / deep_search / browse_page /
│   │     get_page_links / github_search / github_repo_files）
│   ├─ _OBS_CONTENT_MAX = 800                ← Observation 正文上限
│   └─ _URL_RE                               ← URL 抽取正则
│
├─ 模块级工具函数
│   ├─ _make_id(prefix)                      ← "prefix-12hex"
│   ├─ _now_iso()                            ← UTC ISO 时间戳
│   ├─ _tool_text(tool_msg)                  ← ToolMessage.content → 纯文本
│   ├─ _extract_sources(tool_name, tool_msg) ← 文本扫 URL → [Source]（去重）
│   ├─ _make_observation(name, msg, sources, step_id)
│   │   ← 裁剪正文 → Observation + source_refs
│   └─ _resolve_step_id(state)               ← current_step_id 或从 todos 兜底
│
└─ class EvidenceMiddleware(AgentMiddleware)
    ├─ state_schema = ThreadState
    │
    ├─ wrap_tool_call(request, handler)      ← 同步：白名单 → handler → 抽取 → Command
    └─ awrap_tool_call(request, handler)     ← 异步：同上，await handler
```

### 0.2. 运行时调用树（wrap_tool_call / awrap_tool_call 主流程）

```
工具调用进入 wrap_tool_call / awrap_tool_call
│
├─ tool_name = request.tool_call["name"]
├─ if tool_name not in _EVIDENCE_TOOLS:
│     return handler(request) / await handler(request)    ← 非证据工具透传
│
├─ result = handler(request) / await handler(request)
├─ if not isinstance(result, ToolMessage):
│     return result                                       ← 非 ToolMessage（如 Command）原样返回
│
├─ with interrupt_protection():                          ← 抽取过程受中断保护
│   ├─ sources = _extract_sources(tool_name, result)
│   │   ├─ text = _tool_text(result)
│   │   ├─ for match in _URL_RE.finditer(text):
│   │   │   ├─ url = match.rstrip(".,;:")
│   │   │   └─ 去重 → Source(source_id, url, type="web",
│   │   │                       retrieved_at, title="", summary="")
│   │   └─ return [Source, ...]
│   │
│   ├─ step_id = _resolve_step_id(request.state)
│   │   ├─ state["current_step_id"] → 直接用
│   │   ├─ 否则找 todos 首个 in_progress → "todo-{idx}"
│   │   └─ 否则 "todo-0"；todos 空 → None
│   │
│   └─ obs = _make_observation(tool_name, result, sources, step_id)
│       ├─ content = _tool_text(result)[:_OBS_CONTENT_MAX]
│       └─ Observation(observation_id, step_id, content,
│                      source_refs=tuple(s.source_id),
│                      created_at)
│
└─ return Command(update={
     "observations": [obs],         ← 旁路存档
     "sources": sources,            ← 旁路存档
     "messages": [result],          ← 模型可见（保持 tool_call 配对）
   })
```

## 1. 证据类工具是什么

代码里定义的是一份**白名单**：

```python
_EVIDENCE_TOOLS: frozenset[str] = frozenset({
    "web_search",
    "deep_search",
    "browse_page",
    "get_page_links",
    "github_search",
    "github_repo_files",
})
```

它们共同的特征是：**返回的是「外部信息」**——网页搜索结果、页面内容、链接、GitHub 检索结果。这类结果里通常带 URL，是研究报告里可以引用为来源的证据。

不属于白名单的工具（如 `bash`、`present_files`、`delegate_to_*`）直接透传，本中间件不管。

白名单是手维护的（注释写「D9：MVP 手维护」），也就是说新增证据类工具需要手动加进来。

---

## 2. Source / Observation / AgentError 是什么

### 2.1. Source（来源）

从工具结果文本里抽出来的 **URL 记录**。构造方式：

```python
sources.append(Source(
    source_id=_make_id("src"),      # "src-xxxxxxxxxxxx"
    url=url,                        # 抽取到的 URL
    title="",                       # 预留（本中间件不填）
    source_type="web",              # 固定 "web"
    retrieved_at=_now_iso(),        # 抽取时间
    summary="",                     # 预留（本中间件不填）
))
```

含义：这条 URL 是本次工具调用「带回来的来源」，将来报告引用时按 `source_id` 关联。

去重按 URL：同一个 URL 只产生一个 Source。

### 2.2. Observation（观察）

从工具结果文本里裁剪出来的**正文片段**，并关联本次抽到的 Source。构造方式：

```python
Observation(
    observation_id=_make_id("obs"),              # "obs-xxxxxxxxxxxx"
    step_id=step_id,                             # 关联到某个 todo 步骤
    content=text[:_OBS_CONTENT_MAX],             # 前 800 字正文
    source_refs=tuple(s.source_id for s in sources),  # 本次的 Source id 列表
    created_at=_now_iso(),
)
```

含义：这是「本次工具调用在某个研究步骤上看到的内容」的结构化记录，供后续 Reflection / 报告撰写引用。`source_refs` 把 Observation 和 Source 关联起来，形成「观察 → 来源」的链路。

正文截 800 字，是防止把整页内容塞进 state 导致膨胀；完整内容仍留在 `messages` 的 ToolMessage 里。

### 2.3. AgentError

**本文件里没有构造 AgentError**。模块 docstring 标题写了「沉淀 Source/Observation/AgentError」，但代码里只构造了 `Source` 和 `Observation`。

代码里有一条明确注释说明原因：

```python
# FD17：Evidence 只管证据抽取（成功时）；失败分类/账本归 ToolCallMiddleware（外层捕获异常）
```

也就是职责划分：
- **EvidenceMiddleware**：只处理工具**成功返回**时的证据抽取。
- **ToolCallMiddleware**（更外层）：负责捕获异常、判失败、构造 `AgentError`、记 errors 账本。

所以「沉淀 AgentError」实际由 `ToolCallMiddleware` 完成，本文件不参与。这是**文档标题与实现的偏差**，实现上只沉淀 Source 和 Observation。

## 3. 拦截和沉淀是怎么实现的

### 3.1. 拦截：靠 `wrap_tool_call` + 白名单

```python
@override
def wrap_tool_call(self, request, handler):
    tool_name = request.tool_call.get("name", "")
    if tool_name not in _EVIDENCE_TOOLS:
        return handler(request)          # 非证据工具：直接放行

    result = handler(request)            # 证据工具：先正常执行
    if not isinstance(result, ToolMessage):
        return result                    # 非 ToolMessage（如 Command）：原样返回

    ...
```

拦截的实现要点：

1. **入口**：挂 `wrap_tool_call`，能包住工具调用、拿到最终结果。
2. **过滤**：名字不在 `_EVIDENCE_TOOLS` 白名单就 `return handler(request)`，
   等于没它一样——这叫 **passthrough**，不干扰其他工具。
3. **不是阻止执行**：对白名单工具，`handler(request)` 照常调用，工具确实执行了。
   所谓「拦截」是「拦截结果」，不是「阻止调用」。
4. **只处理 ToolMessage**：如果内层返回的是 `Command`（已有控制流），
   直接原样返回，不抽取，避免丢控制流。

### 3.2. 抽取：在 `interrupt_protection()` 里做三件事

```python
with interrupt_protection():
    sources = _extract_sources(tool_name, result)
    state = request.state
    step_id = _resolve_step_id(state)
    obs = _make_observation(tool_name, result, sources, step_id)
```

- `interrupt_protection()`：把这段抽取包在中断保护上下文里，
  防止抽取中途被外部中断打断、留下半成品。
- 三件事：
  1. `_extract_sources`：文本扫 URL → 去重 → `[Source]`；
  2. `_resolve_step_id`：确定这条 observation 归属哪个步骤；
  3. `_make_observation`：裁剪正文 + 关联 source_refs → `Observation`。

**`_resolve_step_id` 为什么要兜底**：
首轮模型可能没先 `write_todos` 就直接搜，此时 `current_step_id` 缺失。
若 `step_id=None`，后续 Reflection 做覆盖度判断会误判。
所以从 `todos` 里找首个 `in_progress`（返回 `todo-{idx}`），
都没有就用 `todo-0`，实在没有 todos 才返回 None。

### 3.3. 沉淀：返回 `Command(update=...)` 双写

```python
return Command(update={
    "observations": [obs],     # 旁路存档
    "sources": sources,        # 旁路存档
    "messages": [result],      # 模型可见
})
```

双写的两侧：

| 字段 | 给谁看 | 作用 |
|---|---|---|
| `messages: [result]` | LLM | 原始工具结果照常进消息历史，模型能看到，且保持 `AIMessage(tool_calls) → ToolMessage` 配对完整 |
| `observations: [obs]` | 系统 / 下游 | 结构化观察，供 Reflection / 报告引用 |
| `sources: sources` | 系统 / 下游 | 结构化来源，报告引用时按 source_id 关联 |

用 `Command(update=...)` 而不是直接返回 `result`，是因为要**同时改多个 state 字段**
（observations / sources / messages），普通返回值只能替换工具结果本身，改不了 state。

### 3.4. 同步 / 异步两条路径

`wrap_tool_call` 与 `awrap_tool_call` 逻辑完全一致，唯一区别是：

```python
result = handler(request)          # 同步
result = await handler(request)    # 异步
```

抽取、构造、返回 Command 的代码在两条路径里各写一遍（未抽公共函数），
但行为等价。

### 3.5. 整体流程一图

```
LLM 发出 tool_call: web_search
        │
        ▼
wrap_tool_call(request, handler)
        │
        ├─ tool_name 不在白名单 → handler(request) 透传（本中间件无感）
        │
        └─ tool_name 在白名单
              │
              ├─ result = handler(request)         ← 工具真的执行了
              │
              ├─ result 不是 ToolMessage → 原样返回
              │
              └─ with interrupt_protection():
                    ├─ sources = _extract_sources(...)       ← URL → Source
                    ├─ step_id = _resolve_step_id(state)     ← 步骤归属
                    └─ obs     = _make_observation(...)      ← 正文 → Observation
              │
              ▼
        return Command(update={
            observations: [obs],     ← 旁路存档
            sources: sources,        ← 旁路存档
            messages: [result],      ← 模型可见 + 配对完整
        })
```

## 4. 总结

- **证据类工具**：白名单里的 6 个「返回外部信息」的工具。
- **Source**：从结果文本抽出的 URL 记录（按 url 去重）。
- **Observation**：结果正文裁到 800 字的片段，用 `source_refs` 关联本次 Source，并挂到某个 `step_id` 上。
- **AgentError**：本文件不构造，由外层的 `ToolCallMiddleware` 负责；标题里的这半句与实现不符。
- **拦截**：`wrap_tool_call` + 白名单过滤，只拦结果不阻止执行，非白名单透传。
- **沉淀**：在 `interrupt_protection()` 内抽取 Source/Observation，返回 `Command(update=...)` 双写——messages 给模型，observations/sources 给旁路存档。



## 5. 为什么要这么做

因为**模型的 ReAct 循环只认 messages，不认「结构化证据」**。工具跑完，结果就是一条 ToolMessage，模型看得到，但系统侧拿不到「这条结果里有哪些 URL、属于哪个步骤、以后报告怎么引用」。`EvidenceMiddleware` 存在的意义就是把「对话流里的临时结果」转成「state 里的结构化档案」。

至于 `AgentError`，如前面所说，**本文件并不构造它**，它由外层的 `ToolCallMiddleware` 写。所以下面分开讲：为什么沉淀 Source / Observation（本文件），以及为什么要沉淀 AgentError（外层，但同属这套设计）。

---

### 1. 为什么只拦「证据类工具」

不是所有工具的结果都值得结构化。证据类工具（web_search / browse_page / github_search…）的共同点是：

- 返回的是**外部信息**，可能是报告里要引用的**来源**；
- 内容里通常**带 URL**，可抽成 Source；
- 结果**天然对应某个研究步骤**（搜什么、在查哪一步）。

而 `bash`、`present_files`、`delegate_to_*` 这类工具：

- bash 返回的是命令输出，不是「来源」；
- present_files 返回的是产出物路径，另有 SandboxMiddleware 处理；
- delegate_to_* 是委派，另有 OrchestrationMiddleware 处理。

如果对所有工具都抽取，一是噪音大（把命令输出当 source），二是白费算力。所以用白名单精准拦截，**只对「会带回证据的工具」做结构化**。

---

### 2. 为什么沉淀 Source / Observation

#### 2.1. messages 会「沉下去」，结构化档案不会

- `messages` 是**滑动上下文**：长对话会被压缩、截断、甚至外置，
  早期工具结果的 URL 可能就丢了。
- `observations` / `sources` 是 **state 字段**，随 run 持久化，
  不受上下文窗口影响。
- 报告撰写阶段要引用来源，靠的是 `sources` 里稳定的 `source_id`，
  而不是去翻可能已被压缩掉的 messages。

#### 2.2. 把「非结构化文本」变成「可引用实体」

工具结果是自由文本，里面散落着 URL。要做引用、去重、覆盖度分析，
需要一个稳定结构：

```
Source:      source_id, url, source_type, retrieved_at
Observation: observation_id, step_id, content, source_refs
```

有了这两层：

- 同一 URL 只产生一个 Source（去重）；
- Observation 用 `source_refs` 指向 Source，形成「观察 → 来源」链路；
- 报告可以按 `source_id` 引用，而不是贴一段不可追溯的文本。

#### 2.3. 把「结果」挂到「步骤」上

`Observation.step_id` 让每条观察归属于某个 todo 步骤
（`_resolve_step_id` 从 `current_step_id` 或 todos 派生）。
这让下游能做**覆盖度判断**：哪些步骤有证据、哪些没有。
如果没有 step_id，Reflection 只能看到一堆无归属的观察，无法判断
「这一步查够了吗」。

#### 2.4. 让 Reflection / 报告不用重解析文本

如果每次要引用证据都去 `messages` 里正则扫 URL，会有两个问题：

- **重复劳动**：每次都要重扫；
- **不一致**：不同地方扫出来的结果可能不同。

在工具调用当下**只抽一次**，写进 state，后续所有消费者读同一份结构化数据，
既省算力又保证一致。

#### 2.5. 保持 ReAct 内核不变（只加旁路）

- 抽取逻辑放在**中间件**，不放业务工具里，也不改 ReAct 决策流程。
- 工具实现不需要感知 observation / source 结构；
- 模型看到的 messages 完全不变（ToolMessage 原样保留）；
- 相当于在消息流旁边**开了一条旁路**，主线不受影响。

---

### 3. 为什么要沉淀 AgentError（外层 ToolCallMiddleware）

本文件不做这件事，但它属于同一套「把临时结果结构化」的思路，顺带讲清：

- **异常不能直接抛**：LLM 发出的 `AIMessage(tool_calls)` 后面必须有对应
  ToolMessage，否则下一轮 model 调用 400。所以异常要转成 `status="error"`
  的 ToolMessage。
- **失败要可统计**：光有「错误消息」看不出失败类型、连续次数。
  写成 `AgentError(kind="failure", error_type=..., attempt=...)` 后，
  外层才能据此：
  - 判 per-tool 连续失败、触发禁工具；
  - 算 per-run 调用数、触发硬预算；
  - 生成失败摘要注入给模型。
- **成功也要记**：`AgentError(kind="success")` 让 errors 成为一份**完整账本**
  （成败都记），per-run 计数才能用 `len(errors) - baseline` 算出来。

所以 AgentError 的沉淀目的和 Source / Observation 一样：
**把对话流里一次性的东西，变成 state 里可统计、可追溯、可复用的结构化数据。**

---

### 4. 总结

拦截证据类工具、沉淀 Source / Observation 进 state，是为了：

1. **抗上下文压缩**——结构化档案不受窗口影响；
2. **可引用**——报告按 `source_id` 引用，可追溯；
3. **可归步骤**——`step_id` 支撑覆盖度判断；
4. **只抽一次**——下游读同一份数据，省算力且一致；
5. **不侵入**——旁路存档，ReAct 内核与工具实现都不改。

AgentError 同理，只是职责落在更外层的 `ToolCallMiddleware`，
用于**失败分类 + 预算控制 + 账本统计**。
