---

name: OrchestrationMiddleware — 横切打点 + 产物汇总。

description:

【整体职责】
在工具调用层拦截 `delegate_to_*` 这类「委派给 specialist」的调用，做两件事：
1. 打点：在调用前后维护多 agent 的四个计数器
   （selection / invoked / completion / fallback）。
2. 产物汇总：把 specialist 返回的 artifacts 归一化成 ArtifactRef 列表，
   写进 ThreadState.orchestration（active_specialists + specialist_artifacts）。

【不做编排决策】
调哪个 specialist 由 LLM 自己决定（soft routing），本中间件不做路由，
只做横切记录与汇总。

【失败处理】
specialist 执行抛异常时，转成一条 error ToolMessage 返回，
保证 AIMessage(tool_calls) → ToolMessage 配对完整（INV#6）。

【挂载位置】
在 ToolCallMiddleware 之后。

【set_current_state】
在 handler 执行前，把当前 state 通过 set_current_state 暴露出去，
供 specialist 的 tool handler 读取 ThreadState。

## 1. 横切打点 + 产物汇总

### 1.1. 路由分流（是不是 delegate 工具）

```python
tool_name = request.tool_call.get("name", "")
if not self._is_delegate_tool(tool_name):
    return handler(request)         # 同步
    return await handler(request)   # 异步
```

- 只处理名字以 `delegate_to_` 开头的工具（`delegate_to_researcher`、
  `delegate_to_reporter` 等）。
- 其他工具（web_search、bash、present_files…）一律原样透传，
  本中间件对它们零介入。
- `specialist_name = tool_name.removeprefix("delegate_to_")`
  剥出「被委派者」的名字，作为打点 key 和 artifacts 归属者。

### 1.2. Before handler：暴露 state + 打前两个点

```python
def _before_handler(self, request, specialist_name):
    state = request.state if isinstance(request.state, dict) else {}
    set_current_state(state)
    if self._metrics:
        self._metrics.record_selection(specialist_name)
        self._metrics.record_invoked(specialist_name)
```

- `set_current_state(state)`：把当前 ThreadState 通过 ContextVar 暴露出去，
  让 specialist 的 tool handler 能读到 state（否则 handler 里拿不到）。
- `record_selection`：记录「被选中」——LLM 决定调它。
- `record_invoked`：记录「已调用」——确实执行了。
- 两个计数器分开，是为了区分「选中了但可能调用失败」与「真正进入执行」。

### 1.3. handler 执行（try / except）

```python
try:
    result = handler(request)
except Exception as exc:
    if self._metrics:
        self._metrics.record_fallback(specialist_name)
    return self._make_error_response(request, exc, specialist_name)
```

- 正常路径：拿到 `result` 往下走。
- 异常路径：打 `record_fallback`（回退），然后构造错误响应——
  这里**不向上抛**，因为上层需要一条 ToolMessage 来配对 tool_call。

### 1.4. 失败路径：合成 error ToolMessage

```python
def _make_error_response(self, request, exc, specialist_name):
    call_id = request.tool_call.get("id", "")
    error_msg = ToolMessage(
        content=json.dumps({
            "success": False,
            "error": {"type": type(exc).__name__, "message": str(exc)},
            "suggestion": "retry, fallback to another specialist, or self-do",
        }),
        tool_call_id=call_id,
        status="error",
    )
    orch = {"active_specialists": [specialist_name], "specialist_artifacts": []}
    return Command(update={"messages": [error_msg], "orchestration": orch})
```

- 关键点：`tool_call_id` 必须填对，否则消息配对不完整。
- content 是一个 JSON 结构，含三部分：
  - `success: False`
  - `error.type` / `error.message`
  - `suggestion`（提示模型重试 / 换 specialist / 自己做）
- 同时写 orchestration（即使失败也记 active_specialists，artifacts 为空）。
- 返回 Command，让 LangGraph 按新消息继续。

### 1.5. After handler：打后两个点 + 汇总产物

```python
def _after_handler(self, specialist_name, result):
    success = self._is_success(result)
    if self._metrics:
        if success:
            self._metrics.record_completion(specialist_name)
        else:
            self._metrics.record_fallback(specialist_name)
    return self._build_orchestration_update(specialist_name, result)
```

- `_is_success` 从结果 JSON 里读 `success` 字段（解析失败视为 False）。
- 成功 → `record_completion`；失败 → `record_fallback`。
- 然后构造 orchestration 更新。

### 1.6. 成功判定

```python
def _is_success(self, result):
    text = _tool_text(result)
    try:
        data = json.loads(text)
        return bool(data.get("success", False))
    except (json.JSONDecodeError, TypeError):
        return False
```

- 约定：specialist 工具返回 JSON，含 `success` 字段。
- 先把结果压平成字符串（`_tool_text` 处理 ToolMessage / Command 两种形态）。
- 解析失败一律按失败算（保守）。

### 1.7. 产物汇总

```python
def _build_orchestration_update(self, specialist_name, result):
    artifacts: list[ArtifactRef] = []
    text = _tool_text(result)
    try:
        data = json.loads(text)
        for a in data.get("artifacts", []):
            artifacts.append(ArtifactRef(
                path=a.get("path", ""),
                artifact_type=a.get("type", ""),
                specialist_name=specialist_name,
            ))
    except (json.JSONDecodeError, TypeError):
        pass
    return {
        "active_specialists": [specialist_name],
        "specialist_artifacts": artifacts,
    }
```

- 从结果 JSON 的 `artifacts` 列表逐项构造 `ArtifactRef`，
  并给每个 artifact 打上「是哪个 specialist 产出的」标签。
- `active_specialists` 记本次 specialist；`specialist_artifacts` 记产物列表。
- 解析失败 / 无 artifacts → 空列表，不报错。

### 1.8. 合并返回

```python
orch_update = self._after_handler(specialist_name, result)

if isinstance(result, Command):
    merged = dict(result.update)
    merged["orchestration"] = orch_update
    return Command(update=merged)

return Command(update={"messages": [result], "orchestration": orch_update})
```

- 若 handler 本身返回 `Command`（内层已有控制流），
  把 orchestration 合并进它的 update，保留原控制流。
- 否则包成 `Command(update={messages: [result], orchestration: orch_update})`。

## 2. 为什么要这么做

### 2.1. 为什么用「中间件」而不是写在 specialist 里

- **横切关注点**：打点 / 汇总对所有 specialist 一视同仁，
  写在中间件里就一处维护，不用每个 specialist 各写一遍。
- **统一拦截**：所有 `delegate_to_*` 调用都经过这里，
  不会因为某个 specialist 忘了打点而漏统计。

### 2.2. 为什么「不做编排决策」

- 调哪个 specialist 是**语义决策**，LLM 比规则更擅长（soft routing）。
- 中间件做规则路由会僵化，且与 LLM 的判断冲突。
- 所以中间件只做**记录**，把决策权留给模型。

### 2.3. 为什么失败要转 error ToolMessage 而不是抛异常

- LLM 发出的 `AIMessage(tool_calls)` 后面**必须**跟对应的 ToolMessage，
  否则下一轮 model 调用会 400（pairing 完整性，INV#6）。
- 抛异常会把 tool_call 悬空，破坏消息历史。
- 转 error ToolMessage 后，模型看到「调用失败 + 建议」，
  可以据此决定重试 / 换 specialist / 自己做。

### 2.4. 为什么四个计数器（selection / invoked / completion / fallback）

它们构成一条完整的委派漏斗：

```
selection   ← LLM 选中了它
invoked     ← 真的开始执行
completion  ← 执行成功
fallback    ← 执行失败（或异常）
```

有了这四个数，才能算出：
- **选中→调用**的转化率（有没有「选了没调」）；
- **调用→成功**的成功率；
- 哪个 specialist 失败多（fallback 高）需要优化。

只记「调用次数」看不出这些维度，所以拆成四个点。

### 2.5. 为什么要 `set_current_state`

- specialist 的 tool handler 需要读 ThreadState（比如查 governance、
  看历史、写产物）。
- 但 handler 的函数签名里通常没有 state 参数。
- 用 ContextVar 暴露 state 是「不侵入 handler 签名」的解法：
  handler 想读就 `get_current_state()`，不想读也无感。

### 2.6. 为什么要归一化 artifacts

- specialist 返回的 artifacts 形态各异（可能只有 path、可能含 type）。
- 统一成 `ArtifactRef(path, artifact_type, specialist_name)` 后：
  - 下游汇总 / 展示 / 下载只需要认一种结构；
  - `specialist_name` 打上归属，知道产物是谁做的；
  - 写进 `state.orchestration` 后，UI / 报告可以直接读取。

### 2.7. 为什么要兼容 Command 返回

- 有些 specialist 或内层中间件返回 `Command`（带自己的控制流）。
- 直接包一层 `Command` 会**丢掉内层控制流**（比如跳转、额外 update）。
- 所以先判断是不是 Command：
  - 是 → 把 orchestration **合并**进它的 update，保留原控制流；
  - 否 → 自己包一层。

### 2.8. 总结

这个中间件把「多 agent 委派」的**记录与汇总**从业务里抽出来，
做成一个统一、无侵入、失败安全的横切层：

- **统一**：所有 delegate 调用一处拦截；
- **无侵入**：通过 ContextVar 暴露 state，不改 specialist 签名；
- **失败安全**：异常转 ToolMessage，保消息配对；
- **可观测**：四计数器 + artifacts 汇总，支撑统计与展示；
- **不越权**：只记录，不替 LLM 做路由决策。
