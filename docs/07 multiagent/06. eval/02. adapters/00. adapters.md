## 1. 评估器是做什么的

## 1.1. 一句话

**评估器是 L3 评估层的"打分员"——给定 candidate（L2 变异出的新版本）和 baseline（当前活跃版本），让两者在同一批任务上各跑一遍，比较表现，返回 `EvalResult` 供 L2 决定是否晋升。**

---

## 1.2. 评估器解决什么问题

L2 进化层会**变异出 candidate**（新版本产物）。但"变异"不保证"更好"——**需要一个客观的比较机制**。

评估器就是这个机制：

```
L2 变异出 candidate
    │
    │ 问题：candidate 真的比 baseline 好吗？
    ▼
评估器：
    ├─ 让 candidate 跑一批任务
    ├─ 让 baseline 跑同一批任务
    ├─ 比较两者的成功率 / 得分
    └─ 返回 EvalResult
    │
    ▼
L2 PromotionGate 根据 EvalResult 决定：晋升 / 丢弃
```

**没有评估器，L2 就是"瞎变异"**——不知道新版本是好是坏。

---

## 1.3. 评估器做什么

**三个动作**：

| 动作 | 说明 |
|---|---|
| **遍历任务** | 对 `ctx.task_sample` 里的每个 task |
| **双跑对比** | candidate 和 baseline 各跑一遍 |
| **聚合打分** | 算平均分 + Wilson 置信区间 |

**输出 `EvalResult`**：

```python
EvalResult(
    candidate_score=0.85,      # candidate 的平均分
    baseline_score=0.72,       # baseline 的平均分
    ci_low=0.78,               # candidate 的 CI 下界
    ci_high=0.92,              # candidate 的 CI 上界
    sample_size=10,
    method_used="programmatic",
    success=True,
)
```

---

## 1.4. 评估器在 L2 循环里的位置

```
L2 检测退化 → 触发进化
    │
    ▼
L2 变异出 candidate
    │
    ▼
L2 抽样 task_sample
    │
    ▼
★ 评估器（L3）：candidate vs baseline
    │
    └─ 返回 EvalResult
    │
    ▼
L2 PromotionGate.decide(EvalResult)
    ├─ candidate 更好 → 晋升
    └─ 没更好 → 丢弃
```

**评估器是"L2 晋升决策的输入提供者"。**

---

## 1.5. 评估器评估什么

| 概念 | 是什么 |
|---|---|
| **评估对象** | `EvolutionArtifact`（candidate / baseline） |
| **评估任务** | `EvalTask`（L2 抽样的历史调用记录） |
| **评估方式** | 规则判定 或 LLM 打分 |
| **评估结果** | `EvalResult`（candidate_score / baseline_score / CI） |

**核心**：评估器评的是"版本质量"，不是"单次调用对错"——这是 L3 和 L1 的根本区别。

---

## 1.6. 评估器和 Facade 的区别

**别混淆——两者都可能被叫"评估器"**：

| | 评估器（Adapter） | Facade |
|---|---|---|
| 层次 | L3 adapter | L2 用的 facade |
| 接口 | `EvalAdapter` | `EvalBridge` |
| 启用条件 | L3 启用 | L3 未启用 |
| 注册位置 | `SpecialistEvalRegistry` | 直接注入 `PromotionGate` |
| 数量 | 3 个 | 1 个 |

**两者都实现"评估"这件事**，但**位置、接口、生命周期不同**。

---

## 1.7. 总结

> **评估器是 L3 的"打分员"——给定 candidate 和 baseline，让两者在同一批任务上各跑一遍，比较表现，返回 EvalResult 供 L2 晋升决策。它解决"变异出的新版本是否真的更好"这个问题，是 L2 从"瞎变异"变成"有依据地进化"的关键。评估对象是 EvolutionArtifact（版本产物），不是单次调用结果——这是 L3 和 L1 的根本区别。**

## 2. 三个评估器有什么区别

## 2.1. 一句话

**评估对象相同（`EvolutionArtifact`：candidate vs baseline），流程相同（遍历 task_sample → 评分 → 算 Wilson CI），唯一区别是"怎么给一个 task 打分"：两个用规则判 bool（0/1），一个用 LLM 打连续分（[0,1]）。**

---

## 2.2. 三者核心对照

| 维度 | ProgrammaticAdapter | LongitudinalPairsAdapter | LLMJudgeAdapter |
|---|---|---|---|
| **method_used** | `"programmatic"` | `"longitudinal_pairs"` | `"llm_judge"` |
| **评分来源** | `evaluator.evaluate()` → bool | `evaluator.evaluate()` → bool | `judge_fn()` → float |
| **分数形态** | 二值 1.0 / 0.0 | 二值 1.0 / 0.0 | 连续 [0, 1] |
| **依赖** | L2 `Evaluator`（规则检查） | L2 `Evaluator`（规则检查） | LLM（四维加权打分） |
| **成本** | 极低 | 低 | **高**（调 LLM） |
| **信息量** | 少（只知成/败） | 少（只知成/败） | **多**（知好到什么程度） |
| **适用场景** | 有明确成败标准的任务 | 版本对比场景 | 开放式任务 / 质量评估 |
| **实现代码** | 几乎逐字相同 | 几乎逐字相同 | 评分逻辑不同 |

---

## 2.3. 两个"规则派"几乎一模一样

`ProgrammaticAdapter` 和 `LongitudinalPairsAdapter` 的 `evaluate` **代码逐字相同**：

```python
# ProgrammaticAdapter
for task in ctx.task_sample:
    c_met = self._evaluator.evaluate(ctx.candidate, task)   # bool
    b_met = self._evaluator.evaluate(ctx.baseline, task)    # bool
    candidate_scores.append(1.0 if c_met else 0.0)
    baseline_scores.append(1.0 if b_met else 0.0)
...
method_used="programmatic"

# LongitudinalPairsAdapter
for task in ctx.task_sample:
    c_met = self._evaluator.evaluate(ctx.candidate, task)   # bool
    b_met = self._evaluator.evaluate(ctx.baseline, task)    # bool
    candidate_scores.append(1.0 if c_met else 0.0)
    baseline_scores.append(1.0 if b_met else 0.0)
...
method_used="longitudinal_pairs"
```

**唯一区别是 `method_used` 字符串不同。**

**为什么两份都保留**：注释说 "3 adapter 各自实现（L3-3.1 决策 b）"——**刻意不共享基类**，让每个 adapter 独立演进。

---

## 2.4. 区别的"语义层"在哪

虽然代码几乎一样，但**语义定位不同**：

| Adapter | 语义定位 | task_sample 来源 |
|---|---|---|
| `ProgrammaticAdapter` | **通用程序化评估** | L2 抽样 |
| `LongitudinalPairsAdapter` | **纵向配对对比**（80% 失败 + 20% 成功） | L2 抽样（特定策略） |
| `LLMJudgeAdapter` | **LLM 质量评分** | L2 抽样 |

**`LongitudinalPairsAdapter` 的特殊性在于 "longitudinal"（纵向）**——它强调"跨版本、同批任务对比"的语义。抽样策略（80% 失败 + 20% 成功）由 L2 负责，**让评估聚焦在"失败案例上新版本有没有改善"**。

**`ProgrammaticAdapter` 是通用版**——不限定抽样策略，只做"规则判定 + 聚合"。

---

## 2.5. `LLMJudgeAdapter` 的本质区别

**它不只换评分来源，还换了"评什么"**：

```
Programmatic / LongitudinalPairs：
    评"这个 task 成不成"
    → 二值

LLMJudge：
    评"这个 task 干得多好"
    → 四维加权：
        task_completion  (0.50)
      + response_quality (0.35)
      + efficiency       (0.05)
      + tool_usage       (0.10)
    → 连续 [0,1]
```

**LLM judge 提供更丰富的信号**：

- **能区分"勉强完成"和"完美完成"**——规则只能判"成/不成"
- **适合开放式任务**——没有明确成败标准时，规则无法判定，LLM 可以打分
- **代价是成本高**——每次评分都要调 LLM

---

## 2.6. 三者怎么被使用

**由 `OrchestrationBridge` 按 method 名选择**：

```
L2 触发评估
    │
    └─ Bridge.evaluate(ctx)
        │
        ├─ 决定 method：
        │   ├─ ctx.eval_method_hint 有值 → 用它
        │   └─ 否则用默认
        │
        └─ registry.get(method)
            ├─ "programmatic"        → ProgrammaticAdapter
            ├─ "longitudinal_pairs"  → LongitudinalPairsAdapter
            └─ "llm_judge"           → LLMJudgeAdapter
```

**选哪个由 method 名决定**——而 method 名可能来自：

- `EvalContext.eval_method_hint`（L2 建议）
- Bridge 的默认策略
- 配置

---

## 2.7. 什么时候用哪个

| 场景 | 推荐 |
|---|---|
| 任务有明确成败标准（测试通过 / 文件存在） | `programmatic` |
| 想聚焦"失败案例上有没有改善" | `longitudinal_pairs` |
| 开放式任务 / 需要质量评分 | `llm_judge` |
| 预算有限 | `programmatic` / `longitudinal_pairs` |
| 追求评估精度 | `llm_judge` |

**实际选择由 L2 决定**——L2 根据任务类型、预算、历史表现等选 method。

---

## 2.8. 和 `MultiagentProgrammaticFacade` 的区别

**别混淆——facade 不是第三个 adapter**：

| | MultiagentProgrammaticFacade | 三个 adapter |
|---|---|---|
| 层次 | L2 用的 facade | L3 的 adapter |
| 接口 | `EvalBridge` | `EvalAdapter` |
| 启用条件 | **L3 未启用** | **L3 启用** |
| 注册位置 | 直接注入 PromotionGate | 注册进 SpecialistEvalRegistry |
| 数量 | 1 个 | 3 个 |

**Facade 是"L3 未启用时的降级门面"**——它和 `ProgrammaticAdapter` 代码几乎一样，但**位置、接口、生命周期都不同**。

## 2.10. 总结

> **三个评估器评估对象相同（EvolutionArtifact：candidate vs baseline）、流程相同（遍历任务 → 评分 → 算 Wilson CI），唯一区别是"怎么给一个 task 打分"：`ProgrammaticAdapter` 和 `LongitudinalPairsAdapter` 用规则判 bool（0/1），代码几乎逐字相同，区别只在 method 名和语义定位（后者强调纵向配对、80% 失败抽样）；`LLMJudgeAdapter` 用 LLM 四维加权打连续分（[0,1]），信息量更大但成本更高。三者由 `OrchestrationBridge` 按 method 名选择——选哪个由 L2 根据任务类型、预算、评估精度决定。**
