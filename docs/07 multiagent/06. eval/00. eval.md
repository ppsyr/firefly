## 1. L3 Eval 整体总结

## 1.1. 概述

**L3 是 multiagent 的"评估层"——当 L2 变异出新版本（candidate）时，L3 让 candidate 和 baseline 在同一批任务上各跑一遍，比较表现，返回 `EvalResult` 供 L2 决定是否晋升。**

---

## 1.2. L3 在 L1/L2/L3 三层里的位置

```
L1 运行层（常开）—— 记录每次派活的指标
    │
    │ 读指标
    ▼
L2 进化层（默认关）—— 变异 + 晋升决策
    │
    │ 需要打分时调
    ▼
L3 评估层（默认关）—— 打分
```

| 层 | 职责 | 默认 | 核心文件 |
|---|---|---|---|
| L1 | 记录指标 | 常开 | `metrics.py` |
| L2 | 变异 + 晋升 | 关 | `evolution/` |
| L3 | 评估打分 | 关 | `eval/` |

**注意**：编号不是执行顺序——**L2 在进化流程中调 L3**，所以顺序是 L2 触发 → L3 评估 → L2 晋升。

---

## 1.3. L3 的组件全貌

```
eval/
├── types.py                  ← 词汇表（EvalContext / SpecialistHealthReport / DecisionLogRecord）
├── registry.py               ← 评估器注册表 + EvalAdapter Protocol
├── bridge.py                 ← EvalBridge 契约 + OrchestrationBridge 实现
├── facade.py                 ← MultiagentProgrammaticFacade（L3 未启用时用）
├── db.py                     ← schema 管理（2 张表）
├── decision_log.py           ← 决策日志读写门面
├── runtime_tracker.py        ← 健康监控 + degraded 检测
├── bootstrap.py              ← L3 装配入口
├── cli.py                    ← CLI 命令树 skeleton（暂不实现）
└── adapters/
    ├── programmatic.py       ← 程序化评估
    ├── llm_judge.py          ← LLM 四维加权评估
    └── longitudinal_pairs.py ← 纵向配对评估
```

---

## 1.4. 三个评估器（adapter）

| Adapter | method_used | 评分方式 | 成本 |
|---|---|---|---|
| `ProgrammaticAdapter` | `"programmatic"` | evaluator → bool → 0/1 | 极低 |
| `LongitudinalPairsAdapter` | `"longitudinal_pairs"` | evaluator → bool → 0/1 | 低 |
| `LLMJudgeAdapter` | `"llm_judge"` | judge_fn → [0,1]（四维加权） | 高 |

**评估对象相同**（`EvolutionArtifact`：candidate vs baseline），**流程相同**（遍历 task_sample → 评分 → 算 Wilson CI），**唯一区别是怎么给一个 task 打分**。

**LLM judge 的四维权重**：

```python
WEIGHTS = {
    "task_completion": 0.50,     # 任务完成
    "response_quality": 0.35,    # 响应质量
    "efficiency": 0.05,          # 效率
    "tool_usage": 0.10,          # 工具使用
}
```

---

## 1.5. 两个 Facade（L3 未启用时的降级）

| | OrchestrationBridge | MultiagentProgrammaticFacade |
|---|---|---|
| 接口 | `EvalBridge` | `EvalBridge`（同一个） |
| 启用条件 | L3 启用 | L3 未启用 |
| 评估方法 | 通过 registry 选（3 种） | 只支持 programmatic |
| `list_available_methods` | registry 里有啥返回啥 | 固定 `("programmatic",)` |
| 依赖 | `SpecialistEvalRegistry` | `Evaluator` callable |

**两者实现同一 `EvalBridge` 契约**——L2 的 `PromotionGate` 无论 L3 是否启用，调用方式完全一样。**这是"渐进迁移"的设计。**

---

## 1.6. 完整评估流程

```
① L2 检测退化 → 触发进化
        │
        ▼
② L2 变异出 candidate
        │
        ▼
③ L2 抽样 task_sample
        │
        ▼
④ L2 调 bridge.evaluate(ctx)               ← EvalBridge 契约
        │
        ▼
⑤ OrchestrationBridge.evaluate(ctx)        ← L3 启用时走这里
        │
        ├─ _select_method(ctx)              ← 四级优先级选 method
        │   ① eval_method_hint
        │   ② 全 task 有 expected_outcome → longitudinal_pairs
        │   ③ task_type == "open_ended" → llm_judge
        │   ④ 默认 → programmatic
        │
        ├─ registry.get(method)             ← 取 adapter
        │
        └─ adapter.evaluate(ctx)            ← 打分
            ├─ 遍历 task_sample
            ├─ candidate / baseline 各评一次
            ├─ 算平均分 + Wilson CI
            └─ 返回 EvalResult
        │
        ▼
⑥ L2 PromotionGate.decide(EvalResult)
        ├─ candidate 更好 → 晋升
        └─ 没更好 → 丢弃
```

## 1.7. 决策日志（DecisionLog）

**决策日志是 L3 的"跨 run 经验累积"**：

| 组件 | 角色 |
|---|---|
| `DecisionLogWriter` | L1 写入门面（fire-and-forget 异步写） |
| `DecisionLogReader` | L2 读取门面（查最近 N 条 lesson） |
| `_DecisionLogStore` | 持久化契约（`MultiAgentMetricsStore` 实现） |

**关键设计**：

- **异步写**：`ThreadPoolExecutor(max_workers=1)` 串行写，不阻塞 L1。
- **lesson 不进 prompt**：作为 L2 EvolutionMutator 的输入样本，不注入当前对话。
- **归档不删除**：90 天后移到 `specialist_decision_log_archive` 表。

---

## 1.8. 健康监控（RuntimeTracker）

**`SpecialistRuntimeTracker` 做两件事**：

| 方法 | 用途 |
|---|---|
| `health_report(name)` | 生成单个 specialist 的健康报告（trend / cost / latency） |
| `degraded_specialists(threshold)` | 列出已 degraded 的 specialist |

**degraded 判定**：`total_invoked >= 5` 且 `completion_rate < threshold`——**样本不足时不判**。

**触发方式**：`trigger_l2_evolution_if_degraded` 只 enqueue 消息，**不直接调 L2**——解耦。

---

## 1.9. L3 的装配（bootstrap）

**`setup_l3(config, metrics_store, task_queue)`**：

```
① enabled=false → return None（L2 行为不变）
② 构造 SpecialistEvalRegistry + 注册 3 adapter（MVP 全 None）
③ 构造 OrchestrationBridge
④ 构造 SpecialistRuntimeTracker
⑤ 构造 DecisionLogWriter / Reader
⑥ 构造 MultiagentProgrammaticFacade
⑦ 启动 6h 健康检查 daemon 线程
⑧ 打包 L3Setup 返回
```

**装配位置**：`setup_l3` 嵌套在 `setup_l2` 里——**L3 是 L2 的子层**。

---

## 1.10. L3 的关键设计原则

| 原则 | 体现 |
|---|---|
| **契约优先** | `EvalAdapter` / `EvalBridge` 都是 Protocol；实现方无需继承 |
| **fail-closed** | 评估异常不抛，返回 `EvalResult(success=False)` |
| **渐进迁移** | L3 未启用时用 facade，启用后换 bridge，接口不变 |
| **解耦** | L3 只 enqueue 消息，不直接调 L2 TriggerManager |
| **同步优先** | 评估是 sync 调用（与 L1 一致） |
| **不复用 skill** | L3 自建 EvalBridge / RuntimeTracker，因类型不兼容 |
| **成本分层** | programmatic 极低 → longitudinal_pairs 低 → llm_judge 高 |

## 1.12. L3 与 L1 / L2 的关系

| 方向 | 接口 | 说明 |
|---|---|---|
| L3 读 L1 | `MetricsView` Protocol | 读 specialist 指标 |
| L2 调 L3 | `EvalBridge` Protocol | 请求评估 |
| L3 写 L1 | `_DecisionLogStore` Protocol | 写决策日志 |
| L3 触发 L2 | `cron_queue.put(...)` | enqueue 消息（不直调） |

**L3 与 L1 / L2 全部通过契约交互**——**没有直接依赖具体实现**。

---

## 1.13. 一句话总结

> **L3 是 multiagent 的评估层——它用 3 个 adapter（programmatic / llm_judge / longitudinal_pairs）评估 candidate vs baseline，返回 EvalResult 供 L2 晋升决策。通过 EvalBridge 契约与 L2 解耦（L3 未启用时用 facade 降级），通过 MetricsView 契约读 L1 指标，通过 _DecisionLogStore 契约写决策日志。核心设计原则是契约优先、fail-closed、渐进迁移、解耦。唯一未实现的组件是 CLI（刻意保留设计，等更好的可观测形态）。**
