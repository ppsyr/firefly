## 0. MultiAgent 完整结构树

### 0. 顶层结构

```
poirot/backend/agents/multiagent/          ← MultiAgent 子系统根目录
│
├── __init__.py                            ← 包初始化
│
├── 【配置与类型层】
│   ├── config.py                          ← MultiAgentConfig / L2Config / L3Config / BudgetConfig
│   ├── types.py                           ← 核心数据契约（Request / Result / Capability / ...）
│   └── exceptions.py                      ← SpecialistError + SubagentError 两条独立层次
│
├── 【装配与启动层】
│   └── bootstrap.py                       ← setup_multiagent() 装配入口
│
├── 【运行时核心层】
│   ├── registry.py                        ← SpecialistRegistry（花名册）
│   ├── middleware.py                      ← OrchestrationMiddleware（拦截 delegate_to_*）
│   ├── tools.py                           ← 动态生成 delegate_to_* 工具
│   ├── metrics.py                         ← L1 指标存储（SQLite，多张表）
│   ├── sandbox_binder.py                  ← 沙箱绑定桥（multiagent ↔ sandbox）
│   └── intent_strengthened.py             ← 意图识别 + candidate metadata
│
├── 【契约层（Protocol）】
│   ├── specialist.py                      ← SpecialistAgent 契约
│   ├── specialist_runtime.py              ← SpecialistRuntime 契约
│   ├── subagent.py                        ← SubagentProvider 契约
│   ├── credential_provider.py             ← CredentialProvider 契约
│   ├── context_summarizer.py              ← ContextSummarizer 契约
│   ├── result_summarizer.py               ← ResultSummarizer 契约
│   └── sandbox_binder.py                  ← SandboxBinder 契约
│
├── 【实现层】
│   ├── specialists/                       ← Specialist 实现
│   ├── runtimes/                          ← Runtime 实现
│   ├── credentials/                       ← Credential 实现
│   ├── summarizers/                       ← Summarizer 实现
│   ├── installer/                         ← Pi 专属安装器
│   └── extensions/                        ← Pi 专属 TS extension
│
├── 【L2 进化层】
│   └── evolution/                         ← 完整 L2 子系统
│
├── 【L3 评估层】
│   └── eval/                              ← 完整 L3 子系统
│
└── 【MCP 桥】
    └── mcp/
        └── specialist_mcp_server.py       ← specialist 通过 MCP 调 Poirot 8 接口
```

> **MultiAgent 完整结构 = 契约层（7 个 Protocol）+ 实现层（4 specialist + 4 runtime + 3 credential + 8 summarizer + 1 installer + 1 extension）+ 装配层（setup_multiagent → setup_l2 → setup_l3 三层嵌套）+ 运行时核心（registry / middleware / tools / metrics）+ L2 进化子系统（15 个组件）+ L3 评估子系统（10+ 个组件）+ MCP 桥。核心流程是"装配 → L1 graph 触发 → LLM 派活 → middleware 拦截 → tools handler 编排 → runtime 执行 → L2 worker 消费 → L3 评估"。L2 与 L3 通过 EvalBridge 契约交互，共享 task_queue / metrics_store / multiagent.db。**
## 1. MultiAgent 整体定位

### 1.1. 概述

**MultiAgent 是 Poirot 的"多 Agent 编排层"——让 Leader Agent 能把任务派给外部 specialist（Claude Code / Codex / Pi）或自复制 subagent，并通过 L1/L2/L3 三层实现"运行记录 → 评估 → 进化"的闭环。**

### 1.2. 它在整个 Poirot 里的位置

```
app/bootstrap.py（应用启动）
    │
    └─ bootstrap_runtime
        ├─ setup_multiagent（multiagent 装配）
        │   ├─ specialist + metrics + middleware + tools
        │   └─ setup_l2（L2 装配）
        │       └─ setup_l3（L3 装配）
        │
        ├─ CapabilityRegistry（注入）
        └─ make_lead_agent（Leader 构造）
            └─ LLM 看到 delegate_to_* 工具
```

**核心**：multiagent 是"给 Leader 装上派活能力"的子系统。

## 2. MultiAgent 的核心流程（7 步）

```
① Leader 决策
   └─ leader/agent.py + prompts/system/leader/*.md
      判断：自己干还是派活？派给谁？

② 选 Specialist
   └─ multiagent/registry.py
      按 capabilities 查表，拿到 Specialist 实例

③ 摘要上下文（进）
   └─ ContextSummarizer（按 specialist 类型选）
      把 Leader 的完整上下文压成子 Agent 能消费的输入

④ 注入凭证
   └─ CredentialProvider（claude / codex / pi）
      以什么身份跑

⑤ Runtime 执行
   └─ SpecialistRuntime（claude_code / codex / pi / subagent）
      真正把活跑起来；需要沙箱时经 sandbox_binder.py 绑定

⑥ 摘要结果（出）
   └─ ResultSummarizer（按 specialist 类型选）
      把子 Agent 原始输出压成 Leader 能消费的结果

⑦ 回 Leader
   └─ 结果进 Leader 上下文，继续下一轮决策
```

**关键**：这 7 步是"一次派活"的完整链路。

## 4. 四个 Specialist 的对比

### 4.1. 总览

| 维度 | subagent | ClaudeCode | Codex | Pi |
|---|---|---|---|---|
| **本质** | 进程内自复制 | 外部 CLI | 外部 ACP | 外部 CLI + RPC + TS extension |
| **capability** | RESEARCH | REVIEW | CODING | CODING |
| **执行方式** | `agent.invoke` | `subprocess.run` | ACP 异步 | `subprocess.Popen` + RPC |
| **通信** | 进程内 | CLI + stdout | JSON-RPC | stdio JSON-RPC |
| **依赖** | 无外部依赖 | claude CLI | codex-acp adapter | pi CLI + TS extension |
| **装配闸门** | 无 | 凭证探测 | 凭证探测 | 安装器 + 凭证提供者 |
| **输入摘要** | LLM + 规则 | 纯规则 | 纯规则 | 纯规则 |
| **输出摘要** | 纯继承 | 继承 + 2 覆写 | 继承 + 2 覆写 | 覆写 summarize（三段解析） |
| **token 用量** | ❌ | ❌ | ❌ | ✅ 从 agent_end 提取 |
| **强制 MCP** | ❌ | ❌ | ❌ | ✅ |
| **跨语言桥** | ❌ | ❌ | ❌ | ✅ TS extension |
| **物理隔离** | 无 | 无 | 无 | 无（逻辑约束） |

### 4.2. 为什么 Pi 和 Codex 都是 CODING

- **capability 是"能力标签"不是"唯一主键"**
- 多个 specialist 可以共享同一能力
- 好处：① 用户装哪个用哪个；② 能力有差异可择优选；③ 一个失败可换另一个
- 当前不足：tool description 一样，LLM 区分度低

### 4.3. 为什么 Pi 需要 installer，Claude / Codex 不需要

- **Pi 的可用性只取决于"CLI 装没装"**——不需要登录、装完设个 API key 就能用
- **Claude / Codex 需要登录**（OAuth 或交互式）——"装"只是第一步，Poirot 无法代替用户完成登录
- 所以 Pi 走"自动安装"，Claude / Codex 走"凭证探测"

## 5. 三层学习/进化体系（L1 / L2 / L3）

### 5.1. 三层总览

| 层 | 名称 | 干什么 | 默认 | 触发方式 | 核心文件 |
|---|---|---|---|---|---|
| **L1** | 运行层 | 每次派活记录指标 | **常开** | 每次调用 | `metrics.py` |
| **L2** | 进化层 | 读指标 → 变异 specialist → 产新版本 | **关闭** | 数据驱动 | `evolution/` |
| **L3** | 评估层 | 给 specialist 产出打分 → 产决策日志 | **关闭** | 数据驱动 | `eval/` |

**核心思想：便宜的事常做，贵的事按需做。**

### 5.2. 三层的执行顺序（重要修正）

**编号不是执行顺序**——真实顺序是：

```
L2 触发进化 → L2 变异 → L3 评估 → L2 根据评估结果晋升
```

**评估在"变异之后、晋升之前"**——"L2 进化、L3 评估"说的是**职责分工**，不是执行顺序。

### 5.3. L2 演化在演化什么

**演化的是两种模板**：

| 产物 | 代号 | 控制什么 | 演化什么 |
|---|---|---|---|
| `ContextSummaryTemplate` | **W2** | specialist 调用前的 context 生成 | extractors / filters / max_tokens / prompt_skeleton |
| `SkillInjectionTemplate` | **W4** | specialist 调用时的 skill 注入 | skill_selector / injection_format / max_skills |

**演化方向由 FailureCategory 驱动**：

- `CONTEXT_INSUFFICIENT` → 演化 W2
- `ABILITY_INSUFFICIENT` → 演化 W4
- `GOAL_UNCLEAR` / `SANDBOX_ISSUE` → **不演化**（转告警）

**L2 不演化**：specialist 本身（外部工具）、Leader、L3（避免递归到 L4）。

### 5.4. L3 评估是专门为 L2 服务的吗

**主要是，但不完全**：

| 能力 | 组件 | 服务对象 |
|---|---|---|
| **评估打分** | `OrchestrationBridge` + 3 adapter | **L2**（晋升决策的输入） |
| **健康监控** | `SpecialistRuntimeTracker` | **L2**（degraded 触发）+ **运维/可观测** |
| **跨 run 决策日志** | `DecisionLogWriter/Reader` | **L2**（EvolutionMutator 输入样本）+ **L1**（写） |

**核心评估能力专为 L2**——其他两个跨层。

## 6. L2 Evolution 完整流程

### 6.1. 装配（setup_l2）

```
setup_l2(config, metrics_store)
│
├─ ① VersionDAG(db_path)                    ← 版本 DAG
├─ ② metrics_view = metrics_store           ← 复用 L1 实例
├─ ③ FailureFocuser(window_seconds)         ← 失败聚焦
├─ ④ EvolutionMutator(llm_caller=None)      ← 变异器（MVP None）
├─ ⑤ bridge 构造（L3 启用时）                ← L2→L3 连接点
├─ ⑥ PromotionGate(evaluator=None, bridge)  ← 晋升门
├─ ⑦ task_queue = queue.Queue()             ← 共享队列
├─ ⑧ thresholds = TriggerThresholds(...)
├─ ⑨ TriggerManager(task_queue, ...)        ← 触发管理
├─ ⑩ L2TriggerMiddleware(...)               ← L1 graph 钩子
├─ ⑪ budget_limits = _build_budget_limits(...)
├─ ⑫ BudgetGuard(...)                       ← 预算守卫
├─ ⑬ OrchestrationMetricsL2(...)            ← 11 种事件打点
├─ ⑭ L2EvolutionWorker(...)                 ← daemon 线程
└─ ⑮ l3_setup = setup_l3(...)               ← L3 嵌套装配
```

### 6.2. 运行时流程

```
① L1 graph 每轮 model 后
L1 graph after_model 钩子
    │
    └─ L2TriggerMiddleware.after_model
        ├─ TriggerManager.should_trigger（四源 + 1h 冷却）
        └─ 命中 → enqueue EvolutionTask → task_queue
    │
    ▼
② L2EvolutionWorker（daemon 线程）消费
    │
    └─ _run_evolution(task)
        ├─ ① FailureFocuser.analyze → FailureStats
        │   └─ dominant_category is None → REJECT
        ├─ ② VersionDAG.get_active → current
        │   └─ None → REJECT
        ├─ ③ EvolutionMutator.evolve_* → candidate
        │   └─ 失败 → FAILED
        ├─ ④ PromotionGate.evaluate
        │   └─ ★ L3 调用点：bridge.evaluate(ctx)
        ├─ ⑤ PromotionGate.decide
        │   ├─ VersionDAG.hash_exists_in_recent → REJECT（防环）
        │   ├─ not eval_result.success → FAILED
        │   └─ ci_low > b_high → ACCEPT / 否则 REJECT
        ├─ ⑥ VersionDAG.commit（accept/reject 都存）
        └─ ⑦ OrchestrationMetricsL2.record_*
```

### 6.3. L2 与 L3 的接口位置

**L2 → L3（唯一调用点）**：

```python
# PromotionGate.evaluate
if self._bridge is not None:
    ctx = EvalContext(candidate, baseline, task_sample)
    return self._bridge.evaluate(ctx)      # ← L3 的 OrchestrationBridge
```

**L3 → L2（两个回流点）**：

```python
# 回流点 A：L3 健康监控 enqueue L2 队列
cron_queue.put(("specialist_degraded", name))

# 回流点 B：L3 DecisionLog lessons 喂给 L2 变异
mutator.evolve_context_summary(current, failures, lessons=...)
```

**共享资源**：

| 资源 | L2 | L3 |
|---|---|---|
| `task_queue` | TriggerManager 写 / Worker 读 | trigger_l2_evolution_if_degraded 写 |
| `metrics_store` | metrics_view 读 | RuntimeTracker / DecisionLog 读写 |
| `l2_metrics` 表 | OrchestrationMetricsL2 写 | L3 事件加 `l3_` 前缀写同一张表 |
| `multiagent.db` | VersionDAG / BudgetGuard 读写 | L3SchemaManager 建表 / DecisionLog 读写 |

## 7. L3 Eval 完整流程

### 7.1. 装配（setup_l3）

```
setup_l3(config, metrics_store, task_queue)
│
├─ ① SpecialistEvalRegistry + 注册 3 adapter
│   ├─ ProgrammaticAdapter(evaluator=None)
│   ├─ LLMJudgeAdapter(judge_fn=None)
│   └─ LongitudinalPairsAdapter(evaluator=None)
│
├─ ② OrchestrationBridge(adapter_registry)  ← L2 调 L3 的入口
├─ ③ SpecialistRuntimeTracker(...)          ← 健康监控
├─ ④ DecisionLogWriter / Reader(...)        ← 决策日志
├─ ⑤ MultiagentProgrammaticFacade(...)      ← L3 未启用时备用
└─ ⑥ 启动 6h 健康检查 daemon 线程
```

### 7.2. 三个评估器

| Adapter | method_used | 评分来源 | 分数形态 | 成本 |
|---|---|---|---|---|
| `ProgrammaticAdapter` | `"programmatic"` | evaluator → bool | 0/1 | 极低 |
| `LongitudinalPairsAdapter` | `"longitudinal_pairs"` | evaluator → bool | 0/1 | 低 |
| `LLMJudgeAdapter` | `"llm_judge"` | judge_fn → float | [0,1] 四维加权 | 高 |

**评估对象相同**（`EvolutionArtifact`：candidate vs baseline），**流程相同**（遍历 task_sample → 评分 → 算 Wilson CI），**唯一区别是"怎么给一个 task 打分"**。

**LLM judge 的四维权重**：

```python
WEIGHTS = {
    "task_completion": 0.50,     # 任务完成
    "response_quality": 0.35,    # 响应质量
    "efficiency": 0.05,          # 效率
    "tool_usage": 0.10,          # 工具使用
}
```

### 7.3. 两个 Facade（L3 未启用时的降级）

| | OrchestrationBridge | MultiagentProgrammaticFacade |
|---|---|---|
| 接口 | `EvalBridge` | `EvalBridge`（同一个） |
| 启用条件 | L3 启用 | L3 未启用 |
| 评估方法 | 通过 registry 选（3 种） | 只支持 programmatic |
| 依赖 | `SpecialistEvalRegistry` | `Evaluator` callable |

**两者实现同一 `EvalBridge` 契约**——L2 调用方式完全一样。**这是"渐进迁移"设计。**

### 7.4. L3 的调用链

```
L2 触发评估
    │
    └─ PromotionGate.evaluate(candidate, baseline, task_sample)
        │
        ├─ bridge 非 None → EvalContext(candidate, baseline, task_sample)
        │   → bridge.evaluate(ctx)
        │       → OrchestrationBridge._select_method(ctx)
        │           ├─ ① ctx.eval_method_hint
        │           ├─ ② 全 task 有 expected_outcome → longitudinal_pairs
        │           ├─ ③ task_type == "open_ended" → llm_judge
        │           └─ ④ 默认 → programmatic
        │       → registry.get(method) → adapter
        │       → adapter.evaluate(ctx) → EvalResult
        │
        └─ bridge 为 None → floor eval
```

## 10. 关键设计点汇总

### 10.1. 契约优先

- 所有 specialist / runtime / summarizer / provider 契约都是 **Protocol**
- 实现方无需显式继承，靠"方法签名匹配"通过检查

### 10.2. 成本分层

- **L1 常开**：每次派活打点，极低
- **L2 默认关**：周期/阈值触发，中（调 LLM 变异）
- **L3 默认关**：按需，高（LLM judge）

### 10.3. 失败语义分离

- `SpecialistError` 层次：外部 specialist 失败
- `SubagentError` 层次：内部 subagent 失败
- **两条独立层次**，不共用基类

### 10.4. 渐进迁移

- L3 未启用 → `MultiagentProgrammaticFacade`（floor eval）
- L3 启用 → `OrchestrationBridge`（完整评估）
- **两者实现同一 `EvalBridge` 契约**——L2 调用方式不变

### 10.5. 解耦

- L3 只 enqueue 消息，不直接调 L2 TriggerManager
- `task_queue` 是 L2 与 L3 的共享通道
- **触发端和消费端分离**

### 10.6. 防环机制

- `hash_exists_in_recent`：近 5 版 hash 检查
- `_task_use_count`：单 task 累计 ≤ 3 次
- `l2_blocked_patterns`：被阻断的 pattern

### 10.7. 三层跨语言桥（Pi 特有）

    ▼

    │ jiti 加载 TS extension
    ▼

    ▼

## 11. 总结

> **MultiAgent 是 Poirot 的"多 Agent 编排层"——让 Leader 能派活给 4 个 specialist（subagent / ClaudeCode / Codex / Pi），通过 L1/L2/L3 三层实现"运行记录 → 评估 → 进化"闭环。核心流程是"LLM 决策 → 选 specialist → 压上下文 → 注入凭证 → runtime 执行 → 压结果 → 回 Leader"7 步。三层装配嵌套：setup_multiagent → setup_l2 → setup_l3。L2 与 L3 通过 EvalBridge 契约交互，L2 在 PromotionGate.evaluate 处唯一调用 L3；L3 通过 task_queue 回流触发 L2 进化。全部契约用 Protocol 表达，实现方无需继承。这是"契约优先、成本分层、渐进迁移、解耦"的设计。**
