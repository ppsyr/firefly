## 1. multiagent 是谁决定是否启用的

### 1.1. 一句话

**由 `MultiAgentConfig.enabled` 决定，而它来自 `load_multiagent_config()` 从环境变量 `POIROT_MULTIAGENT_ENABLED` 读取——最终决定权在用户（env）和代码默认值（True）。**

---

### 1.2. 决策链条（4 层）

```
① 环境变量 POIROT_MULTIAGENT_ENABLED
        │
        │ _env_bool("POIROT_MULTIAGENT_ENABLED", True)
        ▼
② MultiAgentConfig.enabled（默认 True）
        │
        │ load_multiagent_config() 产出
        ▼
③ ma_config = load_multiagent_config()      ← bootstrap_runtime 第 ⑧ 步
        │
        │ 传给 setup_multiagent
        ▼
④ setup_multiagent(ma_config, ...)
        │
        ├─ config.enabled == False → return _EMPTY_SETUP
        └─ config.enabled == True  → 装配 specialist
```

**唯一的判断点在 ④：`if not config.enabled: return _EMPTY_SETUP`。**

---

### 1.3. 逐层看代码

#### 第 ① 层：环境变量（用户）

```python
def _env_bool(name: str, default: bool = False) -> bool:
    val = os.getenv(name)
    if val is None:
        return default
    return val.lower() in ("true", "1", "yes")
```

调用处：

```python
enabled=_env_bool("POIROT_MULTIAGENT_ENABLED", True),
```

**用户行为**：

- 不设 env → 用默认值 `True`（**默认启用**）
- `POIROT_MULTIAGENT_ENABLED=false` → 显式关闭
- `POIROT_MULTIAGENT_ENABLED=1` → 启用

#### 第 ② 层：配置字段

```python
@dataclass(frozen=True)
class MultiAgentConfig:
    enabled: bool = True
    ...
```

**默认值是 `True`**——这是"opt-out"设计：不配置也启用。

#### 第 ③ 层：bootstrap_runtime 读取

```python
# bootstrap_runtime 第 ⑧ 步
ma_config = load_multiagent_config()
ma_setup = setup_multiagent(ma_config, agent_factory=_subagent_factory)
```

**`bootstrap_runtime` 不做判断**——它无条件调 `load_multiagent_config()` 和 `setup_multiagent`。

#### 第 ④ 层：setup_multiagent 短路

```python
def setup_multiagent(config, agent_factory=None):
    if not config.enabled:
        return _EMPTY_SETUP
    ...
```

**唯一的判断在这里**——不启用就返回空 setup，后续装配全部跳过。

---

### 1.4. 谁"决定"——三种说法

| 说法 | 主体 | 说明 |
|---|---|---|
| **用户决定** | 用户（env） | 通过 `POIROT_MULTIAGENT_ENABLED` 显式开关 |
| **代码默认决定** | `config.py` 的默认值 | 不设 env 时 `enabled=True`（默认启用） |
| **判断点决定** | `setup_multiagent` | 实际执行"启用/不启用"分支 |

**严格说，是"用户通过 env + 代码默认值共同决定，setup_multiagent 执行判断"。**

---

### 1.5. 不启用时会发生什么

`return _EMPTY_SETUP`：

```python
_EMPTY_SETUP = MultiAgentSetup(
    specialist_registry=None,
    subagent_provider=None,
    metrics_store=None,
    orchestration_middleware=None,
    specialist_tools=(),
    l2_setup=None,
)
```

后续影响：

| 组件 | 影响 |
|---|---|
| `ma_setup.specialist_registry` | `None` → `CapabilityRegistry.specialist_registry = None` |
| `ma_setup.specialist_tools` | `()` → Leader 的 `specialist_tools` 参数为 `None` |
| `ma_setup.orchestration_middleware` | `None` → Leader 不挂 OrchestrationMiddleware |
| LLM 看到的工具 | **没有 `delegate_to_*` 工具** |
| Leader 行为 | **完全不变**——不派活，只自己干 |

**核心**：enabled=false 时，Leader 就像"没有 multiagent 这个子系统"一样运行。

---

### 1.6. 与 sandbox / skill / memory 的对比

| 子系统 | 决定字段 | 来源 | 默认 |
|---|---|---|---|
| **multiagent** | `MultiAgentConfig.enabled` | env `POIROT_MULTIAGENT_ENABLED` | **True** |
| sandbox | `config.sandbox.use` | config 文件 | 空 → 不启用 |
| skill | `build_skill_manager()` 内部判断 | `.env` + 目录存在性 | 无 → 不启用 |
| memory | `config.memory.use` | config 文件 | 空 → 不启用 |

**multiagent 的特殊性**：

- **默认启用**（True）——其他子系统大多默认关闭
- **只看一个布尔开关**——sandbox / memory 看"use 字段是否有值"
- **判断点集中在 `setup_multiagent` 一处**——不分散

---

### 1.7. 完整决策链（图示）

```
用户设 env？
    │
    ├─ 设了 POIROT_MULTIAGENT_ENABLED=false
    │       │
    │       ▼
    │   _env_bool(..., True) → False
    │       │
    │       ▼
    │   MultiAgentConfig(enabled=False)
    │       │
    │       ▼
    │   setup_multiagent → _EMPTY_SETUP
    │       │
    │       ▼
    │   Leader 无 delegate_to_* 工具
    │
    ├─ 设了 POIROT_MULTIAGENT_ENABLED=true
    │       │
    │       ▼
    │   enabled=True → 正常装配
    │
    └─ 没设 env
            │
            ▼
        用默认值 True → enabled=True → 正常装配
```

---

### 1.8. 总结

> **multiagent 是否启用由 `MultiAgentConfig.enabled` 决定，它来自 `load_multiagent_config()` 读取的 env `POIROT_MULTIAGENT_ENABLED`（默认 True）。真正的判断点在 `setup_multiagent`：`if not config.enabled: return _EMPTY_SETUP`。所以是"用户通过 env + 代码默认值共同决定，setup_multiagent 执行判断"——不启用时 Leader 完全不知道 multiagent 存在。**

## 2. 配置允许，LLM 会自己判断吗？用户能指定吗？

### 2.1. 概述

**当前实现下：配置是"总闸"，LLM 是"分闸"——总闸开了（multiagent 装配），LLM 才有机会"自己判断要不要派活"；总闸关了，LLM 连工具都看不到。用户目前不能显式指定"这轮用/不用 multiagent"。**

---

### 2.2. 三层决策，各管一段

```
第 1 层：配置开关（总闸）
    POIROT_MULTIAGENT_ENABLED
        │
        ├─ false → 不装配 → LLM 看不到任何 delegate_to_* 工具
        │                     → "想派活也没得派"
        │
        └─ true  → 装配 → LLM 看到 delegate_to_codex / delegate_to_pi / ...

第 2 层：LLM 决策（分闸）
    配置开了之后，LLM 每轮自己决定：
        ├─ 调 delegate_to_xxx → 派活给 specialist
        └─ 不调，自己干      → 当作普通工具一样忽略

第 3 层：用户显式指定（当前无）
    对话窗口里没有 "这轮用/不用 multiagent" 的开关
```

**关键：第 1 层不开，第 2 层根本没得选。**

---

### 2.3. 配置开了之后，LLM 怎么"自己判断"

**是的，LLM 会自己判断。** 机制是 **soft routing（软路由）**：

#### 2.3.1. LLM 看到什么

配置开了后，LLM 的 tool 列表里出现：

```
delegate_to_codex
delegate_to_pi
delegate_to_claude
delegate_to_subagent
```

每个工具的 description 是：

> "Delegate task to specialist. Provide goal and success_criteria..."

#### 2.3.2. LLM 怎么决定

**没有硬编码规则**——LLM 根据：

- **任务性质**："这个任务我能不能自己干？"
- **工具描述**：看到 `delegate_to_codex`，理解"这是可以外包的"
- **历史经验**：prompt 里如果有"遇到编码任务优先派 codex"，LLM 会参考
- **Leader 提示词**：`prompts/system/leader/*.md` 里可能有路由指导

**它可能：**

- 调 `delegate_to_codex` —— 认为"这个任务该外包"
- 不调任何 delegate 工具 —— 认为"我自己能搞定"
- 先调再判 —— 派了失败再换别的

#### 2.3.3. 配置层的字段辅助

`MultiAgentConfig` 里有几个字段会**影响 LLM 能看到什么**：

| 字段 | 作用 |
|---|---|
| `specialists_use` | 决定**哪些 specialist 被装配**（进 registry + 生成工具） |
| `max_concurrent` | 并发上限（可能影响多任务场景） |
| `auto_approve` | 是否自动批准（可能在需要确认的场景用） |

**但这些是"装配参数"，不是"LLM 的决策参数"。** 它们决定"LLM 看到哪些选项"，不决定"LLM 选不选"。

#### 2.3.4. 关键：LLM 的"判断"是隐式的

**LLM 不做"要不要用 multiagent"这个元决策**——它只做"要不要调这个工具"的具体决策。

- **没有工具**（配置关闭）→ 无法决策（选项不存在）
- **有工具**（配置打开）→ 按需决定调不调

**"要不要用 multiagent"这个判断，被拆成了"要不要调某个 delegate_to_* 工具"。**

---

### 2.4. 用户能指定吗

#### 2.4.1. 对话窗口层面：当前没有

**Poirot 目前没有"这轮对话禁用 multiagent"的开关。** 用户在 TUI / CLI 里：

- 不能说"这次别派活"
- 不能说"这次必须派活"
- 只能通过重启 + 改 env 来切换总闸

#### 2.4.2. 但用户可以通过其他方式间接影响

| 方式 | 效果 |
|---|---|
| **改 env 重启** | `POIROT_MULTIAGENT_ENABLED=false` → 总闸关 |
| **改 env 重启** | `POIROT_MULTIAGENT_SPECIALISTS=codex` → 只装配 codex，LLM 只看到它 |
| **对话里明说** | "用 codex 帮我改这个文件" → LLM 可能因此调 `delegate_to_codex` |
| **对话里明说** | "你自己做，不要外包" → LLM 可能不调 delegate 工具 |
| **改 Leader prompt** | 在 `prompts/system/leader/*.md` 加路由规则 |

**注意**：后面两种是"间接影响"，不保证 100% 生效——**因为 LLM 的行为有不确定性**。

#### 2.4.3. 为什么不做"每轮开关"

推测的取舍：

| 角度 | 说明 |
|---|---|
| **简化 UI** | 每轮加个开关会让 CLI/TUI 复杂 |
| **LLM 已经能判断** | soft routing 够用，不需要额外开关 |
| **配置粒度够** | 想改行为就改 env 重启，能覆盖大多数场景 |
| **可能留待后续** | 这是 MVP 选择，不是"不该做" |

---

### 2.5. 谁真正"决定"用不用 multiagent

拆成三个层次：

| 层次 | 决策者 | 决定什么 | 手段 |
|---|---|---|---|
| **能不能用** | 用户（配置） | 工具是否出现 | `POIROT_MULTIAGENT_ENABLED` |
| **有哪些选项** | 用户（配置） | 出现哪些 specialist | `POIROT_MULTIAGENT_SPECIALISTS` |
| **这次用不用** | **LLM** | 调不调 `delegate_to_*` | soft routing（隐式） |
| **强制用/不用** | —— | 无此能力 | 当前不支持 |

**所以"用不用 multiagent"的最终决定权在 LLM**——但它的"选项空间"由用户配置决定。

---

### 2.6. 三个具体场景

#### 场景 A：配置开，任务简单

```
配置：POIROT_MULTIAGENT_ENABLED=true
任务："1+1 等于几？"

LLM 看到：delegate_to_codex / delegate_to_pi / ...
LLM 想："这任务我自己一秒就答了，不用派活"
LLM 行为：直接回答，不调任何 delegate 工具
结果：multiagent 装配了但没被用
```

#### 场景 B：配置开，任务复杂

```
配置：POIROT_MULTIAGENT_ENABLED=true
任务："审查这个 Python 文件的代码质量问题"

LLM 看到：delegate_to_claude（capability=REVIEW）
LLM 想："这任务适合 claude 干"
LLM 行为：调 delegate_to_claude
结果：multiagent 被用了
```

#### 场景 C：配置关

```
配置：POIROT_MULTIAGENT_ENABLED=false
任务："审查这个 Python 文件的代码质量问题"

LLM 看到：没有 delegate_to_* 工具
LLM 想："没有可用的外部专家，我自己审"
LLM 行为：自己分析代码
结果：multiagent 没装配，完全无感
```

---

### 2.7. 总结

> **配置是总闸，LLM 是分闸。配置开了，LLM 才看到 `delegate_to_*` 工具，之后每轮自己决定调不调（soft routing）——这是隐式的、不确定的。配置关了，LLM 连工具都看不到，想派活也没得派。用户目前不能"每轮显式指定用不用 multiagent"，只能通过改 env 重启（总闸级）或对话里明说（软影响）。所以"用不用 multiagent"的最终决定权在 LLM，但"能不能用"的决定权在配置。**

---

## 3. 这几个工具在哪里给 LLM 看的

### 3.1. 一句话

**它们通过 `create_poirot_agent(tools=tools, ...)` 传进 LangChain 的 Agent 构造，LangChain 把 `BaseTool` 列表转成 tool schema 绑给 LLM——LLM 从模型的 tool 参数里"看到"它们。**

---

### 3.2. 完整链路（5 步）

```
① make_specialist_tool() 造出 BaseTool
        │
        │ 名字：delegate_to_codex / delegate_to_pi / ...
        ▼
② 工具列表汇总
   tools = [..., delegate_to_codex, delegate_to_pi, ...]
        │
        │ 打包进 MultiAgentSetup.specialist_tools
        ▼
③ Leader factory 取用
   tools = builtin_tools + registry.specialist_tools
        │
        │ 传给 create_poirot_agent
        ▼
④ create_poirot_agent(tools=tools, ...)
        │
        │ LangChain 内部：BaseTool 列表 → tool schema
        ▼
⑤ LLM 的 tool 参数
   LLM API 调用时带上 tools=[{name, description, parameters}, ...]
   → LLM 从模型层面"看到"这些工具
```

**关键：不是"Poirot 告诉 LLM"，而是"Poirot 把工具交给 LangChain，LangChain 在每次 LLM 调用时带上 tool schema"。**

---

### 3.3. 逐层看代码

#### 第 ① 步：造工具（`multiagent/tools.py`）

```python
def make_specialist_tool(name, specialist, ctx_sum, res_sum, ...):
    @tool(f"delegate_to_{name}")          # ← 名字在这里定
    def delegate_tool(goal, success_criteria, sandbox_id=None):
        ...
    return delegate_tool
```

`@tool` 装饰器把函数包装成 `BaseTool`，**自带 name / description / args_schema**。

#### 第 ② 步：汇总（`multiagent/bootstrap.py`）

```python
tools: list[BaseTool] = []
for name in config.specialists_use:
    loaded = _load_specialist(...)
    ...
    tools.append(make_specialist_tool(name, specialist, ...))

return MultiAgentSetup(
    specialist_tools=tuple(tools),         # ← 打包
    ...
)
```

#### 第 ③ 步：注入 Leader（`app/bootstrap.py` → `leader/factory.py`）

在 `bootstrap_runtime` 里：

```python
leader_agent = make_lead_agent(
    ...,
    specialist_tools=list(ma_setup.specialist_tools) if ma_setup.specialist_tools else None,
    ...
)
```

`make_lead_agent` 内部（`leader/factory.py`）：

```python
tools = [
    *builtin_tools,
    *sandbox_tools,
    *mcp_tools,
    *specialist_tools,        # ← multiagent 工具在这里进列表
]
agent = create_poirot_agent(tools=tools, middlewares=middlewares, ...)
```

#### 第 ④ 步：LangChain 转 schema（`create_poirot_agent` 内部）

**这一步不在 Poirot 代码里，在 LangChain 里。**

LangChain 的 Agent 构造会把 `tools` 列表转成 OpenAI / Anthropic 的 tool schema：

```python
# LangChain 内部伪代码
tool_schemas = [
    {
        "type": "function",
        "function": {
            "name": tool.name,                 # "delegate_to_codex"
            "description": tool.description,   # "Delegate task to specialist..."
            "parameters": tool.args_schema,    # {goal, success_criteria, sandbox_id}
        }
    }
    for tool in tools
]
```

#### 第 ⑤ 步：LLM 看到（每次模型调用）

**每次调 LLM 时，LangChain 把 `tool_schemas` 作为请求的一部分发给模型 API：**

```
POST /v1/chat/completions
{
    "model": "...",
    "messages": [...],
    "tools": [                              # ← LLM 在这里"看到"工具
        {"type": "function", "function": {"name": "delegate_to_codex", ...}},
        {"type": "function", "function": {"name": "delegate_to_pi", ...}},
        ...
    ]
}
```

**LLM 收到请求后，从 `tools` 字段里读到所有可用工具——这就是它"看到"的方式。**

---

### 3.4. 关键点：不是"注册"，是"每次调用时带上"

**容易误解的地方**：以为工具"注册到某个地方，LLM 去查"。

**实际不是。** 真相是：

```
每次 LLM 调用
    │
    └─ LangChain 把当前 agent 的 tool 列表转成 schema
        └─ 作为 API 请求的一部分发给 LLM
            └─ LLM 从请求里读到工具列表
```

**所以：**

- 工具不需要"注册"到 LLM——**每次调用时"随请求带上"**
- LLM 不需要"查询"工具——**工具列表就在请求里**
- 改工具列表 = **下次 LLM 调用时带不同的 schema**

**这解释了为什么热切换（`reload_mcp_tools` / `switch_model`）要"重建 LeaderAgent"**——重建后新的 tool 列表会在下次 LLM 调用时生效。

---

### 3.5. 工具名和 schema 从哪来

#### 工具名：`@tool` 装饰器的参数

```python
@tool(f"delegate_to_{name}")     # name = "codex" → "delegate_to_codex"
def delegate_tool(...): ...
```

#### 描述：函数的 docstring

```python
@tool(f"delegate_to_{name}")
def delegate_tool(goal, success_criteria, sandbox_id=None) -> str:
    """Delegate task to specialist. Provide goal and success_criteria. sandbox_id optional (uses thread sandbox if omitted)."""
    ...
```

**这段英文 docstring 就是 LLM 看到的 description。**

#### 参数 schema：函数签名

```python
def delegate_tool(
    goal: str,                    # → {"goal": {"type": "string"}}
    success_criteria: str,        # → {"success_criteria": {"type": "string"}}
    sandbox_id: str | None = None # → {"sandbox_id": {"type": "string"}}（可选）
) -> str:
```

**`@tool` 从函数签名自动推断参数 schema。**

---

### 3.6. 和"注册到 registry"的区别

| | SpecialistRegistry | LLM 看到的工具 |
|---|---|---|
| 存什么 | `SpecialistAgent` 实例 | `BaseTool` 对象（转 schema） |
| 谁查 | Poirot 代码（`registry.get(name)`） | **LLM（从 API 请求里读）** |
| 怎么"送达" | 代码调用 `registry.get()` | **LangChain 每次调用时带 schema** |
| 需要"注册"吗 | 需要（`registry.register`） | **不需要——随请求带上** |

**"注册"是给 Poirot 代码用的；"给 LLM 看"是随 API 请求带的。两回事。**

### 3.7. 完整图示

```
┌────────────────────────────────────────────────────────────┐
│ 装配期（bootstrap_runtime）                                  │
│                                                             │
│ ① make_specialist_tool("codex", ...) → BaseTool            │
│ ② tools = [..., delegate_to_codex, delegate_to_pi, ...]     │
│ ③ MultiAgentSetup(specialist_tools=tuple(tools))            │
│ ④ CapabilityRegistry.specialist_tools = ...                 │
│ ⑤ Leader factory: tools = builtin + registry.specialist_tools│
│ ⑥ create_poirot_agent(tools=tools, ...)                     │
│      └─ LangChain 保存 tools 列表在 Agent 内部               │
└──────────────────────────┬─────────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────────┐
│ 运行期（每次 LLM 调用）                                      │
│                                                             │
│ LangChain Agent 执行                                        │
│   └─ 构造 LLM 请求：                                         │
│       {                                                     │
│         "messages": [...],                                  │
│         "tools": [                                          │
│           {"function": {"name": "delegate_to_codex", ...}}, │
│           {"function": {"name": "delegate_to_pi", ...}},    │
│           ...                                               │
│         ]                                                   │
│       }                                                     │
│   └─ 发给 LLM API                                           │
│       └─ LLM 从请求的 tools 字段里"看到"所有工具             │
│           └─ LLM 决定：调 / 不调                             │
└────────────────────────────────────────────────────────────┘
```

### 3.8. 总结

> **这几个工具不是"注册到 LLM"，而是通过 `create_poirot_agent(tools=tools)` 交给 LangChain。LangChain 在每次 LLM 调用时，把 tools 列表转成 tool schema，作为 API 请求的 `tools` 字段发给模型——LLM 从请求里"看到"这些工具。所以"给 LLM 看"发生在每次调用时，不是装配时。装配时只是把工具交给 LangChain 存着。**
