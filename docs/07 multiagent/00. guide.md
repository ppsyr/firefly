# MultiAgent 层学习路线规划（优化版）

> 基于对整个 multiagent 代码库的实际阅读，对原 guide 做**事实校正**与**结构重组**。
> 核心思路不变：**先建词汇表 → 再看契约 → 最短路径跑通 → 外部异构 → 接入 Leader → 验证闭环**。

---

## 阶段零：先明确你要回答的 9 个问题（贯穿全程）

在读代码前先把这 9 个问题写在纸上，每读完一个阶段尝试回答一次：

**流程类：**

1. **Leader 什么时候决定"派活给子 Agent"，而不是自己干？** —— 由 LLM 通过 soft routing 决定，配置只是"总闸"。
2. **一个 specialist 从被选中到返回结果，中间经历了哪些环节？** —— `OrchestrationMiddleware.wrap_tool_call` → `tools.py` handler → ContextSummarizer → Specialist.invoke → Runtime.invoke → ResultSummarizer → 回 middleware。
3. **子 Agent 的上下文从哪来？Leader 的完整对话历史会传给它吗？** —— 不会。只传 `context_summary`（由 per-specialist ContextSummarizer 压缩）。
4. **子 Agent 的结果怎么回到 Leader？是原文返回还是被摘要？** —— 被摘要。ResultSummarizer 产出 `SpecialistResult`，再 `json.dumps` 成 ToolMessage。
5. **多个子 Agent 能并行吗？它们的沙箱/凭证是共享还是隔离？** —— `max_concurrent` 控制；沙箱共享 thread sandbox_id，凭证不共享（各自 CredentialProvider）。

**架构类：**

6. **`Runtime` 和 `Specialist` 是什么关系？** —— **Specialist 持有 Runtime**（组合，非继承）。Specialist 是"Agent 语义封装"，Runtime 是"进程/协议执行器"。
7. **`Subagent` 和异构 `Specialist` 的区别？** —— **两条并列路径**：subagent 走"进程内自复制 + SubagentRuntime"；其他走"外部进程 + 各自 Runtime"。不是子集关系。
8. **`eval` 和 `evolution` 是运行时的一部分，还是离线任务？** —— **是 L2/L3 层，不是 L1 运行时的一部分**。L1 常开（打点），L2/L3 默认关（数据驱动触发）。
9. **specialist 崩了/超时了，Leader 会感知吗？重试在哪层？** —— 会。异常被 `OrchestrationMiddleware` 转成 error ToolMessage 回 Leader；重试由 Leader 决策（LLM 自己决定 retry / fallback / self-do）。

> **补充一个关键语义**：
>
> 10. **L1/L2/L3 是什么？** —— L1 运行层（常开，记录指标）、L2 进化层（默认关，变异模板）、L3 评估层（默认关，打分）。**编号不是执行顺序**——真实顺序是 L2 触发 → L3 评估 → L2 晋升。

## 阶段一：建立骨架（配置 + 类型 + 7 个契约 + 装配）

**目标**：搞清楚「有哪些抽象」和「它们怎么拼起来」，先不关心具体是 Claude 还是 Codex。

### 1.0 先看配置与类型基础

| 顺序 | 文件 | 你要弄明白的事 |
|---|---|---|
| 0 | `config.py` | `MultiAgentConfig` 结构；`enabled` 默认 **True**（非 opt-in）；`STARTUP_ONLY_FIELDS`；`L2Config` / `L3Config` / `BudgetConfig` 嵌套 |
| 1 | `types.py` | 核心数据契约：`SpecialistRequest` / `SpecialistRawResult` / `SpecialistResult` / `SubagentRequest` / `SubagentResult` / `SpecialistCapability`；**全部 frozen** |
| 2 | `exceptions.py` | **两条独立层次**：`SpecialistError`（外部异构）+ `SubagentError`（内部自复制）；`details` 展开格式统一 |
| 3 | `metrics.py` | L1 指标存储（9 张表）；4 计数器 + 明细；**同时是 L2/L3 的持久化层** |

**阶段产出 A**：
- `config.enabled` 决定 multiagent 是否启用（默认 True）
- `config.specialists_use` 决定启用哪些 specialist
- `config.max_concurrent` 决定并发上限

### 1.1 注册表 + 7 个契约（不是 5 个）

| 顺序 | 文件 | 你要弄明白的事 |
|---|---|---|
| 4 | `registry.py` | `SpecialistRegistry`：名字注册；`get` 缺失抛 `SpecialistNotFoundError`；**实例级非全局单例** |
| 5 | `specialist.py` | `SpecialistAgent` Protocol：`name` / `capabilities` / `invoke`；**黑盒 + 持有 Runtime** |
| 6 | `specialist_runtime.py` | `SpecialistRuntime` Protocol：只有 `invoke`；**sync only**；不感知 summarizer / ThreadState |
| 7 | `subagent.py` | `SubagentProvider` Protocol：`spawn`；**leaf role + isolated context + shared sandbox** |
| 8 | `credential_provider.py` | `CredentialProvider` Protocol：`get_credential`；**只发现不管理**；凭证不进 ThreadState |
| 9 | `context_summarizer.py` | `ContextSummarizer` Protocol：`summarize` 输入端；per-specialist 实现 |
| 10 | `result_summarizer.py` | `ResultSummarizer` Protocol：`summarize` 输出端；per-specialist 实现 |
| 11 | `sandbox_binder.py` | `SandboxBinder` Protocol：`bind`；**multiagent 与 sandbox 的桥** |

**阶段产出 B**：契约依赖图（修正版）

```
SpecialistRegistry（花名册，名字 → SpecialistAgent）
  └── holds: dict[str, SpecialistAgent]

SpecialistAgent（Agent 语义封装，Protocol）
  ├── name: str
  ├── capabilities: SpecialistCapabilities
  ├── holds: SpecialistRuntime      ← 进程/协议执行器（怎么跑）
  ├── holds: CredentialProvider     ← 凭证来源（用什么身份跑）
  ├── uses:  ContextSummarizer      ← 进：ThreadState → context_summary
  └── uses:  ResultSummarizer       ← 出：raw_output → SpecialistResult

SubagentProvider（自复制特例，Protocol）
  └── spawn(SubagentRequest) → SubagentResult
      └── 走 SubagentRuntime + SelfCopy*Summarizer（与异构并列）

OrchestrationMiddleware（拦截层）
  └── 拦截 delegate_to_* tool call
      ├── before: set_current_state + 打点
      └── after: 打点 + 归集 ArtifactRef

编排顺序（一次派活）：
  LLM 决策 → OrchestrationMiddleware.wrap_tool_call → tools.py handler
    → ContextSummarizer → Specialist.invoke → Runtime.invoke
    → ResultSummarizer → 回 middleware → ThreadState 更新
```

**阶段产出 C**：
- **Specialist 持有 Runtime（不是继承）**
- **两个摘要器独立**（进 / 出，两个 Protocol）
- **7 个契约**（原 guide 说 5 个，实际 specialist / runtime / subagent / credential / context_summarizer / result_summarizer / sandbox_binder = 7 个）

### 1.2 装配与启动

| 顺序 | 文件 | 你要弄明白的事 |
|---|---|---|
| 12 | `bootstrap.py` | `setup_multiagent` 装配主入口；enabled=false → `_EMPTY_SETUP`；L3 嵌套在 L2 里 |
| 13 | `middleware.py` | `OrchestrationMiddleware`：拦截 `delegate_to_*`；**打点 + 汇总 + fail-closed** |
| 14 | `tools.py` | `make_specialist_tool` / `make_subagent_tool`；**动态生成工具**；ContextVar 传 ThreadState |

**阶段产出 D**：装配链

```
bootstrap_runtime（app 层）
  └─ setup_multiagent(config, agent_factory)
      ├─ metrics = MultiAgentMetricsStore(...)
      ├─ l2_setup = setup_l2(config, metrics)          ← L2 嵌套
      │   └─ l3_setup = setup_l3(config, metrics, task_queue)  ← L3 嵌套
      ├─ orch_mw = OrchestrationMiddleware(...)
      ├─ registry = SpecialistRegistry()
      ├─ for name in specialists_use: _load_specialist + register + make_tool
      ├─ if l2_setup: l2_setup.worker.start()
      └─ return MultiAgentSetup(...)
```

## 阶段二：先跑通"自复制"路径（最短路径）

**目标**：`subagent` 是 Leader 自己复制自己——**无外部协议、无凭证、无跨语言桥**，是最短路径。

| 顺序 | 文件 | 重点 |
|---|---|---|
| 1 | `specialists/subagent_specialist.py` | 纯适配器：`invoke` 只转发给 runtime；`name="subagent"`，`capability=RESEARCH` |
| 2 | `runtimes/subagent_runtime.py` | `_get_agent` → `agent_factory()`；`_create_isolated_state`（全新 ThreadState + 复用父 sandbox_id）；`_extract_output` |
| 3 | `summarizers/context/self_copy_context_summarizer.py` | 规则路径（无 LLM）：goal + user_input + observations[-5:]；截断 3000 字符 |
| 4 | `summarizers/result/self_copy_result_summarizer.py` | **纯继承** BaseResultSummarizer，零覆写 |
| 5 | `summarizers/result/base.py` | **模板方法**：`summarize` 固定流程 + 钩子（`_evaluate_success` / `_extract_gap` / `_compress` / `_classify_failure`） |

**阶段产出**：完整链路

```
delegate_to_subagent handler
  ├─ ctx_summarizer.summarize → context_summary
  ├─ SubagentSpecialist.invoke → SubagentRuntime.invoke
  │   ├─ _get_agent() → agent_factory() 造 leaf-role agent
  │   ├─ _create_isolated_state（goal + context_summary + 父 sandbox_id）
  │   └─ agent.invoke(state) → 抽最后一条消息
  └─ result_summarizer.summarize → SpecialistResult
```

**关键问题**：
- 自复制子 Agent 和 Leader 共享 memory 吗？共享 sandbox 吗？—— **上下文隔离，沙箱共享**。
- `SubagentRuntime` 和 `sandbox` 什么关系？—— **sandbox 是 runtime 的底座**（通过 `sandbox_id` 传入），不是 runtime 本身。
- 为什么自复制要单独 summarizer？—— 因为它是**并列路径**，不是"简化版 specialist"。

## 阶段三：外部异构 Specialist（真正的 multiagent）

**目标**：理解三种外部运行时的完整生命周期，以及它们和自复制的差异。

### 3.1 ClaudeCode 路径（CLI 子进程）

| 顺序 | 文件 | 重点 |
|---|---|---|
| 1 | `runtimes/claude_code_runtime.py` | `subprocess.run(["claude", "--print", goal])`；透传 4 个 auth env；异常映射 |
| 2 | `credentials/claude_credential.py` | 三级查找（env token > env 路径 > 默认文件）；过期检测 |
| 3 | `specialists/claude_code_specialist.py` | name="claude"，capability=REVIEW |
| 4 | `summarizers/context/claude_code_context_summarizer.py` | 提代码块 + review 关键词；零 LLM |
| 5 | `summarizers/result/claude_code_result_summarizer.py` | 覆写 `_evaluate_success`（+suggestion）+ `_extract_gap` |

### 3.2 Codex 路径（ACP 协议）

| 顺序 | 文件 | 重点 |
|---|---|---|
| 6 | `runtimes/codex_runtime.py` | ACP 协议 + stdio JSON-RPC；同步壳包异步；lazy import `acp` 包 |
| 7 | `credentials/codex_credential.py` | 兼容 legacy + nested 两种 JSON 格式 |
| 8 | `specialists/codex_specialist.py` | name="codex"，capability=CODING |
| 9 | `summarizers/context/codex_context_summarizer.py` + `summarizers/result/codex_result_summarizer.py` | 提代码 + 文件路径；覆写（+0 passed 检查） |

### 3.3 Pi 路径（最复杂：installer + 跨语言桥）

| 顺序 | 文件 | 重点 |
|---|---|---|
| 10 | `installer/pi_installer.py` | 后台 npm install（daemon 线程）；flag 文件；**为什么 Pi 需要而 Claude/Codex 不需要** |
| 11 | `credentials/pi_credential.py` | 双轨解析：config 优先 + env 兜底；13 个 provider（国内优先） |
| 12 | `runtimes/pi_runtime.py` | `pi --mode rpc` + stdio JSON-RPC；**强制走 MCP**（`--no-builtin-tools` + `-e extension`）；**唯一返回 token 用量** |
| 13 | `specialists/pi_specialist.py` | name="pi"，capability=CODING；**唯一接收 credential 参数** |
| 14 | `summarizers/context/pi_context_summarizer.py` | 提代码（finditer）+ 文件路径（正则扫 observations + messages） |
| 15 | `summarizers/result/pi_result_summarizer.py` | **覆写 summarize**（三段解析：What You Did / Success / Gaps） |
| 16 | `extensions/pi-sandbox-bridge/index.ts` | **TS extension**：注册 8 个 `poirot_*` 工具；jiti 加载 |
| 17 | `mcp/specialist_mcp_server.py` | specialist 通过 MCP 调 Poirot 8 接口 |

### 3.4 四种运行时横向对比

| 维度 | subagent | claude_code | codex | pi |
|---|---|---|---|---|
| **Runtime 交互方式** | 进程内 `agent.invoke` | CLI 子进程 `subprocess.run` | ACP 异步 | `subprocess.Popen` + RPC |
| **通信方式** | 进程内 | stdout 一次性 | stdio JSON-RPC | stdio JSON-RPC |
| **凭证来源** | 继承 Leader | `~/.claude/.credentials.json` | `~/.codex/auth.json` | 13 个 env + config |
| **是否需要 installer** | 否 | 否 | 否 | **是（后台 npm install）** |
| **Context summarizer** | self_copy（LLM + 规则） | 纯规则（代码 + review） | 纯规则（代码 + 路径） | 纯规则（代码 + 路径） |
| **Result summarizer** | 纯继承 | 继承 + 2 覆写 | 继承 + 2 覆写 | **覆写 summarize** |
| **需要 sandbox bridge** | 否 | 否 | 否 | **是（TS extension）** |
| **capabilities** | RESEARCH | REVIEW | CODING | CODING |
| **token 用量** | ❌ | ❌ | ❌ | ✅ |
| **强制 MCP** | ❌ | ❌ | ❌ | ✅ |

**关键问题**：
- 三种 runtime 继承同一基类吗？—— **不继承，各写各的**；契约统一在 `SpecialistRuntime` Protocol。
- Pi 为什么单独 installer + TS 扩展？—— **Pi 的可用性只取决于"CLI 装没装"**（不需要登录），且 pi 的 extension 机制只接受 JS/TS。
- `specialist_mcp_server.py` 干嘛的？—— **specialist 通过 MCP 调 Poirot 的 8 个沙箱接口**，经 PathTranslator + SecurityGuard。

## 阶段四：接入 Leader（真正跑起来）

**目标**：理解 Leader 怎么发现 specialist、怎么派活、结果怎么回来、沙箱怎么绑。

| 顺序 | 文件 | 重点 |
|---|---|---|
| 1 | `agents/leader/agent.py` | Leader 在哪一步决定派活；**soft routing**（LLM 自决） |
| 2 | `agents/leader/factory.py` | Leader 怎么拿到 `specialist_tools` + `orchestration_middleware` |
| 3 | `agents/leader/prompts.py` + `prompts/system/leader/*.md` | 提示词怎么描述 specialist |
| 4 | `multiagent/tools.py`（回看） | **工具注入点**：`make_specialist_tool` 产出的工具进 Leader tools |
| 5 | `multiagent/middleware.py`（回看） | `OrchestrationMiddleware.wrap_tool_call` 拦截 |
| 6 | `multiagent/sandbox_binder.py` | 多 Agent 场景下沙箱怎么绑 |
| 7 | `agents/middlewares/skill_activation_middleware.py` | 技能激活和 specialist 选择的关系 |
| 8 | `app/services/stream_service.py` | 子 Agent 过程怎么流式回前端 |

**阶段产出**：完整调用链

```
bootstrap_runtime
  └─ make_lead_agent(tools, middlewares)
      └─ create_poirot_agent(tools=tools, middlewares=middlewares)
          └─ LLM 看到 delegate_to_* 工具（每次调用时随请求带 schema）

运行期：
  LLM tool_call("delegate_to_codex", {goal, success_criteria})
    └─ OrchestrationMiddleware.wrap_tool_call
        ├─ before: set_current_state + record_selection + record_invoked
        ├─ handler = delegate_to_codex（tools.py 闭包）
        │   ├─ get_current_state()
        │   ├─ budget_guard.check_and_record()
        │   ├─ ctx_summarizer.summarize()
        │   ├─ specialist.invoke() → runtime.invoke()
        │   ├─ result_summarizer.summarize()
        │   └─ decision_log_writer.write_async()
        └─ after: record_completion/fallback + _build_orchestration_update
    └─ ThreadState.orchestration 更新 → LLM 下一轮
```

**关键问题**：
- Leader 派活是"显式工具调用"还是"提示词引导"？—— **两者配合**：工具提供"能力"，提示词引导"何时用"。
- 子 Agent 沙箱继承 Leader 吗？—— **继承**（shared thread sandbox_id）。
- 并发派活时 summarizer 线程安全吗？—— 取决于实现（当前都是无状态的，应该安全）。
- 子 Agent 失败会冒泡吗？—— **会**。`OrchestrationMiddleware` 转 error ToolMessage 回 Leader。

## 阶段五：Eval / Evolution（L2 + L3）

**目标**：理解评估和进化在 multiagent 里的位置。

### 5.1 L1 → L2 → L3 三层定位

| 层 | 干什么 | 默认 | 触发方式 |
|---|---|---|---|
| **L1** | 每次派活记录指标 | **常开** | 每次调用 |
| **L2** | 读指标 → 变异模板 → 产新版本 | **关闭** | 数据驱动 |
| **L3** | 给 specialist 产出打分 | **关闭** | 数据驱动 |

**核心思想**：**便宜的事常做，贵的事按需做。**

**关键修正**：**编号不是执行顺序**——真实顺序是：

```
L2 触发进化 → L2 变异 → L3 评估 → L2 根据评估结果晋升
```

评估在"变异之后、晋升之前"。

### 5.2 L2 Evolution 阅读顺序

| 顺序 | 文件 | 重点 |
|---|---|---|
| 1 | `evolution/types.py` | `EvolutionArtifact` / `FailureCategory` / `ContextSummaryTemplate` / `SkillInjectionTemplate` |
| 2 | `evolution/bootstrap.py` | `setup_l2` 装配入口 |
| 3 | `evolution/trigger_manager.py` | 四源触发 + 1h 冷却 |
| 4 | `evolution/failure_focuser.py` | 失败聚焦（不调 LLM） |
| 5 | `evolution/evolution_mutator.py` | LLM 变异执行 |
| 6 | `evolution/promotion_gate.py` | 评估 + 晋升（★ L3 调用点） |
| 7 | `evolution/version_dag.py` | 版本持久化 + is_active 单指针 |
| 8 | `evolution/worker.py` | daemon 线程消费 |
| 9 | `evolution/metrics_l2.py` | 11 种事件打点 |
| 10 | `evolution/metrics_view.py` | 读 L1 指标契约 |
| 11 | `evolution/budget_guard.py` | 三维度预算 |
| 12 | `evolution/trigger_middleware.py` | L1 graph 钩子 |
| 13 | `evolution/cli.py` | CLI skeleton（暂不实现） |

### 5.3 L3 Eval 阅读顺序

| 顺序 | 文件 | 重点 |
|---|---|---|
| 1 | `eval/types.py` | `EvalContext` / `SpecialistHealthReport` / `DecisionLogRecord` |
| 2 | `eval/registry.py` | `EvalAdapter` Protocol + `SpecialistEvalRegistry` |
| 3 | `eval/bridge.py` | `EvalBridge` Protocol + `OrchestrationBridge`（★ L2 调 L3 的唯一入口） |
| 4 | `eval/facade.py` | `MultiagentProgrammaticFacade`（L3 未启用时用） |
| 5 | `eval/adapters/programmatic.py` | 最简评估器（先读） |
| 6 | `eval/adapters/llm_judge.py` | LLM 四维加权 |
| 7 | `eval/adapters/longitudinal_pairs.py` | 纵向配对 |
| 8 | `eval/decision_log.py` | 决策日志读写 |
| 9 | `eval/runtime_tracker.py` | 健康监控 |
| 10 | `eval/db.py` | L3 表 schema |
| 11 | `eval/bootstrap.py` | `setup_l3` 装配入口 |
| 12 | `eval/cli.py` | CLI skeleton（暂不实现） |

**阶段产出 A**：
- L1 记录、L2 变异、L3 打分
- 三个评估器评估对象相同（EvolutionArtifact），流程相同，唯一区别是"怎么给一个 task 打分"
- L2→L3 唯一调用点：`PromotionGate.evaluate` 的 bridge 分支
- L3→L2 回流：`trigger_l2_evolution_if_degraded` enqueue + lessons 回流

**阶段产出 B**：闭环图

```
L1（每次派活打点）
    │ 读指标
    ▼
L2 触发（TriggerManager 四源）
    │
    ▼
L2 变异（EvolutionMutator）
    │
    ▼
L3 评估（PromotionGate.evaluate → bridge.evaluate）
    │
    ▼
L2 晋升（PromotionGate.decide → VersionDAG.commit）
    │
    ▼
L1 下次派活读到新活跃模板（VersionDAG.get_active）
```

**关键问题**：
- L2 变异的是 specialist 的 prompt 吗？—— **不是**。演化的是 `ContextSummaryTemplate`（W2）和 `SkillInjectionTemplate`（W4）。
- `trigger_manager` 触发条件是？—— **四源**：失败聚焦 / specialist 降级 / metric 告警 / 周期兜底。
- 进化出的新版本如何回滚？—— `VersionDAG.rollback(artifact_id)` 把 is_active 指针回退。
- `promotion_gate` 和 `git_ratchet` 什么关系？—— 两套独立体系：multiagent 版本晋升 vs skill 版本棘轮。

## 阶段六：验证闭环

### 6.1 五个验证实验

| 实验 | 做法 | 验证什么 |
|---|---|---|

### 6.2 一个完整追踪练习

在以下 6 个位置各打一个 log，跑一次派活，看日志顺序：

1. `OrchestrationMiddleware.wrap_tool_call` 入口
2. `tools.py` 的 `delegate_tool` handler 入口
3. `ContextSummarizer.summarize` 出口
4. `SpecialistRuntime.invoke` 入口 / 出口
5. `ResultSummarizer.summarize` 出口
6. `OrchestrationMiddleware.wrap_tool_call` 的 `_after_handler`

**不一致的地方就是你理解错的地方。**

### 6.3 两个语义确认

- **Specialist 持有 Runtime（不是继承）**——通过类型标注和构造参数验证。
- **`Subagent` 与异构 `Specialist` 是两条并列路径**——通过 registry 里两者的注册方式和 summarizer 配对验证。
