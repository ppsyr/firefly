```
① L2 检测到指标退化 / 失败超阈值
        │
        ▼
② L2 触发进化
        │
        ├─ ② -1 抽取历史样本（task_sample）
        ├─ ② -2 用 mutator 变异出 candidate（新版本）
        │
        ▼
③ L2 调 L3 评估
        │
        └─ L3.evaluate(EvalContext)
            ├─ candidate vs baseline
            ├─ programmatic / llm_judge
            └─ 返回 EvalResult
        │
        ▼
④ L2 根据评估结果决定是否晋升
        │
        └─ promotion_gate(EvalResult)
            ├─ 新版本更好 → 晋升
            └─ 没变好 / 更差 → 丢弃
```

## 1. L2 演化在演化什么

### 1.1. 概述

**L2 演化的是"specialist 调用时用的两个模板"——ContextSummaryTemplate（W2，控制 context 怎么生成）和 SkillInjectionTemplate（W4，控制 skill 怎么注入）。不是演化 specialist 本身，也不是演化 Leader。**

---

### 1.2. 两种演化产物

从 `types.py` 看，L2 的演化产物有两种：

| 产物 | 代号 | 控制什么 | 演化什么 |
|---|---|---|---|
| `ContextSummaryTemplate` | **W2** | specialist 调用前的 context 生成 | extractors / filters / max_tokens / prompt_skeleton |
| `SkillInjectionTemplate` | **W4** | specialist 调用时的 skill 注入 | skill_selector / injection_format / max_skills |

**W2 是"喂给 specialist 什么上下文"，W4 是"给 specialist 注入什么技能"。**

---

### 1.3. 演化触发条件：从失败分类出发

L2 不是"随便变异"——它由 `FailureCategory` 驱动：

```
L1 ResultSummarizer 判定失败
    │
    └─ 输出 FailureCategory：
        ├─ CONTEXT_INSUFFICIENT  → 演化 W2（改 context 生成）
        ├─ ABILITY_INSUFFICIENT  → 演化 W4（改 skill 注入）
        ├─ GOAL_UNCLEAR          → 不演化（转告警）
        └─ SANDBOX_ISSUE         → 不演化（转告警）
```

**演化方向由失败原因决定**：

- 失败因为"上下文不够" → 改 W2
- 失败因为"能力不足" → 改 W4
- 失败因为"目标不清"或"沙箱问题" → **不演化**（这些不是模板能解决的）

---

### 1.4. 演化流程（一次完整的 L2 进化）

```
① 触发（TriggerSource 五选一）
    ├─ PERIODIC（6h cron 兜底）
    ├─ FAILURE_FOCUSED（24h 内某 failure_category ≥ 5）
    ├─ SPECIALIST_DEGRADED（completion_rate < 0.4）
    ├─ COST_ALERT（单次 > $1）
    └─ LATENCY_ALERT（单次 > 5min）
        │
        ▼
② 聚焦（FailureFocuser）
    └─ 聚类失败记录 → 找 dominant_category + top 样本
        │
        ▼
③ 变异（EvolutionMutator）
    ├─ 读当前活跃版本（baseline）
    ├─ 读失败样本
    ├─ 用 LLM 变异
    └─ 产出 candidate（新版本模板）
        │
        ▼
④ 评估（L3）
    └─ candidate vs baseline 在同批 task 上对比
        │
        ▼
⑤ 晋升（PromotionGate）
    ├─ ACCEPT：CI 下界 > baseline CI 上界 → 晋升
    ├─ REJECT：CI 重叠 / hash 命中近 5 版
    └─ FAILED：演化或 eval 失败
        │
        ▼
⑥ 提交（VersionDAG）
    └─ ACCEPT → 写 evolution_artifacts 表 + 更新 is_active
```

---

### 1.5. 演化的"边界"——不演化什么

| 不演化的东西 | 原因 |
|---|---|
| **specialist 本身** | specialist 是外部 CLI（Claude / Codex / Pi），Poirot 改不了 |
| **Leader** | Leader 是编排者，不是被演化对象 |
| **GOAL_UNCLEAR 类失败** | 目标不清不是模板能解决的 |
| **SANDBOX_ISSUE 类失败** | 沙箱问题不是模板能解决的 |
| **L3 本身** | L3 不演化——避免无限递归到 L4 |

**L2 演化的是"模板"——可变异、可版本化、可 diff、可回滚的结构化产物。**

---

### 1.6. 为什么演化模板而不是别的

| 对象 | 能不能演化 | 原因 |
|---|---|---|
| specialist 二进制 | ❌ | 外部工具，Poirot 无控制权 |
| specialist prompt | ⚠️ 部分 | 有些 specialist 不支持定制 prompt |
| **ContextSummaryTemplate** | ✅ | Poirot 自己生成的，完全可控 |
| **SkillInjectionTemplate** | ✅ | Poirot 自己生成的，完全可控 |
| Leader 决策策略 | ⚠️ 复杂 | 涉及整个编排逻辑 |

**模板是"最容易演化、影响最可控"的对象**——改一个模板，只影响"喂给 specialist 的上下文 / 技能"，不涉及 specialist 内部。

---

### 1.7. 总结

> **L2 演化的是两种模板：ContextSummaryTemplate（W2，控制 context 怎么生成）和 SkillInjectionTemplate（W4，控制 skill 怎么注入）。演化方向由 FailureCategory 驱动：CONTEXT_INSUFFICIENT → 改 W2，ABILITY_INSUFFICIENT → 改 W4，其他两类不演化。L2 不演化 specialist 本身（外部工具无控制权）、不演化 Leader、不演化 L3（避免递归到 L4）。模板是"最容易演化、影响最可控"的对象。**

---

## 2. L3 评估是专门为 L2 服务的吗

### 2.1. 概述

**主要是，但不完全——L3 的核心服务对象是 L2（为晋升决策提供评估），但它还提供两个 L2 之外的独立能力：健康监控（runtime_tracker）和跨 run 决策日志（decision_log）。**

---

### 2.2. L3 的三块能力

| 能力 | 组件 | 服务对象 |
|---|---|---|
| **评估打分** | `OrchestrationBridge` + 3 adapter | **L2**（晋升决策的输入） |
| **健康监控** | `SpecialistRuntimeTracker` | **L2**（degraded 触发）+ **运维/可观测** |
| **跨 run 决策日志** | `DecisionLogWriter/Reader` | **L2**（EvolutionMutator 输入样本）+ **L1**（写） |

**三块能力里，第一块是"专为 L2"，后两块是"主要为 L2 但也被其他场景用"。**

---

### 2.3. 评估打分：专为 L2

**这是 L3 最核心的能力**——也是"L3 评估层"这个名字的来源：

```
L2 变异出 candidate
    │
    │ 问题：candidate 比 baseline 好吗？
    ▼
L3.evaluate(ctx) → EvalResult
    │
    ▼
L2 PromotionGate.decide(EvalResult)
```

**没有 L2，就没有"评估"这个需求**——L1 不需要评估（它只记录），L3 存在的首要理由就是"给 L2 提供晋升依据"。

**证据**：

- `EvalContext` 的字段全是 L2 视角：`candidate` / `baseline` / `task_sample`
- `EvalResult` 的输出全是给 L2 用的：`candidate_score` / `baseline_score` / `ci_low` / `ci_high`
- `PromotionDecision`（ACCEPT / REJECT / FAILED）是 L2 的决策枚举

**这块是"专为 L2 服务"。**

---

### 2.4. 健康监控：为 L2 + 为运维

**`SpecialistRuntimeTracker` 做两件事**：

```
health_report(name) → SpecialistHealthReport
    ├─ 给谁用：L2 cron 周期读（判断趋势）
    └─ 也给：运维/CLI 看（虽然 CLI 是 skeleton）

degraded_specialists(threshold) → list[str]
    └─ 给谁用：trigger_l2_evolution_if_degraded → enqueue L2 cron queue
```

**健康监控直接服务于 L2 的"触发决策"**——degraded 命中就触发进化。

**但它同时有"运维价值"**——`SpecialistHealthReport` 里的 `avg_cost_usd` / `avg_latency_seconds` 是运维关心的指标。**CLI skeleton 里的 `l3 health` 就是为这个设计的**（虽然暂未实现）。

**所以：主要为 L2，但也被运维用。**

---

### 2.5. 决策日志：为 L2 + 为 L1

**`DecisionLog` 有两个使用方**：

| 组件 | 使用方 | 用途 |
|---|---|---|
| `DecisionLogWriter.write_async` | **L1**（tool handler 调用后） | 写"这次调用发生了什么" |
| `DecisionLogReader.get_recent_lessons` | **L2**（EvolutionMutator） | 读"最近有哪些失败经验" |

**L1 写入、L2 读取**——**决策日志是 L1 → L2 的信息通道**。

**它不专为 L2 服务**——L1 也要写。但"读"这个动作专为 L2。

---

### 2.6. 严格来说，L3 的定位是什么

| 说法 | 准确性 |
|---|---|
| "L3 专为 L2 服务" | ⚠️ 部分准确——核心评估能力专为 L2，但还有健康监控 + 决策日志 |
| "L3 是 L2 的评估器" | ✅ 准确——这是 L3 的主要定位 |
| "L3 是独立的评估层" | ⚠️ 不准确——L3 默认关闭，为 L2 而存在 |
| "L3 是 multiagent 的可观测层" | ⚠️ 部分准确——健康监控 + 决策日志有可观测价值 |

**最准确的说法**：**L3 是 L2 的评估层——核心职责是"给 L2 的晋升决策提供评估"，同时附带"健康监控"和"决策日志"两个能力。**

---

### 2.7. 为什么 L3 不完全是 L2 的附属

**因为它有三个"独立于 L2 生命周期"的特征**：

1. **决策日志由 L1 写**：L3 的 `DecisionLogWriter` 被 L1 调用——**L1 不依赖 L2**。
2. **健康监控可独立消费**：`SpecialistHealthReport` 可以被 CLI / 运维看——**不经过 L2**。
3. **L3 可以在 L2 关闭时启用**：理论上 L3 可以只做健康监控 + 决策日志，不做评估——虽然当前实现总是绑在一起。

**但实践中，L3 的启用条件就是"L2 需要评估"**——`L3Config.enabled` 默认 `False`，数据驱动触发（L2 演化产物 > 5 版 + floor eval 不足等）。

**所以"主要为 L2 服务"是对的，但"专为"太绝对。**

---

### 2.8. 层级关系图

```
        ┌──────────────────────────────────────┐
        │  L2 进化层（默认关）                   │
        │  ├─ 变异出 candidate                  │
        │  ├─ 调 L3 评估                        │
        │  └─ 根据结果晋升                      │
        └──────────────────────────────────────┘
                    │ 调
                    ▼
        ┌──────────────────────────────────────┐
        │  L3 评估层（默认关）                   │
        │  ├─ 评估打分（★ 专为 L2）             │
        │  ├─ 健康监控（主要 L2 + 可观测）       │
        │  └─ 决策日志（L1 写 + L2 读）         │
        └──────────────────────────────────────┘
                    ▲ 写
                    │
        ┌──────────────────────────────────────┐
        │  L1 运行层（常开）                     │
        │  └─ 每次派活后写决策日志              │
        └──────────────────────────────────────┘
```

---

### 2.9. 总结

> **L3 评估的"核心能力"（评估打分）专为 L2 服务——没有 L2 的晋升需求，就没有 L3 的评估需求。但 L3 还有两个能力不专属于 L2：健康监控（L2 用它触发进化，运维也可看）和决策日志（L1 写入、L2 读取）。所以严格说：L3 是为 L2 服务的评估层，但附带健康监控与决策日志两个跨层能力。它的启用条件（数据驱动：L2 演化产物 > 5 版 + floor eval 不足）也印证了"主要为 L2 而存在"。**
