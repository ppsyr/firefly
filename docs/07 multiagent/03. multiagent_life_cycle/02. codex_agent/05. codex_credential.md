---

name: CodexCredentialProvider — 读 ~/.codex/auth.json 复用 Codex CLI 登录态。

description: 

【整体职责】
发现 Codex CLI 的凭证：读 auth.json（路径可被 $CODEX_AUTH_PATH 覆盖，
默认 ~/.codex/auth.json），兼容 legacy 与 nested 两种 JSON 格式，
解析出 access_token / account_id，返回 CodexCredential。
凭证缺失时返回 None（不抛异常）。

【内容摘要】
- CodexCredential              : 凭证数据类，含 access_token / account_id。
- CodexCredentialProvider      : 凭证发现主类，实现 get_credential()。
- get_credential()             : 读文件 → 兼容两种格式 → 解析字段，返 CodexCredential | None。
- _resolve_path()              : 解析 auth.json 路径（env 覆盖 + 默认路径）。
- _load_json()                 : 读取并解析 JSON 文件，失败返回 None。

【职责边界】
- 只负责：发现凭证、读取文件、兼容两种 JSON 格式、解析字段。
- 不负责：刷新凭证、存储凭证、管理凭证生命周期、写 ThreadState。
- 不持有运行时状态：每次 get_credential 重新读取。

## 0. 结构树

### 0.1. 静态结构树

```
codex_credential.py — CodexCredentialProvider（读 ~/.codex/auth.json）
│
├─ CodexCredential(Credential, frozen)        ← Codex CLI 凭证
│   │                                            只传给 specialist runtime，不写 ThreadState
│   │                                            kind 固定 "codex"
│   ├─ access_token: str                      ← CLI 访问令牌
│   └─ account_id: str = ""                   ← 账户 ID（可选）
│
└─ CodexCredentialProvider                    ← 凭证发现主类
    │                                            复用 CLI 登录态，不管理凭证
    │                                            兼容 legacy + nested 两种 JSON 格式
    │                                            凭证缺失返 None，不抛异常
    │
    ├─ get_credential() -> CodexCredential | None
    │   │                                        ← 主入口
    │   ├─ ① _resolve_path() 解析路径
    │   ├─ ② _load_json(path) 读文件
    │   │     └─ None → 返回 None
    │   ├─ ③ 取 data["tokens"]（非 dict → {}）
    │   ├─ ④ access_token 三级查找：
    │   │     ├─ data["access_token"]（legacy）
    │   │     ├─ data["token"]（另一种 legacy）
    │   │     └─ data["tokens"]["access_token"]（nested）
    │   ├─ ⑤ account_id 两级查找：
    │   │     ├─ data["account_id"]
    │   │     └─ data["tokens"]["account_id"]
    │   ├─ ⑥ access_token 为空 → 返回 None
    │   └─ ⑦ 返回 CodexCredential(kind="codex", ...)
    │
    ├─ _resolve_path() -> Path                ← 解析 auth.json 路径
    │   ├─ $CODEX_AUTH_PATH 存在 → Path(env).expanduser()
    │   └─ 否则 → ~/.codex/auth.json
    │
    └─ _load_json(path) -> dict | None        ← 读取并解析 JSON
        ├─ 文件不存在 / 是目录 → None
        ├─ JSONDecodeError / OSError → None
        └─ 成功 → dict
```

### 0.2. 运行时调用树

```
① 装配期（bootstrap._load_specialist 的 codex 分支）
_load_specialist("codex", config)
    │
    ├─ CodexCredentialProvider().get_credential()       ← 本文件
    │   │
    │   ├─ ① _resolve_path()
    │   │     ├─ $CODEX_AUTH_PATH → 指定路径
    │   │     └─ 默认 ~/.codex/auth.json
    │   │
    │   ├─ ② _load_json(path)
    │   │     ├─ 不存在 / 目录 / 解析失败 → None
    │   │     └─ 成功 → dict
    │   │
    │   ├─ ③ 兼容两种 JSON 格式
    │   │     ├─ legacy: {"access_token": ...}
    │   │     └─ nested: {"tokens": {"access_token": ...}}
    │   │
    │   ├─ ④ 解析 access_token / account_id
    │   │     └─ access_token 为空 → None
    │   │
    │   └─ 返回 CodexCredential | None
    │
    ├─ cred is None → return None（specialist disabled）
    │   └─ bootstrap 打印 warning：如何安装 + 登录 Codex
    │
    └─ cred 非 None → 构造 CodexSpecialist + Summarizers
        → registry.register(specialist)
        → make_specialist_tool(...)
        ═══════════ 进入 Agent 循环 ═══════════

② 运行期（派活给 codex 时）
CodexRuntime.invoke(request)
    │
    ├─ _build_env()
    │   ├─ 再次读 auth 相关 env 变量
    │   │   （CODEX_AUTH_PATH / OPENAI_API_KEY / CODEX_HOME）
    │   └─ 透传给 codex-acp 子进程
    │
    └─ spawn_agent_process(...) 启动 ACP 会话
        │
        └─ codex-acp 子进程内部读自己的登录态（文件 / env）
```

**注意**：`get_credential` 只用于**装配期判断 specialist 是否可用**（auth.json 是否存在、是否有 access_token）；**运行期不再调它**——`CodexRuntime._build_env` 直接读 env 变量透传给子进程，凭证的实际使用发生在 `codex-acp` 子进程内部。

### 0.3. 补充

**`codex_credential.py` 是 Codex specialist 的"身份探测闸门"——装配期判断"用户是否登录过 Codex CLI"，决定 specialist 是否注册。**

几点补充：

- **装配期发现，运行期透传**：`get_credential()` 只在 bootstrap 时调一次，判断 specialist 是否可用；运行时 `CodexRuntime._build_env` 把 env 变量透传给 `codex-acp` 子进程，由子进程自己读登录态。**Provider 不直接传 token 给 runtime，只负责"探明是否存在"。**
- **兼容两种 JSON 格式**：Codex CLI 的历史版本格式变过——旧版是 top-level（`{"access_token": ...}`），新版是 nested（`{"tokens": {"access_token": ...}}`）。**Provider 同时支持新旧，避免旧用户升级后凭证失效。**
- **access_token 三级查找**：`data["access_token"]` > `data["token"]` > `data["tokens"]["access_token"]`。**兜住所有已知写法。**
- **无过期检测**：auth.json 里没有 `expiresAt` 字段，所以不做过期判断——**探测到文件存在且有 access_token 就认为可用**。这与 Claude 的 Provider 不同（Claude 有 `expires_at` 检测）。
- **无"env 直接传 token"路径**：Claude 支持 `$CLAUDE_CODE_OAUTH_TOKEN` 直接传 token，Codex **只读文件**（`$CODEX_AUTH_PATH` 只是指定文件路径，不是传 token）。
- **IO 失败统一返 None**：文件不存在、是目录、JSON 解析失败、读取异常——四种情况都不抛异常，统一返 None。**保证"凭证探测"永不阻塞启动流程。**
- **和 ClaudeCredentialProvider 的对照**：

| 维度 | Claude | Codex |
|---|---|---|
| JSON 格式 | 单一（`claudeAiOauth.accessToken`） | **两种兼容**（legacy + nested） |
| 过期检测 | ✅ 有 | ❌ 无 |
| env 直接传 token | ✅ 有（`CLAUDE_CODE_OAUTH_TOKEN`） | ❌ 无 |
| refresh_token | ✅ 读 | ❌ 无此字段 |
| 查找层级 | 三级 | 两级 |
