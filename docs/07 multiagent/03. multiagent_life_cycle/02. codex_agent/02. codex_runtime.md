---

name: CodexRuntime — ACP 协议实现（启动 codex-acp 子进程 + stdio JSON-RPC）。

description: 

【整体职责】
实现 SpecialistRuntime 契约：通过 ACP 协议（agent-client-protocol）启动 codex-acp
子进程，建立 stdio JSON-RPC 会话，把 goal 作为 prompt 发给子进程，收集流式返回的
文本块，拼成原始输出返回。

【内容摘要】
- CodexRuntime           : runtime 主类，实现 invoke()。
- invoke()               : 同步入口，用 asyncio.run 包装异步 _run_acp_session。
- _run_acp_session()     : 异步 ACP 会话：spawn 子进程 → initialize → new_session → prompt → 收 chunks。
- _build_mcp_config()    : 构造 ACP new_session 的 MCP servers 配置（含 SpecialistMcpServer）。
- _build_env()           : 透传 auth 相关环境变量给 codex-acp 子进程（白名单）。

【职责边界】
- 只负责：启动 ACP 子进程、建立会话、发 prompt、收集输出、异常归一化。
- 不负责：上下文摘要（ContextSummarizer 负责）、结果摘要（ResultSummarizer 负责）、
  凭证发现（CredentialProvider 负责）、沙箱生命周期（sandbox 层负责）。
- 不持有运行时状态：每次 invoke 启动新进程 + 完成关闭，不做连接池。

## 0. 结构树

### 0.1. 静态结构树

```

│

    │   │   ├─ SpecialistError 子类  → 原样抛出
    │   │   ├─ FileNotFoundError    → SpecialistStartupError

    │   └─ return SpecialistRawResult(raw_output, duration_seconds)
    │
    ├─ _run_acp_session(request) -> str（async）
    │   │                                        ← 异步 ACP 会话
    │   ├─ ① lazy import acp 包
    │   │     └─ ImportError → SpecialistStartupError（提示 pip install）
    │   ├─ ② _build_mcp_config(request.sandbox_id)
    │   │     └─ 构造 MCP servers 配置（含 SpecialistMcpServer）
    │   ├─ ③ 定义 _Collector(Client)
    │   │     └─ session_update 收集 TextContentBlock 文本到 chunks
    │   ├─ ④ agent_env = self._build_env()
    │   ├─ ⑤ async with spawn_agent_process(...)
    │   │     ├─ conn.initialize(protocol_version, client_capabilities, client_info)
    │   │     ├─ conn.new_session(cwd=artifacts_path, mcp_servers=...)
    │   │     ├─ asyncio.wait_for(conn.prompt(goal), timeout=request.timeout_seconds)
    │   │     └─ 退出 async with → 自动关闭子进程
    │   └─ return "".join(chunks)
    │
    ├─ _build_mcp_config(sandbox_id) -> list[dict]
    │   ├─ sandbox_id is None → 返回 []
    │   └─ 非 None → [{name, type: "stdio", command: "python", args: [...]}]

        ├─ CODEX_HOME              → env
        └─ 无命中 → None（子进程继承父 env）

    内部辅助类：
    └─ _Collector(Client)                     ← 会话更新收集器

```

### 0.3. 补充

**`codex_runtime.py` 是 Codex specialist 的"ACP 协议执行器"——启动 `codex-acp` 子进程，通过 stdio JSON-RPC 建立会话，流式收集输出。**

几点补充：

- **同步壳包异步**：对外只暴露同步 `invoke`，内部用 `asyncio.run` 包装异步 `_run_acp_session`。**这是为了满足 SpecialistRuntime 契约的 sync only 要求**，同时内部又能用 ACP 包的 async API。
- **ACP 是 lazy import**：`acp` 包是可选依赖，未安装时抛 `SpecialistStartupError` 并提示 `pip install agent-client-protocol`。**避免硬依赖导致整个 Poirot 起不来。**
- **异常映射有优先级**：`SpecialistError` 子类**原样抛出**（不包装），确保 `_run_acp_session` 里主动抛的 `SpecialistStartupError` 不被外层再包成 `SpecialistCrashError`。**顺序很重要**：`except SpecialistError: raise` 必须在 `except Exception` 之前。
- **`_Collector` 是流式收集器**：ACP 的 `session_update` 会多次回调，每次收到 `TextContentBlock` 就 append 到 `chunks`。**最终输出是 chunks 拼接**，而不是单次返回。
- **MCP 配置走 `new_session` 参数**：与 ClaudeCode 的 `claude mcp add` 命令不同，Codex 通过 ACP 协议的 `new_session(mcp_servers=...)` 参数动态传入。**两种 specialist 接入 MCP 的方式不同。**
- **env 白名单更窄**：只透传 3 个变量（`CODEX_AUTH_PATH` / `OPENAI_API_KEY` / `CODEX_HOME`），比 ClaudeCode 的 4 个还少。**防泄漏优先。**
- **`cwd` 取 `artifacts_path`**：会话工作目录来自 `request.artifacts_path`，未设置时用 `"."`。**这让 codex 的文件操作有明确的落脚点。**


# 1. ClaudeCode 与 Codex Runtime 对比

## 1.1. 一张表看清差异

| 维度 | ClaudeCodeRuntime | CodexRuntime |
|---|---|---|
| **通信方式** | `subprocess.run` + stdout | ACP 协议 + stdio JSON-RPC |
| **同步/异步** | 纯同步 | 同步壳（`asyncio.run`）包异步 |
| **子进程启动** | `subprocess.run(["claude", "--print", goal])` | `spawn_agent_process(client, "npx", "-y", "@zed-industries/codex-acp")` |
| **输入传递** | goal 作为命令行参数 | goal 作为 prompt 经 JSON-RPC 发送 |
| **输出收集** | 一次性读 `result.stdout` | 流式 `session_update` 回调 + chunks 拼接 |
| **依赖** | 无（标准库） | `acp` 包（lazy import，可选依赖） |
| **MCP 配置方式** | `claude mcp add` 命令（提前注册） | `new_session(mcp_servers=...)` 参数（会话内传入） |
| **MCP 配置时机** | invoke 前独立调 `configure_mcp` | 会话建立时随 `new_session` 传 |
| **env 白名单** | 4 个（CLAUDE_CODE_OAUTH_TOKEN / ANTHROPIC_AUTH_TOKEN / ANTHROPIC_API_KEY / CLAUDE_CODE_CREDENTIALS_PATH） | 3 个（CODEX_AUTH_PATH / OPENAI_API_KEY / CODEX_HOME） |
| **超时机制** | `subprocess.run(timeout=...)` | `asyncio.wait_for(conn.prompt(...), timeout=...)` |
| **子进程生命周期** | run 内自动（阻塞→退出） | `async with` 管理（会话结束→关闭） |
| **异常映射** | TimeoutExpired / FileNotFoundError / returncode | asyncio.TimeoutError / SpecialistError / FileNotFoundError / 其他 |
| **命令默认值** | `claude` | `npx -y @zed-industries/codex-acp` |

**核心差异一句话**：Claude 走"**启动-等待-收 stdout**"的进程模型，Codex 走"**建立会话-流式交互**"的协议模型。

## 1.2. 为什么 Claude 用 CLI

### 原因 ①：Claude Code CLI 本身设计成"一次性可调用"

`claude --print` 是 Claude Code 提供的**非交互模式**：

```bash
claude --print "帮我审查这段代码"
```

**跑完即退，结果打到 stdout。** 这正是 `subprocess.run` 最擅长的场景——启动、等待、收输出。

### 原因 ②：CLI 是最简单的集成方式

| 集成方式 | 复杂度 |
|---|---|
| CLI 子进程 | 极低——只要程序在 PATH 里 |
| ACP 协议 | 中——需要协议实现、握手、会话管理 |
| SDK 集成 | 高——需要引入依赖、适配 API |

**Claude Code 的 `--print` 提供了"零协议"的调用方式**，没理由不用。

### 原因 ③：无协议依赖，稳定性更高

CLI 方式**只依赖操作系统**：

- 不需要 `acp` 这样的第三方包
- 不需要处理 JSON-RPC 握手
- 不需要管会话生命周期

**代价**：拿不到流式输出（只能等全部跑完）、无法细粒度控制。

### 原因 ④：Claude Code 当时没有 ACP adapter

注释里明确写了：

> **不走 ACP（无 Claude Code ACP adapter）**

**不是"不想用 ACP"，而是"Claude 侧没有提供 ACP 适配器"。** 既然只能 CLI，就用最直接的 CLI 方式。

---

## 1.3. 为什么 Codex 用 ACP

### 原因 ①：Codex 有官方 ACP adapter

```python
args=("-y", "@zed-industries/codex-acp")
```

`@zed-industries/codex-acp` 就是 Codex 的 **ACP 适配器**。它把 Codex 的能力包装成 ACP 协议服务端。

**既然有现成的，就用标准的。**

### 原因 ②：ACP 能拿到流式输出

CLI 模式的 `subprocess.run` 是**阻塞式**的——必须等子进程全部跑完才能拿到 stdout。

ACP 模式通过 `session_update` 回调**实时收每个文本块**：

```python
class _Collector(Client):
    async def session_update(self, session_id, update, **kwargs):
        if isinstance(update.content, TextContentBlock):
            chunks.append(update.content.text)
```

**好处**：

- 能展示"正在输出"的过程
- 能对长任务做更细的超时控制
- 能在中途取消

### 原因 ③：ACP 是"协议"而非"命令"，能力更强

| 能力 | CLI | ACP |
|---|---|---|
| 传 goal | 命令行参数 | JSON-RPC 消息 |
| 传 MCP 配置 | 提前 `mcp add`（全局注册） | `new_session(mcp_servers=...)`（按会话传入） |
| 多轮交互 | ❌ 一次性 | ✅ 会话内可多次 prompt |
| 流式输出 | ❌ 等全部 | ✅ 逐块回调 |
| 结构化元数据 | ❌ 只有 stdout | ✅ JSON-RPC 字段 |

**ACP 把"一次性调用"升级为"会话"**——Codex 需要这个能力。

### 原因 ④：MCP 配置更自然

Claude 走 CLI，MCP 得**提前注册**：

```bash
claude mcp add poirot_sandbox -- python -m ... --sandbox-id ...
```

**这是"全局副作用"**——注册后所有 claude 会话都会带上这个 MCP。

Codex 走 ACP，MCP 配置**随会话传入**：

```python
await conn.new_session(
    cwd=...,
    mcp_servers=[{"name": "poirot_sandbox", ...}],
)
```

**这是"按需传入"**——不影响其他会话。

**从设计上，ACP 的 MCP 配置更干净。**

## 1.4. 为什么不是"两个都用 CLI"或"两个都用 ACP"

### 如果两个都用 CLI

- **Codex 会退化**：拿不到流式输出、MCP 配置只能全局注册、无法多轮交互
- **要自己造协议**：Codex 侧有 ACP adapter，用 CLI 反而绕远路

### 如果两个都用 ACP

- **Claude 侧没有 ACP adapter**：注释里说得很清楚
- **强行适配代价高**：要么等 Claude 官方提供，要么自己写 adapter

**所以最终是"按各自的能力选择最优路径"**：

- Claude 有 CLI 无 ACP → 走 CLI
- Codex 有 ACP → 走 ACP

## 1.5. 两条路径的本质差异

```
ClaudeCodeRuntime（CLI 模型）
─────────────────────────────────
invoke()
  → subprocess.run(["claude", "--print", goal])
  → 阻塞等待
  → 一次性读 stdout
  → 返回

特点：
  ├─ 无状态（每次独立进程）
  ├─ 阻塞式（等全部完成）
  ├─ 输出一次性
  └─ 依赖少（只用标准库）


CodexRuntime（ACP 模型）
─────────────────────────────────
invoke()
  → asyncio.run(_run_acp_session())
      → spawn_agent_process(...)     ← 起进程 + 建连接
      → conn.initialize(...)          ← 握手
      → conn.new_session(...)         ← 建会话
      → conn.prompt(goal)             ← 发消息
          → session_update 回调       ← 流式收
      → 关闭会话
  → 返回

特点：
  ├─ 会话式（有握手/会话/关闭）
  ├─ 异步（内部 asyncio）
  ├─ 流式输出
  └─ 依赖 acp 包
```

**一句话**：Claude 是"**调用一次程序**"，Codex 是"**和程序对话**"。

---

## 1.6. 为什么这种差异是合理的

| 角度 | 解释 |
|---|---|
| **外部工具能力** | Claude 提供 `--print`，Codex 提供 ACP adapter。**用什么取决于对方给什么。** |
| **能力上限** | ACP 能做 CLI 做不到的（流式、会话、按需 MCP）。**有则用。** |
| **依赖代价** | CLI 零依赖，ACP 依赖 `acp` 包。**能用零依赖就不引依赖。** |
| **一致性 vs 最优** | 本可以"统一都用 CLI"求一致，但那样 Codex 会损失能力。**选"各自最优"。** |
| **封装隔离** | 两种差异被 `SpecialistRuntime` 契约封住——**上层 Specialist / Tool / Leader 完全不感知**。 |

**关键点**：这个差异**没有泄漏到上层**。`CodexSpecialist` 和 `ClaudeCodeSpecialist` 的 `invoke` 签名完全一样，都是 `invoke(request) -> SpecialistRawResult`。**上层只看到"一个 specialist"，看不到底层是 CLI 还是 ACP。**

---

## 1.7. 补充：两种方式可能统一吗

**理论上可以，但没必要。**

- **统一成 CLI**：Codex 要放弃 ACP 能力，得不偿失。
- **统一成 ACP**：Claude 侧没 adapter，得自己写。
- **抽象成"通用外部进程 runtime"**：CLI 和 ACP 差异太大（一个是一次性、一个是会话），强行抽象会得到"两不像"。

**所以当前设计是"统一契约，各自实现"**——`SpecialistRuntime` 是统一契约，`ClaudeCodeRuntime` / `CodexRuntime` 是各自最优实现。

**这正是契约存在的意义**：让差异被封装在实现层，不污染上层。

---

## 1.8. 总结

> **Claude 用 CLI，因为 Claude Code 提供了 `--print` 非交互模式且没有 ACP adapter；Codex 用 ACP，因为 Codex 有官方 `codex-acp` adapter 且 ACP 能提供流式、会话、按需 MCP 等更强能力。这不是偏好，是"按对方能力选最优路径"。两者差异被 `SpecialistRuntime` 契约封住，上层无感知。**
