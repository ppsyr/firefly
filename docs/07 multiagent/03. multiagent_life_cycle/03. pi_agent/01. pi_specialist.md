## 1. Pi 和 Codex 都是 CODING
## 1.1. 从代码看

```python
# CodexSpecialist
capabilities=(SpecialistCapability.CODING,)

# PiSpecialist
capabilities=(SpecialistCapability.CODING,)
```

**两个 specialist 声明同一能力。**

对照其他两个：

| Specialist | capability |
|---|---|
| `ClaudeCodeSpecialist` | REVIEW |
| `SubagentSpecialist` | RESEARCH |
| `CodexSpecialist` | **CODING** |
| `PiSpecialist` | **CODING** |

**只有 CODING 有两个 specialist。**

---

## 1.2. capability 的作用：过滤，不是唯一

`capability` 用在 `list_specialists(capability=...)`：

```python
def list_specialists(self, capability=None) -> list[str]:
    if capability is None:
        return names
    return [
        name for name in names
        if self._specialists[name].capabilities.has(capability)
    ]
```

**它的语义是"哪些 specialist 能做这类事"，不是"哪一件事只能谁做"。**

调用 `list_specialists(CODING)` 会返回：

```python
["pi", "codex"]     # 两个都能做编码
```

**这是一个候选列表，不是唯一答案。**

---

## 1.3. 为什么 CODING 需要两个

### 原因 ①：可用性不同——"哪个装了用哪个"

| Specialist | 可用条件 |
|---|---|
| Codex | Codex CLI 已装 **+ 已登录**（`~/.codex/auth.json` 存在） |
| Pi | Pi CLI 已装 **+ 有 API key**（env 或 config） |

**用户的机器上可能只满足一个**：

- 装了 Codex 并登录 → Codex 可用
- 只设了 API key 没装 Codex → Pi 可用
- 两个都满足 → 两个都能用

**声明同一 capability，让"能用的那个"被选中。**

### 原因 ②：能力有差异——"哪个更合适用哪个"

虽然都叫 CODING，但两者定位不同：

| 维度 | Codex | Pi |
|---|---|---|
| 通信方式 | ACP 协议 | CLI + MCP bridge |
| 依赖 | codex-acp adapter | pi CLI + poirot-sandbox-bridge |
| 特色 | 测试通过率 + diff 校验 | 强制走 Poirot 沙箱 |
| 触发条件 | 装了 + 登录了 | 装了 + 有 key |

**Leader 可以按任务细节选择**——比如"需要严格测试验证"选 Codex，"需要沙箱隔离"选 Pi。

### 原因 ③：渐进式降级——"一个不行换另一个"

如果 Codex 派活失败（超时 / 崩溃），Leader 可以：

```
① 尝试 codex（CODING 首选）
② 失败 → 尝试 pi（CODING 备选）
③ 都失败 → 自己干
```

**两个同能力 specialist 提供了"冗余"**——一个挂了还有另一个。

---

## 1.4. 这和"唯一性"矛盾吗

**不矛盾。** capability 是**标签**，不是**主键**。

| 概念 | 语义 | 是否唯一 |
|---|---|---|
| `name` | specialist 标识 | ✅ 唯一（registry 的 key） |
| `capability` | 能力标签 | ❌ 可多个 specialist 共享 |

**类比**：

- `name` = 员工工号（唯一）
- `capability` = 技能标签（"会写代码"——多个人都可能有）

**招聘时可以说"找会写代码的人"，可能找到多个。** 最终选谁，由 Leader 决定。

---

## 1.5. Leader 怎么在两者间选

**Poirot 不做硬编码路由**（soft routing）——**由 LLM 根据工具描述自己决定**。

LLM 看到的两个工具：

```
delegate_to_codex
  "Delegate task to specialist. Provide goal and success_criteria..."

delegate_to_pi
  "Delegate task to specialist. Provide goal and success_criteria..."
```

**两个工具的 description 目前是一样的**（都是 `make_specialist_tool` 生成的通用描述）。所以 LLM 的选择依据主要是：

- 工具名（`codex` vs `pi`）
- 任务的语义（"用 codex 做" / "用 pi 做"）
- 历史经验（如果 Leader prompt 里有提及）

**严格来说，当前实现下 LLM 没有强区分依据**——它可能随机选，也可能按名字偏好选。

---

## 1.6. 设计上是否合理

| 角度 | 评价 |
|---|---|
| **语义正确** | ✅ 两个都是编码工具，标 CODING 没错 |
| **可用性适配** | ✅ 用户装哪个用哪个 |
| **冗余降级** | ✅ 一个失败可换另一个 |
| **路由明确性** | ⚠️ 当前 description 一样，LLM 区分度低 |
| **是否冗余** | ❌ 不是——功能重叠但可用性/依赖/特色不同 |

**唯一可议的点**：`make_specialist_tool` 生成的 tool description 是通用的，没体现 codex 和 pi 的差异。**如果未来想让 LLM 精准选，需要给每个 specialist 定制 description。**

---

## 1.7. 总结

> **Pi 和 Codex 都声明 CODING，这是合理的——capability 是"能力标签"不是"唯一主键"，多个 specialist 可以共享同一能力。这样设计的好处是：① 用户装哪个用哪个（可用性适配）；② 能力有差异可择优选（Codex 关注测试、Pi 强制沙箱）；③ 一个失败可换另一个（冗余降级）。当前实现的不足是 tool description 一样，LLM 区分度低——这可能需要后续给每个 specialist 定制描述来改善。**
