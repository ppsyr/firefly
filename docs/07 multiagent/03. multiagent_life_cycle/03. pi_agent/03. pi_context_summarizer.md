---

name: PiContextSummarizer — 规则提取（代码片段 + 文件路径，零 LLM）。

description: 

【整体职责】
为 Pi specialist 生成 context_summary：从父 ThreadState 中提取代码块和文件路径，
拼成一段精简上下文。零 LLM，纯规则提取，控制 token 成本。

【内容摘要】
- _CODE_BLOCK_RE / _MAX_CODE_BLOCKS / _MAX_PATHS / _MAX_SUMMARY_CHARS : 规则常量。
- _field()                      : 从 dict 或对象中统一取字段。
- PiContextSummarizer           : 输入端转换器主类。
- summarize()                   : 入口，拼装 goal + 代码块 + 文件路径。
- _extract_code_blocks()        : 从 messages 提取代码块（最多 3 个）。
- _extract_file_paths()         : 从 observations + messages 提取文件路径（最多 10 个）。

【职责边界】
- 只负责：从 ThreadState 规则提取代码块与文件路径，拼成 context_summary 字符串。
- 不负责：结果压缩（ResultSummarizer 负责）、specialist 执行、LLM 调用。
- 不持有运行时状态：纯函数式读取，不写回 state。

## 0. 结构树

### 0.1. 静态结构树

```
pi_context_summarizer.py — PiContextSummarizer（规则提取：代码 + 文件路径）
│
├─ 常量
│   ├─ _CODE_BLOCK_RE                         ← 代码块正则：``` ... ```（含跨行）
│   ├─ _MAX_CODE_BLOCKS: int = 3              ← 最多提取的代码块数量
│   ├─ _MAX_PATHS: int = 10                   ← 最多提取的文件路径数量
│   └─ _MAX_SUMMARY_CHARS: int = 3000         ← 总摘要最大字符数，超出截断
│
├─ _field(item, name) -> Any                  ← 统一字段访问
│   ├─ dict → item.get(name)
│   └─ 对象 → getattr(item, name, None)
│
└─ PiContextSummarizer                       ← 输入端转换器主类（零 LLM，纯规则）
    │
    ├─ summarize(state, goal, success_criteria, template=None) -> str
    │   │                                        ← 入口：拼装 context_summary
    │   ├─ ① 拼 "Goal: ..." / "Success criteria: ..."
    │   ├─ ② _extract_code_blocks(state)
    │   │     └─ 非空 → 拼 "Relevant code:" + 各代码块
    │   ├─ ③ _extract_file_paths(state)
    │   │     └─ 非空 → 拼 "Relevant files:" + 各路径
    │   ├─ ④ 总长 > 3000 → 截断 + "... (truncated)"
    │   └─ ⑤ 返回 summary
    │
    ├─ _extract_code_blocks(state) -> list[str] ← 从 messages 提取代码块
    │   ├─ 遍历 messages → _field(msg, "content")
    │   ├─ 非 str → 跳过
    │   ├─ _CODE_BLOCK_RE.finditer(content)     ← 逐个匹配（非 findall）
    │   ├─ 找够 _MAX_CODE_BLOCKS=3 → break
    │   └─ 返回 blocks
    │
    └─ _extract_file_paths(state) -> list[str]  ← 从 observations + messages 提取路径
        ├─ ① 遍历 observations → content
        │   ├─ 正则 path_re = [\w/\-\.]+\.\w+ 匹配
        │   ├─ 去重追加
        │   └─ 满 10 条 → return
        ├─ ② 遍历 messages → content
        │   ├─ 同样正则匹配
        │   ├─ 去重追加
        │   └─ 满 10 条 → return
        └─ 返回 paths
```

### 0.3. 补充

**`pi_context_summarizer.py` 是 Pi specialist 的"输入端闸门"——从父 ThreadState 里挑出"代码块 + 文件路径"，压成一段精准上下文，零 LLM。**

几点补充：

- **零 LLM，纯规则**：与其他 context summarizer 一样，没有任何 LLM 路径。**完全靠正则和列表遍历**。
- **与 CodexContextSummarizer 同构，但路径来源不同**：
  - **Codex**：从 `state["artifacts"]` 读结构化 `path` 字段——精确、无正则
  - **Pi**：从 `observations` + `messages` 的文本内容用正则扫——模糊、可能误抓
  - **为什么不同**：Pi 强制走 Poirot MCP，它的操作记录落在 `observations` 里（工具调用记录），不一定进 `artifacts`。**所以要从文本扫。**
- **双源提取 + 提前返回**：先扫 `observations`，满 10 条直接 `return`；不够再扫 `messages`。**优先用 observations（更接近实际执行），后补 messages。**
- **代码块用 `finditer` 而非 `findall`**：逐个匹配、找够即停。**比 `findall` 一次性收集全部再截断更省内存。**
- **路径正则是"宽松匹配"**：`[\w/\-\.]+\.\w+` 会匹配任何"路径样式"的字符串——**可能误抓 URL、版本号（如 `v1.2`）等**。这是"零 LLM 纯规则"的固有代价。
- **截断后缀与其他 summarizer 略有不同**：Pi 用 `"\n... (truncated)"`（多一个空格），Codex 用 `"\n...(truncated)"`。**这是实现细节差异，不影响功能。**
- **`template` 参数全程未用**：L2 扩展预留位，与其他 context summarizer 一致。
