---

name: tools.py — 动态生成 specialist tool + subagent tool。

description: 

【整体职责】
为每个 specialist / subagent 动态生成一个 LangChain BaseTool（delegate_to_<name>），
供 Leader 的 LLM 调用。tool handler 内部完成整条派活编排：
ContextSummarizer → specialist.invoke → ResultSummarizer → 返回 JSON 字符串。
LLM 只需填 3 个参数（goal / success_criteria / sandbox_id 可选），其余内部处理。

【内容摘要】
- set_current_state() / get_current_state() : 通过 ContextVar 暴露 / 读取当前 ThreadState。
- _extract_sandbox_id()                     : 从 state 或显式参数解析 sandbox_id。
- _write_decision_log_async()               : 异步写 DecisionLogRecord（L3 扩展，fire-and-forget）。
- make_specialist_tool()                    : 为 specialist 生成 delegate_to_<name> 工具。
- make_subagent_tool()                      : 为 subagent 生成 delegate_to_subagent 工具。

【职责边界】
- 只负责：tool 生成、tool handler 内的派活编排、JSON 序列化、异常转 error JSON。
- 不负责：路由决策（LLM 负责）、打点（OrchestrationMiddleware 负责）、
  specialist 实际执行（runtime 负责）、上下文/结果摘要的实现（summarizer 负责）。
- 不持有状态：`_current_state` 是 ContextVar，随调用上下文隔离。

## 0. 结构树

### 0.1. 静态结构树

```
tools.py — 动态生成 specialist tool + subagent tool
│
├─ _current_state: ContextVar[dict | None]    ← 跨调用隔离的 ThreadState 传递通道
│   │                                            由 OrchestrationMiddleware 写入
│   │                                            由 tool handler 读取
│   │                                            default=None
│   │
│   ├─ set_current_state(state) -> None       ← OrchestrationMiddleware 调用：写入 state
│   └─ get_current_state() -> dict            ← tool handler 调用：读取 state（未设 → 空 dict）
│
├─ _extract_sandbox_id(state, sandbox_id)     ← 解析 sandbox_id
│   └─ 优先级：显式参数 > state["sandbox"]["sandbox_id"] > None
│
├─ _write_decision_log_async(writer, name, goal, success_criteria, result)
│   │                                            ← L3 扩展：异步写 DecisionLogRecord（fire-and-forget）
│   ├─ lazy import L3 类型                      ← 避免循环依赖
│   ├─ failure_category 从 result 取             ← 字符串 → FailureCategory 枚举；转换失败置 None
│   ├─ 构造 DecisionLogRecord
│   └─ writer.write_async(record)              ← 不阻塞 L1 turn
│
├─ make_specialist_tool(name, specialist, context_summarizer, result_summarizer, *,
│                       max_steps=50, timeout_seconds=600,
│                       version_dag=None, budget_guard=None, decision_log_writer=None)
│   │                                            ← Factory：生成 delegate_to_<name> tool
│   │
│   └─ delegate_tool(goal, success_criteria, sandbox_id=None) -> str
│       │                                        ← 内层 tool handler（@tool 装饰）
│       │                                        LLM 只填 goal + success_criteria（+ 可选 sandbox_id）
│       │
│       ├─ ① get_current_state()               ← 读 ThreadState
│       ├─ ② _extract_sandbox_id               ← 解析 sandbox_id
│       ├─ ③ budget_guard 检查（若非 None）
│       │   └─ 超限 → 返回 BudgetExceeded JSON（不再调用 specialist）
│       ├─ ④ context_summarizer.summarize      ← 压上下文
│       ├─ ⑤ 构造 SpecialistRequest
│       ├─ ⑥ specialist.invoke(request)
│       │   └─ except SpecialistError → 返回 error JSON
│       ├─ ⑦ result_summarizer.summarize       ← 压结果 + 程序化评估
│       ├─ ⑧ decision_log_writer 写日志（若非 None）
│       └─ ⑨ 返回 JSON {success, summary, specialist, gap_analysis, artifacts}
│
└─ make_subagent_tool(subagent_provider, context_summarizer, result_summarizer, *,
                     max_steps=20, timeout_seconds=300)
    │                                            ← Factory：生成 delegate_to_subagent tool
    │
    └─ delegate_tool(goal, success_criteria, sandbox_id=None) -> str
        ├─ ① get_current_state()
        ├─ ② _extract_sandbox_id
        ├─ ③ context_summarizer.summarize
        ├─ ④ 构造 SubagentRequest
        ├─ ⑤ subagent_provider.spawn(request)
        │   └─ except SubagentError → 返回 error JSON
        ├─ ⑥ result_summarizer.summarize
        └─ ⑦ 返回 JSON（结构同 specialist 版，specialist 字段固定 "subagent"）
```

### 0.2. 运行时调用树

```
① 装配期
setup_multiagent
    ├─ make_specialist_tool(name, specialist, ctx_sum, res_sum,
    │                       budget_guard=..., decision_log_writer=...)
    │   → 加入 tools 列表
    └─ make_subagent_tool(...)                 ← 仅当 "subagent" 不在 specialists_use 时
        → 加入 tools 列表
    → 工具列表注入 Leader
        ═══════════ 进入 Agent 循环 ═══════════

② 运行期（LLM 调用 delegate_to_codex）
Leader LLM → tool_call("delegate_to_codex", {goal, success_criteria})
    │
    ▼
ToolNode → OrchestrationMiddleware.wrap_tool_call
    ├─ _before_handler
    │   └─ set_current_state(state)            ← 写入 ContextVar
    │       └─ metrics 打点（selection / invoked）
    │
    ▼
delegate_tool(goal, success_criteria, sandbox_id=None)   ← 本文件
    ├─ get_current_state()                     ← 读 ContextVar
    ├─ _extract_sandbox_id
    ├─ budget_guard.check_and_record(name, cost)   ← L2 检查
    ├─ context_summarizer.summarize(state, goal, criteria)
    ├─ SpecialistRequest(...)
    ├─ specialist.invoke(request)
    │   ├─ 成功 → SpecialistRawResult
    │   └─ 异常 → SpecialistError → 返回 error JSON
    ├─ result_summarizer.summarize(raw_output, artifacts, goal, criteria)
    │   └─ → SpecialistResult
    ├─ _write_decision_log_async(writer, ...)  ← L3 fire-and-forget（若 writer 非 None）
    └─ return json.dumps({success, summary, specialist, gap_analysis, artifacts})
    │
    ▼
OrchestrationMiddleware.wrap_tool_call（返回后）
    ├─ _after_handler
    │   ├─ _is_success（解析 JSON） → record_completion / record_fallback
    │   └─ _build_orchestration_update（构造 ArtifactRef 列表）
    └─ return Command{update: {messages, orchestration}}
        → ThreadState.orchestration 更新
        → LLM 拿到 ToolMessage 继续推理
```

### 0.3. 补充

**`tools.py` 是 multiagent 的"派活工具工厂"——为每个 specialist / subagent 造一个 LLM 可见的工具，tool handler 内部完成整条派活编排（摘要 → 执行 → 摘要 → JSON）。**

几点补充：

- **LLM 只看到 3 个参数**：`goal` / `success_criteria` / `sandbox_id`（可选）。其余（max_steps、timeout、context_summary、artifacts_path）全部由 factory 闭包捕获或 handler 内部解析，LLM 不感知。**这是控制 LLM 认知负担的关键设计。**
- **ContextVar 是"暗线"**：`state` 不是通过参数传进 handler 的，而是由 `OrchestrationMiddleware` 在调用前 `set_current_state` 写进 ContextVar，handler 内 `get_current_state` 读取。这样 tool 的对外签名（给 LLM 的）能保持极简，而 handler 内部又能拿到完整 ThreadState。
- **两条路径结构同构**：`make_specialist_tool` 和 `make_subagent_tool` 的 handler 流程几乎一样（读 state → 摘要 → 执行 → 摘要 → JSON），差别只在：
  - specialist 走 `specialist.invoke` + `SpecialistError`
  - subagent 走 `subagent_provider.spawn` + `SubagentError`
  - 返回 JSON 里 `specialist` 字段硬编码为 `"subagent"`
- **异常不外抛，全部转 JSON**：`SpecialistError` / `SubagentError` 都被捕获并转为 `{"success": false, "error": {...}}`。这样 LLM 能通过 ToolMessage 看到失败原因，自行决定 retry / fallback / self-do。
- **L2 / L3 都是可选扩展**：`budget_guard` 和 `decision_log_writer` 为 None 时对应分支完全跳过，L1 行为不变。
- **`version_dag` 是死参数**：`make_specialist_tool` 签名里有 `version_dag`，但函数体内完全没有使用——是预留位，等待后续接入。

## 完整流程（分清两个动作）

```
① tools.py 的工厂函数被调用
   make_specialist_tool("codex", ...)
        │
        └─ 产出：delegate_to_codex（一个 BaseTool 对象）  ← tools.py 干的

② setup_multiagent 收集这些产出
   tools = [delegate_to_codex, delegate_to_claude, ...]
   MultiAgentSetup(specialist_tools=tuple(tools))
        │
        └─ 产出：一批 BaseTool                              ← bootstrap 干的

③ CapabilityRegistry 存放
   registry.specialist_tools = setup.specialist_tools
        │
        └─ registry 手里拿着这批工具                          ← registry 干的

④ Leader factory 注入
   tools = builtin_tools + registry.specialist_tools
   create_poirot_agent(tools=tools, ...)
        │
        └─ 工具进了 Leader 的构造参数                          ← Leader factory 干的

⑤ LLM 可见
   LLM 的 tool schema 里出现 delegate_to_codex
```

**`tools.py` 只负责 ①，注入发生在 ④。**

## 用比喻说清

| 阶段 | 比喻 |
|---|---|
| **`tools.py`** | 工厂：生产"派活按钮" |
| **`setup_multiagent`** | 仓库管理员：把生产出的按钮装箱（`MultiAgentSetup`） |
| **`CapabilityRegistry`** | 中央仓库：存放这批箱子 |
| **Leader factory** | 装修队：从仓库取出按钮，装到 Leader 这台机器上 |
| **LLM** | 机器操作员：看到按钮，按下去 |

**`tools.py` 是"造按钮的工厂"，不是"装按钮的装修队"。**

---

## 为什么 `tools.py` 不直接注入

因为**职责分离**：

- `tools.py` 的工厂函数签名是 `make_specialist_tool(name, specialist, ...)`——它**不知道 Leader 的存在**，也不需要知道。它只负责"给我一个 specialist，我还你一个工具"。
- 注入 Leader 需要知道"Leader 有哪些内置工具、中间件怎么排、factory 怎么调"——这是 `Leader factory` 的职责。

**如果让 `tools.py` 直接注入，它就要 import Leader、import factory、import 一堆东西，耦合爆炸。** 现在这样：`tools.py` 只依赖 specialist / summarizer 契约，Leader factory 只依赖 registry，各管一段。

## 代码层面的证据

`tools.py` 里没有任何一行提到 Leader：

```python
# tools.py 的函数签名
def make_specialist_tool(
    name: str,
    specialist: SpecialistAgent,          # ← 依赖 specialist 契约
    context_summarizer: ContextSummarizer, # ← 依赖 summarizer 契约
    result_summarizer: ResultSummarizer,   # ← 依赖 summarizer 契约
    ...
) -> BaseTool:                             # ← 产出 BaseTool，不碰 Leader
    ...
    return delegate_tool
```

它**只产出 `BaseTool`**，交给调用方处置。**调用方怎么用（存 registry、注入 Leader），不关它的事。**

## 所以回答你的疑问

> "你不是说在这里注入工具吗？那 tools.py 干的什么"

- **"注入工具"** 指的是 **④ Leader factory 把工具放进 Leader 的 `tools` 列表**。
- **`tools.py` 干的是 ① 造工具** —— 在"注入"之前，工具得先被造出来。

**两者是流水线上的前后两道工序：`tools.py` 造，Leader factory 装。** 我之前说"bootstrap 造好工具"里的"造"，指的就是调 `tools.py` 的工厂函数。措辞上确实容易混，但指的是同一件事：

```
"bootstrap 造好工具"  =  bootstrap 调用 tools.py 的工厂函数，产出 BaseTool
"Leader factory 注入" =  Leader factory 把产出塞进 Leader 的 tools 参数
```

---

## 一句话总结

> **`tools.py` 是"生产工具的工厂"，产出的是 `BaseTool` 对象；"注入"是 Leader factory 把这些对象塞进 Leader 的过程。工厂生产 ≠ 装修安装，是两步。**
